Track B · Lesson 5≈ 3.5 h

MPI + CUDA — many machines, explicit messages, and the audit that predicts scaling

MPI is 5.3's discipline at datacenter scale: N processes, N private memories, and NOTHING moves unless you say so. This lesson gives you the rank model, the CUDA-aware path (and how to verify you're actually ON it), the halo exchange your B3 harness was built for — and the two-lane arithmetic that predicted a 99%-vs-50% scaling split before any cluster time was burned.

Concept

The rank model: SPMD, private worlds

MPI_Comm_rank(MPI_COMM_WORLD, &rank);   // who am I   (5.2's identity)
MPI_Comm_size(MPI_COMM_WORLD, &size);   // of how many
cudaSetDevice(rank % gpus_per_node);    // ONE GPU per rank — the standard
                                        // marriage (and gotcha 6's bug when
                                        // forgotten: all ranks on device 0)
MPI_Send(buf, n, MPI_DOUBLE, dest, tag, comm);   // explicit, message-shaped
MPI_Recv(buf, n, MPI_DOUBLE, src,  tag, comm, &st);
// blocking semantics: Send MAY wait for the receiver (buffering is the
// library's choice, not your right) — which is why naive exchange patterns
// deadlock (quiz 1) and why the nonblocking forms exist:
MPI_Isend/Irecv(..., &request);   MPI_Wait(&request, &st);
// the 5.3 async law verbatim: between Isend and Wait, the buffer is NOT
// yours to touch — same contract, new spelling.

CUDA-aware MPI and GPUDirect: device pointers on the wire

MPI_Send(d_halo, n, MPI_DOUBLE, …)     // yes, a DEVICE pointer — CUDA-aware
                                        // builds (OpenMPI 5.x + UCX) accept it
what happens underneath, best→worst:
  GPUDirect RDMA: NIC reads GPU memory directly — no host copy, ~full fabric BW
  pipelined staging: chunked D2H→send overlap — decent, not free
  naive staging: full D2H, send, H2D — the 4-hop path (and what you silently
  get when the build/module isn't CUDA-aware: gotcha 3's whole scenario)
THE VERIFY RITUAL (before believing anything): osu_bw-style benchmark with
  device buffers, compare to the fabric spec — 3 GB/s on a 25 GB/s link means
  you're staging; fix the MODULE, not your code (5.1's toolchain literacy).

The halo exchange, distributed — and its two-lane audit

per step, per rank (B3's harness, now over MPI):
  post Irecv (4 neighbors) → post Isend (my edges) → COMPUTE INTERIOR
  → MPI_Waitall → compute the 4 edge strips → swap buffers
the audit (course ledger: T4-class compute, IB ~25 GB/s, ~5 µs latency):
WEAK scaling, 4096² per rank (B3's r2: 1.4 ms/step compute):
  halo = 4·4096·8 B = 131 KB → wire ~5 µs + latency ~2·5 µs ≈ 15 µs
  → comm/compute ≈ 1% → predicted efficiency ≈ 99% — scale to thousands
STRONG scaling, 4096² TOTAL split 64 ways (512² per rank):
  compute = 1.4 ms/64 ≈ 22 µs; halo = 4·512·8 = 16 KB ≈ 5.6 µs + 10 µs lat
  → comm/compute ≈ 70%… overlapped: max-lane still ~50% efficiency cliff
same code, same cluster: 99% vs 50% — the LABEL (weak/strong) and the
surface/volume arithmetic decide, before any allocation burns (A7's law,
now with B3's numbers plugged in).

NCCL vs MPI: two tools, one app

NCCL: GPU-resident COLLECTIVES (allreduce/bcast/…) — topology-tuned rings/
  trees over NVLink+IB (A7's machinery); stream-ordered (5.9-native)
MPI:  point-to-point (halos!), control plane, CPU data, the launcher itself
the standard marriage in 2026 science codes: MPI owns ranks/halos/control;
  NCCL owns dense GPU collectives when they dominate (spectral sums, global
  reductions every step). Halo exchange stays MPI: 4 small point-to-point
  messages is MPI's home turf; NCCL has no Send/Recv-shaped sweet spot there
  (it has p2p, but the ecosystem default stands). Don't religion this —
  benchmark the ONE collective that dominates and pick per-call.

Worked example

Task: The distributed correctness ladder for B3's heat stepper — how a pro takes a working single-GPU code to 64 ranks WITHOUT a debugging season. Every rung is a fixture from a prior lesson, re-aimed.

r0  single-GPU split-domain oracle (B3 Ex.2): 2 subdomains in ONE memory,
    explicit halo copies, BITWISE equal to unsplit — the decomposition
    debugged where printf works and ranks don't exist
r1  2 ranks, same node, SYNCHRONOUS exchange (Sendrecv): bitwise vs r0
    (same arithmetic order → same bits, 5.11's doctrine — any diff is
    indexing, and the ramp-pattern trick names the guilty cell)
r2  2 ranks + NONBLOCKING overlap: bitwise vs r1 (overlap changes TIMING,
    not values — if bits change, you touched a buffer before Wait: the
    5.3 law's fingerprint)
r3  4→64 ranks, 2D decomposition: conservation ledger + symmetry fixture
    per scale (B3's suite); corners now cross FOUR ranks — the diagonal
    neighbor exchange everyone forgets (gotcha 4)
r4  the audit vs reality: predicted 99% weak efficiency; measured 97.2%
    (representative) — gap attributed (jitter + Waitall tails), FILED
each rung took ~an hour; teams that skip to r3 spend the week that
"parallel debugging" is famous for — in a 64-rank hang with no stack.

What to internalize: distributed correctness is built INCREMENTALLY on bitwise oracles — split-without-MPI, then sync-MPI, then async, then scale — so every new failure has exactly ONE new suspect. The two-lane audit meanwhile predicts the performance endgame before rung r1. Ladders and arithmetic: the same two instruments as every other lesson, pointed at a cluster.

Key points

  • MPI is SPMD over private memories: rank branches the work, one GPU per rank (set it explicitly!), and nothing moves without a message — 5.3's explicitness at fleet scale.
  • Blocking Send/Recv can deadlock in cycles (buffering is a favor, not a contract); nonblocking Isend/Irecv + Wait is the idiom, and the buffer-hands-off rule between them is 5.3's async law verbatim.
  • CUDA-aware MPI takes device pointers; GPUDirect RDMA makes them fast — but the PATH is a build/module property you VERIFY with a device-buffer bandwidth test, never assume (3 GB/s on a 25 GB/s fabric = you're staging).
  • The halo audit is two lanes and a label: weak scaling at 4096²/rank predicts ~99%; strong scaling to 512²/rank predicts ~50% — surface/volume arithmetic decides before cluster time burns.
  • NCCL owns GPU-resident collectives, MPI owns point-to-point/control — the standard marriage; pick per dominant call by benchmark, not religion.
  • Distributed correctness climbs a bitwise ladder: split-domain oracle → sync-MPI → async → scale, each rung adding ONE suspect — the alternative is the 64-rank hang with no stack.

Quiz

1. A student's 2D halo code works on 4 ranks, hangs on 16 — sometimes. Pattern: every rank does MPI_Send(north) then MPI_Send(south)… then the Recvs. On 4 ranks (2×2, periodic) it "always worked." Explain the deadlock mechanism, why 4 ranks got lucky, why 16 is INTERMITTENT, and the three standard fixes ranked by robustness.
"Works small, hangs big, intermittently" is THE eager-threshold signature — one of a handful of distributed fingerprints worth memorizing (with A7 P4's stuck-collective and B3 quiz 2's seam). The deeper law: correctness that depends on library BUFFERING is luck wearing a green test suite; the Isend/Irecv+Waitall idiom removes the assumption class entirely, which is why the worked example's r2 rung standardizes it. Fingerprint + mechanism + idiom — that's the whole distributed-debugging trade in one quiz.
2. Your CUDA-aware halo exchange benchmarks at 2.8 GB/s on nodes with 25 GB/s InfiniBand and NVLink'd GPUs. MPI_Send with device pointers "works fine" (correct results). Rank the four hypotheses, give each one's 60-second test, and state which single command settles most of them.
"Works fine (correct) but slow" is the CUDA-aware trap's signature: the API contract is honored either way, the PATH is the variable — exactly like A3 quiz 1's default-stream op (fast standalone, poison in context): correctness tests can't see path bugs; bandwidth tests are the fixture. Option 4 is checkable in the same sweep (bandwidth-vs-size curve: small messages are latency-bound — 4.6's tolls — but 2.8 GB/s FLAT across sizes is a path ceiling, not a toll). The topology check (option 3's nvidia-smi topo -m) becomes routine on every new cluster — 10 seconds that explain years of mysteries.

Go deeper — the distributed craft sheet

1. Nonblocking semantics: the contract, precisely

MPI_Isend(buf, …, &req):  returns immediately; buf is UNTOUCHABLE until
  MPI_Wait(&req) completes it (read OR write — the library may still be
  reading it: 5.3's async-buffer law, federal edition)
MPI_Irecv + Wait: buf undefined until Wait returns
overlap pattern (the only one you need):
  Irecv×4 → Isend×4 → interior compute → Waitall(8) → edges → swap
progress caveat: some MPI stacks progress messages only INSIDE MPI calls —
  a long kernel between Isend and Wait may stall the wire (test with a
  probe/Test loop or enable async-progress threads; fabric-dependent, and
  the 5.10-style timeline shows it as comm hiding that... doesn't)

2. Communicators, topology, and placement

MPI_Comm_split: sub-teams (e.g., per-node comms for hierarchical reductions —
  A7's scenario fix: reduce intra-node over NVLink, inter-node over IB)
MPI_Cart_create: the 2D/3D grid communicator — neighbor ranks by
  MPI_Cart_shift instead of hand-rolled index math (fewer B3-seam bugs)
placement flags (mpirun --map-by ppr:4:node --bind-to numa): rank→core→GPU→
  NIC affinity — quiz 2's hypothesis 3; on modern nodes the difference
  between aligned and crossed NUMA paths is 2–3× on the wire (4.6, again)

3. Gotchas

All ranks, device 0. Forgetting cudaSetDevice(rank%N) — four ranks time-slicing one GPU while three idle: "MPI scaling is terrible" reports that are one line from greatness. nvidia-smi during a run is the 10-second audit.
Touching buffers before Wait. r2's bitwise rung catches it; in the wild it's intermittent halo corruption that LOOKS like B3 quiz 2's indexing bug — the ladder exists to separate the suspects.
Assuming CUDA-aware. Quiz 2. The module system offers five OpenMPIs; one is UCX-CUDA. The device-buffer bandwidth test runs on every new cluster, day one, before any science.
Forgotten diagonal neighbors. 2D corners need the 4 diagonal exchanges (or a two-phase trick: exchange X, THEN Y — corners ride for free through the second phase: know WHICH your code does). The symmetry fixture on a diagonal-symmetric input convicts (B3 P3's corner graveyard, distributed).
Tag/count mismatches. Recv with the wrong tag waits forever; count smaller than the send TRUNCATES silently on some paths (check MPI_Get_count in fixtures). Tags are contracts — name them with enums, not literals.
Collective order divergence. One rank's early-exit path skips an Allreduce → fleet hang, no stack (A7 gotcha 3, MPI spelling). Collectives are structurally unconditional; the per-rank-log diff (A7 P4's protocol) names the deviant.

Scenario — the "MPI is slow on GPUs" verdict, overturned in an afternoon

A CFD group inherits cluster time on a new machine and ports their B3-style multi-GPU solver. First scaling run: 34% efficiency at 16 nodes where the old cluster gave 91%. The group's write-up draft blames "immature CUDA-aware MPI on the new system" and proposes a месяц of hand-staged communication rewrites. A B-track-literate postdoc runs the lesson's rituals first. Ritual one, the device-vs-host bandwidth pair: host buffers 23.1 GB/s, device buffers 2.9 GB/s — staging convicted in ninety seconds; ucx_info shows the default module lacks CUDA transports; module swap to the ucx-cuda build → device 21.8 GB/s. Efficiency: 61%. Ritual two, the binding report: ranks bound round-robin to cores but ALL claiming GPU 0 on each node (the port dropped one cudaSetDevice line — gotcha 1) — nvidia-smi shows one saturated GPU and three tourists. Fix: one line. Efficiency: 88%. Ritual three, the two-lane audit against the remaining 3%: predicted Waitall tails at their strong-scaling tile size — matches, filed as expected, documented in the report per b10-report's standard. Total time: one afternoon; lines of communication code rewritten: one. The draft's conclusion was inverted before it embarrassed anyone: the paradigm was fine; the PATH and the PLACEMENT were misconfigured — and both are testable in minutes by rituals, not rewrites. The postdoc's afternoon became the group's onboarding checklist, which is how ritual knowledge is supposed to propagate.

Practice

1. Write the byte-and-latency budget for one halo step of a 3D 512³-per-rank decomposition (6 faces, fp64, 25 GB/s + 5 µs), compare to its compute lane (7-point stencil at 220 GB/s effective), and verdict the weak-scaling health — then find the tile size where efficiency crosses 90%.
Faces: 6 × 512² × 8 B = 12.6 MB → wire 0.50 ms + 6 latencies ≈ 0.53 ms. Compute: 512³ cells × 2 fields' round-trip ≈ 2×(512³×8)/220e9 ≈ 9.8 ms. Ratio ≈ 5.4% → overlapped efficiency ~97–99% (comm hides under a 9.8 ms interior easily): healthy. Crossing 90% unoverlapped: need comm ≤ 11% of compute; comm/compute ∝ 6n²·8/(2·n³·8/220e9 ... ) scales as 1/n → solve: n ≈ 512×(0.054/0.11) ≈ 250³-class tiles. The 3D surface/volume ratio (6/n vs 2D's 4/n) makes 3D MORE communication-hungry at equal n — the dimension tax every 3D code pays (and why 3D strong scaling cliffs earlier than Ex.2's 2D cells suggested).
2. Design the hierarchical allreduce for 8 nodes × 4 GPUs (NVLink intra, IB inter) using comm-splitting (§2): the three phases, the bytes each phase moves per GPU, and the speedup vs a flat 32-rank ring over IB (A7's formula both ways).
Phases: (1) intra-node reduce (NCCL over NVLink, 4 GPUs): 2·(3/4)·S per GPU at 200 GB/s; (2) inter-node ring over the 8 node-leaders (IB): 2·(7/8)·S at 25 GB/s — the only IB-touching phase, and only leaders pay it; (3) intra-node bcast: ~S at NVLink speed. Flat 32-ring over IB: 2·(31/32)·S ≈ 2S at 25 GB/s for EVERY GPU. Per-GPU IB bytes: hierarchical ≈ 2S×(1/4 of GPUs participate... per-GPU averaged: leaders move 1.75S over IB, others 0) vs flat 2S each → aggregate IB traffic ÷4 → wall-clock ≈ 3–4× faster when IB is the bottleneck (it is). MPI_Comm_split(node_id) + split(local_rank==0) — six lines of communicator surgery for the A7-scenario fix; NCCL does this internally given correct topology, which is WHY topology hints matter (quiz 2's hypothesis 3 at the collective layer).
3. Your r2 (overlap) rung FAILS bitwise vs r1 only when the interior kernel runs longer than ~10 ms. Using §1's progress caveat + the 5.3 buffer law, give the two candidate mechanisms, the discriminating experiment, and the fix for each.
Candidates: (1) buffer touched before Wait — the edge computation (or a prefetch) reads halo cells while Irecv is still landing: timing-dependent (long kernel = recv lands late = the race window opens): discriminate by moving Waitall BEFORE any edge access (already the pattern? then audit for aliased views — M2's shares_memory drill on the halo slices); (2) progress stall — the wire doesn't move during the long kernel (no async progress thread), so recvs complete only INSIDE Waitall: that's SLOW but not wrong — it can't corrupt bits... unless the code polls MPI_Test and proceeds on a stale flag: audit the completion logic. Discriminator: run with MPI async progress enabled / a Test-loop that logs completion times — if corruption tracks completion-after-access, it's (1); if bits are fine and only overlap efficiency died, it's (2). Fixes: (1) restore the Waitall fence (and the bitwise rung to CI — it just paid for itself); (2) enable progress threads or split the interior kernel to create MPI call points. The drill's meta: bitwise rungs turn timing races into reproducible experiments — the whole reason the ladder insists on them.
4. Translate A7's bucket-tuning quiz to halo world: your code sends each of 4 halos as 40 separate row-messages ("it was easier with the old data layout"). At 5 µs latency, price the damage for 512² tiles, name the M2 L5 concept that fixes it, and the MPI feature that fixes it WITHOUT changing the layout.
Damage: 160 messages × 5 µs = 800 µs of pure latency vs the 22 µs compute lane (strong-scaling tile) — comm-dominated by tolls alone, 36× over the single-message-per-face cost (4.6's toll law: same bytes, 40× the messages). Fix 1 (layout): make each halo face CONTIGUOUS — the M2 L5 stride insight: store boundary strips packed, or pack/unpack kernels (one D2D gather into a send buffer: 5.7's way-station, message edition — this is what production codes do, on-GPU pack kernels). Fix 2 (no layout change): MPI Derived Datatypes (MPI_Type_vector describing the strided rows) — ONE message per face, library packs; with CUDA-aware + datatype support the pack may even run on-GPU. Toll arithmetic → layout-or-datatype: the entire message-aggregation doctrine in one drill (A7's buckets, B5's faces, same law).
5. Fault reality: at 512 ranks × 40 hours, SOMETHING will fail. Contrast MPI's default failure model with the checkpoint/restart discipline (B7 preview), and compute the sweet-spot checkpoint interval for: ckpt write 90 s, node MTBF such that P(job sees a failure) ≈ 30% per 40 h run (Young's formula from b7-checkpoint).
MPI default: one rank dies → the job dies (collectives can't complete — A7 P4's hang, then the watchdog kills all): fault tolerance is YOUR responsibility via checkpoint/restart (ULFM-style recoverable MPI exists but isn't the 2026 default in practice). Young: interval ≈ √(2·write·MTBF). Effective MTBF for the JOB: 30% per 40 h → ~1 failure per 133 h ≈ 4.8e5 s. Interval ≈ √(2·90·4.8e5) ≈ 9,300 s ≈ 2.6 h → overhead 90/9300 ≈ 1%, expected loss per failure ≈ 1.3 h ≈ 3% of the run amortized: total fault tax ~4% — versus losing 40 h × 30% probability = 12 h expected without checkpoints. The arithmetic that turns "checkpointing is annoying" into "checkpointing is a 3× expected-value trade" — B7 operationalizes it with the SIGTERM trap.
6. Write the six-line "new cluster, day one" ritual (the scenario's onboarding checklist) — each line a command-level action with the failure it pre-empts and its lesson citation.
(1) Device-vs-host bandwidth pair (osu_bw or 20-line equivalent) vs fabric spec — staging/path bugs (quiz 2, scenario ritual 1). (2) nvidia-smi topo -m + --report-bindings on a test job — NUMA/NIC affinity crossings (quiz 2 h3). (3) The all-ranks-GPU audit: nvidia-smi during a 4-rank smoke run — device-0 pileup (gotcha 1, scenario ritual 2). (4) Eager-threshold probe: all-Send-first toy at growing sizes — know YOUR threshold before it knows you (quiz 1, Ex.1). (5) The r0→r2 ladder on the heat toy — bitwise green establishes the harness on THIS stack (worked ex). (6) One weak + one strong scaling point vs the Ex.2 workbook's prediction — a 20% gap on day one means a config problem TODAY, not a mystery in the paper's reviews (B10). Six commands, one morning, and every classic first-month incident is pre-empted — rituals are how afternoons stay afternoons.
