Thrust, CUB & cuFFT — the primitives you stop hand-rolling today

You built reductions from warp shuffles (5.8) so that libraries would never be mysteries — and now you graduate to using them. Thrust for one-liners, CUB for in-kernel building blocks, and the primitive you COULDN'T build in 5.8's model — scan — delivered by the library that solved its impossible dependency. Plus cuFFT, where M1's logarithms cash out at a measured 600×, and mathematics itself supplies the test suite.

Concept

The abstraction ladder

thrust::sort(d.begin(), d.end());                    // the STL, on device
thrust::reduce(d.begin(), d.end(), 0.0, plus());     // 5.8's ladder, bought
thrust::inclusive_scan(...); thrust::copy_if(...);   // scan + compaction!
// CUB: same engine, more control — device-wide with YOUR streams/workspace:
cub::DeviceReduce::Sum(d_temp, temp_bytes, d_in, d_out, n, stream);
//   (query temp size, allocate once, reuse — B2 §1's workspace law)
// and BLOCK-scale primitives to compose INSIDE your kernels:
using BlockReduce = cub::BlockReduce<double, 256>;
double block_sum = BlockReduce(smem).Sum(thread_val);   // your 5.8 tree,
//   vendor-tuned, one line — hand shuffles remain for the exotic 10%

Scan: the primitive 5.8 couldn't build — and what it unlocks

inclusive_scan([3,1,4,1,5]) = [3,4,8,9,14]     // running totals
// why 5.8's model failed: element i needs ALL predecessors — a sequential
// dependency that block-independence (5.2's law) can't express; 5.8 P1e
// named it the obstruction. CUB ships decoupled-lookback scan: blocks
// publish partial states and PEEK at predecessors' published results —
// a lock-free protocol built on 5.8's atomics, achieving ~memcpy speed.
// You buy it; you also now UNDERSTAND it — both matter.
what scan unlocks (the reason it's THE primitive):
  stream compaction: keep-flags → scan → scatter to compacted slots
    (B4 P5's path-killing remedy — now you know its engine)
  bucketing/histogram layout, radix sort's digit passes, CSR row_ptr
    construction (B2's format, BUILT by scan), load balancing prefix maps
one mental model: scan converts "where do I go?" (needs everyone before me)
into two parallel passes — the trick that parallelized bookkeeping itself.

cuFFT: plans, batches, and the 600× logarithm

cufftPlanMany(&plan, rank, dims, …, batch);   // ONCE: picks algorithms,
cufftSetStream(plan, s);                       // allocates workspace (B2 §1)
cufftExecZ2Z(plan, d_in, d_out, CUFFT_FORWARD); // thousands of times
MEASURED (n=8192): FFT 0.1 ms vs naive DFT-as-matmul 60 ms — 600×.
  O(N log N) vs O(N²): M1's logarithm lesson, cashing its largest check.
batch dim: 1000 independent 1D FFTs = ONE call (5.2's launch floor —
  B2 P6's batching law; spectral codes live on this)
layout: batched/strided plans read M2 L5's strides — plan FOR your memory
  layout; transposing data to fit a plan is usually backwards (5.7's
  way-station only when truly forced).

Mathematics as the fixture supplier

Parseval:   Σ|x|² == Σ|X|²/N            VERIFIED exact-class in fp64
round-trip: ifft(fft(x)) ≈ x            (budget: n·eps-class — B8's ladder)
known pairs: delta→flat, sine→two spikes, Gaussian→Gaussian
linearity:  fft(ax+by) == a·fft(x)+b·fft(y)
what these actually catch (because cuFFT itself is correct): YOUR 1/N
scaling convention (cuFFT is UNNORMALIZED — the #1 integration bug),
YOUR strides/batch layout, YOUR real-vs-complex packing (R2C's N/2+1
layout — the #2 bug), YOUR dtype plumbing. M2 L6's law, third library:
fixture the SEAM, not the vendor.

Worked example

Task: Rebuild B4's histogram-and-compact pipeline with primitives — the 5.8 quiz 1 problem, solved the production way — and price each stage against its hand-rolled ancestor.

problem: 100M samples → histogram (256 bins) + compact the outliers (0.1%)
hand-rolled (5.8/B4 era): privatized shared-memory histograms + two-phase
  merge (5.8 quiz 1's design) + a hand compaction you couldn't write well
  (the scan obstruction — you punted to atomics-with-contention)
primitive build:
  histogram: thrust sort + reduce_by_key?  NO — sorting 100M for 256 bins
    is a sledgehammer (sort ≈ several passes; 5.8's privatized atomics ≈
    ONE pass): keep the 5.8 design OR cub::DeviceHistogram (which IS that
    design, tuned) — knowing when the library's generic path loses to the
    specialized one is B2's format-judgment, again
  compaction: flags → cub::DeviceSelect::Flagged (decoupled-lookback scan
    inside): one call, ~memcpy speed — the obstruction, purchased: outliers
    land dense, ready for B4's regeneration (P5's population control)
  the ledger: histogram 1 pass (unchanged — the hand design was already
    right); compaction: contended-atomics hack (~8 ms, nondeterministic
    ORDER — B8 P3's rung-1 killer!) → DeviceSelect (~1.3 ms, deterministic
    order preserved): faster AND a reproducibility rung recovered.

What to internalize: the primitive library didn't retire your 5.8 knowledge — it PRICED it. You kept the privatized histogram (your design matched the specialized library's), bought the scan (your hand version was both slower and rung-breaking), and could explain WHY in both directions. That bidirectional judgment — build-vs-buy per primitive, with mechanisms — is what the track's early hand-rolling was purchasing all along.

Key points

  • The ladder: Thrust one-liners → CUB device primitives (streams + workspace, B2's citizenship) → cub::Block* composed inside your kernels → raw 5.8 shuffles — descend only when the profile names a reason.
  • Scan is THE primitive: it parallelizes bookkeeping itself (compaction, bucketing, CSR construction, sort passes) via decoupled lookback — the 5.8 P1e obstruction, solved by a lock-free protocol you can now read.
  • cuFFT is plan-once/execute-many with batch dims for small transforms — 5.3's alloc-once and 5.2's launch-floor laws; measured 600× over naive DFT at n=8192 (M1's logarithms, cashed).
  • Transform fixtures come from theorems — Parseval (verified), round-trips, known pairs, linearity — and they catch YOUR seams: the unnormalized-scaling convention, R2C packing, strides (M2 L6's law, third library).
  • Primitives can RECOVER reproducibility: DeviceSelect's order-preserving compaction replaced a rung-breaking atomic hack — faster and contract-cleaner (B8's ladder, shopping edition).
  • Build-vs-buy is priced per primitive with mechanisms (the histogram stayed hand-designed; the scan was bought) — the early hand-rolling existed to make this judgment possible, not to be a lifestyle.

Quiz

1. A spectral-solver team reports: "cuFFT is 40× slower than the benchmark claims." Their loop: per timestep, for each of 2,048 rows — cufftPlan1d, cufftExecC2C, cufftDestroy. Also, results are 8192× too large after a forward+inverse round trip ("we patched it with a magic divide"). Diagnose both symptoms, give the four-line fix, and name the two lessons they skipped.
Plan-per-call is cuFFT's version of cublasCreate-per-call (B2 gotcha 2) and cudaMalloc-in-loops (5.3) — the SAME law surfacing in every library, which is why the course drills laws over APIs. The unnormalized convention bites every first integration; the difference between a "magic divide" and a contract line is whether the NEXT person trusts it (3.6's comment discipline). Option 1's "write custom kernels" would burn a quarter rediscovering Cooley–Tukey at 0.3× cuFFT — the anti-B2 move.
2. Your particle code uses thrust::sort_by_key every step to bucket 50M particles by cell (for B3-style neighbor interactions). Profiling shows sort = 61% of step time. A teammate says "sort is O(N log N), it's optimal, nothing to do." Attack the premise three ways — the primitive swap, the algorithmic insight about YOUR data, and the frequency question — with expected magnitudes.
Three attack angles — better primitive configuration, exploit data structure, question the frequency — form the standard triage for ANY dominant library call (they're 5.10's loop specialized to primitives). The presortedness insight is the deep one: libraries optimize for adversarial inputs; your simulation's inputs are CORRELATED ACROSS TIME, and that temporal coherence is exploitable structure (the B-track's version of A8's prefix-caching). "It's optimal" ended the teammate's analysis exactly where the interesting engineering begins.

Exercises

Exercise 1 — The primitive rebuild (Colab, cupy exposes thrust/cub-class + cuFFT): (a) reduce/sort/scan one-liners on 10M elements with do_bench-style timing vs your 5.8 reduction (expect parity-to-slightly-better — and write WHY parity is the expected result); (b) the compaction pipeline: flags → cumsum → scatter, verified against np-based oracle, then via cupy's compress — order preserved (check it — B8's rung 1 evidence); (c) cuFFT via cupy.fft: reproduce the 600×-class DFT-vs-FFT gap, then the FULL Parseval/round-trip/known-pairs/linearity fixture file — and deliberately hit the unnormalized convention (norm=None vs 'ortho') to catch quiz 1's 8192× in your own hands.
expected: (a) parity because BOTH sit at the bandwidth ceiling (4.7 — a
reduction is a read-everything op; vendor tuning buys the last 10%, not
regimes); (b) compress preserves input order — screenshot the assert;
(c) cupy defaults differ from raw cuFFT on normalization (norm parameter!) —
your fixture file catches the convention in 4 lines, which is the entire
point: conventions are seams, seams get fixtures. Keep fixture_fft.py
forever; it ports to every FFT library you'll ever touch (numpy/cupy/cuFFT/
FFTW all differ in conventions, none differ in Parseval).
Exercise 2 — Read the impossible primitive: implement a SEQUENTIAL scan, then a work-efficient parallel scan simulation (up-sweep/down-sweep on paper or NumPy — Blelloch's two trees), verify equivalence on random inputs + the B8-style order question (is the parallel scan's float result bitwise-equal to sequential? test, explain), and then write the four-sentence explanation of decoupled lookback (what each block publishes, what it peeks, why it doesn't deadlock — 5.2's independence law respected via 5.8's atomics).
expected: up/down-sweep == sequential for INTEGERS bitwise; for floats,
DIFFERENT bits (tree order ≠ left-to-right — 5.11 quiz 2's law applied to
scan: reordered ADDS this time, genuinely different results within budget).
Decoupled lookback, four sentences: each block computes its local sum and
publishes (aggregate, then inclusive-prefix when known) with a status flag;
blocks poll PREDECESSORS' published states, summing aggregates backward
until hitting a block with a full prefix; atomically-published monotone
states mean progress is guaranteed (someone's prefix is always complete —
block 0's is by definition); no block WAITS on a later block, so 5.2's
scheduling independence is never violated — it's a one-directional
information flow built from 5.8's primitives, which is why it works where
naive "wait for block i−1" deadlocks (5.8's gotcha 2).

You now hold scan at all three levels: what it does, how it parallelizes, why the production version is safe. That's the full stack this track promised for every primitive you BUY.

Go deeper — primitive craft

1. Thrust ergonomics that matter in real codes

execution policies: thrust::cuda::par.on(stream)   — 5.9 citizenship (default
  policy syncs the legacy stream: A3 quiz 1's trap, thrust edition!)
device_vector: RAII device memory (3.7's pattern) — but per-call temporaries
  allocate/free (5.3's hot-loop sin): pass a cached allocator or use cub
  directly for steady-state loops
fancy iterators: transform_iterator (fuse the map into the reduce — A5's
  fusion as an iterator: thrust::reduce over transform_iterator does
  read→op→accumulate in ONE pass), zip_iterator (SoA views — M2 L7),
  counting_iterator (indices without materializing them)
  — these are the difference between thrust-as-toy and thrust-as-tool.

2. CUB in your kernels: the composition pattern

__global__ void my_physics_kernel(...) {
    // ... your per-thread physics (B4's paths, B3's cells) ...
    using BR = cub::BlockReduce<double, 256>;
    __shared__ typename BR::TempStorage tmp;         // CUB names its smem
    double block_total = BR(tmp).Sum(my_contribution);
    if (threadIdx.x == 0) partials[blockIdx.x] = block_total;   // slot array:
}                                                     // B8 P3's deterministic
// the pattern: YOUR physics + THEIR reduction in one kernel — fusion (A5)
// without hand-rolling the tree; TempStorage is 5.5's shared budget line
// (it counts against the occupancy dial — 5.6's table still runs).

3. Gotchas

Default-stream thrust. Policy-less calls ride (and sync) the legacy stream — the A3 quiz 1 picket fence via a container library. par.on(stream), always, in pipeline code.
Plan/temp churn. cufftPlan or thrust temporaries per iteration (quiz 1) — the 5.3 law's two newest costumes. Plans and workspaces are setup-phase citizens.
The unnormalized surprise. cuFFT forward+inverse = ×N; libraries disagree on WHERE 1/N lives (Ex.1c). The round-trip fixture is four lines and permanent.
R2C's packed layout. Real-to-complex outputs N/2+1 complex values (Hermitian symmetry) — indexing it like N values reads garbage beyond the fold (M2 L5's shape-vs-storage, spectral edition). The known-pairs fixture (sine → spike at ±k) catches mis-indexing instantly.
sort_by_key as a reflex. Quiz 2: generic sorts ignore your data's temporal coherence, key-bit narrowness, and required frequency — three multipliers the call site owns, not the library.
Reading benchmarks without the batch dim. "cuFFT does X GFLOP/s" assumes batched/large transforms; 2,048 separate 1D calls live under 5.2's launch floor instead. Benchmark the SHAPE you'll ship (5.9 P6's regime labels, transform edition).

Scenario — the plasma code that bought back its Tuesdays

A plasma-physics group's spectral solver (Fourier transforms every step, filtering in k-space, back-transform) consumes their allocation twice as fast as budgeted, and the student maintaining the hand-written FFT — inherited from a 2009 thesis, radix-2 only, forcing power-of-two grids that over-resolve one dimension 1.6× — spends every Tuesday on its quirks. The B-track audit, run by a new postdoc in one week: the hand FFT benchmarks at 0.22× cuFFT (nobody had ever compared — the 2009 author's benchmark beat 2009's CPU); the power-of-two constraint costs that 1.6× over-resolution (cuFFT handles mixed radix: the grid shrinks to the physics' actual need); plan-per-step churn found in the wrapper (quiz 1's signature, 15% of runtime by itself); and the k-space filter runs as a separate kernel between transforms — fused into a cuFFT callback (the library's epilogue hook: A11's fusion instinct, provided as an API). Cumulative: 4.7× on the solver, the allocation back on budget, power-of-two liberation shrinking memory 38%, and — the part the group actually celebrates — the 2009 FFT retired with honors and its Tuesdays returned. The fixture file (Parseval, round-trip, known pairs) that certified the migration took the postdoc one afternoon and caught two convention mismatches (scaling and R2C packing) before they touched science. The group's new rule, this lesson in one line: hand-rolled primitives must re-justify themselves against the library annually, with benchmarks — sentiment is not a performance characteristic.

Practice

1. Build-vs-buy verdicts with mechanisms (one line each): (a) global sum for B3's ledger; (b) 256-bin histogram of uint8 (5.8 quiz 1's); (c) stream compaction of MC survivors; (d) segmented reduction over 50M variable-length segments; (e) a fused "square then sum" pass; (f) top-16 per row of a 10k×10k matrix.
(a) BUY (cub::DeviceReduce) but keep the slot-array variant for rung-1 CI (B8 P3) — two builds, one flag. (b) Keep the 5.8 privatized design or cub::DeviceHistogram (same design inside — either way, NOT sort-based: worked example's verdict). (c) BUY DeviceSelect — the scan obstruction, purchased (and order-preserving: reproducibility bonus). (d) BUY cub::DeviceSegmentedReduce — variable segments hand-rolled = load-balancing hell (the scan-built prefix maps doing exactly this inside). (e) Thrust transform_iterator + reduce — fusion via iterator (§1), one pass, no custom kernel. (f) BUILD-ish: per-row top-k has no perfect primitive fit — cub::BlockRadixSort per row-block or the 5.8 P1f mergeable-summary design; the one honest "the shelf is thin here" answer (knowing where the shelf ends is the skill).
2. Price quiz 1's plan-churn exactly: plan creation ~2.5 ms, exec ~0.03 ms per 1D-8192 row, 2048 rows, 10⁴ steps. Compute the churn build's time, the batched build's time, the ratio, and the fraction of the churn build that was pure plan cost — then name the B7 consequence at allocation scale.
Churn: 2048 × (2.5 + 0.03) ms × 1e4 steps = 51.8 ks ≈ 14.4 hours (plan fraction: 2.5/2.53 ≈ 98.8% — the exec was a rounding error on the waste). Batched: one plan (2.5 ms once) + per-step one batched exec ≈ 2048×0.03 amortized-and-parallelized ≈ ~6 ms/step-class → 60 s total: ratio ≈ 860×. At B7's meter: 14.4 h × N-GPU allocation burned on REDISCOVERING 5.3's alloc-once law — the same arithmetic that priced malloc-in-loops, handle-churn (B2), and per-rank files (B7 quiz 2). Four costumes, one law, one habit: setup-phase citizens stay in the setup phase.
3. The R2C fixture drill: for a real input of N=8 samples of sin(2πk·1/8), write down EXACTLY what the R2C output's 5 complex values should contain (which bin, what magnitude, given unnormalized conventions), and the three distinct bugs a wrong answer pattern would each indicate.
sin at frequency 1: X[1] = −i·N/2 = −4i (unnormalized; energy at bin 1), X[0]=X[2]=X[3]=X[4]=0 (bins 0..N/2 = 5 values; the negative frequency lives implicitly in Hermitian symmetry). Wrong patterns: (1) magnitude 8 not 4 at bin 1 → you summed both symmetric halves or double-applied a convention (scaling seam); (2) energy at bin 7-equivalent/garbage past index 4 → you allocated/indexed N complex values instead of N/2+1 (the packed-layout bug — gotcha 4); (3) spike at the RIGHT bin but real-valued or +4i → sign/direction convention (FORWARD vs INVERSE definitions differ across libraries) — harmless alone, catastrophic when mixing libraries mid-pipeline. One hand-sized test, three seams distinguished by SIGNATURE — the M2 L6 hand-checkable-case doctrine at its purest (B2's 3×2·2×4, spectral edition).
4. Design the fused ledger kernel for B10 using §2's composition: per-cell stencil update + block-level energy contribution + slot-array partials, in one kernel — state the shared-memory budget line (CUB TempStorage + your tile), the occupancy check (5.6's table), and why this beats a separate thrust::reduce pass (two mechanisms).
Kernel: your B3 tile update computes each cell's new value AND its energy contribution in registers → BlockReduce::Sum over the block's contributions → thread 0 writes partials[blockIdx] (deterministic slot array — B8 P3); a tiny second kernel merges partials in fixed order. Budget: tile smem (e.g., 34×34×8 B ≈ 9.2 KB) + BR TempStorage (~256×8 = 2 KB-class) ≈ 11 KB → 5.6's min() table: still 4+ blocks/SM on 48–64 KB parts ✓ (state the check, don't vibe it). Beats separate reduce: (1) the energy pass otherwise RE-READS the entire field — one full 4.6 round trip deleted (A5's fusion ledger: the field was already in registers); (2) one fewer launch + no thrust default-stream risk (gotcha 1). The composition pattern is the B-track's version of A11's epilogue fusion — same instinct, bought parts.
5. Your scan-based compaction (Ex.2) must now run every step on data that's 99.9% "keep." Explain why compaction is nearly free in this regime but the WRITE pattern still costs, what "select the REJECTS instead" buys (arithmetic), and when the whole stage should instead become B4 P5's in-place population control.
At 99.9% keep: the scan itself is O(N) bandwidth regardless (read flags, read/write offsets — can't skip), and the scatter writes ~N elements to NEW locations: the compacted copy is a full extra field round-trip per step (4.6's ledger: ~2× the stage's traffic) for nearly-unchanged order. Selecting rejects: DeviceSelect on the 0.1% inverts the write cost — output is 50k elements, not 50M (÷1000 on the scatter); keepers stay IN PLACE, and you process the reject-list separately (regenerate/retire — B4's population control): total stage cost collapses toward the flag-scan floor. When even that's too much: if rejects only need handling every k steps (staleness budget — quiz 2's frequency question), batch them. The general law: compaction's cost is the WRITE of the survivors — so arrange to write the SMALLER side, which is a one-line change that most codes never notice they're missing.
6. The library-update audit (B6 P3 / 5.6's weather, primitive edition): CUB/Thrust major versions and cuFFT plans can change algorithms under you. Write the five-line CI canary that catches primitive-behavior drift per toolkit upgrade — what each line asserts and which incident class it pre-empts.
(1) Bitwise replay of the rung-1 reference pipeline (fixed inputs through reduce/scan/select) — catches algorithm swaps that reorder floats (B8's rung 1; scan tree changes are LEGAL for the library and lethal for un-contracted CI). (2) The FFT fixture file (Parseval/round-trip/pairs) — catches convention/normalization drift and plan-algorithm changes at accuracy's edge. (3) Perf tripwires: do_bench medians per primitive vs recorded baselines ±tolerance (5.10 §2) — catches the 0.7× regression that release notes called a refactor. (4) TempStorage-size assertions for §2's composed kernels — CUB may grow its smem ask → your occupancy table silently shifts (5.6's dial): assert the budget line. (5) Workspace-size queries re-recorded (cuFFT/cub temp bytes) — allocation-shape changes caught before production OOMs. Five asserts, five drift classes — libraries are dependencies with WEATHER, and this canary is the umbrella the whole course has been building one gotcha at a time.
