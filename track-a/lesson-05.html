Track A · Lesson 5≈ 4 h

ML Kernel Patterns — fusion is the whole game, FlashAttention is its masterpiece

Every famous ML kernel of the last decade is one idea executed well: stop driving tensors to HBM between steps. This lesson builds that idea from the softmax traffic ledger up to a from-scratch FlashAttention you'll verify to machine epsilon — and by the end, "we should fuse this" will be an arithmetic conclusion you compute, not a vibe you inherit.

Concept

The traffic ledger: where a "fast" model leaks

torch.softmax(x)  as four eager ops on a (4096, 4096) fp32 tensor (64 MB):
  m = x.max(-1)      read 64 MB
  e = exp(x − m)     read 64 + write 64
  s = e.sum(-1)      read 64
  y = e / s          read 64 + write 64        Σ ≈ 384 MB of HBM traffic
FLOPs: ~3 per element → AI ≈ 0.2 FLOP/B — the 4.7 memory cellar, permanently.
fused (A4's kernel): read 64 + write 64 = 128 MB → traffic ÷3, same math.
T4 arithmetic: 384 MB ÷ 220 GB/s ≈ 1.75 ms vs 0.58 ms — the entire speedup
was DELETED TRIPS. This ledger, drawn per operator, is Track A's daily tool:
elementwise/normalization layers are ~free in FLOPs and expensive in trips.

Online softmax: the identity that makes streaming legal

state (m, s);  new chunk c:
  m' = max(m, max(c));   s' = s·exp(m − m')  +  Σ exp(c − m');   (m,s) ← (m',s')
# the rescale term is the whole trick: history was accumulated against the
# OLD max; one multiply re-expresses it against the new one (exp algebra:
# e^(x−m) = e^(x−m')·e^(m'−m)). EXECUTED: 10 chunks vs full pass → ratio
# 1.0 exactly (fp64). The max-shift itself is M1 L8's overflow shield
# (fp32 exp overflows at 89 — A4's measured wall).
# Why you care: a reduction that can be RESTARTED against new normalizers
# can be TILED — and softmax was the one op everyone said couldn't tile.

LayerNorm: the cancellation trap wearing a normalization costume

var(x) = E[x²] − E[x]²        # the "one pass" formula every intern writes
EXECUTED, fp32, row = 1000 + noise(σ=0.01), n=4096:
  one-pass:  0.0               ← TOTAL cancellation (E[x²] ≈ 1e6, E[x]² ≈ 1e6:
                                  their difference ~1e-4 is 10 decimal digits
                                  below the operands — M1 L8's subtraction law)
  two-pass:  1.007e-4  ✓        (subtract mean FIRST, then square)
var=0 → rsqrt(0+ε) → normalization explodes or flatlines. Production rule:
two-pass (or Welford's running form) + fp32 accumulation even for bf16
tensors (A3 quiz 2's law) — layernorm is ONE kernel doing mean, var,
normalize, scale, shift in a single trip: fusion AND numerics, one artifact.

FlashAttention: 5.5's tiling + the online identity = O(N) traffic

naive attention, per head:  S = QKᵀ (N×N!) → P = softmax(S) → O = PV
  N=4096 fp32: S alone = 64 MB written+read per head — and A1 P3 showed the
  TRAINING bill: 8.6 GB of tape per layer at batch 8 × 32 heads.
flash: for each K/V tile j:
  Sij = Q·Kjᵀ  (in SRAM — 5.5's tile)          m' = max(m, rowmax(Sij))
  O ← O·e^(m−m') + e^(Sij−m')·Vj               l ← l·e^(m−m') + rowsum(e^(Sij−m'))
  (the ONLINE state grew a third member: O rescales exactly like l)
finally O /= l.   EXECUTED (N=64, d=16, fp64): max|flash − naive| = 3.3e-16 —
machine epsilon: not approximately attention, IS attention, reordered.
traffic: O(N²) score tensor deleted → O(N·d) reads of Q,K,V,O. Memory-bound
→ compute-bound (4.7's MOVE), and the tape shrinks from N² to N (A1 P3).

Worked example

Task: Implement FlashAttention forward in 15 lines of NumPy, prove exactness, and read the two ledgers (traffic + tape) that explain why this algorithm reorganized the industry. All numbers executed.

m = full(N, -inf); l = zeros(N); O = zeros((N, d))
for j in range(0, N, Bc):                        # stream K/V tiles
    S  = Q @ K[j:j+Bc].T / sqrt(d)               # tile of scores, SRAM-sized
    m2 = maximum(m, S.max(1))
    P  = exp(S - m2[:,None])                     # safe: shifted by tile max
    l  = l * exp(m - m2) + P.sum(1)              # online softmax (verified §2)
    O  = O * exp(m - m2)[:,None] + P @ V[j:j+Bc] # the SAME rescale, on O
    m  = m2
O /= l[:,None]
exactness: max|flash − naive| = 3.3e-16 (fp64) — the rescale identity is
  algebra, not approximation; fp32 lands ~1e-6 (budget compare, M1 L8).
ledger (N=4096, d=64, fp16, per head): naive materializes S+P: 2·N²·2 B =
  64 MB round-tripped; flash touches Q,K,V,O ≈ 4·N·d·2 B = 2 MB. Ratio: N/d
  ≈ 32× less traffic — and the ratio GROWS with sequence length, which is
  why long-context models are only possible in the flash regime.
tape (training): stores O, m, l — O(N) — instead of P — O(N²): A1 P3's
  8.6 GB/layer becomes ~17 MB/layer; backward RECOMPUTES tiles from Q,K,V
  (checkpointing's trade, applied surgically to the one tensor that mattered).

What to internalize: FlashAttention contains zero new mathematics — softmax algebra (M1 L8), tiling (5.5), online rescaling (§2), recompute-vs-store (A1 §3). Its genius is COMPOSITION under a hard constraint (SRAM size), which is precisely the skill this course trains. When the next "impossible to tile" op appears in your career, the question sequence is now yours: what's the running state? does an identity let me restart it against new normalizers? what does backward need saved vs recomputed?

Key points

  • Draw the traffic ledger before optimizing anything: unfused elementwise/normalization chains cost one full tensor round-trip PER OP at ~zero FLOPs — fusion's win is deleted trips (÷3 for softmax, measured arithmetic).
  • Online softmax's rescale identity (s·e^{m−m'}) makes the "untileable" softmax streamable — verified exact; the max-shift doubles as the fp32-overflow shield (exp dies at 89).
  • Never compute variance as E[x²]−E[x]²: fp32 returns literally 0.0 at mean 1000, σ 0.01 (executed) — two-pass or Welford, with fp32 accumulation regardless of storage dtype.
  • FlashAttention = K/V tiles through SRAM + the online identity extended to the output accumulator: exact to machine epsilon, O(N²)→O(N·d) traffic, and an O(N²)→O(N) tape — the training-memory win is as important as the speed.
  • Fused kernels must decide what backward sees: save-minimum or recompute (flash recomputes tiles from Q,K,V, storing only m,l,O) — A3's save_for_backward economics at algorithm scale.
  • Fusion couples your kernel to model structure (masks, GQA head-broadcasts, dtypes): every architecture variant gets its own golden-output fixture, or silent wrongness ships (scenario).

Quiz

1. A profiler shows a transformer block spending 41% of time in matmuls (already cuBLAS/TC) and 38% across ~9 small ops (bias, GELU, dropout, residual adds, layernorms). Two engineers propose: (A) hand-optimize the matmuls ("they're the biggest single item"); (B) fuse the 9 small ops into 2–3 kernels. Arbitrate with the two ledgers, and predict B's ceiling.
Option 4 is the half-right trap: launch overhead (5.2's floor) is real but SECONDARY — the dominant cost is each op's full read+write of the activation tensor (the §1 ledger; a 64 MB tensor's trip is ~0.3 ms on T4 while a launch is ~5 µs). Getting the MECHANISM right matters because it predicts the fix's shape: fusion helps even for LARGE tensors where launch overhead is negligible. This quiz is A9's a9-when table derived by hand — and the exact reasoning torch.compile's authors baked into Inductor.
2. Your from-scratch flash kernel matches naive attention at rtol 1e-5 on random Q,K,V — but a colleague claims flash attention is "approximate attention" and demands you switch to the "exact" naive version for a compliance-sensitive model. Adjudicate with mathematical precision, including what IS different between the two outputs and the one scenario where naive is legitimately preferable.
"Tiled = approximate" is a surprisingly common senior-level misconception, and the refutation must be surgical: identity-based reordering (exact, flash) vs genuine approximation (sparse/linear attention variants, which DO change the math). The compliance answer mirrors 5.11 quiz 2's bitwise doctrine: fix the ORDER if you need bit-reproducibility (flash is deterministic per config!), state budgets otherwise. Go deeper — the fusion craft sheet

1. What fuses, what can't, and why (the boundary rules)

FUSES FREELY: elementwise chains (bias→GELU→dropout→residual: one loop body),
  elementwise → reduction (softmax's exp+sum), reduction → elementwise
  (norm's var→scale), matmul EPILOGUES (bias/activation on the C tile while
  it's in registers — a11-fused, the capstone)
FUSES WITH THOUGHT: two reductions over the same data (max then sum → online
  identity required — §2's whole story); attention (three ops + softmax → the
  running-state trick)
RESISTS FUSION: matmul→matmul through a full hidden dim (the intermediate is
  each program's INPUT from other programs' outputs — 5.2's block-independence
  wall; you'd need grid-wide sync = separate kernels, 5.8's law), big
  reshuffles (transpose-like data movement between ops wants its own 5.7
  way-station)
the test: can one PROGRAM compute its output tile reading only ITS input
  tiles + O(1) running state? yes → fusible; no → kernel boundary is real.

2. Flash backward, honestly (where the memory went)

backward needs P (N²) — but P was never stored. Solution: store per-row
(m, l) [O(N)] + recompute each tile's P from Q,K,V during backward, fusing
the dP/dS softmax-Jacobian algebra into the same tile loop. Cost: ~1 extra
forward's worth of FLOPs (attention recompute) — the checkpointing trade
(A1 §3) at its best exchange rate, because attention is exactly the layer
whose activations were quadratic. dQ/dK/dV accumulate across tiles → the
5.8 rules apply (block-column parallelism + atomics or split accumulators —
implementations differ; the nondeterminism registry (A2 P4) knows which).

3. Gotchas

exp without the shift. Softmax on logits ≥ 89 in fp32 → inf/NaN cascade (A4's measured wall). The shift is not a nicety; any fused softmax you review without it is a bug report.
One-pass variance. Executed: literal 0.0 at mean 1e3. Two-pass/Welford + fp32 acc, and the adversarial-row fixture forever (Ex.1).
eps outside the rsqrt. normalize = (x−μ)·rsqrt(σ²+ε): ε inside. Outside, σ²→0 rows blow up first and get "rescued" after the inf already propagated.
Fusing across the tape without a plan. A fused op that saves every intermediate "to be safe" un-wins the memory (A3 gotcha 3); one that saves nothing and can't recompute breaks backward. Decide per tensor: save, recompute, or derive (A3 P1's table — now for 5-op fusions).
Assuming fusion helps compute-bound code. A fused epilogue on an already-TC-saturated GEMM buys the epilogue's traffic only — if the epilogue was 3% of time, that's the ceiling (quiz 1's arbitration, inverted). Ledger first, always.
Silent variant drift. Causal mask, ALiBi, GQA, sliding window — each changes the fused kernel's inner logic. The library kernel "worked" on the new variant because nothing crashed (5.3's worst kind of wrong). Golden-output fixtures per variant (scenario), no exceptions.

Scenario — the fused kernel that was right about the wrong model

An inference team fuses their 7B model's attention + norms into a tight Triton stack (this lesson's toolkit): 2.1× end-to-end, fixtures green, deployed, celebrated. Four months later the research team ships a successor model — same dimensions, but grouped-query attention (8 query heads share each KV head) and a sliding-window mask. The serving team bumps the config, throughput looks great, quality metrics sag by "a weird 4%," and — because nothing ERRORED — three weeks go to data-drift and quantization theories. The actual bug, found when someone finally diffs against an eager-mode golden run: the fused kernel's head indexing still assumed one-KV-per-Q (it broadcast the WRONG kv head for 7 of every 8 queries — plausible outputs, wrong attention: 3.2's silent-UB flavor at the model level), and the sliding-window mask was applied post-softmax in one branch (renormalization skipped — probabilities summing over the window's complement leaked in). Two fixes, one afternoon, quality recovered. The postmortem's systemic finding is this lesson's closing law: a fused kernel is a compiled COPY of the model's structure; when the model moves, the copy silently stales. Their fix-forward: every fused op carries an eager-composition twin (M2 L6's reference oracle) and a per-architecture-variant golden suite that runs on every model onboarding — the same 40-line habit that would have converted three weeks into one red test on day one.

Practice

1. Ledger drill — for a (8192, 8192) fp16 tensor on an H100 (3.35 TB/s): price the eager chain bias→GELU→residual→layernorm (reads/writes per op, total ms) vs a two-kernel fusion (bias+GELU+residual | layernorm). Then state the FLOP count's role in your answer.
Tensor = 128 MB fp16. Eager: bias (r128+w128... bias vector negligible) + GELU (r+w) + residual (r 2×128 + w 128) + LN (r + w, two internal passes if unfused: charge r×2+w) ≈ reads 5×128+ext, writes 4×128 → ~1.3 GB → ~0.39 ms. Fused pair: kernel 1 reads x+res (256), writes 128; kernel 2 reads 128 (stats in-kernel), writes 128 → 640 MB → ~0.19 ms → ~2×. FLOPs' role: NONE — they never entered the arithmetic (each op is ≤ a few FLOPs/element; at 3.35 TB/s vs ~1000 TF fp16 the ridge is ~300 FLOP/B — these ops sit at ~0.02). Being able to say "I didn't need the FLOPs" with a straight face IS the ledger literacy this lesson certifies.
2. Extend the online trick: which of these reductions can stream with O(1) running state and a restart identity, and what's the state? (a) max; (b) mean; (c) variance; (d) softmax denominator; (e) median; (f) top-k. For the streamables, name the identity; for the rest, name the obstruction.
(a) max: state m, identity trivial (max is associative — no rescale needed). (b) mean: (count, sum) — Welford's simplest case. (c) variance: (count, mean, M2) — Welford's merge formula (parallel variance combine: the B8 preview). (d) softmax denom: (m, s) with the §2 rescale — the star of the show. (e) median: NO O(1) state — order statistics need the distribution (obstruction: not decomposable into a bounded merge; approximations like t-digest exist = changing the SPEC). (f) top-k: state = the k candidates (O(k), fine for small k — 5.8 P1f's mergeable-summary). The general test: does a MERGE operation exist on bounded state with associativity? — that's the map of what can ever be fused/tiled/distributed (5.8's privatize-merge, A7's allreduce: same algebra all the way up).
3. Your fused flash kernel must add ALiBi (a per-head linear bias added to S before softmax). List every place in the worked example's loop the change touches, the one numerics interaction to re-check, and the two fixtures the variant must add (scenario's law).
Touches: S computation only — S += slope_h·(j_positions − i_positions) inside each tile (bias is position-dependent → computed per tile from offsets, M2 L4's broadcasting in index space). The rescale machinery (m, l, O) is UNTOUCHED — biases pre-softmax flow through the identity unchanged (that's why additive-bias variants are cheap in flash-world, and multiplicative/post-softmax ones are not — quiz territory). Numerics re-check: the bias grows with distance — at long N, S+bias can push fp16/bf16 score range; confirm the max-shift still bounds exp inputs (it does — shift is per-row AFTER bias; but check S's dtype BEFORE the max if computing in fp16: A6's range tables). Fixtures: (1) golden vs eager-with-ALiBi at several N incl. long; (2) slope=0 degenerate must EXACTLY match the no-ALiBi kernel (a differential fixture that isolates the diff — M2 L6's controlled-variable testing). One-afternoon change, two permanent tests: the scenario's economics, pre-paid.
4. Why does flash's advantage GROW with sequence length while its advantage over naive at N=256 may be negative (Ex.2's crossover)? Derive both ends: the traffic ratio as f(N, d), and the two fixed overheads that dominate small N. Then: does bigger d help or hurt flash's relative win?
Ratio: naive traffic ≈ 2·N²·b (S and P round-trips) + Nd terms; flash ≈ 4·N·d·b → advantage ≈ N/(2d): LINEAR in N (at N=4096, d=64: 32×; at N=64k: 512× — hence long-context's dependence on it). Small N: (1) the rescale/exp overhead per tile is FLOPs naive pays once (and small-N S fits L2 — naive's "traffic" partially never reaches HBM: 5.7 quiz 2's cache-rescue, working against flash!); (2) skinny per-tile matmuls underuse TCs vs one chunky GEMM (a6-tc shapes). Bigger d HURTS the relative win (ratio N/2d shrinks) while raising naive's absolute cost too — which is why d stays ~64–128 across the industry while N exploded: architecture co-evolved with the kernel's economics. Seeing model hyperparameters as KERNEL-ECONOMICS decisions is the track's quiet superpower.
5. A junior proposes fusing the entire transformer block — "QKV projection through FFN, one kernel." Using §1's boundary rules, write the three-sentence review comment: what breaks, what the legitimate maximal fusion units are, and what the compiler (A9) will find on its own.
"The QKV→attention→output-proj→FFN chain crosses two full matmuls whose intermediates each program would need from ALL other programs' outputs — that's the block-independence wall (5.2/§1): fusing through it requires grid-wide sync, i.e., it's not one kernel, it's kernels. Legitimate maximal units: (matmul + its epilogue) [a11-fused], (attention's three ops via flash's running state) [§flash], and (the elementwise/norm glue between them) [Ex.1] — which is, not coincidentally, exactly the partition Inductor/torch.compile converges to (a9-stack), so hand-fusing further than the compiler's partition needs an evidence bar, not enthusiasm (5.10 P5). Happy to pair on the epilogue fusion — that one's real and unclaimed." Three sentences, two citations, one redirect: the review-comment format that teaches instead of gatekeeps.
6. Fusion changes the NUMERICS spec, not just speed: enumerate the three float-order differences a fused softmax→matmul introduces vs eager, the correct comparison policy for each fixture tier (M1 L8/5.11), and the sentence you put in the PR that pre-empts the "results changed!" ticket.
Order diffs: (1) softmax's sum order (tile partials vs row-sequential — quiz 2); (2) the P·V products interleave with rescales (multiply-then-accumulate order per tile); (3) acc dtype boundaries move (fused keeps fp32 register chains where eager round-tripped through bf16 storage — fused is often MORE accurate: the direction surprises people). Policy: unit fixtures vs fp64 oracle with per-dtype rtol (never bitwise vs eager); differential fixtures (variant vs variant, P3's slope=0 trick) MAY be bitwise when the code path is genuinely shared; end-to-end model tests use metric budgets. PR sentence: "Outputs differ from eager in final bits by design (reordered accumulation, documented in NUMERICS.md §fusion; typically closer to the fp64 reference than eager was — see attached error table); comparison policy is rtol=1e-3 bf16 / 1e-6 fp32 per our M1-L8 ladder." The pre-emption line converts a week of tickets into a doc link — A3 P4's memo skill, now standard operating procedure.
