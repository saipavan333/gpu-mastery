Capstone — CPU Matmul & the Honest Ladder

Everything in this module converges: build matmul in C, prove it correct against your own oracle chain (hand → Python → NumPy → C), then climb the performance ladder — loop order, blocking, all cores — measuring honestly at every rung. The number you end with is the baseline the GPU must beat in 5.11, and the method you use is the method for the rest of your career.

The project brief

Build cpu-matmul: the 3.6 P7 design, realized — matmul.h with swappable implementations (naive, ikj, blocked, omp), a fixture-driven test suite, a statistics-honest bench harness, and a README whose numbers you can defend line by line. Acceptance = the stranger test (M2 L7): clone → make test green → make bench → a GFLOP/s table appears with medians and spreads.

The chain of trust: M1 L6 hand-computed [[50,32],[122,77]] → M2 L4's Python oracle verified it → M2 L5's A @ B verified against that → tonight, NumPy generates binary fixtures → your C verifies against them within a budgeted tolerance. Four independent implementations agreeing is how numerical software earns trust — no single link is taken on faith.

Stage 1 — naive, correct, measured

void matmul_naive(const float *A, const float *B, float *C,
                  size_t M, size_t N, size_t K) {
    for (size_t i = 0; i < M; i++)
        for (size_t j = 0; j < N; j++) {
            float s = 0.0f;
            for (size_t k = 0; k < K; k++)
                s += A[i*K + k] * B[k*N + j];      /* IDX inline: i,k and k,j     */
            C[i*N + j] = s;
        }
}

/* ikj: hoist A[i][k], stream B and C rows — every access stride-1                */
for (size_t i = 0; i < M; i++) {
    for (size_t k = 0; k < K; k++) {
        const float a = A[i*K + k];               /* one load, N reuses           */
        for (size_t j = 0; j < N; j++)
            C[i*N + j] += a * B[k*N + j];         /* two streams, both forward    */

}   /* note: C must be zeroed first — a CONTRACT change; document it or memset    */

Key points

  • The chain of trust — hand → Python oracle → NumPy → C fixtures — plus ragged sizes and budgeted tolerances is what "verified" means for numerical code.
  • Benchmarks: warmup, ≥15 reps, median±IQR, consume every output, one flag-set per table — or the numbers are fiction (M1 L7 + 3.1 P6, forever).
  • Loop order is YOUR job — float non-associativity (M1 L8) forbids the compiler from reordering; ikj's stride-1 walks buy 2–10× for identical FLOPs.
  • Blocking engineers arithmetic intensity (M1 L3 §4): tiles that fit cache get reused K/T times — the same idea shared memory hand-implements in 5.5.
  • OpenMP on disjoint tiles parallelizes without races (purity's dividend — M2 L3); sub-linear scaling is usually bandwidth saturation, not a bug.
  • Report peak-fraction and the distance to a tuned library honestly; naming your ceiling (SIMD microkernels) beats pretending it isn't there.

Quiz

1. You test three builds against plain-naive: (a) ikj at -O2, (b) naive at -O3 -ffast-math -march=native, (c) a pairwise tree-sum version (5.8's shape). Which may legally differ from the reference, and which must match bitwise?
The subtle one — verified by measurement in this course's own QA: naive/ikj/blocked all sum each cell in ascending k, so they agree to the BIT under default flags (loop order ≠ addition order!). What changes addition order: -ffast-math's vectorized partial sums, explicit tree reductions, and atomics-based parallel sums — those need the K·ε budget (and trees are usually MORE accurate: seq_sum of {1e8, 1.0×8} loses all eight 1.0s to absorption; tree_sum returns 100000008 — M1 L8 §3, demonstrable in 10 lines of C). Knowing WHICH transformations preserve order is what lets you demand bitwise tests where they're valid and budgets where they aren't.
2. Adding #pragma omp parallel for to the naive ijk's OUTER loop works fine, but a teammate put it on the INNER k-loop and gets wrong results AND 10× slowdown. Both effects, explained?
Parallelize where iterations are INDEPENDENT (i or j: different C cells — purity!) and where the work-per-fork amortizes the ~microsecond fork/join cost (M1 L3 estimation: 1M forks × 1µs = seconds of pure overhead). The k-loop is a REDUCTION — parallelizing it correctly needs reduction machinery (omp reduction clause, or 5.8's tree), not a bare pragma. 'Which loop gets the pragma' is the CPU rehearsal of 'which loop becomes the grid' (3.4 Ex.1) — the same design instinct, third appearance.

Exercises

Exercise 1 — The tile sweep with evidence: run blocked with T ∈ {16, 32, 64, 128, 256} on 1024³, produce the table (median±IQR each), and ANNOTATE it with cache arithmetic: working set per tile-step = 3·T²·4 bytes vs your L1 (~48 KB) and L2 (~1.25 MB per core — check yours: lscpu / sysctl). Where does the math predict the knee, and where IS it?
T     working set   vs cache        typical result (yours WILL differ)
16    3 KB          « L1            12.1 GFLOP/s  (loop overhead dominates)
32    12 KB         fits L1         13.9
64    48 KB         ≈ L1 boundary   14.5   ← knee usually here-ish
128   196 KB        L2 territory    13.8

Prediction: best T where 3T²·4 ≈ L1-ish (T≈64 for 48 KB) — and the measured knee usually agrees within one step, but NOT exactly (prefetchers, associativity, TLBs — M4's territory peeking through). Exercise 2 — Falsify your own harness (the paranoia pass): three sabotage tests — (a) benchmark an empty function: what SHOULD the harness report, and what does yours do? (b) remove the sink consumption at -O3: how far does the "speedup" inflate? (c) run the full bench twice back-to-back and compare medians: what drift is acceptable before you blame thermals/turbo (and what's the fix for benchmarking on laptops)?

(a) Empty function: should report ~timer-resolution noise (µs-scale medians with IQR ≈ median — i.e., "this measurement is floor"); a harness printing a confident 0.00 ms ±0.00 is LYING about its resolution — add a resolution self-check that warns when median < 50× clock granularity (clock_getres tells you). (b) Without the sink, -O3 may delete the whole call (3.1 P6): "matmul" at 0.001 ms = infinite GFLOP/s — if your speedup column ever shows this, the harness caught itself; keep (b) as a PERMANENT negative test (make test includes a "sink-removal canary" that asserts the empty-vs-real ratio is huge). (c) Back-to-back drift of 2–5% is normal (turbo states, thermals — M1 L7's variance made of silicon); >10% on a laptop means throttling — fixes: performance governor, cooldown sleeps between kernels, longer warmup, and REPORTING the environment (the M2 L7 provenance dict grows cpu-governor and temperature fields). A harness you've actively tried to fool is the only kind whose numbers you may put in a README — this exercise IS the difference between benchmarking and wishful timing.

3. What OpenBLAS knows that you now almost do

The remaining 3–10×: SIMD microkernels — the innermost tile computed in hand-scheduled AVX registers (8–16 FMAs in flight, register-blocked 6×16 sub-tiles), packing — copying tiles into contiguous scratch first so the microkernel reads perfectly-strided data (a deliberate extra copy that PAYS — the same counterintuitive trade as GPU shared-memory staging in 5.5), and per-CPU dispatch — selecting kernels per microarchitecture at runtime. None of it is magic; all of it is this lesson's ideas pushed to the register level. You could learn it (BLIS's papers are readable with your current tools); the course routes that energy to the GPU instead, where the same three ideas — vector width, staging, occupancy — are 5.5–5.11's entire arc. LIMITS.md says exactly this, in three sentences, which is what "honestly labeled" means.

4. Gotchas

Benchmarking the wrong build. The asan objects linked into bench (3.6 P6's collision) → all numbers 2× slow, conclusions inverted. The bench target depends on a clean non-sanitized build BY MAKEFILE RULE, and the table names its flags.
Un-zeroed C in += kernels. ikj/blocked accumulate into C — garbage in, garbage summed (3.2's uninitialized locals at heap scale). memset in the kernel or document the precondition; the fixtures catch it (integer fixture explodes) IF you run them per-variant — test every implementation, not just naive.
Tuning on one size. T=64 wins at 1024³, loses at 4096³ (L2/L3 dynamics shift). The bench sweeps sizes; conclusions state their domain. "Best" without "at what size" is marketing.
Threads × threads. OpenMP over OpenBLAS-linked code can nest thread pools (8×8 threads thrashing). OMP_NUM_THREADS and OPENBLAS_NUM_THREADS are separate dials; the harness pins both and records them (provenance).
First-touch NUMA surprises (big machines). On multi-socket boxes, memory belongs to the socket that FIRST touches it — init arrays in parallel with the same schedule as compute, or cores starve across the interconnect. Laptop-invisible, server-decisive (M4 will name it).
Comparing your fp32 to NumPy's fp64 default. np.random.rand gives float64; forgetting .astype(np.float32) in make_fixtures makes tolerances mysteriously fail (dtype mismatch — M2 L5's creep, striking the test data itself). Fixtures declare dtype explicitly, always.

Practice — extensions

1. Transpose-B variant: pack Bᵀ once (one O(N·K) pass), then the naive loop reads BOTH operands stride-1 without full blocking. Measure vs ikj; account for the packing cost at K=64 vs K=4096 (amortization — M1 L2's series thinking); relate to §3's "packing" and to cuBLAS's op(B) transpose flags (M1 L6!).
Bᵀ makes the naive dot-product loop read B's "column" as a contiguous row: often lands within ~1.5× of ikj with simpler code. Packing cost O(NK) amortizes over M uses — negligible at 1024³ (one pass vs K reuses; the geometric-amortization argument), meaningful for skinny matrices (M small). This IS §3's packing idea in miniature, and it's WHY BLAS exposes transpose flags: op(B)=T often means "the layout that makes MY kernel stream" — M1 L6's row/col-major schism as a performance lever. GPU echo in 5.5: staging tiles into shared memory transposed to dodge bank conflicts — same trick, third costume.
2. aligned_alloc(64, ...) all three matrices + report alignment in provenance: measure the delta (often 0–5% on CPU with -march=native, occasionally more). Why is the same change worth up to 2× on GPU (5.7 preview), and what does the contrast teach about porting intuitions?
CPU: caches + hardware prefetch mostly forgive misalignment (unaligned AVX loads are near-free on modern cores) — small, real, occasionally-zero win; measure, report, don't oversell. GPU: memory transactions are 32-byte sectors served to 32-thread warps in lockstep — misalignment splits every warp load into two transactions: up to 2× traffic, mechanically (M1 L1's masks become throughput). The porting lesson: intuitions don't transfer, MODELS do — "what does one memory transaction serve, and what breaks its efficiency" is the portable question; its ANSWER is hardware-specific. You'll re-derive it per-platform forever (Track D8 makes a living from exactly this).
3. The fp64 ladder: rerun everything in double (the template from 3.7 Ex.2 pays off — one recompile). Predict first: which rungs lose ~2× (bandwidth-bound ones — bytes doubled) vs less (compute-bound ones — CPU fp64 FMA is half-rate, but...). Compare tables; write the three-sentence dtype-policy paragraph for LIMITS.md.
Typical: naive/ikj lose ~1.7–2× (streaming rungs: bytes doubled, bandwidth fixed — M1 L3's budget); blocked+omp lose ~2× too on most consumer CPUs (fp64 SIMD lanes halve: 8→4 per register — both walls move together, conveniently). The policy paragraph: "This project benchmarks fp32 as the GPU-relevant dtype; fp64 costs ~2× on CPU (bytes + lanes) and 8–32× on consumer GPUs (unit ratios — 3.2 Ex.2), so dtype is a first-class axis in every table, never a footnote. Fixtures pin dtype explicitly; tolerances are budgeted per-dtype (ε₃₂ vs ε₆₄ — M1 L8)." Three sentences, four lessons compressed — and Track A6's mixed-precision work will quote it back.
4. Strassen, discussed and declined: the recursion multiplies 2×2 blocks with 7 multiplies instead of 8 → O(n^2.807) (M1 L3's exponent lever!). Estimate the crossover vs your blocked kernel given Strassen's ~3× extra additions and worse locality; then justify, in numbers, why production BLAS mostly declines too (numerical stability footnote included — M1 L8).
Crossover arithmetic: saving per level = 12.5% of multiplies, cost = extra passes over data (bandwidth! the additions are memory-bound) + lost blocking locality; with your measured GFLOP/s for adds-vs-FMAs, the break-even lands at n ≈ several thousand at BEST for one recursion level — and each level's temporaries eat cache (Ex.1's knee math working against you). Stability: Strassen's error bounds are ~n^log7-ish worse-conditioned (subtractions of products — M1 L8 §2's cancellation surface grows); fp32 at n=4096 can visibly degrade. Verdict for LIMITS.md: "asymptotics win asymptotically; at practical n, constants, locality, and conditioning keep classical blocked GEMM king — we measured, we declined, we documented." The exponent lever (M1 L3) is real; knowing when the constant term vetoes it is the engineering.
