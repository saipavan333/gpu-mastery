Why C — and what really happens between source and binary

CUDA is a C++ dialect; drivers, runtimes, and every kernel you'll ever ship live on this side of the fence. Module 2 made you productive; Module 3 makes you close to the machine. First step: watch your text become a program, stage by stage — because when builds break (and they will), this pipeline is the map.

Set up in 60 seconds: Colab works for C too — %%writefile hello.c in one cell, !gcc -Wall -Wextra -O2 hello.c -o hello && ./hello in the next. Locally: WSL2/Linux has gcc via sudo apt install build-essential. Details: Lab setup.

Concept

Why a Python person learns C (the honest pitch)

Three reasons, in ascending importance. (1) Performance floor: M2 L5 measured the ~100× interpreter tax; C code IS the compiled side you were calling. (2) The GPU speaks it: a CUDA kernel is C/C++ with three extra keywords — there is no "CUDA for Python people" that skips this. (3) Mechanical sympathy: pointers, memory layout, and lifetime — invisible in Python, decisive for performance everywhere — are C's surface syntax. You already own the concepts (M1's addresses, M2's tags and buffers); C just removes the padding between you and them.

hello.c, honestly annotated

#include <stdio.h>                    /* preprocessor: paste in printf's declaration */

int main(void) {                      /* the OS calls main; int = exit status type  */
    int n = 4096;                     /* declare THEN use — types are compile-time  */
    printf("matmul(%d) = %.2f ms\n",  /* %d int, %.2f double, \n newline            */
           n, 2.0 * n * n * n / 50e12 * 1000);
    return 0;                         /* 0 = success; nonzero = error (shell checks) */
}
$ gcc -Wall -Wextra -O2 -g hello.c -o hello && ./hello
matmul(4096) = 2.75 ms

Everything is declared before use; statements end in ;; blocks live in { } (indentation is for humans now — the compiler ignores it, the exact opposite of Python's rule, and a classic source of misread code: braces are the truth, indentation is a claim).

The pipeline: four machines in a trench coat

gcc -E hello.c | tail -20     # 1 PREPROCESS: #include/#define are TEXT PASTE — see main()
                              #   at the bottom of ~800 pasted lines of stdio declarations
gcc -S -O2 hello.c            # 2 COMPILE: C → hello.s (assembly — readable! try it)
gcc -c hello.c                # 3 ASSEMBLE: → hello.o (machine code, not yet runnable)
gcc hello.o -o hello          # 4 LINK: stitch your .o with libc → executable

Two stages generate most real-world confusion, so meet them now: the preprocessor is dumb text substitution (powerful, dangerous — deep dive §2), and the linker is a matchmaker pairing every "I call this function" with exactly one "here is its body":

Static typing: errors move left

int n = "4096";               /* error: initialization of 'int' from 'char *'      */
float f = flops(n, 50e12)     /* error: expected ';'                                */
undeclared_var + 1;           /* error: 'undeclared_var' undeclared                 */

Python raised these at runtime — possibly in production, possibly never on the path you tested (M2 L6). C refuses to build. The cost: you declare types everywhere. The payoff: -Wall -Wextra is a free, instant test suite, and reading its output is a professional skill exactly like reading tracebacks was. From today, warnings are bugs: fix them or consciously silence them, never scroll past.

printf: formatted output with a loaded gun

SpecifierType it expectsMismatch consequence
%dintUndefined behavior — printf trusts you and reads raw argument bytes as told. Garbage numbers on YOUR machine, crashes on another (a real portability bug class). gcc's -Wformat (in -Wall) catches most — another reason warnings are law.
%ld / %lld / %zulong / long long / size_t
%f / %e / %gdouble (floats auto-promote here)
%p / %s / %cpointer / char* string / char

Worked example

Task: Port M2 L1's kernel-time estimator to C, then look at what -O2 actually did to it — your first read of compiler output as evidence rather than mystery.

/* estimate.c — the M2 L1 estimator, compiled edition */
#include <stdio.h>

double flops_matmul(double n)        { return 2.0 * n * n * n; }
double time_ms(double work, double peak) { return work / peak * 1000.0; }

int main(void) {
    double n = 4096, peak = 50e12, bw = 1.0e12;
    double t_compute = time_ms(flops_matmul(n), peak);
    double t_memory  = time_ms(3.0 * n * n * 4.0, bw);
    printf("compute floor: %.2f ms   memory floor: %.2f ms\n", t_compute, t_memory);
    printf("bound by: %s\n", t_compute > t_memory ? "COMPUTE" : "MEMORY");
    return 0;
}
$ gcc -Wall -Wextra -O2 estimate.c -o estimate && ./estimate
compute floor: 2.75 ms   memory floor: 0.20 ms
bound by: COMPUTE

Now the interesting part. gcc -S -O2 estimate.c and open estimate.s: the functions flops_matmul and time_ms exist… but main doesn't call them. With every input known at compile time, -O2 computed the whole program and embedded the answers as constants (you'll find 2.75's bit pattern in the data section). This is constant folding + inlining — and it's your first direct evidence of the compiler as an aggressive collaborator: it will fold, inline, reorder, and delete anything the language rules permit. Most of the time that's your 10× for free. The exception — when YOUR code breaks the rules (UB) and the optimizer's assumptions turn surgical — is Lesson 3.2's cliffhanger. Decision made: we compiled with -O2 and -Wall from the very first program: optimization and hygiene are defaults, not upgrades.

Key points

  • C is the language of the compiled layer you've been calling all through Module 2 — and CUDA is C++ with extensions; there is no route around it.
  • Build = preprocess (text paste) → compile (→ assembly) → assemble (→ .o) → link (match needs with provides); -E/-S/-c stop after each stage.
  • Braces are the block structure; indentation is now merely a claim about it. Semicolons end statements; declarations precede use.
  • Static typing moves a whole bug class from runtime (Python, 3am) to compile time (now); -Wall -Wextra makes the compiler your first test suite.
  • printf format specifiers are typed promises; a mismatch is UB, not a formatting quirk — -Wformat catches most, so warnings are law.
  • "Undefined reference" is a LINKER error: a call with no body provided (missing .o or -l library) — different stage, different fix than "undeclared".

Quiz

1. gcc main.c -o prog fails with undefined reference to 'sqrt' — yet #include <math.h> is right there at the top. What's actually wrong?
Headers are promises, libraries are deliveries (the m3l1-symbols picture). The compiler was satisfied by the declaration; the matchmaker found no body. On Linux, libm is separate: gcc main.c -o prog -lm. Distinguishing compile-stage from link-stage errors by MESSAGE alone is a skill interviewers actively probe.
2. printf("%d\n", 2.75); compiles (with a warning) and prints garbage like 536870912. Why garbage and not 2 or an error?
No conversion happens: printf reads the argument bytes AS an int because you promised int. A double's bit pattern (sign/exponent/mantissa — M1 L8) read as int32 is meaningless. It "works" differently across machines and optimization levels — the definition of UB. The warning you scrolled past named this exactly.

Exercises

Exercise 1 — Port M2 L1's VRAM calculator to C: params = 7e9, bytes_per_param = 2; print weights in GiB (2 decimals) and the 3 TB/s tokens/sec ceiling. Then break it on purpose three ways (wrong specifier, missing semicolon, missing declaration) and file the three error/warning messages in your notes — you're building an error-message phrasebook.
#include <stdio.h>
int main(void) {
    double params = 7e9, bytes_per = 2.0, bw = 3e12;
    double weight_bytes = params * bytes_per;
    printf("weights: %.2f GiB\n", weight_bytes / (1024.0*1024.0*1024.0));  /* 13.04 */
    printf("ceiling: %.2f tok/s\n", bw / weight_bytes);                     /* 214.29 */
    return 0;
}

The three breaks teach the phrasebook: %d for weight_bytes → warning: format '%d' expects 'int' but argument has type 'double' (compile-time, thanks to -Wall); dropped semicolon → error: expected ';' before — reported on the NEXT line (the compiler noticed too late; look one line UP from syntax errors, always); using Params → error: 'Params' undeclared (C is case-sensitive like Python, but tells you at build time). Note 2**30 doesn't exist in C — no exponent operator; write the multiplication or use (double)(1u << 30) (M1 L1 shifts, careful with width — 3.2 territory).

Exercise 2 — Pipeline forensics: run all four stages on estimate.c yourself. Report (a) how many lines -E produces vs your source, (b) one recognizable line of assembly from -S and what it does, (c) what nm estimate.o shows as U (needed) vs T (provided), and (d) which single stage fails if you misspell printf as pintf — and HOW the message differs from a misspelled variable.

(a) ~800–1000 lines from ~15 (stdio.h pasted — and stdio includes other headers transitively). (b) In main you'll find e.g. movsd .LC1(%rip), %xmm0 — "load a double constant into floating-point register xmm0"; with -O2 those constants ARE your precomputed answers (the worked example's evidence). (c) U: printf (needed from libc); T: main, flops_matmul, time_ms (provided). (d) The cruel one: pintf(...) — older C assumed implicit declarations; modern gcc errors at COMPILE time ('pintf' undeclared... did you mean 'printf'?) — but if a stray declaration existed, it would sail through to a LINKER error "undefined reference to pintf". A misspelled variable always dies at compile. The lesson: the same typo class can surface at two different stages, and the stage tells you where to look.

Go deeper — the complete guide

The preprocessor's true nature, optimization levels as a dial, reading enough assembly to be dangerous, why C is fast (it's the memory model), and the flags that make up a professional default.

1. Optimization levels: what the dial does

FlagMeaningWhen
-O0no optimization; code matches source line-by-linedebugging sessions (gdb steps sanely — 3.8)
-O2inlining, folding, vectorization-lite, loop transformsthe production default, and this course's default
-O3-O2 plus aggressive vectorization/unrollingnumeric hot loops — measure, don't assume (3.9 does)
-Og / -goptimize-for-debugging / embed symbol info-g ALWAYS (costs nothing at runtime; enables 3.8's tools)
-ffast-mathlet the compiler break IEEE rules (reassociate, assume no NaN)M1 L8 §5's trade, CPU edition: speed for reproducibility — opt-in per file, never globally by habit

The mental model from the worked example generalizes: the optimizer rewrites your program into any equivalent-under-the-rules program. "Equivalent" is defined by the language standard, not your intent — which is why float non-associativity (M1 L8) blocks reorderings unless -ffast-math grants them, and why UB (3.2) voids the contract entirely.

2. The preprocessor: powerful, dumb, everywhere

#define BLOCK 256                      /* textual constant — no type, no scope     */
#define SQR(x) ((x) * (x))             /* macro "function" — parenthesize EVERYTHING */
SQR(a + 1)   /* → ((a + 1) * (a + 1)) ✓  without inner parens: a + 1 * a + 1 ✗   */
SQR(i++)     /* → ((i++) * (i++)) — i incremented TWICE. UB. Macros aren't calls! */

#ifdef __CUDACC__                      /* conditional compilation — one source,     */
  #define WHERE __host__ __device__    /* different builds. CUDA headers do exactly */
#else                                  /* this to share code between CPU and GPU    */
  #define WHERE
#endif

It's find-and-replace running before the compiler: no types, no scoping, arguments evaluated per appearance. Modern C prefers const double PEAK = 50e12; and real functions (the compiler inlines them anyway — you watched it). But you must READ macros fluently: CUDA's own headers are macro-dense (__global__ and friends are #defines), and #ifdef blocks are how one codebase serves Linux/Windows/GPU/CPU. Rule for writing your own: constants and include guards yes, clever function-macros no.

3. Assembly literacy: the 20-minute version

double axpy(double a, double x, double y) { return a * x + y; }
# gcc -S -O2 -mfma:                    # x86-64; args arrive in xmm0..2 (floats)
axpy:                                  # (-mfma or -march=native enables FMA;
    vfmadd132sd %xmm1, %xmm2, %xmm0    #  plain -O2 emits separate mul+add)
    ret                                # ONE instruction: xmm0 = xmm0*xmm1 + xmm2

You don't write assembly in this course — you glance at it to answer specific questions, and you already know enough to decode this one: vfmadd is the fused multiply-add from M1 L3/L8 — one rounding, one cycle-ish, the exact instruction your FLOP estimates count. Three glances you'll actually use: is my arithmetic using FMA/SIMD (v...pd = packed doubles = vectorized)? did the call get inlined (no call instruction)? did my "optimization" change anything at all (diff the .s files)? Compiler Explorer (godbolt.org) does this interactively with color-matching to source lines — bookmark it; it's the community's shared microscope, and it speaks CUDA too.

4. Why C is fast: the memory model IS the answer

Fold together what M2 already proved and this module makes explicit: a Python float is a heap-boxed object behind a pointer (M2 L4 §4: ~24 bytes + indirection + refcount churn); a C double is 8 naked bytes wherever you declared it — in a register, on the stack, in a contiguous array (M2 L5's ndarray buffer is literally a C array). No boxes, no tags at runtime (types were compile-time), no interpreter loop between statements. Consequences: arithmetic compiles to single instructions (§3); arrays walk at cache speed (M1 L3's ladder); and NOTHING stands between you and every mistake the runtime used to absorb — the trade this entire module teaches you to win. When people say "C is fast," they mean: C's data is laid out the way hardware wants, and its operations are the hardware's operations. You will make the identical argument about CUDA vs framework overhead in Track A.

5. The professional default (copy this into your Makefile)

CFLAGS = -Wall -Wextra -O2 -g          # warnings, warnings, speed, debuggability
# per-situation additions:
#   -Werror            warnings ARE errors (CI builds — keep local builds friendlier)
#   -fsanitize=address,undefined       dev/test builds (3.8 — the safety net)
#   -std=c17           pin the language version explicitly (avoid dialect drift)
#   -lm                link libm when you use sqrt/sinf/pow (quiz 1)

6. Gotchas

The stale binary. Edit hello.c, rerun ./hello, "my change did nothing" — you ran the OLD build. Compile-then-run every time (shell: gcc ... && ./hello — the && runs only on build success), or use make (3.6), which exists because humans forget.
if (x = 5) compiles. Python refused (M2 L1); C assigns 5, evaluates truthy, and proceeds — silently. -Wall warns (parentheses suggestion); some teams write 5 == x ("Yoda conditions") so the typo can't compile. Either way: this is warning-as-law example #1.
Reading indentation instead of braces. if (err)\n log();\n cleanup(); — cleanup runs ALWAYS (no braces = one-statement body). Apple shipped a famous TLS vulnerability on exactly this shape ("goto fail"). House rule: braces on every if/for, no exceptions.
Integer division still truncates. 2/3 * n is 0, always; n * 2/3 "works" by luck of left-to-right evaluation. Write doubles (2.0/3.0) or restructure — M1 L2/M2 L1's rule, now without a REPL to catch you experimenting.
Missing -lm (and library ORDER). Undefined reference to sqrt/sinf → add -lm — AFTER your files on the command line (the linker resolves left to right; libraries listed before the .o that needs them can be skipped). Order-sensitivity bites everyone once.
Trusting a clean compile as correctness. The compiler checks types and syntax, not logic or memory safety. "It compiles" is where C debugging BEGINS — Python's runtime guardrails are gone, and 3.8's tools take their place.

Scenario — the build that broke three ways before lunch

First week of a research assistantship: you inherit a 9-file C project ("just make it run") and hit the full pipeline in one morning — which, with this lesson, is a guided tour instead of a hazing. Error 1: fatal error: tensor.h: No such file — a preprocess-stage failure; the header lives in include/, so the paste-machine needs the path: -Iinclude. Error 2: ten screens of undefined reference to blas_sgemm — link-stage; nothing wrong with any source file, the Makefile simply lost -lopenblas (and it must come after the .o files — the order rule). Error 3, the subtle one: the program builds but prints impossible timings on YOUR machine while working on the professor's — a printf("%ld", some_int64)... no wait, the code says %d, and on your platform the mismatched read grabs half a 64-bit value (UB "working" elsewhere by accident — quiz 2 at production scale). You fix the specifier, add -Wall -Wextra to the Makefile, and 41 warnings appear — including two more latent format bugs and one if (x = threshold). An afternoon of warning-cleanup later, the project builds silently on both machines and you've met every character in this lesson: paste-machine, matchmaker, and the compiler that only checks what you let it. Your report to the professor is one line long: "warnings are now errors in CI."

Practice

1. Which STAGE fails (preprocess / compile / link / run), and what's the one-line fix: (a) #include <stdoi.h>; (b) printf("%f\n", "hello"); (c) calling my_kernel() that exists only in another .c you forgot to list; (d) a program that builds clean but prints nonsense timings.
(a) Preprocess: 'stdoi.h: No such file' — fix the typo. (b) Compile-time WARNING (with -Wall) + runtime garbage — UB; fix specifier to %s. (c) Link: undefined reference — add the .c/.o to the command. (d) Run(-time logic or UB): builds prove nothing; reach for 3.8's tools + suspicious-specifier audit. Stage identification from symptoms alone = half of build debugging.
2. Predict each printf's output, then verify: printf("%d %d\n", 7/2, 7%2); · printf("%.3f\n", 1.0f/3.0f); · printf("%zu\n", sizeof(double)); · printf("%d\n", 2.99); (last one: what does -Wall say?)
3 1 (truncation + remainder — M1 L2); 0.333 (float promoted to double in varargs; %.3f rounds the display, M2 L1's format codes); 8 (%zu is THE specifier for sizeof's size_t — %d here is a portability bug); garbage + warning "format '%d' expects int, argument has type 'double'". If any surprised you, run them — the compile-run loop is 3 seconds.
3. Write square.c with double sq(double x) { return x*x; } and a main that prints sq(1e154)*0 == 0. Compile -O0 and -O2, diff the .s files, and answer: at which level does sq still exist as a called function? What happened to the arithmetic? (1e154² = 1e308 ≈ fp64 max — deliberate.)
-O0: real call instruction, real multiplication at runtime. -O2: no call — inlined and folded; and here's the M1 L8 easter egg: 1e154*1e154 ≈ 1e308 flirts with DBL_MAX; the compiler folds it to the same IEEE result the runtime would produce (compilers implement IEEE semantics at compile time — folding must not change observable results). ×0 → 0.0 either way (but note inf*0 would be NaN — if you push to 1e155, the fold produces inf, then NaN, faithfully). The optimizer is thorough precisely because it's bound by the rules — foreshadowing what happens when UB voids them (3.2).
4. The preprocessor trap, live: #define DOUBLE(x) x + x — evaluate 3 * DOUBLE(4) by hand, then fix the macro two ways (parens; then "don't use a macro"). What does the fixed-by-function version cost at -O2?
3 * DOUBLE(4) → 3 * 4 + 4 = 16, not 24 — the paste has no precedence armor. Fix 1: #define DOUBLE(x) ((x) + (x)) — full parens, still double-evaluates arguments (DOUBLE(i++) remains a bug). Fix 2: static inline double dbl(double x){ return x + x; } — type-checked, single evaluation. Cost at -O2: zero — inlined to the identical add (verify with -S). "Real function, zero cost" is why modern C reserves macros for conditional compilation and constants.
5. nm forensics: compile two files where a.c defines int shared_counter; and b.c declares extern int shared_counter; run nm on both .o files and identify the symbol's letter in each (D/B vs U). What breaks if BOTH files define it — and at which stage?
a.o: shared_counter as D or B (defined, data/bss — provides); b.o: U (undefined — needs). Both defining: the LINKER refuses (multiple definition) — two bodies for one name breaks matchmaking. (Historic gcc allowed duplicate tentative definitions; modern gcc ≥10 errors, which occasionally "breaks" ancient codebases at upgrade time — a real-world migration story you can now explain.) The extern keyword is the header-file machinery of 3.6 in miniature: declare everywhere, define once.
6. Flags experiment worth 10 minutes: take Exercise 1's program, add a loop summing i*i for i in 0..99,999,999 (int64), print the sum. Time -O0 vs -O2 vs -O2 with the print REMOVED. Explain the third result with §1's mental model.
-O0: ~0.2–0.5 s (real loop). -O2: often ~0 s — the compiler applies Gauss-like closed forms or vectorizes; with the sum printed it must still COMPUTE it. Print removed: -O2 deletes the entire loop — an unobserved result is dead code, and "equivalent program" includes "no program". Benchmark moral (critical for 3.9): unused results make benchmarks measure nothing; always consume outputs (print a checksum, or write to a volatile sink). You just discovered why benchmark harnesses look paranoid.
7. Design: your team's compile-and-run wrapper script crun (bash, ~6 lines): takes file.c, builds with the professional default flags into /tmp, runs on success only, forwards program arguments, and prints the build command it used. State which gotcha each design choice kills.
#!/usr/bin/env bash set -e src=$1; shift bin=/tmp/$(basename "${src%.c}") echo "gcc -Wall -Wextra -O2 -g -std=c17 $src -o $bin -lm" gcc -Wall -Wextra -O2 -g -std=c17 "$src" -o "$bin" -lm && "$bin" "$@" Choices → gotchas killed: && chain → stale-binary (never runs old build); flags baked in → the "forgot -Wall" drift; -lm at the END → library-order; echo of the command → the "what flags did I even use" archaeology; /tmp binary → no clutter, no accidental committing of binaries. Six lines of bash encoding five scars — that ratio is what automation is for. (make replaces this properly in 3.6.)
