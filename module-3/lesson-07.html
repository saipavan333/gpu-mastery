Module 3 · Lesson 7≈ 3 h

C++ Essentials — exactly the subset CUDA needs

CUDA is C++, but kernel code is C-with-templates, not enterprise OOP. This lesson teaches the precise subset you'll use: references, RAII, vector/string, and light templates — each one retiring a manual C discipline you just earned. Earning it first was the point: you'll know what the automation does.

Mechanics: files become .cpp, compiler becomes g++ (same flags — 3.1 §5's defaults apply verbatim). C code is (nearly) valid C++; today we add, not replace. CUDA 13's nvcc compiles this whole subset in .cu files without ceremony.

Concept

References: the pointer that can't be wrong

void scale(float &x, float k) { x *= k; }     /* & in the SIGNATURE: reference     */
float v = 2.0f;
scale(v, 3.0f);                                /* call site: NO & — v is now 6.0f  */

void report(const std::string &name);          /* const&: look, don't copy,        */
                                               /* don't modify — THE parameter     */
                                               /* idiom for anything non-tiny      */

A reference is an alias: no NULL state, no reseating, no arithmetic — a pointer with the dangerous parts removed. Trade-off to know consciously: the call site scale(v, 3) no longer SHOWS the mutation (C's &v did — 3.3's visibility argument). C++ convention answers: mutation via reference is fine for obvious cases; APIs that want visible mutation take pointers on purpose. Kernel note: device functions use references freely; kernel launch parameters are pointers/values (they cross the PCIe bus — 5.2 explains why).

RAII: the destructor is a free() that cannot be forgotten

struct Timer {                                  /* the worked example builds this  */
    double t0;
    const char *label;
    Timer(const char *l) : label(l), t0(now_ms()) {}     /* ctor: acquire/start   */
    ~Timer() { printf("%s: %.2f ms\n", label, now_ms() - t0); }   /* dtor: ALWAYS */
};
{
    Timer t("matmul");        /* starts here                                      */
    run_matmul();             /* early return? exception? doesn't matter —        */
}                             /* ← dtor fires HERE, every path (M2 L7's `with`!)  */

Resource Acquisition Is Initialization: constructor acquires, destructor releases, scope is the contract. You recognize it — it's Python's with (M2 L7 §1) enforced by braces, and it's 3.5's goto-cleanup with the compiler writing the cleanup label. Everything ownable rides it: memory (vector), files (fstream), locks, CUDA streams and device buffers (Module 5 wraps cudaMalloc/cudaFree in exactly this Timer-shaped pattern).

std::vector: FloatBuf, retired with honors

#include <vector>
std::vector<float> v;             /* your FloatBuf: {data, len, cap} + RAII       */
v.push_back(2.5f);                /* fb_push, with the realloc dance inside       */
v.reserve(1'000'000);             /* preallocate: P2's zero-realloc optimization  */
std::vector<float> m(H * W, 0.0f);/* 3.5's matrix_flat + calloc, one line         */
v.data(), v.size()                /* the (pointer, count) pair — for C APIs and   */
                                  /* cudaMemcpy(d_x, v.data(), bytes, ...) in M5  */
v[i]                              /* unchecked (C speed); v.at(i) throws (checked)*/

Everything you learned survives: growth doubles (M1 L2's series), push_back can move the buffer — every pointer/iterator from before is dead (3.5 Ex.2's rule, verbatim), and .data() is how vectors hand their guts to C and CUDA. What's gone: fb_free (dtor), the realloc-temporary dance (inside), the leak class (structural). What it costs: nothing at -O2 — v[i] compiles to the same indexed load as C (verify with -S; the 3.1 skill keeps paying).

Value semantics: the opposite default from Python

std::vector<float> b = a;          /* DEEP COPY — megabytes if a is big           */
void f(std::vector<float> v);      /* copies on EVERY CALL — the classic perf bug */
void g(const std::vector<float> &v);   /* the fix: borrow, read-only              */
void h(std::vector<float> &v);         /* borrow, may mutate                      */

Templates-lite: dtype as a compile-time parameter

template <typename T>
void saxpy(size_t n, T a, const T *x, T *y) {
    for (size_t i = 0; i < n; i++) y[i] = a * x[i] + y[i];
}
saxpy(n, 2.0f, xf, yf);            /* instantiates saxpy<float>  — fp32 version   */
saxpy(n, 2.0,  xd, yd);            /* instantiates saxpy<double> — fp64 version   */

One source, N compiled specializations — M2 L5's dtype parameter moved to compile time, with zero runtime dispatch cost. This is the reason CUDA kernels are templates: template<typename T> __global__ void saxpy(...) serves fp32/fp16/bf16 from one body (Track A6 lives on this). Critical mechanical fact: template code must live in headers — the compiler needs the source at each instantiation site (deep dive §4 explains the why); it's the reason CUDA utility code ships as .cuh header libraries.

Worked example

Task: Port 3.6's project to C++ — watch 80 lines of manual discipline become 25 lines with the same machine code, then meet the ONE new bug C++ adds.

// bench.cpp — buffer.c + timer.c + main.c, consolidated
#include <cstdio>
#include <vector>
#include <string>
#include <ctime>

static double now_ms() {
    timespec ts; clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec * 1e3 + ts.tv_nsec / 1e6;
}
struct Timer {                                    // RAII, from the concept section
    const char *label; double t0;
    explicit Timer(const char *l) : label(l), t0(now_ms()) {}
    ~Timer() { std::printf("%s: %.2f ms\n", label, now_ms() - t0); }
};

template <typename T>
T checksum(const std::vector<T> &v) {             // const&: borrow (concept §4)
    T s = 0;
    for (T x : v) s += x;                          // range-for: M2 L2's for..in
    return s;
}

int main() {
    std::vector<float> data;
    data.reserve(10'000'000);                      // P2's lesson: pre-size, 0 moves
    {
        Timer t("fill");
        for (int i = 0; i < 10'000'000; i++) data.push_back(i * 0.5f);
    }                                              // "fill: 21.43 ms" prints here
    {
        Timer t("checksum");
        std::printf("sum=%.6e\n", (double)checksum(data));
    }
    return 0;                                      // vector's dtor frees. Nobody forgot.
}

The audit: zero mallocs, zero frees, zero leak-possibilities — and g++ -O2 -S shows the checksum loop compiling to the same vectorized adds the C version got (abstractions that vanish at -O2 are the C++ bargain). The one new bug, demonstrated deliberately: add float *p = &data[0]; before the fill loop, print *p after — garbage or crash: push_back moved the buffer (the vector diagram's red arrow; 3.5 Ex.2's physics, inherited not escaped). The reserve() call is why the fill loop is legal as written. Decision made: we kept printf (kernels use it; iostream is fine host-side — this course won't die on that hill) and marked the ctor explicit (blocks silent conversions — cheap insurance you'll see in every serious codebase).

Key points

  • References are null-free, fixed-target aliases; const T& is THE parameter idiom for non-tiny read-only arguments — borrow, don't copy.
  • RAII: ctor acquires, dtor releases, scope is the contract — Python's with + 3.5's goto-cleanup, enforced by the compiler on every exit path.
  • std::vector is your FloatBuf industrialized: same fields, same doubling, same invalidation-on-growth rule; .data()/.size() feed C and CUDA APIs.
  • C++ assigns by deep copy (opposite of Python's aliasing and C's pointer-passing); pass-by-value vectors is the classic silent performance bug.
  • Templates instantiate per-type at compile time — dtype generality with zero dispatch cost; template code lives in headers (.h/.cuh), a fact CUDA is built on.
  • The abstractions vanish at -O2 (verify with -S, as always); what remains is C's machine code with C++'s guarantees.

Quiz

1. void process(std::vector<float> v) is called in a loop 1000 times with a 40 MB vector. The profiler shows 60% of runtime in memcpy. Diagnosis and the one-character-ish fix?
40 GB of copying hiding behind a clean-looking signature — the valuesem diagram's cost row, live. const& borrows (Python's default, made explicit and safe). The deeper habit: in C++ reviews, every by-value container parameter gets a "did you mean this?" — it's correct occasionally (when you NEED a private copy), and that intent should be visible in a comment.
2. auto &x = v[3]; v.push_back(1.0f); x = 9.0f; — the write to x sometimes updates v[3], sometimes corrupts, sometimes crashes. Which rule from THIS MODULE did the code break, and in which lesson did you first meet it?
The reference is an address into the OLD buffer; push_back at capacity moves the block and frees it (use-after-free wearing modern clothes). "Sometimes fine" = capacity had room (no move) — the same nondeterminism that made 3.5's version a heisenbug. Fixes: reserve() first, take the reference AFTER growth, or store the INDEX (indices survive moves — 3.5 Ex.2's closing rule). You built this bug's engine by hand two lessons ago; that's why you can now diagnose it from the symptom line alone.

Exercises

Exercise 1 — Build DeviceBufferSim: an RAII class owning a malloc'd float buffer (ctor allocates n floats and prints "alloc n", dtor frees and prints "free n", .data()/.size() accessors, copying FORBIDDEN — delete the copy ctor/assignment). Write a main proving: scope exit frees; early return frees; and a copy attempt fails AT COMPILE TIME. Why is no-copy the right policy for a buffer that will become cudaMalloc-backed in Module 5?
#include <cstdio>
#include <cstdlib>
struct DeviceBufferSim {
    float *p; size_t n;
    explicit DeviceBufferSim(size_t n_) : p((float*)std::malloc(n_ * sizeof(float))), n(n_) {
        std::printf("alloc %zu\n", n);
    }
    ~DeviceBufferSim() { std::free(p); std::printf("free %zu\n", n); }
    DeviceBufferSim(const DeviceBufferSim&) = delete;             // no copies
    DeviceBufferSim& operator=(const DeviceBufferSim&) = delete;
    float *data() { return p; }
    size_t size() const { return n; }
};
void user() {
    DeviceBufferSim b(1024);
    if (b.size() > 0) return;        // early return → dtor STILL runs ✓
}
int main() {
    { DeviceBufferSim a(256); }       // prints alloc 256 / free 256 in order ✓
    user();                            // alloc 1024 / free 1024 despite early return ✓
    // DeviceBufferSim c = a;          // uncomment → compile error: deleted ✓
    return 0;
}

Why no-copy: a copy would either double-free (two dtors, one buffer — 3.5's big three) or force an expensive hidden deep copy of GPU memory. Deleting copies makes ownership UNIQUE and misuse a compile error — errors moved left (3.1's whole theme). This class IS the shape of every real CUDA RAII wrapper (and of std::unique_ptr, which you'd use in production: std::unique_ptr<float[]> p(new float[n]); — two lines, same guarantees). Move semantics (transferring ownership) is the natural next chapter — flagged, deferred: the course needs unique ownership, not the full rule-of-five, and honesty about scope beats coverage theater.

Exercise 2 — Template the oracle: port 2.4/3.4's matmul to template<typename T> void matmul(const std::vector<T>& A, const std::vector<T>& B, std::vector<T>& C, size_t M, size_t N, size_t K), verify float AND double against [[50,32],[122,77]], and then — the punchline — measure fp32 vs fp64 on 512³ and explain the ratio you see (or don't) with M1 L8 + hardware knowledge.
template <typename T>
void matmul(const std::vector<T>& A, const std::vector<T>& B,
            std::vector<T>& C, size_t M, size_t N, size_t K) {
    for (size_t i = 0; i < M; i++)
        for (size_t j = 0; j < N; j++) {
            T s = 0;
            for (size_t k = 0; k < K; k++) s += A[i*K + k] * B[k*N + j];
            C[i*N + j] = s;
        }
}
// float: {{50,32},{122,77}} ✓   double: same ✓ (integers ≤ 2²⁴ exact in BOTH — M1 L8)

The measurement surprise: on CPU, fp64 is typically only ~1.3–2× slower here, NOT 2× flat — this naive loop is memory-pattern-bound (the ijk column walk — 3.9's opening act), and doubles move 2× the bytes but the bottleneck mix muddies the ratio. On a gaming GPU the same comparison lands near 32× (fp64 units are 1/32 rate — 3.2 Ex.2's warning becomes a measured fact in Module 5). The template gave you the A/B experiment for one keystroke — that's the feature: dtype becomes an axis you can measure along, which is Track A6's entire methodology in miniature.

Go deeper — the complete guide

The C/C++ interop seam (extern "C" and why), strings without tears, why templates live in headers, the failure modes C++ adds (and their diagnostics), and an honest map of what this course deliberately skips.

1. The interop seam: name mangling and extern "C"

// C++ overloading needs distinct linker names:
void saxpy(float);   → _Z5saxpyf          // "mangled" (encodes types — nm shows these)
void saxpy(double);  → _Z5saxpyd
// C code compiled as C has plain names: saxpy. To share across the seam:
extern "C" {                              // "use C naming for these"
    #include "buffer.h"                    // your 3.6 C modules, callable from C++
}
extern "C" void kernel_launcher(float*, size_t);   // and how CUDA exposes C APIs

Mangling is WHY C++ can overload and C can't — and why linking C and C++ without extern "C" yields 3.1-style "undefined reference" to names that plainly exist (the mangled and plain names don't match; nm makes the mismatch visible — the 3.1 forensics skill, promoted). Every mixed-language codebase — which includes every Python-extension and most CUDA projects — has this seam; now it's a mechanism you can debug, not folklore.

2. std::string: char buffers, retired for host code

std::string name = "tiled";
name += "_v2";                        // no strcat budget math, no overflow class
std::string file = "run_" + std::to_string(i) + ".json";   // M2 L7's filenames
name.c_str()                          // const char* for C APIs (fopen, printf %s)
std::string line; std::getline(f, line);   // the gets() disaster, structurally gone
// snprintf still fine for FORMATTING; string for OWNERSHIP — they compose:
char buf[64]; std::snprintf(buf, sizeof buf, "%.2f ms", ms); std::string s = buf;

The entire 3.4 string-safety table collapses: budgets, terminators, and overflow are the object's problem. Same physics underneath (a growable char buffer — small-string optimization even keeps short ones inline, no heap at all), same invalidation rule on growth. Kernel-side note: no std::string in device code — GPU kernels handle numbers; text belongs to the host (a boundary Module 5 makes physical).

3. Range-for, auto, and the deduction rules that matter

for (float x : v)        // COPIES each element — fine for scalars
for (auto &x : v)        // reference — mutate in place
for (const auto &x : v)  // borrow read-only — the default for non-tiny T
auto n = v.size();       // size_t — auto GETS the right type (3.2's %zu ally)
auto x = v[i];           // float COPY (auto drops the reference!) — the subtle one:
auto &r = v[i];          // you must ASK for the reference back

auto-drops-references is the deduction rule that bites: auto row = m[i] in some matrix classes copies a whole row silently. House style: const auto& when iterating anything heavier than a scalar, plain auto for arithmetic locals, and explicit types on API boundaries (signatures are documentation — M2 L3's hints philosophy, compiled).

4. Why templates live in headers (the two-phase truth)

A template is a recipe, not code; saxpy<float> gets compiled only where instantiated — so the compiler needs the full recipe TEXT in every unit that instantiates it. Put the definition in a .cpp and other units see only the declaration: they emit a call to saxpy<float>… which no unit ever generated → 3.1's "undefined reference," now with a mangled template name (the era's most-Googled linker error). Hence: templates in headers (.h/.cuh), and hence header-only libraries (most CUDA utility ecosystems — CUB, Thrust — ship exactly this way). Cost: each unit recompiles the recipes it uses (build time — 3.6's blast-radius math applies); benefit: full-type-knowledge optimization at every site. The trade is the industry's chosen default for performance code.

6. Gotchas

By-value containers in signatures. Quiz 1's 40 GB. const& by reflex; by-value only with a comment declaring "intentional private copy."
References/pointers across growth. Quiz 2. reserve() up front, or index — the 3.5 rule didn't retire; it got a nicer uniform.
auto swallowing the &. auto row = matrix[i]; copies. When you mean alias, write auto& — and when you see auto in review, ask which was meant.
new[]/delete mismatch. new float[n] pairs with delete[], not delete (UB). Better: don't write either — vector/unique_ptr own this course's allocations.
Missing & in range-for mutation. for (auto x : v) x *= 2; scales copies, discards them, loops happily, changes nothing — the C++ twin of Python's "modify loop variable" gotcha (M2 L2). -Wunused sometimes saves you; auto& always does.
extern "C" forgotten at the seam. Undefined reference to a function you can SEE — check nm for mangled vs plain names before doubting your Makefile (§1's forensic).

The group porting meeting is 45 minutes: buffer.c/h (80 lines) → std::vector (0 lines — deleted outright); the harness's result arrays → vectors with reserve() sized from the dry run (3.5 P7's arena instinct, satisfied more simply); the timer → the RAII Timer, which immediately IMPROVES the science: timing now can't skip the "stop" on early exits, so three benchmarks quietly reporting only their happy paths get honest (M1 L7 would like a word with the old numbers). Practice

1. Predict compile-or-run behavior: (a) int &r = 5; (b) const int &r = 5; (c) std::vector<float> v(10); float *p = v.data(); v.reserve(100); *p = 1; (d) same as (c) but reserve BEFORE taking p.
(a) Compile error — non-const reference can't bind a temporary. (b) Legal! — const& extends the temporary's lifetime (the rule that makes f(const T&) callable with literals). (c) reserve(100) > capacity(10) → buffer moved → *p is use-after-free (runtime lottery; ASan converts to certainty). (d) Safe: capacity is already 100; taking p after any growth-capable calls is the discipline. (b) and (c) together are the reference/pointer lifecycle in four lines — a fair phone-screen question.
2. The Timer's flaw: our RAII Timer prints in the destructor — name two situations where that design misleads a benchmark, and redesign the interface (keep RAII) so the harness receives the number instead of stdout. (M1 L7 + M2 L3 purity are the graders.)
Misleads: (1) dtor-printing includes everything until scope end — accidentally timing the printf of a PREVIOUS timer or cleanup code unless scopes are surgical; (2) output-to-stdout can't be medianed/aggregated — the harness needs values, not text (M2 L3's "return, don't print", violated by v1). Redesign: struct Timer { double t0; double stop() const { return now_ms() - t0; } }; used as Timer t; work(); times.push_back(t.stop()); — RAII still guards nothing here... so keep a second RAII form for SCOPED logging and use the explicit stop() form inside harness loops: two tools, intents separated. Grading rubric satisfied: values flow to stats (median/IQR — M1 L7), effects (printing) stay at the edge (M2 L3). Instrument design is design.
3. Sight-read real CUDA-adjacent C++: template <typename T> __global__ void axpy(int n, T a, const T *x, T *y); and thrust::device_vector<float> d = h; — identify every concept from this lesson (and one from 3.3) in these two lines.
Line 1: template-typename (dtype axis), const T* / T* (3.3's read/write contract), by-value n and a (scalars cross to the device by copy — value semantics doing real work), __global__ (the only new token — 5.2's). Line 2: a vector CLASS whose ctor-from-host-vector performs the cudaMemcpy (RAII + value semantics composing: assignment = deep copy ACROSS THE BUS), dtor cudaFrees. You can now parse ~80% of CUDA library headers before Module 5 begins — which was this lesson's actual KPI.
4. Measure the abstraction tax honestly: time three sum-of-10M-floats loops — raw pointer C-style, vector with v[i], vector with .at(i) — at -O0 and -O2. Predict the -O2 ranking first. What does .at()'s cost buy, and when is paying it correct?
-O2 prediction (verify): raw ≈ v[i] (identical codegen — the "vanishing abstraction" claim, MEASURED not vibed), .at() slower (a branch per access; often 1.2–2× on this loop, sometimes less if the predictor eats it). -O0: everything slow, vector worse (uninlined calls) — why debug builds feel dishonest for perf (3.1 §1). .at() buys a thrown exception instead of UB on OOB — correct at API boundaries and in cold paths (parse/setup code), wrong in hot loops where the bound is already proven by the loop header (the M2 L6 boundary-vs-interior checks doctrine, compiled). Numbers in hand beat folklore: you now have a personal answer to "is vector slow?" — no, at -O2, with receipts.
5. unique_ptr in four lines: rewrite Exercise 1's DeviceBufferSim using std::unique_ptr<float[]> — which of your hand-written members (dtor, deleted copies) come free, what syntax transfers ownership OUT (returning it from a factory), and why does the compiler allow the return despite copies being deleted? (One-word answer exists; explaining it is the exercise.)
struct Buf { std::unique_ptr<float[]> p; size_t n; explicit Buf(size_t n_) : p(new float[n_]), n(n_) {} }; — dtor free (unique_ptr's), copies deleted free (unique_ptr is move-only). Factory: Buf make() { Buf b(1024); return b; } compiles because return performs a MOVE (ownership transfers; source's pointer nulled) — the one-word answer: move semantics. The exercise's honest boundary: this course uses moves where the compiler inserts them (returns) and defers writing move ctors by hand — unique ownership + automatic moves cover the entire curriculum's needs, and knowing WHERE your knowledge's edge sits is itself the professional skill (you'll recognize std::move in read code and know what question to ask).
6. The header-template linker error, staged: put Ex.2's matmul template DECLARATION in matmul.hpp and its definition in matmul.cpp; call matmul<float> from main.cpp; collect the exact linker error text, then fix it two ways (move to header; explicit instantiation) and state when each fix is right.
Error: undefined reference to `void matmul<float>(...)' — mangled template name, no unit generated the instance (§4's mechanism, experienced). Fix A (default): full definition in matmul.hpp — every user instantiates what it needs; right for libraries and this course. Fix B: keep the .cpp, add template void matmul<float>(...); (explicit instantiation) there — right when instantiations are few/known and build time or binary bloat matters (large projects pin their dtype set: float/double/half, done). CUDA parallel: .cuh header templates (A) vs libraries pre-instantiating kernels per-dtype (B — what cuBLAS effectively is). You've now debugged the most-asked C++ linker question from first principles.
