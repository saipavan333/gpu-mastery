Numbers, Bases & Binary — how machines count

Every index, address, mask, and pixel a GPU touches is a binary number. This lesson rebuilds counting from scratch so that binary, hex, and overflow become obvious instead of mysterious.

Concept

Counting in tens is a choice, not a law

When you write 473, you are using a compact code: 4 hundreds + 7 tens + 3 ones. Each position is worth ten times the one to its right — that's all "base 10" means. We use ten symbols (0–9) probably because we have ten fingers. Nothing about mathematics requires ten.

473 = 4×10² + 7×10¹ + 3×10⁰      (10⁰ = 1 — anything to the power 0 is 1)

A computer is built from billions of transistors, and a transistor is reliable at exactly two states: current flowing or not. So computers count with two symbols — 0 and 1 — and each position is worth two times the one to its right. Same idea, different base.

Reading binary: place value with powers of 2

10101101₂ = 1×128 + 0×64 + 1×32 + 0×16 + 1×8 + 1×4 + 0×2 + 1×1 = 173
             128    64     32     16     8     4     2     1   ← position weights

To go the other way (decimal → binary), repeatedly divide by 2 and keep the remainders, bottom-up:

173 ÷ 2 = 86 r 1   ↑ read remainders upward: 10101101
 86 ÷ 2 = 43 r 0
 43 ÷ 2 = 21 r 1
 21 ÷ 2 = 10 r 1
 10 ÷ 2 =  5 r 0
  5 ÷ 2 =  2 r 1
  2 ÷ 2 =  1 r 0
  1 ÷ 2 =  0 r 1

Memorize the small powers of two — they are the multiplication table of this field:

Hexadecimal: binary for humans

Binary is precise but unreadable — 32 bits is a wall of digits. Hexadecimal (base 16) uses symbols 0–9 then A–F (A=10 … F=15). Its superpower: 16 = 2⁴, so one hex digit is exactly one group of 4 bits (a nibble). Conversion is pure pattern-matching, no arithmetic:

10101101₂ → split: 1010 | 1101 → A | D → 0xAD
memory address you'll meet in CUDA:  0x7f8a3c001200   (48-bit pointer)

The 0x prefix just means "what follows is hex." GPU memory addresses, error codes, color values (#FF8800), and bit masks are all written in hex.

Negative numbers: two's complement

Hardware has no minus sign. The trick: for an n-bit signed integer, the top bit's weight is negative. For 8 bits, the weights are −128, 64, 32, 16, 8, 4, 2, 1. That single change gives a range of −128…+127, and — the beautiful part — the same adder circuit works for positive and negative numbers.

to negate: invert all bits, add 1
 5 = 00000101 → invert → 11111010 → +1 → 11111011 = −5
check: 11111011 = −128+64+32+16+8+2+1 = −5  ✓

Fixed width and overflow

Math has infinitely many integers; a register has a fixed number of bits. C, C++, and CUDA integers come in fixed widths, and when a result doesn't fit, it does not raise an error — it wraps or worse:

TypeBitsRangeOn overflow
int8_t8−128 … 127signed: undefined behavior in C/CUDA — compiler may assume it can't happen
int32_t (int)32−2 147 483 648 … 2 147 483 647
int64_t (long long)64±9.2 × 10¹⁸
uint8_t80 … 255unsigned: wraps modulo 2ⁿ (255 + 1 = 0), defined but silent
uint32_t320 … 4 294 967 295
Python integers grow without limit (2**1000 just works) because Python secretly manages multiple machine words for you. The moment you enter C/CUDA/NumPy territory, fixed width is back and overflow is your problem. np.int32(2**31 - 1) + 1 already misbehaves.

Worked example

Task: A grayscale image stores one byte per pixel (0 = black, 255 = white). A pixel reads 0xAD. What brightness is it, what happens if a filter adds 100 to it, and how should the code prevent that?

1 — decode: 0xAD → A=10, D=13 → 10×16 + 13 = 173 (a light gray, since 173/255 ≈ 68% white).

2 — the bug: 173 + 100 = 273, but the pixel is a uint8_t (max 255). It wraps: 273 mod 256 = 17 — a nearly-black pixel in the middle of a bright region. This is a real, visible artifact: bright spots turn into black speckles.

3 — the fix: compute in a wider type, then clamp:

int v = pixel + 100;              // int is 32-bit: 273 fits fine
pixel = (v > 255) ? 255 : v;      // clamp to the valid range ("saturate")

Decision made: widen-then-clamp costs one comparison per pixel and is the standard pattern in image kernels (CUDA even has saturating intrinsics). Letting it wrap costs nothing and corrupts the image. Cheap insurance wins.

Key points

  • A number system is just place value: position i is worth baseⁱ. Binary uses base 2 because transistors have two reliable states.
  • Decimal → binary: divide by 2 repeatedly, read remainders bottom-up. Binary → decimal: add the weights of the 1-bits.
  • One hex digit = exactly 4 bits. Addresses, masks, and colors are hex because it's binary compressed 4:1 for human eyes.
  • Two's complement makes the top bit worth −2ⁿ⁻¹; negate = invert + 1. One adder circuit then handles all integers.
  • Fixed-width integers overflow silently: unsigned wraps modulo 2ⁿ; signed overflow in C/CUDA is undefined behavior, not just a wrong number.
  • 2¹⁰ ≈ 10³ (1 KiB), 2²⁰ ≈ 10⁶ (1 MiB), 2³⁰ ≈ 10⁹ (1 GiB); int32 tops out near 2.1 × 10⁹ — small enough that real arrays exceed it.

Quiz

1. What is 0x2F in decimal?
Hex is base 16: 0x2F = 2×16¹ + F(=15)×16⁰ = 32 + 15 = 47. Reading hex digits as if they were decimal (29) is the classic first-week mistake.
2. An int32_t holds 2 147 483 647 (its maximum) and your CUDA kernel adds 1 to it. What does the C/CUDA standard say happens?
Signed overflow is UB. On most hardware you'll *observe* the wrap to −2 147 483 648, but the compiler is allowed to assume it can't occur — which can delete your bounds checks. Unsigned types wrap by definition; signed types do not promise anything.

Exercises

Exercise 1 — Convert 300 to binary and to hex, then explain what happens if you store it in a uint8_t.

Divide by 2: 300→150 r0, 150→75 r0, 75→37 r1, 37→18 r1, 18→9 r0, 9→4 r1, 4→2 r0, 2→1 r0, 1→0 r1. Reading up: 100101100₂ (9 bits). Group in nibbles from the right: 1 | 0010 | 1100 → 0x12C. Check: 1×256 + 2×16 + 12 = 300 ✓.

A uint8_t keeps only the low 8 bits: 00101100₂ = 44. Equivalently 300 mod 256 = 44. No warning, no error — you simply get 44. This is why image code widens to int before arithmetic.

Exercise 2 — Your kernel computes int idx = blockIdx.x * blockDim.x + threadIdx.x; for an array of 3 billion floats. Diagnose the bug and fix it.

Diagnosis: 3 × 10⁹ > 2 147 483 647, so idx overflows int for the upper half of the array. Worse, the multiply blockIdx.x * blockDim.x overflows before the add, and since these are signed ints, that's undefined behavior. Symptoms in the wild: garbage writes, misaligned-address crashes, or silent corruption that only appears on large inputs — i.e., only in production.

Fix: do the index math in 64-bit:

size_t idx = (size_t)blockIdx.x * blockDim.x + threadIdx.x;
if (idx < N) out[idx] = f(in[idx]);   // N is size_t too

The cast on the first operand promotes the whole expression to 64-bit before the multiply. Casting after the multiply ((size_t)(blockIdx.x * blockDim.x)) is still broken — the overflow already happened inside the parentheses. This exact bug ships in real codebases every year; interviewers love it.

Go deeper — the complete guide

The card above makes you functional. This chapter makes you fluent: general bases, the full conversion toolkit, exact two's-complement mechanics, what overflow really does in each language you'll touch, and the bitwise operations that turn this theory into working GPU code.

1. Place value, generalized

In base b with digits dk…d₁d₀, the value is Σ dᵢ·bⁱ. Three bases matter to you: 10 (humans), 2 (hardware), 16 (humans reading hardware). Base 64 appears in data encoding, and base 256 is a useful mental model: every byte of a file is one "digit" of a giant base-256 number.

base 10:  4 7 3        = 4×100 + 7×10 + 3
base  2:  1 0 1 1      = 1×8 + 0×4 + 1×2 + 1 = 11
base 16:  1 F 4        = 1×256 + 15×16 + 4 = 500

Digits beyond 9 borrow letters: A=10, B=11, C=12, D=13, E=14, F=15. Case doesn't matter (0xad = 0xAD), but a stray O instead of 0 does — hex has no letter O.

2. The conversion toolkit

Decimal → binary (÷2, remainders up) and binary → decimal (sum the weights) you've seen. Two more you need:

Binary ↔ hex: group 4 bits from the right; pad the leftmost group with zeros. Never do this via decimal — it's a straight table lookup both ways.

0x3C7 → 3=0011, C=1100, 7=0111 → 001111000111₂
110010111₂ → pad → 0001 1001 0111 → 0x197

Decimal → hex directly: divide by 16, remainders up. 500 → 500÷16 = 31 r 4; 31÷16 = 1 r 15(F); 1÷16 = 0 r 1 → 0x1F4.

Quick sanity checks that catch most conversion mistakes: an even number always ends in bit 0; a number < 2ⁿ needs at most n bits; k hex digits hold exactly 4k bits.

3. Two's complement, exactly

Formally: an n-bit pattern bn−1…b₀ interpreted as signed equals −bn−1·2ⁿ⁻¹ + Σi<n−1 bᵢ·2ⁱ. Consequences worth internalizing:

FactWhy it matters
Range is asymmetric: −2ⁿ⁻¹ … 2ⁿ⁻¹−1-INT_MIN overflows! Negating −128 in int8 has no answer; abs() of the most negative int is UB.
There is exactly one zeroOlder "sign-magnitude" had +0 and −0; two's complement won partly because it doesn't. (Floats, you'll see in Lesson 8, do have −0.)
Addition is sign-blindThe same circuit adds signed and unsigned; only comparisons and overflow rules differ. This is why mixing signed/unsigned in one expression is dangerous.
Sign extensionWidening int8 −5 (11111011) to int32 copies the top bit leftward: 0xFFFFFFFB. Widening unsigned pads zeros. Mix them up and −5 becomes 251 or 4 294 967 291.

The signed/unsigned comparison trap, which every C programmer hits once, hard:

int n = -1;
unsigned len = 10;
if (n < len) { ... }   // FALSE! n converts to unsigned → 4294967295 < 10 fails

The compiler converts the signed operand to unsigned. −1 becomes the largest possible value. Enable -Wall and take the warning seriously; in CUDA code, prefer size_t or int64_t consistently for sizes and indices.

4. Overflow across your future stack

EnvironmentInteger overflow behavior
Python intNever overflows — arbitrary precision, silently slower for huge values.
NumPy / PyTorch tensorsFixed width, wraps silently: np.array([127], dtype=np.int8) + 1 → -128 (NumPy 2.x raises on some out-of-range conversions, not on arithmetic wrap).
C / C++ / CUDA signedUndefined behavior. Compilers exploit it: for (int i = 0; i <= N; i++) with N = INT_MAX is an infinite loop the optimizer may "prove" terminates.
C / C++ / CUDA unsignedDefined wrap mod 2ⁿ. Useful on purpose (hashes, ring buffers, RNGs) — silent when accidental.

Rule for GPU work: thread indices in 32-bit are fine per-block, but any global index or byte offset that can exceed ~2×10⁹ gets 64-bit math, promoted before the first multiply. Datasets of 3–100 billion elements are routine in 2026; this is not a theoretical concern.

5. Bitwise operations — the tools this unlocks

&   AND    keep bits present in both      x & 0x0F   → low nibble
|   OR     set bits                       flags | ENABLE_BIT
^   XOR    flip where different           x ^ x == 0 (self-inverse)
~   NOT    invert all bits                ~0 == all ones
<<  shift left   multiply by 2ᵏ           1 << 20 == 2²⁰ (1 MiB)
>>  shift right  divide by 2ᵏ (floor)     x >> 3  == x / 8

Patterns you will use constantly in CUDA (warp masks, alignment, packing):

x & 1                 // odd? (last bit)
x & (n - 1)           // x mod n, ONLY when n is a power of two
(x + 63) & ~63        // round x up to a multiple of 64 (alignment!)
(mask >> lane) & 1    // is warp lane's bit set in a 32-bit ballot mask?
0x3FF & (v >> 10)     // extract bits 10..19 (unpacking data)

Why x & (n−1) works: if n = 2ᵏ, then n−1 is k ones (8−1 = 0111), and AND-ing keeps exactly the low k bits — which is the remainder mod 2ᵏ. Division and modulo are among the slowest integer ops on a GPU; shifts and masks are among the fastest. Compilers do this for constants, but you'll write it by hand for runtime power-of-two sizes.

6. Sizes, addresses, and what a pointer really is

Memory is one giant array of bytes; an address is just the index of a byte, and a pointer is a variable holding such an index — typically shown in hex like 0x7f8a3c001200. Three facts to pre-load for Modules 3–5:

1) A float is 4 bytes, so element i of a float array lives at base + 4·i — pointer arithmetic is place-value math. 2) Hardware likes aligned addresses (multiples of 4, 16, 128); the alignment test is a mask: addr & 15 == 0 means 16-byte aligned. 3) GPU global memory is served in 32-byte sectors — a warp of 32 threads each reading a 4-byte float consumes exactly four 32-byte sectors if aligned and consecutive (128 B total). That single sentence is ~40% of CUDA performance tuning; we'll spend Lesson 5.7 on it.

7. Gotchas

Reading hex as decimal. 0x30 is 48, not 30. Error codes and addresses lie to you until the 0x prefix triggers the mental switch.
Casting after the overflow. (int64_t)(a * b) with int a, b overflows in 32-bit first. The cast must hit an operand: (int64_t)a * b.
Signed/unsigned comparison. if (i < vec.size()) with int i negative is false — .size() is unsigned. −1 becomes 4 294 967 295.
Assuming KB = 1024. Storage and marketing use 10³ (KB/GB); memory uses 2¹⁰ (KiB/GiB). A "12 GB" GPU shows ~11.18 GiB. Bandwidth specs use GB = 10⁹ — mixing them makes your roofline math ~7% wrong.
x & (n−1) with non-power-of-two n. The trick silently computes garbage for n = 100. Guard it or assert (n & (n−1)) == 0 (that expression is the power-of-two test).
Trusting Python habits in C. Python's % returns non-negative for positive divisors; C's % can return negative (−7 % 4 == −3 in C, but 1 in Python). Index math ported naively breaks.

Scenario — the 3-billion-element bug hunt

Your team's embedding pipeline processes a 3.2-billion-row tensor on an H100. The kernel works flawlessly in every test (test data: 100 M rows) but in production, monitoring shows a few thousand corrupted embeddings per run, always in the back half of the tensor. A junior engineer blames "GPU memory errors" and requests ECC audits. You look at the kernel instead: int idx = blockIdx.x * blockDim.x + threadIdx.x. With blockDim 256, any blockIdx above 8 388 607 pushes the multiply past 2³¹ — signed overflow, UB, and in practice a negative index that wraps writes into someone else's rows. The fix is one cast: (size_t)blockIdx.x * blockDim.x + threadIdx.x, plus a repo-wide grep for the pattern (it appears 14 more times) and a lint rule banning 32-bit global index math. Cost of the bug: three weeks of corrupted production data. Cost of the fix: 8 characters. The math in this lesson is cheap; not knowing it is not.

Practice

1. Convert 1000 to binary and hex by hand; verify by summing weights.
1000 = 512+256+128+64+32+8 → 1111101000₂. Nibbles: 11 1110 1000 → 0x3E8. Check: 3×256 + 14×16 + 8 = 768+224+8 = 1000 ✓.
2. What are the largest and smallest values of int16_t, and what is 32767 + 1 in it?
Range −32 768 … 32 767 (−2¹⁵ … 2¹⁵−1). 32767+1 is signed overflow: UB in C/CUDA; the bit pattern you'd typically observe is 0x8000 = −32 768. In NumPy int16 it wraps to −32768 by definition.
3. Why does 0x7f8a3c001200 & 0xFF extract the low byte? What is it here?
0xFF is eight 1-bits; AND keeps only those positions. Low byte = 0x00 = 0. (The next byte, (addr >> 8) & 0xFF, is 0x12.)
4. Your buffer needs to start at a 128-byte boundary. Write the expression that rounds an address up, and explain each part.
(addr + 127) & ~(size_t)127. Adding 127 pushes any non-aligned address past the next boundary without moving aligned ones past theirs; ~127 is a mask with the low 7 bits clear; AND-ing floors to a multiple of 128. Works because 128 = 2⁷.
5. A colleague writes if (threadIdx.x - 1 < n) intending "all but thread 0". threadIdx.x is unsigned. What actually happens for thread 0?
0 − 1 in unsigned 32-bit wraps to 4 294 967 295, which is not < n, so thread 0 is excluded — it "works," but by accident and unreadably; for thread 0 the test is false for the wrong reason. If n were compared differently or the expression reused, the wrap becomes a live bug. Write if (threadIdx.x >= 1 && threadIdx.x - 1 < n) or restructure.
6. How many bits do you need to index every byte of a 24 GB GPU? Every float?
24 GB ≈ 24×2³⁰ = 1.5×2³⁴ bytes? Precisely: 24×2³⁰ = 3×2³³ ≈ 2³⁴·⁵⁸ → needs 35 bits for bytes. Floats: /4 → 33 bits. Both exceed 32 bits — int32 indexing cannot even address one modern GPU's memory. size_t or int64_t, always, for byte offsets.
7. Design: you're packing three values into one uint32 — a 12-bit row, a 12-bit col, an 8-bit flag. Write the pack and unpack expressions and state the maximum row/col this supports.
packed = (row << 20) | (col << 8) | flag — row in bits 20–31, col in bits 8–19, flag in 0–7. Unpack: row = packed >> 20; col = (packed >> 8) & 0xFFF; flag = packed & 0xFF;. Max row/col = 2¹² − 1 = 4095; storing 4096 silently corrupts its neighbor field — assert before packing. This exact pattern (bit-packed keys) shows up in GPU sorting and hashing pipelines.
