Algebra as Computation — variables, functions & the Σ you'll write daily

School algebra and programming are the same activity wearing different clothes. This lesson translates between them — and lands on the two formulas (index linearization and ceiling division) that appear in literally every GPU kernel.

Concept

Variables: named boxes, with one big twist

In algebra, x = 5 is a timeless fact. In code, x = 5 is an action: put 5 in the box named x. That's why x = x + 1 is nonsense as an equation but perfectly sensible as an instruction (take what's in the box, add 1, put it back). Every "impossible equation" confusion beginners have dissolves once you read = as "gets," not "equals." (C uses == for actual equality tests.)

Expressions and precedence

PEMDAS from school survives almost intact: parentheses, then * / %, then + −, left to right within a level. Two things school didn't tell you:

7 / 2        → 3   in C/CUDA when both sides are integers (truncation toward 0!)
7 % 2        → 1   the remainder — the other half of integer division
a + b * c    → a + (b*c)   — as in school; when in doubt, add parentheses
Integer division truncates: (a/b)*b + a%b == a always holds, but (a/b)*b ≠ a whenever b doesn't divide a. GPU code exploits truncation deliberately — and is bitten by it accidentally. Watch every / and ask: are both sides integers?

Functions: machines with one job

f(x) = 3x + 2 is a machine: number in, number out. Code is the same machine with a body:

float f(float x) { return 3.0f * x + 2.0f; }

Composition f(g(x)) means "g first, then f" — in code, nested calls or a pipeline. GPU pipelines are compositions at industrial scale: normalize(attention(embed(tokens))). Two properties you'll care about later: a function is pure if the same input always gives the same output (no hidden state) — pure functions are trivially parallelizable, which is why GPU programming loves them.

Solving = inverting: you still need it

School had you isolate x. Professionals invert formulas constantly — just for practical reasons: given a linear index, which (row, col) is it? Given a target occupancy, how many registers per thread can I afford? The moves are the same three you learned: do the same thing to both sides, unwrap operations in reverse order, keep track of integer-vs-real.

i = row·W + col   (0 ≤ col < W)     solve for row, col:
row = i / W   (integer division — throws away col)
col = i % W   (the remainder IS col)                     inverse pair: / and %

Σ and Π: the loop you can already read

Sigma notation intimidates beginners and shouldn't — it's a for-loop invented before computers:

dot product:  a·b = Σᵢ aᵢbᵢ          →  for i: s += a[i]*b[i];
mean:         μ = (1/n) Σᵢ xᵢ        →  sum then divide
softmax denominator: Σⱼ e^{zⱼ}       →  the loop inside every LLM's output layer

Nested Σ = nested loops, and the order of Σs (like the order of loops) doesn't change the sum — but, as you'll learn in Lesson 8, in floating point it changes the rounding, which is why GPU results can differ from CPU results while both are "correct."

Inequalities: the language of bounds checking

Every kernel guards itself with an inequality: if (i < N). Programmers use half-open intervals [0, N) — include 0, exclude N — because lengths add cleanly ([0,N) has exactly N integers) and adjacent ranges [0,k) and [k,N) never overlap. School's closed intervals [1, N] cause the off-by-one errors; half-open is the professional dialect.

Worked example

Task: An RGB image is H=1080 rows, W=1920 cols, 3 channels, stored as one flat array, channel-last (r,g,b,r,g,b,…). Derive the formula for the address of channel c of pixel (row, col), then invert it.

Derive by counting strides: moving down one row skips W·3 = 5760 values; moving right one pixel skips 3; the channel adds 0, 1, or 2:

i = (row·W + col)·3 + c        e.g. pixel (2, 10), green (c=1):
i = (2·1920 + 10)·3 + 1 = 3850·3 + 1 = 11551

Invert by unwrapping in reverse (last operation applied is first undone):

c    = i % 3;          p = i / 3;      // undo the ·3 + c
col  = p % W;          row = p / W;    // undo the ·W + col
check: 11551 % 3 = 1 ✓, 11551/3 = 3850, 3850 % 1920 = 10 ✓, 3850/1920 = 2 ✓

Decision made: we chose the formula from the memory layout, not from habit. If the image were channel-first (all reds, then greens…), the formula becomes i = c·H·W + row·W + col. Same algebra, different strides — layout drives the formula, always. (PyTorch calls these NHWC vs NCHW; entire performance guides exist about choosing one.)

Key points

  • Code's = means "gets," not "equals" — x = x + 1 is an update, and == is the equality test.
  • Integer division truncates toward zero in C/CUDA; / and % form an inverse pair: i = q·W + r ⇔ q = i/W, r = i%W.
  • Linearization i = row·W + col and its inverse are the most-typed formulas in GPU programming — derive them from strides, don't memorize.
  • Σ is a for-loop: lower bound → init, upper bound → condition, term → body. Nested Σ = nested loops.
  • Ceiling division (N + B − 1)/B computes "how many blocks of B cover N" using only integer ops.
  • Half-open intervals [0, N) are the professional convention: lengths add, ranges don't overlap, and if (i < N) is the guard.

Quiz

1. In C/CUDA, with int i = 11551, W = 1920; what is i % 3 and what does it recover in the RGB layout i = (row·W+col)·3 + c?
% undoes the last operation applied (·3 + c): 11551 = 3850·3 + 1, so i % 3 = 1 = c. Inversion always unwraps in reverse order of construction.
2. You need enough blocks of 256 threads to cover N = 1000 elements. Which expression is correct and why?
1000/256 = 3 (truncated) misses 232 elements; +1 gives a spurious extra block when N is an exact multiple; ceil(N/256) on ints truncates BEFORE ceil sees it — the classic trap. (N+B−1)/B is exact in all cases.

Exercises

Exercise 1 — A matrix is stored row-major with H=512 rows, W=768 cols. A profiler shows thread t reads element i = t·768. What is that in (row, col) terms, and why is it a performance disaster? (Preview reasoning — answer with algebra.)

i = t·768 = t·W + 0 → row = t, col = 0: each consecutive thread reads the first element of consecutive rows. Consecutive threads therefore touch addresses 768·4 = 3072 bytes apart — 32 threads spread across 32 different memory segments instead of one contiguous 128-byte block. The algebra (stride W between consecutive t) predicts the disaster before you ever profile: you want consecutive threads to differ by +1 in the linear index (stride 1), i.e., i = row·W + t. "Stride between consecutive threads" is a number you should be able to read off any index formula on sight — that skill is half of Lesson 5.7 (coalescing).

Exercise 2 — Invert this formula: a kernel packs a tile coordinate as k = ty·17 + tx where 0 ≤ tx < 17. A bug report shows k = 200. Which (ty, tx)? Then explain why the designer chose 17 when tiles are 16 wide (real CUDA trick).

ty = 200 / 17 = 11, tx = 200 % 17 = 200 − 187 = 13 → (11, 13).

The 17 with 16-wide tiles is shared-memory padding: an extra phantom column changes the stride so that threads walking a column don't all hit the same shared-memory bank (16 divides the bank count 32; 17 is coprime to it). You'll meet this properly in Lesson 5.5 — the point today: the algebraic stride you choose has hardware consequences, and "wasting" one column of storage can buy a 2–8× speedup on column accesses.

Go deeper — the complete guide

This chapter finishes the translation dictionary: precedence in full, functions as first-class ideas, formula inversion as an algorithm, summation identities you'll actually use, and the grid-sizing algebra every CUDA launch needs.

1. The full precedence story (the part that bites)

highest   ()  []  .  ->            calls, indexing, member access
          !  ~  ++  --  unary-     negation family
          *  /  %
          +  -
          <<  >>                   shifts — LOWER than + !
          <  <=  >  >=  ==  !=
          &   then  ^   then  |    bitwise — LOWER than comparisons !
          &&  then  ||
lowest    = += -= *= ...           assignment

The two famous traps are flagged above: x << 2 + 1 is x << 3, not (x<<2)+1; and if (flags & MASK == 0) parses as flags & (MASK==0) — almost never what you meant. House rule used by every serious codebase: parenthesize all bitwise and shift expressions, no exceptions.

2. Functions, composed and curried by hand

Beyond f(g(x)): in performance work you constantly fuse compositions. Mathematically, h = f∘g is one machine; computationally, computing g's output to memory and reading it back for f costs a full round-trip through DRAM. Fusing means substituting algebraically before coding:

g(x) = x − μ         f(y) = y / σ         h(x) = f(g(x)) = (x − μ) / σ
unfused: 2 kernel launches, 2 reads + 2 writes of the whole tensor
fused:   1 launch, 1 read + 1 write   ← "kernel fusion", Track A's bread & butter

The algebra is trivial; the discipline of seeing compositions as fusable is what you're training. Substitution — school algebra's most boring move — is a 2× speedup generator in ML infra.

3. Inverting formulas: a reliable algorithm

To solve i = ((row·W) + col)·C + c for the inner variables: write the construction as a sequence of operations, then undo them last-to-first, using % to extract what each stage added and / to discard it:

Build (forward)Invert (reverse)Requires
t₁ = row·W + colcol = t₁ % W, row = t₁ / W0 ≤ col < W
i = t₁·C + cc = i % C, t₁ = i / C0 ≤ c < C

The "requires" column is the whole trick: % only recovers a field if that field is strictly smaller than its modulus. This is place value again — mixed-radix place value — and it's why we could decode 11551 unambiguously in the worked example. Any N-dimensional tensor index in any framework is this table with more rows; PyTorch's strides() is exactly the list of multipliers.

4. Summation identities worth owning

Σ (aᵢ + bᵢ)   = Σ aᵢ + Σ bᵢ            split — lets you fuse/unfuse loops
Σ (c · aᵢ)    = c · Σ aᵢ               constants hoist out of loops
Σᵢ Σⱼ aᵢⱼ     = Σⱼ Σᵢ aᵢⱼ              loop interchange (exact in ℝ, reordered rounding in float)
Σᵢ₌₀ⁿ⁻¹ 1     = n                       counting
Σᵢ₌₀ⁿ⁻¹ i     = n(n−1)/2                Gauss — cost of triangular loops
Σᵢ₌₀ⁿ⁻¹ rⁱ    = (1−rⁿ)/(1−r)            geometric — series, amortized costs

Gauss's formula prices every "compare all pairs" loop: n=10⁵ pairs → ~5×10⁹ operations. The geometric sum with r=½ says the total work of repeatedly halving (1 + ½ + ¼ + …) never exceeds 2× the first term — the reason multi-pass reductions cost barely more than one pass. You'll invoke both when estimating kernel cost in your head, which Lesson 3 turns into a habit.

5. Launch-geometry algebra (the CUDA sizing kit)

Everything a kernel launch computes, derived once, used forever:

global id:      i = blockIdx.x * blockDim.x + threadIdx.x
blocks needed:  G = (N + B − 1) / B                 // ceil(N/B) in ints
guard:          if (i < N) { ... }                  // last block is ragged
grid-stride:    for (i = i0; i < N; i += gridDim.x * blockDim.x)

Why (N+B−1)/B works: write N = qB + r with 0 ≤ r < B (division with remainder — school again). If r = 0, (N+B−1)/B = q + (B−1)/B → truncates to q. If r > 0, N+B−1 = (q+1)B + (r−1) → truncates to q+1. Exactly ceil, no branches, no floats. The grid-stride loop decouples grid size from N: each thread handles elements i, i+stride, i+2·stride… — an arithmetic sequence (school again) — letting one launch size serve any N and improving hardware reuse; it's the recommended default pattern in NVIDIA's own guidance.

6. Gotchas

ceil(N/B) with integers. N/B truncates before ceil runs — you get floor, sometimes one block short, corrupting the array tail only when N isn't a multiple of B (i.e., rarely in tests, often in prod).
Off-by-one from closed intervals. for (i = 0; i <= N-1; ...) "works" but invites edits that break it; i <= N overruns by one. Half-open i < N is the convention every reviewer expects.
Negative operands of / and %. C truncates toward zero: −7/4 = −1, −7%4 = −3. Python floors: −7//4 = −2, −7%4 = 1. Porting index math between them silently changes results for negative values.
Precedence of shifts and bitwise ops. 1 << n - 1 is 1 << (n-1). a & b == c is a & (b==c). Parenthesize.
Reusing a variable inside its own update, out of order. col = i % W; row = i / W; is safe, but the "optimized" i /= W before extracting col has already destroyed the remainder. Extract with % before you divide.
Formula drift between layout and index math. Someone flips storage to channel-first but only half the formulas get updated. Defense: one idx() helper function, used everywhere — never inline hand-copied index arithmetic twice.

Scenario — the resize that corrupted the dataset

A vision team preprocesses 40 M images on GPU. After a "small refactor," 0.4% of images come out with a diagonal smear. The refactor changed tile width from 32 to 24 "to save shared memory," and one line still said row = i >> 5 (divide by 32, as a shift) while the new code wrote i = row*24 + col. Two formulas, two moduli, one array. Because 24 divides into 32-based decoding cleanly every 3 rows, only images whose width hit the misalignment window corrupted — rare enough to pass spot checks, common enough to poison training. The fix: replace the shift with i / TILE_W using the named constant, and delete the duplicated index math in favor of one inline helper. Lessons: shifts are divisions only for powers of two; and index formulas are load-bearing — one source of truth, named constants, asserts on ranges. The bug cost a week of retraining; the algebra to prevent it is in this lesson.

Practice

1. Evaluate in C: 17 / 5, 17 % 5, -17 / 5, -17 % 5, and the Python -17 // 5, -17 % 5.
C: 3, 2, −3, −2 (truncate toward 0; remainder takes dividend's sign). Python: −4, 3 (floor; remainder takes divisor's sign). Identity a == (a/b)*b + a%b holds in both — with their own division.
2. Write the linear index for a 4-D tensor [N, C, H, W] (NCHW), element (n, c, h, w), then give the stride between elements adjacent in w, in h, and in c.
i = ((n·C + c)·H + h)·W + w. Strides: w-neighbors differ by 1; h-neighbors by W; c-neighbors by H·W. (This stride list [C·H·W, H·W, W, 1] is literally what tensor.stride() prints in PyTorch.)
3. How many blocks of 128 threads for N = 1 000 000? How many threads are idle in the last block?
G = (10⁶ + 127)/128 = 7813 (7812·128 = 999 936; remainder 64 → one more). Last block: 10⁶ − 7812·128 = 64 active, 64 idle. The guard if (i < N) is what keeps those 64 harmless.
4. Fuse algebraically: g(x) = 2x, f(y) = y + 3, k(z) = z². Give k(f(g(x))) as one expression and count memory round-trips saved vs three separate passes over a 1-GB tensor.
k(f(g(x))) = (2x + 3)². Three passes: 3 reads + 3 writes = 6 GB of traffic; fused: 1 read + 1 write = 2 GB → 3× less memory traffic, which on a bandwidth-bound GPU is ≈ 3× faster. Substitution is a performance tool.
5. Solve for B: you want G ≤ 65535 blocks (a real grid-dimension limit on one axis) with N = 50 000 000. What block sizes B satisfy it?
Need (N+B−1)/B ≤ 65535 → roughly B ≥ N/65535 = 762.9 → B ≥ 763. Practical choices: 768 or 1024 (multiples of 32 — warp size — for reasons you'll learn in 5.6). Or use a grid-stride loop and stop worrying about N entirely.
6. A colleague claims Σᵢ(xᵢ − μ) = 0 always, so centering data is pointless to verify. Prove the identity and say why a float implementation may still print non-zero.
Σ(xᵢ−μ) = Σxᵢ − nμ = Σxᵢ − n·(Σxᵢ/n) = 0. In floats, μ is rounded, and the subtractions/additions round too, so the sum lands near 0 (like 1e−6), not at it. Exact-in-ℝ, approximate-in-float is a distinction you'll formalize in Lesson 8 — and it's why tests use tolerances, not ==.
7. Design: a kernel processes a lower-triangular matrix (only elements with col ≤ row) of an n×n matrix, packed densely. Derive the packed index for (row, col), the total element count, and the inverse (packed → row) using school algebra. (Hard — use Gauss.)
Row r contributes r+1 elements; rows 0..r−1 contribute Σ(i+1) = r(r+1)/2 elements (Gauss). So k = r(r+1)/2 + c, total n(n+1)/2. Inverse: find largest r with r(r+1)/2 ≤ k → solve r² + r − 2k = 0 → r = floor((−1 + √(1+8k))/2), then c = k − r(r+1)/2. The quadratic formula — school's crown jewel — indexing a packed triangular matrix; this exact pair appears in GPU implementations of pairwise-distance and attention-mask kernels.
