Floating Point — how GPUs really store numbers

Module 1's capstone, and the single most bug-generating topic in numerical computing. fp16 overflow NaN'd real training runs; reduction order makes GPU results "randomly" differ from CPU; 0.1 + 0.2 ≠ 0.3. After this lesson, none of that will ever surprise you again.

Concept

The problem: infinite reals, 32 bits

Between 0 and 1 there are infinitely many real numbers; 32 bits give you 2³² ≈ 4.3 billion patterns total (Lesson 1). Something must give. Fixed-point (put the decimal point at a fixed position) wastes range or precision. The winning design — floating point — is scientific notation (Lesson 3) in binary: store a sign, an exponent (where the point floats to), and the leading digits (the fraction/mantissa).

value = (−1)^sign × 1.fraction₂ × 2^(exponent − bias)         bias: 127 for fp32
5.75 = 101.11₂ = 1.0111₂ × 2²  →  sign 0 | exp 2+127=129=10000001 | frac 0111000…0

The hidden "1." is free precision: every normalized binary number starts with 1, so it isn't stored — 23 stored bits buy 24 significant bits. Roughly 7 decimal digits of precision, with a range of ~±3.4×10³⁸.

Relative precision: dense near zero, sparse far out

Every interval [2ᵏ, 2ᵏ⁺¹) contains exactly 2²³ floats — the same count stretched over doubling width. Consequences: the gap between neighbors ("1 ulp") near 1.0 is machine epsilon ≈ 1.19×10⁻⁷; near 2²⁴ = 16 777 216 the gap is 2 — fp32 cannot represent 16 777 217. Above 2²⁴, adding 1.0 to a float does nothing. Precision is relative (~7 digits wherever you are), never absolute — the root fact behind half the gotchas below.

Why 0.1 + 0.2 ≠ 0.3

0.1 = 1/10, and 10 = 2·5. Binary fractions can only represent p/2ᵏ exactly; the factor of 5 makes 0.1 an infinite repeating binary fraction (0.000110011̄₂…), which gets rounded to the nearest float. So 0.1, 0.2, 0.3 are each tiny lies, and (rounded 0.1) + (rounded 0.2) rounds to a float that differs from (rounded 0.3) by one ulp: 0.30000000000000004 in fp64. Nothing is broken — decimal fractions just aren't binary fractions. (Same reason 1/3 isn't a finite decimal.)

Read the table through one lens: exponent bits buy range, mantissa bits buy precision, fewer total bits buy speed (2× the FLOP/s and half the memory traffic per halving, roughly). bf16 vs fp16 is the exam question: bf16 keeps fp32's 8 exponent bits (same range — gradients don't overflow) and pays with 7 mantissa bits (~2 digits). fp16 spends more on mantissa but caps at 65 504 — hence the NaN'd training runs, and the fix in the worked example.

Worked example

Task: Your fp16 training run's loss goes 2.31 → 2.29 → inf → NaN within three steps. Explain the mechanism from the bit layout, apply the standard fix, and say why bf16 makes the problem mostly vanish.

Mechanism: backprop multiplies gradients layer by layer (chain rule — Track A1); a few large activations compound and some gradient hits |g| > 65 504 = fp16 max → rounds to inf. Next step: inf × weight-decay or inf − inf → NaN. NaN ≠ NaN and NaN propagates: one poisoned gradient element infects every weight in one update. (Meanwhile tiny gradients below fp16's subnormal floor ~6×10⁻⁸ flush to zero — silent underflow at the other end.)

Fix — loss scaling (what torch.cuda.amp does): multiply the loss by S (say 2¹⁶) before backprop; by linearity every gradient scales by S, lifting small gradients out of the flush-to-zero zone; divide by S before the optimizer step. If any inf/NaN appears in gradients: skip the step, halve S; if stable for 2000 steps: double S ("dynamic loss scaling"). Exponent arithmetic, nothing more.

scaler = torch.amp.GradScaler()                  # the three-line version
with torch.autocast(device_type="cuda", dtype=torch.float16):
    loss = model(x).loss
scaler.scale(loss).backward(); scaler.step(opt); scaler.update()

Why bf16 mostly ends this: 8 exponent bits → max ~3.4×10³⁸ — gradients essentially can't overflow; underflow floor drops to ~10⁻³⁸ too. Cost: 7 mantissa bits (~2 digits), which training tolerates because gradient noise (Lesson 7!) already exceeds rounding noise. That's why bf16-by-default won 2020s ML — a decision you can now defend from the bit fields alone. Master weights still ride in fp32: tiny updates (lr × grad ≈ 10⁻⁷ relative) would be absorbed entirely at bf16's 2-digit precision (see cancellation, below).

Key points

  • float = sign × 1.fraction × 2^(exp−bias): scientific notation in binary; the hidden leading 1 gives 24 significant bits from 23 stored.
  • Precision is relative: ~7 digits for fp32 anywhere on the line; gaps double each power of two — above 2²⁴, x + 1.0f == x.
  • Decimal fractions like 0.1 repeat forever in binary; every literal is already rounded — compare with tolerances, never ==.
  • NaN ≠ NaN, all comparisons false, and it propagates; inf arises from overflow and 1/0; GPUs often flush subnormals to zero.
  • Formats trade exponent (range) vs mantissa (precision) vs width (speed): fp16 overflows at 65 504; bf16 keeps fp32 range with ~2 digits; fp8 pushes further on tensor cores.
  • Float addition is NOT associative: parallel reductions reorder sums, so GPU ≠ CPU results bitwise — correctness means "within tolerance," and tree sums are actually MORE accurate.

Quiz

1. In fp32, what does 16777216.0f + 1.0f evaluate to, and why?
2²⁴ is where fp32's integer-exactness ends: 24 significant bits are spent, the ulp becomes 2, and 16777217 does not exist in fp32. The add rounds to the nearest representable — the original value. This is absorption, and it silently breaks long float accumulators (frame counters, running sums) in real systems.
2. A parallel GPU sum of the same fp32 array gives 1024.0007 while the sequential CPU sum gives 1024.0011. Who's wrong?
(a+b)+c ≠ a+(b+c) in floats. The GPU's pairwise/tree order keeps partial sums similar in magnitude → less absorption → error O(log n) vs the sequential running sum's O(n). Different ≠ wrong; tests must use tolerances, and "GPU matches CPU bitwise" is the wrong acceptance criterion.

Exercises

Exercise 1 — Encode −0.375 in fp32 by hand: sign, exponent field (binary), first mantissa bits. Verify by decoding.

0.375 = 3/8 = 0.011₂ = 1.1₂ × 2⁻². Sign = 1 (negative). Exponent field = −2 + 127 = 125 = 01111101₂. Mantissa = fraction after the hidden 1: 1000…0 (23 bits). Decode: (−1)¹ × 1.1₂ × 2⁻² = −(1.5)/4 = −0.375 ✓. Note 0.375 is exact (denominator 8 = 2³) while 0.1 never is — representability is about the denominator's prime factors, exactly like 1/3 in decimal.

Exercise 2 — Diagnose: a physics engine accumulates game time as float t; t += 0.016667f; each frame. Players report animations stuttering after ~4–6 hours. Compute where and why, and give two fixes.

After 5 h, t ≈ 18 000. fp32 ulp near 2¹⁴ = 16384 is 2¹⁴⁻²³ = 2⁻⁹ ≈ 0.002. Each frame's +0.016667 still registers (it's 8× the ulp) but rounds to a multiple of 0.002 — ~12% relative quantization per step, and it worsens: near 2²⁰ (~12 days at this rate — servers!) the ulp is 0.125 and the add is mostly absorbed. Meanwhile sin(t)-style wave animations (Lesson 4, Ex. 2) stutter much earlier because they need t's *fractional* precision. Fixes: (1) accumulate time in fp64 (or integer microseconds — Lesson 1's fixed width, doing what it's good at), convert per frame; (2) keep per-effect phase accumulators that wrap mod 2π so the magnitude never grows. Both appear in real engine postmortems; "float time" is a famous class of bug (KSP, Minecraft's Far Lands are the spatial cousin).

Go deeper — the complete guide

Rounding rules, error analysis you can do on a napkin, cancellation and the summation algorithms that defeat it, FMA's secret extra precision, GPU-specific float behavior (FTZ, fast-math, determinism), and the comparison discipline that makes numerical tests trustworthy.

1. Rounding: the default and the alternatives

IEEE default is round-to-nearest-even: ties (exactly halfway) go to the even neighbor, so ties don't drift systematically upward. Guaranteed: every basic op (+, −, ×, ÷, √) returns the exactly-rounded true result — error ≤ ½ ulp per op. Alternatives you'll actually meet: round-toward-zero (integer casts truncate — (int)(-2.7f) is −2, not −3; use floorf), and stochastic rounding (round up with probability = fractional distance — makes rounding error zero-mean, Lesson 7's unbiased-estimator pattern; hardware-supported for fp8 training on recent accelerators). ½ ulp per op sounds tiny; the rest of this chapter is about how tiny errors become big ones.

2. Absorption and catastrophic cancellation

Absorption: big + small = big whenever small < ½ ulp(big) — the +1 at 2²⁴ from the quiz. Cancellation: subtracting nearly-equal numbers erases the leading digits that matched, promoting old rounding errors to the leading digits of the result: (1e8 + 1) − 1e8 = 0 instead of 1 (the 1 was absorbed; the subtraction then reveals the loss). Napkin rule: subtracting numbers that agree in their first k digits costs k digits of accuracy. Classic real instances and their algebraic escapes:

quadratic formula, b>0:  x = (−b + √(b²−4ac))/2a  cancels when 4ac ≪ b²
   fix: x₁ = −(b + √(b²−4ac))/2a  then  x₂ = c/(a·x₁)      (Vieta — no subtraction)
variance: E[X²] − μ²  cancels for large μ (and can go NEGATIVE, then sqrt → NaN)
   fix: Welford's one-pass algorithm, or shift data by an approximate mean first
1 − cos θ for small θ: cancels (cos ≈ 1 − θ²/2)
   fix: use 2·sin²(θ/2)  — trig identity as numerical rescue (Lesson 4 pays rent)

3. Summation: order is an algorithm

Summing n floats naively left-to-right grows error like O(n·ε) — the running total gets big, later terms get partially absorbed. The alternatives, in ascending sophistication:

MethodError growthCostNote
Sequential running sumO(n·ε)n addswhat a naive CPU loop does
Pairwise / tree sumO(log n·ε)n addswhat parallel reductions do anyway — free accuracy!
Kahan compensatedO(ε)4× addscarries the rounding error in a second variable and re-adds it
fp64 accumulator~O(ε) for n < 2²⁹≈ free on modern GPUs for accumulate-onlywhat cuBLAS/tensor cores do: multiply in fp16/bf16, ACCUMULATE in fp32
// Kahan, four lines you should recognize on sight:
float s = 0, c = 0;
for (i…) { float y = a[i] - c; float t = s + y; c = (t - s) - y; s = t; }

The GPU-shaped takeaway: the parallel tree order you're forced into for speed (Lesson 3's log₂ staircase) is also numerically superior to the sequential order — a rare free lunch. And "accumulate in a wider type" is why tensor cores advertise "fp16 multiply, fp32 accumulate": the products are half-precision, the running sum — where absorption lives — is not.

4. FMA: one rounding instead of two

fmaf(a, b, c) computes a·b + c with a single rounding — the product is kept exact (all 48 product bits!) until after the add. It's faster AND more accurate, and GPU compilers contract a*b + c into FMA by default. The flip side: contraction changes results vs un-contracted code, so CPU-vs-GPU diffs and "same code, different flags, different bits" often trace to FMA. Flags to know: nvcc -fmad=true (default) vs false; a cross-platform "exactly reproduce" requirement usually means taming FMA and math-library differences — promise statistical, not bitwise, equality unless you control every flag on every platform (Lesson 7's scenario caveat, now explained).

5. GPU-specific float behavior

Flush-to-zero: CUDA devices default to FTZ for fp32 in many ops (subnormals → 0); -ftz=false restores them at a speed cost. If your algorithm relies on gradual underflow, decide explicitly. Fast math: -use_fast_math swaps sinf/expf/divisions for fast approximate versions (2–4× on transcendentals, errors up to a few ulps or worse at range edges) — great for graphics and many ML inference paths, unacceptable for Track B science without validation; know it's two different functions, __sinf vs sinf, and that the flag flips them globally. Atomics and determinism: atomicAdd on floats commits sums in whatever order threads arrive → run-to-run nondeterminism on the SAME machine. PyTorch's torch.use_deterministic_algorithms(True) exists precisely to route around such kernels (at a perf cost). Interview-ready sentence: "GPU float nondeterminism is scheduling order meeting non-associativity — fix it with ordered/tree reductions or accept tolerance-based testing."

6. Comparing floats like a professional

// absolute epsilon: only near a known scale
fabsf(a-b) < 1e-6f                    // WRONG for a,b ~ 1e8 (ulp there is 8!)
                                      // WRONG for a,b ~ 1e-8 (everything "equal")
// relative + absolute floor (the workhorse — this is numpy.isclose / torch.allclose):
fabsf(a-b) <= atol + rtol * fabsf(b)  // defaults: rtol 1e-5, atol 1e-8
// ULP distance (bit-level: how many floats sit between a and b)

Choosing tolerances is engineering, not superstition: estimate the error budget (ops on the critical path × ulp × magnitudes — the napkin analysis of §2–3), then set rtol with ~10× headroom. When a kernel test flakes only in fp16, only on Tuesdays: recompute the budget — fp16's ε is 9.8×10⁻⁴, three orders looser than fp32's, and a tolerance copy-pasted from an fp32 test is a bug in the test.

7. Gotchas

== on computed floats. Legitimate uses exist (exact constants, flag values, detecting the same rounded result); comparing two differently-computed values with == is the bug. isclose with justified tolerances.
float accumulators for counters/time/money. Absorption at 2²⁴ (counts), quantization (time — Ex. 2), and 0.1's inexactness (money → use integer cents). Integers exist; use them for integer-shaped data.
fp16 range confidence. 65 504 arrives fast: a variance, a squared distance, an un-normalized logit. Square anything ~256 in fp16 and you're at the cliff edge. Compute norms/variances in fp32 even when data is fp16.
NaN's comparison behavior inverting branches. if (x > threshold) is false for NaN — so NaN silently takes the ELSE path: min/max/clamp/sort all misroute it. Sorting with NaNs present is UB-adjacent chaos in most libraries: sanitize at ingestion.
Testing bitwise GPU-vs-CPU equality. FMA contraction + reduction order + libm differences guarantee mismatches that are MORE accurate, not less. Tolerance tests with error budgets; bitwise only within one pinned platform+flags.
Blaming precision, shipping cancellation. "We need fp64" is often "our formula cancels." E[X²]−μ², 1−cosθ, naive quadratic roots: fix the algebra first — it's free — before paying 2–32× for wider types (fp64 is 1/32 rate on some gaming GPUs, 1/2 on datacenter parts — check your target's spec sheet).

Scenario — the model that failed accuracy review by 0.4%

Your team quantizes a recommendation model to fp16 for a 2× serving-cost win. Offline eval: accuracy drops 0.4% — enough to block launch. The postmortem is a tour of this lesson. Finding 1: the feature-normalization step computes variance as E[X²]−μ² in fp16; for a popularity feature with μ ≈ 180 (μ² ≈ 32 400 — brushing 65 504), the subtraction cancels catastrophically and intermittently overflows to inf → those requests silently fell back to unnormalized features. Fix: Welford in fp32 (features stay fp16). Finding 2: cosine similarities computed as dot/(‖a‖‖b‖) with fp16 norms — squared magnitudes overflow for long embeddings; fix: normalize embeddings ONCE in fp32 at index time (Lesson 5's scenario, now with the precision reason attached), serve pure fp16 dots safely (each |aᵢbᵢ| ≤ 1, sums accumulate in fp32 via the tensor-core path). Finding 3: the eval harness itself compared fp16 pipeline vs fp32 golden with rtol = 1e-6 — flagging correct-within-fp16 results as failures and inflating the measured drop; fix the tolerance to the fp16 error budget. Re-run: true accuracy delta 0.05%, launch approved, serving cost halved. Nobody wrote a new model — three bit-layout arguments and one honest tolerance did it. That's floating-point literacy as a business skill.

Practice

1. What are the fp32 ulps near 1.0, 1024.0, and 2²⁴? General formula from the exponent?
ulp(x) for x ∈ [2ᵏ, 2ᵏ⁺¹) is 2^(k−23). Near 1.0 (k=0): 2⁻²³ ≈ 1.19e−7 (machine ε). Near 1024 (k=10): 2⁻¹³ ≈ 1.22e−4. Near 2²⁴: 2¹ = 2. Precision is a sliding scale set by the exponent — memorize the formula, derive the rest.
2. Why is 0.5 exact in every float format but 0.1 exact in none? State the general representability rule.
A decimal terminates in binary iff it equals p/2ᵏ — denominator a pure power of two. 0.5 = 1/2 ✓. 0.1 = 1/10 = 1/(2·5): the factor 5 forces an infinite repeating binary expansion, rounded at storage. Corollary: sums of halves/quarters/eighths (texture coords, mip levels) are exact; sums of tenths drift.
3. Predict, then explain: in fp32, does (0.1f + 0.2f) + 0.3f equal 0.1f + (0.2f + 0.3f)? What property died, and name the GPU consequence.
Generally unequal (each grouping rounds different intermediates; in fp32 these two differ in the last ulp). Associativity died — the compiler may NOT reorder float sums without permission (that's what -ffast-math grants), and parallel reductions that reorder sums produce run-dependent results unless the order is fixed (tree with fixed topology) — the root of "deterministic mode" switches in every ML framework.
4. A logit vector in fp16 contains [12.1, 9.3, 88.0]. Trace what softmax does naively, then with the max-subtraction trick (Lesson 3), all in fp16 terms.
Naive: e^88 overflows even fp32 (e^88 ≈ 1.7e38 ≈ max) and utterly overflows fp16 (max 65504, e^11.1 already exceeds it — e^12.1 ≈ 1.8e5 → inf). inf/inf = NaN: the whole distribution NaNs. Stable: subtract M = 88 → [−75.9, −78.7, 0]; e^−75.9 underflows to 0 (harmlessly — those probabilities ARE ~0), e^0 = 1 → probs ≈ [0, 0, 1]. Underflow to zero is graceful here; overflow was fatal. The asymmetry (protect the top, let the bottom flush) is why the trick subtracts the max rather than centering.
5. Kahan summation stores a correction c. Walk one iteration summing s = 1e8, next term 1.0 (fp32), and show what c captures.
y = 1.0 − 0 = 1.0; t = 1e8 + 1.0 → rounds to 1e8 (ulp there is 8 — absorption); c = (t − s) − y = (0) − 1.0 = −1.0. The "lost" 1.0 now lives in c and is re-injected next iteration (y = a[i] − (−1) = a[i]+1). Kahan is bookkeeping for absorbed crumbs; after n such terms, s + (−c) recovers ≈ the true sum where the naive loop lost all n.
6. Your CUDA kernel's results differ between -O3 and -O0 builds by 1–2 ulps. List the three most likely causes and the flag/test for each.
(1) FMA contraction at -O3: test with -fmad=false. (2) Different math-function paths (fast vs precise, e.g., division/sqrt): check -prec-div/-prec-sqrt and -use_fast_math. (3) Reassociation/vectorization changing sum order (host code too, via -ffast-math). Verify by pinning flags and diffing per-op; then encode the finding as a tolerance-based test with an error budget, not a bitwise golden file.
7. Design: a Track-B style simulation needs the total energy of 10⁹ particles (fp32 values spanning 10⁻⁶ … 10⁶) summed every step, accurate to 1e−6 relative, deterministic across runs on one machine. Specify the reduction (levels, precisions, order), justify against naive summation, and state the residual risks.
Design: per-block tree reduction in shared memory (fixed intra-block order), accumulating each fp32 product/read into an fp64 partial (or Kahan-fp32 if fp64-slow hardware); block partials written to a fixed-index array; final pass sums the ~10⁴ partials in fp64 in a FIXED order (single block tree, not atomics). Why: naive fp32 running sum has error ~n·ε ≈ 10⁹·6e−8 → order-10 relative garbage with mixed magnitudes; tree order cuts growth to log₂n ≈ 30 roundings and fp64 accumulation makes each rounding 2⁻⁵² — total error ≪ 1e−6. Determinism: no atomicAdd anywhere (arrival order!), fixed topology, pinned flags (-fmad choice), same GPU/driver. Residual risks: inputs already contaminated (garbage in, precisely summed garbage out), cross-GPU-model bit drift (promise tolerance, not bits, across models), and a future contributor "optimizing" the final pass with atomics — document WHY it's ordered. This design is, almost line for line, how production HPC codes and cuBLAS-style reductions actually do it.
