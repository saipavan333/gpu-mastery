Triton & MLIR — let the compiler do the porting

Every rung so far asked you to port: rename to HIP, rewrite into SYCL accessors, feature-detect in WGSL. The compiler rung inverts it. You write one kernel in Triton (the language from Track A's A4), and the compiler lowers it through MLIR to NVIDIA's PTX or AMD's AMDGCN — same source, different ISA, zero edits. And because the compiler re-tunes per architecture, it does the one thing a human porter can't do at scale: turn 5.6's occupancy dial optimally for every backend, automatically. Today: how the lowering works, why compilers are eating this problem, and the honest limit where they still lose to vendor libraries.

Concept

Portable by IR: one Python kernel, two vendor ISAs

In A4 you wrote Triton kernels as the Python-with-tiles alternative to CUDA — @triton.jit, tl.load/tl.store with masks, program_id as the block index. Track D's angle is what happens to that kernel underneath. It doesn't compile straight to PTX; it flows through a stack of MLIR intermediate representations, and the vendor split happens near the bottom:

your @triton.jit Python kernel   (you write this ONCE)
        |
   Triton-IR (TTIR)              block-level MLIR dialect — the algorithm, abstractly
        |
   Triton-GPU-IR (TTGIR)         + hardware layout: tiles, warps, memory access patterns
        |
   LLVM-IR                       the gpu dialect lowers to nvvm OR rocdl
        |
   +----+----+
   |         |
  PTX      AMDGCN / hsaco        NVIDIA path         AMD path (ROCm 6.2+)
  (nvvm)   (rocdl)

The key idea is that portability lives in the IR, not in your source. TTIR captures the algorithm; TTGIR adds the hardware-specific layout (how tiles map to warps, how memory is accessed); only at the LLVM-IR-to-machine step does the target vendor matter, where MLIR's gpu dialect lowers to nvvm (NVIDIA) or rocdl (AMD). On AMD, a TritonAMDGPUDialect handles the backend specifics and the result is AMDGCN assembled into an hsaco binary; on NVIDIA it's PTX. You wrote none of that — you wrote the tiled Python once and the compiler retargeted it. This is D1's "IR/compiler" rung: the porting work moved from your hands into the toolchain.

Why compilers are eating this problem: the dial turned by machines

Here's the deeper reason IR-level tools are winning, and it's a direct callback to 5.6. Performance tuning is a search over knobs — tile size, num_warps, num_stages (the pipelining depth), the occupancy dial. On CUDA you turned those knobs by hand, per kernel, guided by the profiler (5.6, 5.10). But the optimal setting differs per architecture — a T4, an H100, and an MI300 have different register files, shared-memory sizes, and warp/wavefront widths, so the best tile size on one is wrong on another. A human porting by hand has to re-tune every kernel for every target; a compiler with @triton.autotune just searches the knob space per backend at compile time. The machine turns 5.6's dial optimally for each GPU, automatically, which is something no human port does at fleet scale. That's why the compiler approach is ascendant: it doesn't just translate the algorithm across vendors, it re-optimizes it for each one — the porting and the tuning, both automated.

The honest limit: vendor libraries still own the peak

Track D's through-line is honesty about the last 10% (D1), and here it's sharp. Triton and compiler-level tools get you excellent, portable performance for custom and fused kernels — often ~90%+ of achievable, rising as the compilers improve. But for the absolute-peak, tensor-core/matrix-core-class operations — a production matmul at the hardware's FLOP ceiling — hand-tuned vendor libraries (cuBLAS on NVIDIA, rocBLAS on AMD, or CUTLASS-level templates) still win the last few percent, because they encode assembly-level scheduling the compiler hasn't matched. So the real-world map is the one 5.11 and D1 keep drawing: use Triton/compilers for the 90% (the custom, fused, portable kernels — Track A's A5 fusion work, now portable), and call the vendor library for the pinned-to-peak 10% (the matmul). The compiler is eating the problem from the bottom up, but the top of the FLOP curve is still vendor territory — and pretending otherwise is how you ship a "portable" matmul that's 2x slower than the library on every card.

What to internalize: the portability ladder is a real gradient of who does the porting. Hand-rewriting means you do all of it. HIP means the tool does the renames and you do the wavefront audit and re-tuning (D2's 6 lines plus the landmine hunt). Triton means the compiler does the renames, the wavefront handling, and the per-architecture tuning — your source delta is zero, and you're left with only the irreducible work that no rung eliminates: numerically re-validating on the new hardware (a fixture is still machine-specific, D2's lesson) and deciding whether this kernel is in the 90% (let Triton have it) or the peak-chasing 10% (call the vendor library). The compiler didn't make porting free; it moved the porting into the toolchain and left you with the judgment calls — which is exactly where a senior engineer's time should go.

Key points

  • A Triton kernel (A4's language) lowers through MLIR — Python to TTIR to TTGIR to LLVM-IR — then branches to PTX (NVIDIA, via nvvm) or AMDGCN (AMD, via rocdl, ROCm 6.2+); portability lives in the IR, so your source delta across vendors is zero.
  • The MLIR gpu dialect lowering to nvvm/rocdl is where the vendor split happens; a TritonAMDGPUDialect handles AMD specifics, producing an hsaco binary versus NVIDIA's PTX.
  • @triton.autotune searches block size, num_warps, and num_stages per architecture — 5.6's occupancy dial turned by a machine, re-optimizing per backend in a way no hand port does at scale.
  • Compilers are ascendant because they automate BOTH the translation and the per-architecture tuning — the porting and the dial-turning — not just one.
  • The honest limit: vendor libraries (cuBLAS/rocBLAS/CUTLASS) still own absolute tensor-core/matrix-core peak, so the map is Triton for the fused/custom 90%, vendor library for the pinned-to-peak matmul 10% (5.11, D1).
  • Zero source changes is not zero work: you still re-validate numerically on the new hardware (fixtures are machine-specific, D2) and re-profile (D8) — the compiler absorbs the porting, not the judgment.

Quiz

1. A team benchmarks a Triton matmul against cuBLAS on NVIDIA and finds Triton ~2x slower at large sizes. They conclude "Triton is a failure for portability." What's the flawed assumption, and what's the correct role for Triton here?
Options 3 and 4 are nonsense (Triton targets both vendors; you can't recompile cuBLAS through Triton). The correct answer draws D1's 90/10 line precisely: matmul-at-peak is the 10% vendor libraries own, so benchmarking Triton there is choosing its worst case. Triton wins where there's no library to call — fused and custom kernels — which is most of a real model's long tail (Track A's fusion story). The general lesson: judge a tool against its purpose, not against a specialist at the specialist's task; "portable custom kernels" and "peak vendor matmul" are different jobs.
2. Moving a hand-written CUDA reduction to AMD took a wavefront-64 audit (D2). Moving a Triton reduction to AMD took zero source changes. A colleague says "so Triton has no wavefront-64 problem — the bug doesn't exist there." Precisely right or subtly wrong?
Option 4 is a factual error (AMD wavefronts are 64). Option 3 is wrong (Triton targets AMD via ROCm 6.2+). The subtle correctness the answer captures: "no source-level bug" is not "no hardware difference" — the compiler assumed responsibility for the 32-vs-64 handling, which is exactly why the IR rung is powerful. But it also means you've traded auditing your own literals for trusting the compiler, so the D2 discipline (re-run fixtures on the actual AMD hardware) still applies — now guarding against compiler bugs instead of your own. Ownership moved; it didn't disappear.

Exercise 2 — Reason about the lowering. Given a Triton kernel with BLOCK_SIZE=1024 and num_warps=4, explain what changes and what stays the same when the target switches from an H100 (warp 32) to an MI300 (wavefront 64), and at which IR stage the difference is introduced.

What stays the same: your Python source (0 changes) and the TTIR (the abstract algorithm — a block of 1024 elements reduced, independent of hardware). What changes: at the TTGIR stage, the compiler maps the block onto the target's SIMD groups — 1024 elements over 32-lane warps (H100) means 32 warps' worth of structure, but over 64-lane wavefronts (MI300) the mapping differs, and num_warps is reinterpreted for the wavefront width. The final LLVM-to-machine step emits PTX vs AMDGCN. So the hardware-specific SIMD-width handling enters at TTGIR (the "GPU-IR" that adds layout), which is exactly why your source didn't need a wavefront audit — TTGIR is where the compiler absorbs the 32-vs-64 difference (quiz 2). Go deeper — the compiler that ports for you

1. The lowering pipeline, stage by stage

stage        what it represents                       vendor-specific?
───────────  ───────────────────────────────────────  ─────────────────
Python       @triton.jit — tiles, tl.load/store, masks  no (you write once)
TTIR         block-level algorithm (MLIR dialect)        no
TTGIR        + layouts: tiles->warps, memory patterns    YES (SIMD width enters here)
LLVM-IR      gpu dialect -> nvvm (NVIDIA) / rocdl (AMD)   the branch point
target       PTX (NVIDIA) / AMDGCN+hsaco (AMD)            fully vendor-specific
insight: the higher IRs are portable (algorithm); vendor detail is pushed as LOW
as possible (TTGIR and below). That's the general compiler-portability principle —
keep the IR abstract, specialize late — and it's why MLIR (multi-level IR) exists.

2. Autotuning: 5.6's dial, searched by machine

@triton.autotune(configs=[
    Config({'BLOCK_SIZE': 256}, num_warps=4, num_stages=2),
    Config({'BLOCK_SIZE': 1024}, num_warps=8, num_stages=4), ...],
    key=['n'])   // re-search when n changes
what it does: benchmarks each config on THIS gpu at compile time, picks the best.
  · BLOCK_SIZE  = tile size (5.5)
  · num_warps   = threads per program (5.6's occupancy)
  · num_stages  = software-pipelining depth (5.9's overlap, as a knob)
why it beats hand-tuning across vendors: the optimal config differs per arch
  (register file, smem, warp/wavefront width), and the tuner just re-searches per
  backend — 5.6's dial turned by a machine, per GPU, for free. A human can't
  re-tune every kernel for every target; the compiler does it on every build.

3. Where compilers win, and where they don't (yet)

compilers (Triton/MLIR) WIN:            vendor libraries/hand-asm still WIN:
  fused/custom kernels (no library)      dense matmul at tensor-core peak (cuBLAS)
  fusion-rich elementwise chains (A5)    the last few % of the FLOP ceiling
  novel ops, research kernels            CUTLASS-level template metaprogramming
  portability across vendors (0 source)  operations with a mature, tuned library
the map (5.11, D1): compilers for the 90% (portable, fused, custom);
  vendor library for the pinned-to-peak 10% (call cuBLAS/rocBLAS, don't reinvent).
trend: the compiler frontier keeps rising — more of the 10% falls to compilers each
  year — but "call the library for peak matmul" remains the safe default in 2026.

Gotchas

Benchmarking Triton against cuBLAS on matmul. That's the peak operation vendor libraries own — testing Triton where it's designed to lose (quiz 1). Compare it on fused/custom kernels no library ships.
Assuming "0 source changes" means "0 work." The compiler absorbs the porting and tuning, but you still re-validate numerically on the new hardware and re-profile (D8). A fixture certifies the machine it ran on (D2), compiler backends included.
Trusting the compiler handled the wavefront width without checking. TTGIR does handle 32-vs-64, but compilers have bugs too — run the reduction fixtures on actual AMD hardware (quiz 2). Ownership moved to the compiler; verification is still yours.
Skipping autotune and hard-coding one config. A block size tuned for an H100 is likely wrong on an MI300 (different smem/registers) — hard-coding forfeits the per-architecture search that is the compiler rung's main advantage (5.6).
Expecting Triton to express everything. Triton's tile-based model fits many kernels but not all (irregular, pointer-chasing, or deeply stateful ones). When the model doesn't fit, drop to HIP/CUDA for that kernel — the rungs of D1's ladder coexist in one project.
Ignoring compile/autotune time in latency-sensitive paths. Autotuning searches configs at first compile — a real one-time cost (like OpenCL's runtime build, D4). Cache the tuned kernel; don't re-autotune in a hot request path.

Scenario — the porting team that automated itself out of a job (the good way)

An ML infrastructure team maintains ~40 custom kernels — fused activations, a few attention variants, some quantization ops (Track A's world) — originally hand-written in CUDA. The company adds AMD MI300 capacity, and the mandate is "make the custom kernels run on AMD too." The team's first plan is to hipify all 40 and audit each for wavefront-64 bugs (D2) — a multi-week slog of renames, warp-literal hunts, and re-tuning, repeated for every kernel and destined to repeat again for the next vendor. A senior engineer proposes the compiler rung instead: rewrite the 40 kernels once in Triton (many were already Triton from Track A's A4 work), and let the compiler lower them to both PTX and AMDGCN with zero per-vendor source. The rewrite-to-Triton is real work up front, but it's paid once, and the payoff is structural: adding AMD becomes a rebuild, not a port; the wavefront-64 handling moves into the compiler (quiz 2); and autotune re-optimizes each kernel for the MI300's register file and wavefront width automatically, which the hand-port would have required a human to do per kernel (5.6, at 40x). The one place they don't use Triton is the matmul-heavy path — that calls cuBLAS on NVIDIA and rocBLAS on AMD, because chasing tensor-core peak is the vendor library's job (quiz 1, D1's last 10%). Six months later a third vendor's hardware arrives, and the custom kernels are a rebuild while the competition is still hand-porting. The moral is the compiler rung's whole thesis: the highest-leverage move in cross-vendor work is often to stop porting by hand and let the toolchain do it — you pay a one-time cost to express the kernel in a portable IR, and in exchange every future vendor is a compile target instead of a project. The team didn't eliminate the porting work; they moved it into the compiler, where it happens once per build instead of once per engineer per vendor.

Practice

1. List the IR stages a Triton kernel passes through from Python to an AMD binary, and name the stage where the wavefront-64 difference is handled.
Python (@triton.jit) to Triton-IR (TTIR, block-level algorithm) to Triton-GPU-IR (TTGIR, adds hardware layout: tiles-to-warps, memory patterns) to LLVM-IR (gpu dialect to rocdl for AMD) to AMDGCN assembled into an hsaco binary. The wavefront-64 (SIMD width) difference is handled at the TTGIR stage, where the abstract block is mapped onto the target's SIMD groups — which is exactly why your Python source never encodes a literal 32 and never needs D2's audit (the compiler owns it there).
2. What does @triton.autotune do that a hand port across vendors can't, and which core lesson's "dial" is it turning?
It benchmarks a set of configs — block size, num_warps, num_stages — on the actual target GPU at compile time and picks the best, then re-does that search per architecture automatically. A hand port has to re-tune every kernel manually for every target, which doesn't scale past a few kernels or a couple vendors. It's turning 5.6's occupancy dial (plus 5.5's tile size and 5.9's pipeline depth), but by machine search instead of human intuition, per backend. That automated per-architecture re-tuning — not just translation — is why the compiler rung is ascendant.
3. Why is comparing Triton to cuBLAS on matmul the wrong benchmark, and what's the right one?
Matmul at large sizes is the tensor-core peak operation that vendor libraries (cuBLAS/rocBLAS) hand-tune to the FLOP ceiling with assembly-level scheduling — the last 10% Triton isn't designed to win (D1). So that benchmark tests Triton at its worst case against a specialist at its specialty. The right benchmark is a fused or custom kernel that no library ships — a fused activation-plus-bias epilogue, a novel attention variant (A5) — where Triton provides portable performance and cuBLAS provides nothing because it can't express the fusion. Judge a tool on its purpose: Triton's purpose is portable custom kernels, not beating the vendor matmul (quiz 1).
4. "Zero source changes to port a Triton kernel to AMD" — what work does that phrase still leave you?
Three things the compiler doesn't do for you: (1) numerically re-validate on the AMD hardware — run the fixtures there, because a fixture certifies the machine it ran on and compilers can have bugs (D2, quiz 2); (2) re-profile on the target — the roofline verdict doesn't port (D8), so confirm the kernel is still doing what you think; (3) the judgment call of whether this kernel belongs to Triton (the fused/custom 90%) or should call a vendor library (the peak matmul 10%). The compiler absorbs the translation and tuning; it doesn't absorb validation, profiling, or architectural judgment — which is precisely the senior-engineer work.
5. Explain the general compiler-portability principle "keep the IR abstract, specialize late" using the TTIR/TTGIR split.
The principle: represent the algorithm in a high, hardware-independent IR for as long as possible, and push vendor-specific detail to the lowest stages, so the portable part is maximized and the specialized part is isolated. In Triton, TTIR holds the abstract block-level algorithm (fully portable — the same for any GPU), and only TTGIR adds hardware layout (tiles-to-warps, SIMD width, memory patterns), with the true vendor branch at LLVM-IR-to-machine (nvvm vs rocdl). So a change of target only re-runs the low stages; the algorithm in TTIR is reused. This is why it's called MLIR (multi-level IR) and why the source never encodes vendor detail — the levels exist precisely to specialize late.
6. When does the Triton/compiler rung NOT fit, and what do you do instead?
It doesn't fit when the kernel doesn't match Triton's tile-based model — irregular or pointer-chasing algorithms (graph traversal, sparse structures with data-dependent access), deeply stateful kernels, or code needing an instruction Triton can't express. It also doesn't fit for peak matmul (call the vendor library). In those cases you drop that specific kernel to HIP/CUDA (the dialect rung) or the vendor library, while keeping the rest of the project on Triton — the rungs of D1's ladder coexist. A real cross-vendor codebase is usually mostly-Triton with a few HIP/CUDA kernels for the parts that don't lower well and library calls for the peak ops. Match each kernel to the rung that fits it.
7. The interview closer: "When do you reach for Triton/compiler-level portability versus hand-porting to HIP versus Kokkos?" Deliver the spoken skeleton.
"These are three rungs of the portability ladder, and I pick by what I'm porting and who should do the work. Triton is my choice for custom and fused GPU kernels — fused epilogues, attention variants, novel ops — because I write the kernel once in Python and the compiler lowers it through MLIR to PTX or AMDGCN with zero source changes AND re-autotunes it per architecture, turning the occupancy dial by machine instead of by hand. So adding a vendor is a rebuild, not a port, and the wavefront-64 handling moves into the compiler. I reach for HIP when I have a large existing CUDA codebase targeting mainly AMD and I want the closest-to-the-metal, lowest-risk port — renames plus a wavefront audit, full control. I reach for Kokkos when it's a big C++ application, especially HPC, that must run WELL across many vendors and outlive the hardware, because it makes layout and memory spaces compile-time parameters so one source is optimal everywhere. And across all three I keep the same discipline: call the vendor library for peak matmul — that's the last 10% Triton and hand-ports both lose to cuBLAS/rocBLAS — and re-validate numerically on each target because a fixture only certifies the machine it ran on. So: Triton for portable custom kernels with automated tuning, HIP for control on a CUDA-heavy AMD port, Kokkos for long-lived multi-vendor C++ apps, and always the vendor library for the peak. The unifying idea is that the compiler rung moves the porting into the toolchain — my job becomes judgment, not translation.' That framing — three rungs, one judgment layer — is the answer."
