SYCL & oneAPI — one C++ file, and a runtime that schedules for you

HIP kept you writing C++-per-vendor. SYCL climbs a rung: one standard C++ source, compiled to any backend — NVIDIA, AMD, Intel, or the CPU in this sandbox. The trade is that you stop declaring the plumbing (5.3's copies, 5.9's streams) and start declaring your intent — which data each kernel reads and writes — and the runtime infers the copies and the schedule for you. Today you'll see that inference is not magic: it's the same dependency DAG you built by hand in 5.9, discovered from your accessors.

Concept

Single-source: host and device in one file

SYCL 2020 (the current standard, revision 6) is single-source: the host code and the device kernel live in the same .cpp, compiled by one compiler that splits them the way nvcc split .cu files (5.1) — except the device half targets SPIR-V, HIP, CUDA, or a CPU backend depending on a flag. The three nouns you must know:

sycl::queue q;                                 // a device + its work stream (5.9's stream)
sycl::buffer<float> A{data, N};                 // wraps host memory; the RUNTIME now owns it
q.submit([&](sycl::handler& h){                // one "command group"
    sycl::accessor a{A, h, sycl::read_write};  // DECLARE intent: I read and write A
    h.parallel_for(N, [=](sycl::id<1> i){       // nd-range = grid/block (5.2)
        a[i] = a[i] * 2.0f;                    // the kernel body
    });
});                                            // buffer copies back on scope exit (RAII)

The accessor is the whole idea. In CUDA you managed a raw device pointer and issued cudaMemcpy yourself (5.3); here you wrap host data in a buffer, and every kernel that touches it does so through an accessor tagged read, write, or read_write. That tag is 5.3's ownership model promoted from discipline to type: the runtime knows who reads and who writes, so it decides when to copy data to the device, when to bring it back, and — the payoff — what may run in parallel. There's a second, more CUDA-like model, USM (unified shared memory: malloc_shared), where you get raw pointers and own the synchronization yourself; we'll weigh the two in Go-deeper. Start with buffers/accessors, because they buy you the next section.

The runtime infers the graph you used to declare

This is where single-source earns its keep, and it's a direct callback to 5.9. There, you got overlap by explicitly creating streams and events and declaring dependencies by hand. SYCL flips it: you write kernels with accessors and no synchronization, and the runtime reads your read/write tags to infer the dependency graph. To prove this isn't hand-waving, here's the runtime's actual logic — hazard detection over accessor sets — executed on four kernels:

four kernels, accessor read/write sets, ZERO user sync:
  K1: writes A            K2: reads A, writes B
  K3: reads C, writes D   K4: reads B and D, writes E
runtime infers hazards (executed):
  K1 depends on —         (nothing writes what it reads)
  K2 depends on [K1]      (RAW: K1 wrote A, K2 reads A)
  K3 depends on —         (independent — touches C,D only)
  K4 depends on [K2, K3]  (RAW: needs B from K2 and D from K3)
schedule the runtime discovers (topological waves):
  wave 1 (CONCURRENT): [K1, K3]   ← overlap, though you wrote no streams
  wave 2:              [K2]
  wave 3:              [K4]

K1 and K3 run at the same time because nothing connects them, and the runtime figured that out from the fact that their accessor sets don't collide — the identical reasoning you did manually with events in 5.9's max-lane law, now automated. This is the single-source bargain stated precisely: you give up writing the schedule and in exchange the compiler/runtime writes a correct one from your declared data intent. When it works, it deletes a whole class of missing-dependency bugs (5.9's hazards) — you literally cannot forget an edge you never had to draw.

nd_range is grid/block, and reductions come in the box

Inside the kernel, nothing is new — only renamed (D1's table). Launch geometry is nd_range<1>{global, local}, your <<<grid, block>>> (5.2). Coordinates come from nd_item: get_global_id() is the 5.2 identity, get_local_id() is threadIdx. Shared memory (5.5) is a local_accessor; the barrier is group_barrier() = __syncthreads(); the warp is a sub_group. And the operation you hand-built across three core lessons — the reduction (5.8) — SYCL ships as a first-class primitive: sycl::reduction passed to parallel_for gives you a correct, tuned tree reduction with no shuffle-offset literals to get wrong (which, after D2, you'll appreciate viscerally). The library-first doctrine (5.11) again: the vendor's reduction is race-free and wavefront-aware, so you don't re-derive the tree per architecture.

Worked example

Task: Predict a SYCL program's execution schedule from its accessors alone — the skill that lets you reason about single-source performance without a profiler. Four kernels submitted in order, each with the accessor sets above. Prediction first: which kernels overlap, and what's the critical-path length (number of sequential waves)?

Prediction (reason from data hazards, like 5.9 by hand):
  K1 (write A) and K3 (read C, write D) share no buffers → they overlap.
  K2 needs A (from K1); K4 needs B (from K2) and D (from K3).
  So critical path is K1 → K2 → K4 = 3 waves; K3 hides inside wave 1.
Result (executed scheduler): wave1=[K1,K3], wave2=[K2], wave3=[K4]. ✓
  3 waves, K3 fully overlapped. Prediction confirmed.

What to internalize: you just did performance analysis on a program with no explicit synchronization, purely by tracing which buffers connect which kernels — because in SYCL the accessors are the dependency graph. This is the mental model shift the single-source rung demands: to reason about overlap you stop looking for stream/event calls (there are none) and start looking at the read/write sets. The upside is that K3's overlap came for free — you didn't schedule it, and you can't forget to. The downside, which the next lessons and gotchas hammer, is that if you accidentally over-declare intent (an unnecessary read_write where read would do, or a stray dependency), you serialize kernels that could have overlapped, and there's no explicit code to point at — the performance bug is in what you declared, not what you called.

Key points

  • SYCL 2020 is single-source: one standard C++ file compiles to CUDA, HIP, Intel, or a CPU backend — the same nvcc-style host/device split (5.1), one rung above HIP on D1's ladder.
  • The accessor is 5.3's ownership model promoted to a type: tagging a buffer read/write/read_write lets the runtime own the data and decide copies — you declare intent, not plumbing.
  • From accessor read/write sets the runtime infers the dependency DAG and overlaps independent kernels automatically (executed: K1 and K3 run concurrently with zero user sync) — 5.9's graph, discovered instead of declared.
  • Inside the kernel everything is renamed, not new: nd_range = grid/block, local_accessor = __shared__ (5.5), group_barrier = __syncthreads, sub_group = the warp.
  • sycl::reduction ships a correct, wavefront-aware tree reduction (5.8 productized) — no shuffle-offset literals to get wrong, the library-first doctrine (5.11) sparing you D2's bug.
  • USM (malloc_shared) is the alternative model with raw pointers and manual sync, closer to CUDA — buffers/accessors buy inferred scheduling; USM buys pointer familiarity and explicit control.

Quiz

1. A developer ports a CUDA pipeline to SYCL using buffers/accessors, but wraps every submit in q.wait() "to be safe, like cudaDeviceSynchronize after each kernel." The result is correct but no faster than serial. What did they do, and what's the fix?
This is the single-source model's signature footgun: importing CUDA's explicit-sync habit (5.3/5.9) into a system that infers synchronization makes every kernel a barrier. Option 4 misdiagnoses — USM can overlap too; the problem is the waits, not the memory model. The correct answer names the mechanism (global barrier per submit kills inferred overlap) and the fix (trust the accessors, wait once). The deep point: in SYCL, correctness comes from declaring data intent, so adding manual synchronization on top doesn't add safety — it only subtracts performance.
2. Your team needs a reduction over 100M floats, portable across NVIDIA and AMD. One engineer wants to hand-write a shuffle-tree reduction "for control"; another wants sycl::reduction. Given D2, which is the defensible default and why?
Option 3 is the D2 bug stated as a (bad) plan. Option 5 defeats the entire point of single-source — two codebases is what portability was supposed to eliminate. The correct answer connects two lessons: SYCL's library reduction is the library-first doctrine (5.11) doing exactly what it's for — encapsulating the wavefront-64 tuning (D2) so your one source is correct everywhere. "For control" is a real reason sometimes, but the burden of proof is on the hand-written path, because control here means owning the landmine.

Exercises

Exercise 1 — Run the scheduler logic yourself (no SYCL needed). Write the ~15-line hazard-detection simulation: given kernels as (reads, writes) sets, infer the dependency edges (RAW/WAW/WAR) and print the concurrent waves. Then add a fifth kernel that reads E and writes A, and predict how the schedule changes before running.
def hazards(i,j,K):            # edge j←i if a hazard exists
    _,ri,wi=K[i]; _,rj,wj=K[j]
    return bool(wi&rj or wi&wj or ri&wj)   # RAW, WAW, WAR
# deps[j] = {i<j : hazards}; waves = repeatedly take kernels whose deps are done

Adding K5 = (reads {E}, writes {A}): it depends on K4 (RAW on E) AND on K1 (WAW on A — both write A) and K2 (WAR — K2 read A, K5 writes A). So K5 lands after K4, extending the critical path to 4 waves. The lesson of the prediction: a single kernel that reuses buffer A serialized the whole tail, because WAW/WAR hazards are real dependencies even without data "flowing." That's precisely why the runtime tracks writes, not just reads — and why aliasing buffers unnecessarily (a stray reuse of A) can quietly serialize a pipeline. Deliverable: the sim plus a note on which hazard type (RAW/WAW/WAR) caused each edge.

Exercise 2 — On your own machine, install a SYCL CPU backend — Intel oneAPI DPC++ (icpx) or the community AdaptiveCpp — and compile a SYCL vector-double and a sycl::reduction, running on the CPU backend. Confirm the reduction matches a serial std::accumulate within an fp budget. (The sandbox for this course has no SYCL toolchain; this one targets your machine, and the CPU backend means you need no GPU at all.)

Expected: icpx -fsycl vec.cpp (or acpp vec.cpp) builds a single binary; selecting the cpu or host device runs the same kernel source on CPU cores. The reduction over, say, 1e7 floats should match std::accumulate in fp64 to within a budget (not bitwise — M1 L8; the tree reduces in a different order than the serial sum). The point of the CPU backend: it proves single-source is real — the identical .cpp that would run on an Intel GPU runs on your laptop's CPU by changing a device selector, no code edits. That "same source, pick the device" moment is the SYCL thesis you can feel. Deliverable: the build command, the device it selected, and the reduction's error vs the serial oracle.

Go deeper — the single-source machine underneath

1. Buffers/accessors vs USM: the model decision

                    buffer + accessor                 USM (malloc_shared/device)
──────────────────  ────────────────────────────────  ────────────────────────────────
data ownership      runtime owns it                   you own it (raw pointers)
synchronization     INFERRED from accessors           MANUAL (depends_on, events)
dependency DAG      built for you (this lesson)        you declare it (like 5.9)
feels like          a build system for data            CUDA with a rename
best when           complex kernel graphs, safety      porting pointer-heavy CUDA,
                    matters, you want overlap free      fine-grained control needed
the trap            over-declaring intent serializes   forgetting a dep = 5.9's race,
                    (quiz 1)                            back in full force

The honest summary: buffers/accessors move you up the abstraction ladder (the runtime schedules), USM keeps you where HIP left you (you schedule, with pointers). Teams porting a large pointer-based CUDA codebase often start with USM to minimize the diff, then migrate hot subsystems to buffers/accessors where inferred overlap pays. Mixing is legal but is where the subtle bugs live — a USM pointer aliasing a buffer is invisible to the accessor DAG.

2. Queues, ordering, and host tasks

in-order queue     : submissions run in program order (simple, less overlap)
out-of-order queue : the DEFAULT — runtime reorders/overlaps per the DAG (this lesson)
host_task          : run host code INSIDE the graph, so a CPU step can be a
                     scheduled node with real dependencies (e.g. an MPI call — B5's world)
event.wait()       : synchronize on one submission, not the whole queue (finer than q.wait)

The out-of-order queue is why the inference matters — an in-order queue would run your kernels in submission order regardless of hazards, forfeiting the K1/K3 overlap. Choosing an in-order queue "for predictability" is a common way to accidentally opt out of the model's main benefit; do it only when you genuinely need program-order semantics.

3. SYCL compiles through SPIR-V — the connection to D4 and D7

your .cpp → SYCL compiler → SPIR-V (an IR) → vendor backend (PTX / AMDGCN / Intel)
  · SPIR-V is why SYCL targets so many devices — it's the portable IR (OpenCL 3.1
    makes SPIR-V ingestion mandatory in core — D4)
  · oneAPI DPC++ 2026 is the reference impl (note: 2026.0 is an ABI-breaking release —
    recompile, don't mix runtimes); AdaptiveCpp is the community impl
  · a native_cpu target (experimental) runs SYCL with no GPU backend at all —
    the sandbox-and-laptop story
this is the same "one IR, many ISAs" idea Triton uses (D7); SYCL just wears C++.

Gotchas

Importing cudaDeviceSynchronize habits. A q.wait() after every submit turns the inferred DAG into a serial chain (quiz 1). Trust the accessors; wait once, at the end or on a host accessor.
Over-declaring accessor intent. Tagging a read-only buffer read_write invents a false write, spawning WAW/WAR edges that serialize kernels that could overlap. Declare the minimum intent — it's a correctness-neutral, performance-critical choice.
Mixing USM and buffers carelessly. A USM pointer that aliases buffer-managed data is invisible to the accessor DAG, so the runtime can't order it — you're back to 5.9's manual hazards without knowing it. Keep a subsystem in one model.
In-order queue by default assumption. The default is out-of-order; if you pick in-order "to be safe," you disable the overlap that justifies single-source. Know which you asked for.
Expecting bitwise-identical reductions. sycl::reduction reduces in a tree order that differs from a serial sum and across backends (M1 L8) — fixtures use budgets, not equality, or a correct port "fails."
Buffer destruction as a hidden barrier. A buffer copies its data back to the host when it's destroyed (RAII) — letting one go out of scope mid-pipeline forces a blocking copy you didn't write. Scope buffers to the whole graph, not one kernel.

Scenario — the pipeline that "SYCL made slow"

A simulation group rewrites a five-stage CUDA pipeline in SYCL to target both their old NVIDIA cluster and a new Intel GPU machine. The port is faithful and the results are correct, but it runs ~30% slower than the CUDA original on the same NVIDIA hardware, and the team's conclusion forms fast: "SYCL's abstraction has real overhead; portability cost us performance." A skeptical senior asks to see the code before they accept that. Two things jump out. First, every submit is followed by q.wait() — a reflex carried from the CUDA version's cudaDeviceSynchronize — which serializes stages that the original CUDA code had explicitly overlapped with streams (5.9). Second, two buffers that are read-only in three of the stages are declared read_write everywhere "for simplicity," inventing dependencies that block overlap even after the waits are removed. Fixing both — delete the per-submit waits, tighten the accessor tags to read where reads suffice — the SYCL version matches the CUDA original within a few percent and, crucially, runs unmodified on the Intel machine. The moral is the single-source model's core discipline: performance in SYCL is governed by what you declare, not what you call. There was no abstraction tax; there was a pile of manual synchronization fighting a runtime built to synchronize for you, plus over-broad intent hiding the parallelism. "The framework is slow" is, nine times in ten, "I'm using the framework against its grain" — and the fix is to declare less and trust more, the opposite of the CUDA reflex.

Practice

1. Name the SYCL spelling for each core concept: <<<grid,block>>>, __shared__, __syncthreads(), the warp, threadIdx.x, a hand-written reduction.
nd_range<1>{global, local} for the launch; local_accessor for __shared__; group_barrier() for __syncthreads(); sub_group for the warp; nd_item.get_local_id(0) for threadIdx.x; sycl::reduction for the reduction (don't hand-write it — quiz 2). Every row is D1's translation table; the last one is also 5.8 productized so you skip D2's landmine.
2. Two kernels: K1 writes buffer X; K2 reads buffer Y and writes buffer Z (X, Y, Z all distinct). You wrote no synchronization. Will they overlap, and how does the runtime know?
Yes, they overlap — their accessor sets are disjoint (K1 touches X, K2 touches Y and Z), so there's no RAW/WAW/WAR hazard between them and the out-of-order queue schedules them concurrently. The runtime knows purely from the read/write tags on the accessors; it never needed you to say "these are independent." This is the K1/K3 case from the worked example — inferred concurrency from declared intent, 5.9 without the manual event bookkeeping.
3. Explain why calling q.wait() after each of five submissions makes a SYCL program run like serial code, in terms of the DAG.
Each q.wait() is a global barrier: it blocks the host until all prior work in the queue completes before the next submission is even enqueued. So the runtime never has two independent kernels in flight to schedule — the DAG it could have exploited is flattened into a strict sequence, one kernel per barrier. The inferred overlap (independent kernels sharing no buffers) requires multiple submissions to be pending at once; per-submit waits guarantee there's only ever one. Delete the waits and the DAG's concurrency reappears (the scenario's fix).
4. When would you choose USM over buffers/accessors, accepting the manual synchronization?
When porting a large, pointer-heavy CUDA codebase where rewriting into buffers/accessors would be a huge diff and you want to minimize risk — USM's raw pointers map almost 1:1 onto CUDA device pointers, so the port is closer to HIP's rename experience. Also when you genuinely need fine-grained, explicit control over data placement and dependencies (e.g., interoperating with an MPI or library call that expects a raw pointer). The cost you accept: you're back to 5.9's world of declaring dependencies by hand, so forgetting one is a real race again. It's the control-vs-safety trade of the two models.
5. A buffer wrapping a host array is declared inside a loop that submits one kernel per iteration, and destroyed at the end of each iteration. Why is this slow, and what's the fix?
Destroying the buffer each iteration triggers its RAII copy-back to the host (blocking), and re-creating it next iteration triggers a copy-to-device — so every iteration pays a full round-trip over the bus (4.6) that the algorithm never needed. It also inserts a hard barrier, killing any cross-iteration overlap. The fix: create the buffer ONCE outside the loop so the data stays resident on the device across iterations, and only bring it back when you actually need the host to see it (a host accessor at the end). This is 5.3's "allocate once, reuse" law wearing SYCL clothes — buffer lifetime is a performance decision.
6. Your SYCL program is correct on the CPU backend but you're told it "isn't really testing the GPU path." Is CPU-backend testing worthless? Where's its value and its limit?
It's far from worthless: the CPU backend runs the identical kernel source and the identical scheduling logic, so it validates your accessor intent, your dependency structure, and your algorithm's correctness — the parts most likely to have logic bugs — anywhere, with no GPU. Its limit is that it can't catch GPU-specific issues: occupancy, coalescing (5.7), shared-memory bank conflicts, or wavefront-width effects (D2) simply don't exist on a CPU. So CPU-backend testing is a fast, universal correctness gate (great for CI), but it is not a performance test and not a substitute for running on the actual target — the same "a test certifies the machine it ran on" principle from D2, applied to backends instead of vendors.
7. The interview closer: "When would you choose SYCL over HIP for a new project, and what do you give up?" Deliver the spoken skeleton.
"I choose SYCL when the project needs to run on more than two vendors or has a long lifetime across changing hardware, because single-source means one C++ codebase the compiler retargets — including a CPU backend that makes it testable anywhere. The big win beyond 'one source' is the scheduling: with buffers and accessors I declare which data each kernel reads and writes, and the runtime infers the dependency graph and overlaps independent work for me — it's 5.9's stream DAG, discovered instead of declared, so I can't forget a dependency edge. What I give up versus HIP is control and directness: HIP is CUDA-with-renames, so for a big existing CUDA codebase targeting mainly AMD, HIP is the lower-risk, closer-to-the-metal port. And SYCL's abstraction has a footgun — if I import CUDA's per-kernel-sync habit or over-declare accessor intent, I serialize work the runtime would have overlapped, and the performance bug is in what I declared, not what I called. So my rule: HIP for a CUDA-heavy, mostly-AMD port where I want control; SYCL when portability breadth and inferred scheduling across many backends outweigh the loss of explicit control — and either way I lean on the library reduction, never a hand-rolled shuffle tree, so I don't re-import the wavefront-64 bug.' That trade — control for breadth-plus-inference — is the whole decision."
