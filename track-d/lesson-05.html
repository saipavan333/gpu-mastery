WebGPU & WGSL — the universal GPU lab you already have installed

Every other backend in this track needs a driver, a toolchain, or specific hardware. WebGPU needs a browser — which means ~5 billion devices are now GPU-compute targets you reach with zero install. Today you will see that a WGSL compute shader is a CUDA kernel with decorators, run the 5.8 reduction on your own GPU from a web page, and learn the one discipline the browser forces on you: code to the guaranteed baseline, feature-detect everything else.

Concept

The universal lab: adapter to device to queue to pipeline

WebGPU is the modern, explicit successor to WebGL, and as of 2026 it ships in every major browser — Chrome and Edge (since 113), Firefox (141 on Windows, 145 on macOS), and Safari (26) — reaching roughly 82% of users. Its object model will feel familiar because it is the same shapes you learned on CUDA: you request an adapter (a physical GPU), get a device and its queue (5.9's stream), allocate buffers, bundle them into a bindGroup (the descriptors a shader sees), compile a WGSL computePipeline, and dispatchWorkgroups (5.2's grid launch). Under the hood two engines do the real work and — importantly — both run outside the browser too: Dawn (C++, powers Chrome, maps to D3D12/Metal/Vulkan) and wgpu (Rust, powers Firefox). That "standalone" fact is why WebGPU is a serious portability target, not just a web toy: the same WGSL runs in a browser tab, in a native app via wgpu/Dawn, and — for you, right now — in a lab page this site hosts.

WGSL: a CUDA kernel with decorators

Open the WebGPU Live Lab in this course and read its shader — it is the 5.8 reduction, and every line maps to something you know:

@group(0) @binding(0) var<storage, read> input: array<f32>;   // a buffer, bound to a slot
@compute @workgroup_size(256)                               // @workgroup_size == blockDim (5.2)
fn main(@builtin(global_invocation_id) gid: vec3<u32>, ...){ // gid.x == the 5.2 global index
    var<workgroup> scratch: array<f32, 256u>;                // var<workgroup> == __shared__ (5.5)
    scratch[lid.x] = sum;
    workgroupBarrier();                                     // workgroupBarrier() == __syncthreads()
    // ... tree reduction in shared memory, exactly 5.8 ...
}

The déjà vu is the whole point: @workgroup_size is your block dimension, global_invocation_id is the blockIdx*blockDim+threadIdx identity (5.2), var<workgroup> is shared memory (5.5), and workgroupBarrier() is __syncthreads() — with the same law that the barrier lives outside the divergence guard (5.6). You are writing the reduction you already wrote, in a language that is CUDA's concepts with a decorator syntax. The bind-group indirection (@group/@binding) is the one genuinely new idea, and it is just the explicit "which buffer is argument 0" wiring that CUDA did implicitly through kernel parameters.

The baseline versus extensions honesty

Portability at browser scale forces one hard discipline: the guaranteed feature set is deliberately small, and everything powerful is an optional extension you must check for. Shared memory (var<workgroup>) and workgroupBarrier are baseline — always there. But subgroups (WGSL's warp-shuffle equivalent) only shipped in Chrome 134 (February 2025) and are not universally available, so a portable kernel cannot assume them. timestamp-query (your 5.10-style GPU timing) has been in Chrome since 121, but its results are quantized to ~100µs for security, and it is an opt-in feature. f16 is common but not everywhere. The rule the browser enforces is exactly OpenCL 3.0's "features are optional, query them" (D4) and the same shape as any portable API: write to the baseline, then adapter.features.has('subgroups') before you touch an extension, with a baseline fallback path. This is the 90/10 tax (D1) in its purest form — the portable core is easy, and the fast-path features cost you a feature-detect-and-fallback branch.

Worked example

Task: Run the 5.8 reduction on your GPU from a web page and validate it against a CPU oracle — the fixture doctrine (M2 L6), in the browser. The Live Lab does exactly this; the numbers below were produced by simulating its two-level reduction (grid-stride workgroup partials, then a host sum of the 64 partials) at fp32. Prediction first: will a GPU fp32 tree reduction match a CPU fp64 sum bitwise, or only within a budget — and how big is the error on 1M random floats?

Prediction: NOT bitwise (fp32 tree order != fp64 serial order — M1 L8);
  within a budget of ~N*1e-3. For N=1M, expect error well under 1049.
Result (executed simulation of the lab's exact algorithm):
  N=64K : gpu 32759.6350  cpu 32759.6354  err 3.8e-4   within budget(66)   OK
  N=1M  : gpu 524594.8325 cpu 524594.8323 err 2.6e-4   within budget(1049) OK
  N=4M  : gpu 2095693.783 cpu 2095693.777 err 6.7e-3   within budget(4194) OK
  all-ones 1M -> gpu = 1048576 exactly (integer sums are exact in fp32 to 2^24)

What to internalize: three lessons converge here. First, the algorithm is identical to the CUDA reduction — grid-stride load (5.2), workgroup tree with a barrier (5.5/5.8), one partial per workgroup, final sum on the host — only the syntax changed, which is the entire thesis of Track D. Second, correctness is judged by budget, not bitwise (M1 L8): the GPU reduces in a different order than the serial CPU sum, so a few parts in 10^6 of disagreement is correct, and a test demanding equality would wrongly fail a right answer. Third, and this is what makes WebGPU special: you just ran this on real GPU hardware with no CUDA install, no driver setup, no cloud account — a web page reached your GPU. That is a genuinely new capability for teaching, demos, and shipping compute to users, and it is why this course can host its own lab.

Key points

  • WebGPU ships in every major browser (Chrome/Edge 113+, Firefox 141+, Safari 26+, ~82% of users) and its engines Dawn (C++) and wgpu (Rust) run standalone too — so the same WGSL targets the browser AND native apps.
  • WebGPU's object model is CUDA's shapes renamed: adapter/device/queue (5.9), buffers, bind groups (explicit argument wiring), a compiled pipeline, and dispatchWorkgroups (5.2).
  • WGSL is a CUDA kernel with decorators: @workgroup_size = blockDim, global_invocation_id = the 5.2 index, var<workgroup> = __shared__ (5.5), workgroupBarrier() = __syncthreads().
  • The 5.8 reduction runs unchanged in WGSL and matches a CPU oracle within an fp32 budget (executed: 2.6e-4 error on 1M), correctness judged by budget not bitwise (M1 L8) — provable live in the course's lab.
  • The guaranteed baseline is small — shared memory and barriers yes; subgroups (Chrome 134+), timestamp-query (Chrome 121+, quantized 100µs), and f16 are optional extensions.
  • Browser-scale portability forces the discipline "code to the baseline, feature-detect the rest" (adapter.features.has) with a fallback — OpenCL 3.0's optional-features model (D4) and D1's 90/10 tax in purest form.

Quiz

1. A developer writes a fast WGSL reduction using subgroupAdd (the warp-shuffle equivalent), tests it in Chrome where it flies, and ships. Bug reports flood in from Firefox and Safari users: the feature silently does nothing or the pipeline fails to create. What went wrong and what is the correct pattern?
Option 1 is factually wrong (all three ship WebGPU as of 2026). Option 4 misunderstands WGSL — it is compiled at runtime by each browser's engine, not per-browser by you. The correct answer names the mechanism (an optional extension used unconditionally) and the fix (feature-detect + baseline fallback), which is the browser edition of D4's "SVM is optional, query it" and D1's 90/10 tax: the portable core is free, the fast-path feature costs a detect-and-fallback branch. The general law: at browser scale, "works in my Chrome" certifies exactly one engine.
2. Your WebGPU reduction returns 524594.83 while the CPU fp64 sum returns 524594.8323 — they differ in the 7th digit. A teammate flags it as a GPU bug. Is it?
Option 4 is a factual trap: WebGPU's baseline is fp32, not fp64 (f16 is an extension, fp64 generally unavailable). Options 1/3 apply a bitwise-equality standard that M1 L8 spent a whole lesson dismantling — floating-point sums depend on order, and parallel reductions reorder by design. The correct answer is the reduction's correctness policy from 5.8 and 5.11, cross-vendor: budget-based fixtures, with the exact-integer case as the algorithm check. This is the same "do not expect bitwise across execution orders" lesson that governs every backend in this track.

Exercises

Exercise 1 — Open this course's WebGPU Live Lab in a WebGPU browser and run the reduction at all four sizes with both fills. Record your GPU's reported name, the absolute error at N=4M, and whether timestamp-query was available (and if so, the compute time). Confirm the all-ones case returns exactly N.

Expected: the reduction matches the CPU oracle within the budget at every size (error grows slowly with N because more fp32 adds accumulate rounding — M1 L8), and all-ones returns the exact N (integer sums are exact in fp32 up to 2^24). Whether you see a timing depends on your browser — Chrome exposes timestamp-query (quantized ~100µs); Safari/Firefox may not, in which case the lab honestly reports "n/a." The device name may be hidden by the browser for privacy (WebGPU deliberately limits fingerprinting) — that is expected, not a bug. Deliverable: your device string, the N=4M error, and the timing (or "n/a"). You just measured a GPU kernel from a web page — note how much less ceremony that was than a CUDA toolchain install (5.1).

Exercise 2 — Modify the lab's WGSL on your machine: change @workgroup_size(256) to 64 and 128 and observe whether the result stays correct and whether timing changes; then add a fused map (square each element before summing, computing the sum of squares). Predict each outcome before running.

Predictions and results: changing @workgroup_size keeps the result correct ONLY if you also update the shared array array<f32, 256u> and the initial halving stride to match the new size — otherwise the tree reads past the live data and you get a bug (a sharp lesson in matching shared-memory size to block size, 5.5). Timing may shift with occupancy (5.6) — smaller workgroups can mean more or less overlap depending on your GPU. Adding the square (sum = sum + input[i]*input[i]) is a fused map-reduce (Track A's fusion idea, A5) — it computes the sum of squares in the same passes, changing the answer but not the structure. Deliverable: a note on which change required also editing the shared-array size, and the sum-of-squares result checked against a CPU reference. The point: WGSL is editable and immediate — the browser is a real REPL for GPU compute.

Go deeper — the browser's GPU, in full

1. Buffers, bind groups, and the pipeline

concept          WebGPU object                 CUDA analogue
───────────────  ────────────────────────────  ─────────────────────────
device memory    GPUBuffer (usage flags)       cudaMalloc + purpose flags
kernel arguments  bind group (@group/@binding)  kernel parameters (implicit)
compiled kernel   GPUComputePipeline            a loaded kernel (5.1 module)
launch            pass.dispatchWorkgroups(n)    kernel<<<n, wgsize>>>()
readback          COPY_SRC -> MAP_READ buffer   cudaMemcpy D2H
the one new idea: buffers are explicitly TYPED by usage (STORAGE, COPY_DST,
MAP_READ...) — you declare what a buffer is FOR at creation, and the runtime
enforces it. It is 5.3's ownership discipline turned into required API flags.

The usage-flags system is WebGPU's safety model: a buffer you will read back on the CPU needs MAP_READ, a buffer a shader writes needs STORAGE, and you cannot map a storage buffer directly (hence the copy-to-a-readback-buffer step in the lab). It is more ceremony than cudaMemcpy, but it makes an entire class of misuse a validation error instead of undefined behavior — the same trade as WebGPU's overall design.

2. Baseline vs extensions, and honest timing

feature              status       detect with
───────────────────  ───────────  ─────────────────────────────────
var<workgroup> + barrier  BASELINE  always available
subgroups (warp ops)  extension    adapter.features.has('subgroups')   [Chrome 134+]
timestamp-query       extension    adapter.features.has('timestamp-query') [Chrome 121+]
f16                   extension    adapter.features.has('shader-f16')
timing caveat: timestamp-query is quantized to ~100µs (a security/fingerprinting
defense) — fine for "is this pass 3ms or 30ms" (5.10's regimes), useless for
sub-100µs microbenchmarks. Enable finer timing only behind a dev flag.

3. The same WGSL, outside the browser

Dawn (C++, Google)  and  wgpu (Rust, Mozilla)  are the two implementations —
and both are STANDALONE libraries. So WGSL/WebGPU is a native portability
target too:
  · a native app links wgpu/Dawn -> runs WGSL on D3D12/Metal/Vulkan under the hood
  · one shader language spans web delivery AND native apps
  · this is why WebGPU sits on D1's "portable API" rung alongside OpenCL, but with
    a cleaner, safer, more modern API and a browser distribution channel OpenCL lacks
takeaway: "WebGPU" is misnamed — it is a portable GPU API that happens to also
run in browsers, not a browser-only toy.

Gotchas

Assuming subgroups (or any extension) is present. subgroups shipped in Chrome 134 and are not universal; a pipeline requiring them fails where they are absent. Feature-detect and keep a baseline fallback (quiz 1).
Expecting bitwise-identical sums. WGSL is fp32 baseline and reductions reorder (M1 L8) — use budget fixtures, not equality (quiz 2). Demanding equality fails correct code.
Mapping a storage buffer directly. You cannot — storage buffers are not host-mappable. Copy to a separate MAP_READ buffer first (the lab's readBuf). The usage flags enforce this at validation time.
Trusting timestamp-query for microbenchmarks. It is quantized to ~100µs for security, so sub-100µs measurements are meaningless. Use it for pass-level regimes (5.10), not fine timing, unless a dev flag lifts the quantization.
Barrier inside a divergence guard. workgroupBarrier() must be reached by all invocations in the workgroup — putting it inside if (lid.x < s) is 5.6's classic deadlock/UB, same law as __syncthreads(). Keep the barrier outside the guard (the lab does).
Shared-array size not matching workgroup size. var<workgroup> scratch: array<f32, 256u> must match @workgroup_size(256) and the reduction's starting stride — change one, change all three, or the tree reads garbage (Exercise 2's trap).

Scenario — the demo that only worked on the presenter's laptop

A team builds an in-browser image-processing demo — GPU-accelerated filters via WebGPU — to show at a conference. It is beautiful on the developer's Chrome, so they ship the demo link. At the conference, half the audience opening it on Safari and Firefox see either a blank canvas or a console full of pipeline-creation errors. The post-mortem finds two baseline-versus-extension sins. First, a blur kernel used subgroupAdd for a fast reduction because "it made the FPS counter look great" — a Chrome-134 extension that simply is not there on the other engines, so the pipeline failed to create and the whole render fell over. Second, they had used timestamp-query to drive an on-screen profiler overlay and required the feature unconditionally, so browsers without it crashed at startup. The fix is the discipline this lesson exists to teach: check adapter.features.has(...) for every non-baseline feature, request only what is present, and provide a baseline path (a var<workgroup> + workgroupBarrier reduction that runs everywhere; a profiler overlay that hides itself when timing is unavailable — exactly what the course's lab does when it reports "n/a"). Shipped again, the demo runs on every engine, a little slower where subgroups are missing, which is the 90/10 tax paid honestly. The moral is WebGPU's version of D2's "a test certifies the machine it ran on": "works in my browser" certifies one engine, and browser-scale portability means your baseline path is the product — the extensions are garnish you must be able to live without.

Practice

1. Translate each to WGSL: <<<64, 256>>>, __shared__ float s[256], __syncthreads(), threadIdx.x, blockIdx.x*blockDim.x+threadIdx.x.
Launch: @compute @workgroup_size(256) in the shader + dispatchWorkgroups(64) on the host (the split is deliberate — block size is a shader decorator, grid size is a host call). Shared: var<workgroup> s: array<f32, 256u>;. Barrier: workgroupBarrier(). threadIdx.x: local_invocation_id.x. Global index: global_invocation_id.x. Every row is D1's translation table — the reduction you wrote in 5.8 ports by renaming, exactly as the lab shows.
2. Why must a WebGPU app feature-detect subgroups but not workgroupBarrier?
Because workgroupBarrier and var<workgroup> shared memory are part of WebGPU's guaranteed baseline — every conformant implementation has them — while subgroups are an optional extension that shipped in Chrome 134 and is not present on all engines/devices. Requesting a device or creating a pipeline that requires subgroups fails where the feature is absent, so you must query adapter.features.has('subgroups') and fall back to a baseline reduction. The baseline never needs detection (it is the contract); extensions always do (they are privileges). Same model as OpenCL's optional features (D4).
3. Explain why the lab copies partials to a separate buffer before reading them on the CPU, instead of mapping the storage buffer directly.
WebGPU's usage flags forbid it: a buffer used as STORAGE (writable by the shader) cannot also be host-mapped for reading — those usages are mutually exclusive by design, to keep the memory model safe and let the driver place buffers optimally. So the pattern is: shader writes the STORAGE | COPY_SRC partials buffer, an encoder command copies it into a separate COPY_DST | MAP_READ buffer, and only that second buffer is mapped on the CPU. It is more steps than cudaMemcpy, but the flags make illegal access a validation error instead of undefined behavior — WebGPU's safety-over-brevity trade (Go-deeper section 1).
4. WebGPU baseline is fp32. What does that mean for porting an fp16-heavy ML kernel (Track A's mixed precision) to the browser?
You cannot assume f16 — it is the shader-f16 extension, present on many but not all devices — so a portable browser port either feature-detects f16 and falls back to fp32, or accepts fp32 throughout. That has real consequences from Track A's A6: no baseline tensor-core-style fp16 accumulation, larger memory traffic (fp32 is 2x the bytes of fp16 — 4.6), and different numeric budgets (M1 L8). The honest plan mirrors the whole track: get correctness on the fp32 baseline everywhere, then use f16 as a detected fast path where available. "Portable ML in the browser" means baseline-fp32 first, f16 as garnish.
5. A native desktop app wants one GPU codebase for Windows, macOS, and Linux without writing D3D12/Metal/Vulkan three times. How does WebGPU help without a browser involved?
By linking Dawn (C++) or wgpu (Rust) as a standalone library: both implement WebGPU/WGSL natively and map to D3D12 on Windows, Metal on macOS, and Vulkan on Linux under the hood. So the app writes WGSL and WebGPU API calls once, and the library translates to each platform's native GPU API — no browser, no three-way rewrite. This is why WebGPU sits on D1's "portable API" rung as a genuine native option (Go-deeper section 3): the "Web" in the name undersells it. The trade vs Vulkan-directly is a slightly higher-level, safer API for a small abstraction cost — the usual 90/10.
6. On the lab, the all-ones sum is exact but the random-fill sum differs from fp64 in the 7th digit. Reconcile these two facts with one principle.
One principle: fp32 represents integers exactly up to 2^24, but real-valued sums are order-dependent because fp32 addition is non-associative (M1 L8). All-ones sums are integer additions staying well under 2^24, so every partial and the final total are exact — no rounding to disagree about. Random floats accumulate rounding at each of the ~million adds, and the GPU's tree order rounds differently than the CPU's serial fp64 order, producing a few parts in 10^6 of disagreement that is correct, not buggy. Same reduction, two inputs, one rule: exactness is about magnitude and integer-ness; the 7th-digit wobble is about floating-point order — which is why fixtures use budgets (quiz 2).
7. The interview closer: "Why is the browser a legitimate GPU-compute target, and when would you actually ship WebGPU?" Deliver the spoken skeleton.
"WebGPU is legitimate because it is a real, explicit GPU API — compute shaders, storage buffers, workgroups, shared memory, barriers — not a graphics toy, and WGSL is genuinely just CUDA's concepts with decorators: @workgroup_size is blockDim, global_invocation_id is the thread index, var<workgroup> is shared memory, workgroupBarrier is __syncthreads. It ships in every major browser now, ~82% of users, and crucially its engines Dawn and wgpu run standalone, so the same WGSL targets native apps across Windows, macOS, and Linux without writing D3D12/Metal/Vulkan three times. I would ship WebGPU when I want zero-install distribution — an in-browser demo, tool, or client-side inference that reaches any device with a link — or when I want one GPU codebase across web and native. What I plan around is the baseline: the guaranteed feature set is small, so I code to var<workgroup> and barriers and feature-detect subgroups, f16, and timestamp-query with a fallback, because 'works in my Chrome' certifies exactly one engine. And I judge correctness by budget, not bitwise — it is fp32 and reductions reorder. So: WebGPU for reach and web-plus-native portability, with the discipline that my baseline path is the actual product and the extensions are a fast path I can live without.' That baseline-first discipline is the hire signal — it shows I have shipped to more than my own laptop."
