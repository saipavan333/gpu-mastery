The All-Reduce Visualizer

Training on many GPUs means every GPU computes a gradient on its own slice of the batch, and then all of them must agree on the sum before the next step. That operation is called an all-reduce, and how you do it decides whether adding GPUs makes training faster or just moves the bottleneck around. Step through the two classic approaches on a ring of GPUs and watch where the bytes actually go.

How to read it

Every GPU starts with its own full gradient. In the ring, the gradient is cut into N chunks, and the work happens in two laps around the ring. In the first lap — reduce-scatter — each GPU sends one chunk to its right neighbor and adds the chunk it receives from the left, every step, for N−1 steps. When the lap finishes, each GPU owns exactly one chunk that is the complete sum across all GPUs (watch a single cell in each node climb to N contributors and turn green). The second lap — all-gather — passes those finished chunks around the ring so everyone ends up with all of them. Two laps of N−1 steps, each step moving one chunk of size D/N, so every GPU moves exactly 2(N−1)/N · D bytes — and crucially, every link carries the same load. There is no hotspot.

The parameter server is the obvious first idea and the reason people move away from it. Every worker sends its whole gradient to one central server, the server adds them and sends the result back to everyone. Simple — but the server's single link has to carry (N−1) · D bytes inbound and another (N−1) · D outbound, while each worker only moves 2D. Add GPUs and the ring's per-GPU cost barely changes (it climbs from D toward 2D and stops), but the server's link cost grows without limit. At N GPUs the server bottleneck is N/2× the ring's per-GPU traffic. That single fact — 2(N−1)/N · D, independent of N, balanced everywhere — is why NCCL, PyTorch DistributedDataParallel, and Horovod all use ring/tree all-reduce, and why MPI_Allreduce (Track B) is built the same way. Both approaches compute the identical sum; only the traffic pattern differs.

This is the multi-GPU echo of a single-GPU lesson: performance at scale is a communication problem, not a compute one. The gradient sum is cheap arithmetic; the whole game is moving bytes without creating a chokepoint — the same roofline instinct from Lesson 4.7, now between GPUs instead of between an SM and its memory. Track A's Lesson A8 uses the 2(N−1)/N term to size real training runs; this lab is where you can feel why it holds.
