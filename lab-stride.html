The Stride Cliff — coalescing, measured on your GPU

Lesson 5.7 claims that reading memory with a stride wrecks bandwidth, because the GPU fetches whole aligned sectors and a strided access wastes most of each one. This lab stops asserting it and measures it: the same kernel reads the same number of values from a big buffer, but with a growing stride between neighboring threads. Watch the achieved bandwidth fall off a cliff toward the 1/8 floor that fp32's 32-byte sector predicts — on your own hardware.

How to read it

Every bar reads exactly the same number of floats — only the pattern changes. At stride 1, neighboring threads read neighboring floats, so a warp's reads fall in a few consecutive 32-byte sectors and coalesce: almost every byte the memory system fetches is used, and you get close to peak bandwidth. As the stride grows, neighboring threads land in different sectors, so the hardware still fetches a full 32-byte sector but you use only 4 bytes of it (one fp32). Beyond a stride of 8 floats (32 bytes), essentially every access wastes 7/8 of its sector, and achieved bandwidth floors at roughly 1/8 of peak — the executed cliff Lesson 5.7 predicts. (The exact floor and shape depend on your GPU's cache and sector policy; the trend is universal.)

This is the single most valuable performance lesson in CUDA, and it is the direct GPU descendant of the CPU cache-line story from Lesson 0.2: on both machines, victory comes from marching through memory the way the hardware fetches it. The fix in real kernels is to arrange threads so consecutive lanes touch consecutive addresses — coalesced access — or to stage data through fast on-chip shared memory so the strided pattern is paid only once. Play with the Coalescing Visualizer to see the sectors themselves, then come here to feel the bandwidth cost.

The kernel (WGSL)

One thread per element, each reading K values from the buffer stride floats apart, accumulating so the compiler can't delete the loads. Only stride changes between runs.
