The CPU — built for latency

Last lesson we found the villain: waiting on memory. The CPU is a machine built around one obsession — finish the task in front of it as fast as humanly (electronically) possible, which means never waiting if it can help it. Understanding how it fights the wait, and what that costs, is the perfect mirror for understanding the GPU, which makes the opposite bet.

Concept

The CPU's one goal: low latency

Latency is the time to finish a single task, start to end. A CPU is engineered to make that time as small as possible: open your laptop, click a link, run a script — you want the answer now, and usually there's only one main thing to do at a time. So the CPU pours nearly all of its ingenuity into a single question: how do I keep one instruction stream racing forward without ever stalling? Almost every famous CPU feature — caches, branch prediction, out-of-order execution — is an answer to that one question.

Keep this word latency close. The GPU (next lesson) optimizes a different word — throughput — and essentially every difference between the two machines flows from that one choice of what to make fast.

Caches: keep the data close so you rarely wait

Reaching main memory costs ~100 nanoseconds (Lesson 0.1). The CPU's headline weapon against that is the cache: small, extremely fast memories that sit right next to the core and hold recently-used data. If the number you need is already in the cache — a cache hit — you skip the long trip entirely and get it in a nanosecond or few. Modern CPUs stack several cache levels, each bigger and slower than the last:

Representative desktop-CPU figures. Each level up the ladder is roughly 3–10× slower but far larger. The whole art is arranging your data so most accesses are caught by the fast, small levels.

Caches work because real programs are predictable: they tend to reuse the same data soon (temporal locality) and to touch neighboring data next (spatial locality). A cache bets on both — when you ask for one byte it quietly grabs a whole neighboring chunk (a cache line, typically 64 bytes), guessing you'll want the neighbors too. When the guess is right, memory feels 100× faster than it is. When it's wrong — a cache miss — you pay the full ~100 ns. Writing cache-friendly code is one of the highest-leverage skills in all of computing, and it has a direct GPU cousin you'll meet in Lesson 5.7 (coalescing).

Branch prediction: guess so the pipeline never stalls

Recall the pipeline from 0.1: the core is an assembly line fetching future instructions before finishing current ones. A branch (if) threatens it — until the condition is computed, the core doesn't know which instructions come next. Rather than wait, a CPU guesses which way the branch will go and speculatively runs ahead. Modern predictors are startlingly good (well above 95% on typical code) because branches are habitual — a loop's "keep going?" test says "yes" thousands of times before the one "no." Guess right and there's no stall at all; guess wrong and the core throws away the speculative work and restarts — a real but occasional cost.

Out-of-order & superscalar: do more than one thing per tick

A CPU core doesn't run instructions in strict order at one-per-tick. It is superscalar (it has several execution units, so it can start multiple independent instructions in the same tick) and out-of-order (if the next instruction is stuck waiting on memory, it looks ahead and runs later instructions that are ready, then sorts the results out). This squeezes extra speed from a single instruction stream — called instruction-level parallelism — but there's a ceiling: one stream only contains so many independent instructions to overlap, and finding them costs a lot of transistors and power.

The shape this produces: a few big, clever cores

Add it up and a CPU core is mostly not arithmetic. The bulk of its silicon and energy goes to the machinery that avoids stalls — caches, branch predictors, reorder buffers, schedulers — wrapped around a relatively small set of arithmetic units. Because each core is so large and power-hungry, a chip only fits a handful of them (a typical laptop has, say, 4–16). They are a few Formula-1 cars: extraordinary at getting one driver around the track as fast as possible.

Proportions are illustrative, but the message is real: a CPU core spends most of its silicon on not waiting (control + cache), and relatively little on arithmetic. That is the price of low latency — and precisely the budget the GPU spends differently.

Why this is the wrong tool for a million identical jobs

All this cleverness is perfect when you have one urgent, unpredictable, branchy task. But now imagine the Lesson 0.1 job: add two arrays of a billion numbers. There are no clever branches to predict, no reuse to cache cleverly — just a billion identical, independent little sums. A CPU's Formula-1 machinery is wasted here; you don't want one incredibly fast driver, you want ten thousand ordinary ones each carrying a parcel. That realization is the whole reason the next lesson exists.

Worked example

Task: A loop reads one million values from memory. On our representative CPU, an access costs ~1 ns if it hits L1 cache and ~100 ns if it misses to main memory. Compare the total read time at a 95% hit rate versus a 5% hit rate, and draw the lesson.

1 — 95% hits (cache-friendly): 950,000 × 1 ns + 50,000 × 100 ns = 0.95 ms + 5 ms ≈ 5.95 ms.

2 — 5% hits (cache-hostile): 50,000 × 1 ns + 950,000 × 100 ns = 0.05 ms + 95 ms ≈ 95 ms.

3 — the punchline: same code, same million reads, same CPU — but a ~16× difference in run time, decided entirely by whether your data access pattern is friendly to the cache. The arithmetic never changed; only the data movement did (exactly the theme from 0.1).

Decision made: this is why experienced engineers restructure loops to march through memory in order (spatial locality) and reuse data while it's hot (temporal locality). The same instinct, transplanted to the GPU, becomes memory coalescing — and it is worth roughly the same 8–16× there. Data layout is not a detail; it is often the whole game.

Key points

  • The CPU optimizes latency — the time to finish one task — because that's what interactive, mostly-serial workloads need.
  • Caches (L1/L2/L3) are small fast memories that exploit locality; a hit is ~100× faster than main memory. Cache-friendly data layout can swing real programs by 10× or more.
  • Branch prediction guesses the direction of ifs so the pipeline never stalls; it's right >95% of the time on typical code, and a misprediction costs a pipeline flush.
  • Superscalar + out-of-order execution extracts instruction-level parallelism from one stream, but a single stream has a hard ceiling on how much independent work it contains.
  • All this makes a core big and power-hungry and mostly not arithmetic — so a CPU has only a handful of cores. A few Formula-1 cars, not a swarm.
  • For one urgent branchy task, this is ideal. For a million identical independent tasks, it's the wrong shape — which is the door the GPU walks through.

Quiz

1. What does it mean that a CPU is optimized for "latency"?
Latency is time-to-finish-one-task. The CPU's caches, branch predictors, and out-of-order machinery all exist to race a single instruction stream forward without stalling. "Most tasks per second regardless of individual speed" describes throughput — the GPU's goal, next lesson.
2. Most of a CPU core's silicon area is spent on…
A CPU spends the bulk of its transistors and energy on caches, branch prediction, and scheduling — everything needed to keep one stream from stalling. Only a small fraction is arithmetic. The GPU flips this budget, spending most of its area on arithmetic units.

Exercises

Exercise 1 — Define temporal and spatial locality in one sentence each, and give an everyday code example of each.

Temporal locality: data used recently is likely to be used again soon — e.g. a loop counter or an accumulator variable touched every iteration. Spatial locality: data near recently-used data is likely to be used soon — e.g. walking through the elements of an array a[0], a[1], a[2]… in order, where each cache line brings in several neighbors at once. Caches exploit both: they keep hot data and prefetch neighbors.

Exercise 2 — A branch predictor is right 97% of the time; a misprediction wastes ~15 cycles. On average, how many cycles does a branch cost in wasted work? Why does this favor loops?

Average waste = 0.03 × 15 ≈ 0.45 cycles per branch — almost free. Loops are ideal for predictors because the loop-back branch is taken many times in a row before the single "exit" — a highly regular pattern the predictor learns instantly. Unpredictable, data-dependent branches (e.g. if (random_value > x)) are the ones that hurt, and — foreshadowing 0.3 — they hurt GPUs far more.

Exercise 3 — Using the worked example's numbers, at what cache hit rate does the million-read loop take about 20 ms?

Let h be the hit rate. Time (ms) ≈ 1,000,000 × [h × 1 ns + (1−h) × 100 ns] = h + 100(1−h) in milliseconds… let's keep units: total ns = 10⁶[h·1 + (1−h)·100] = 10⁶[100 − 99h] ns = [100 − 99h] ms. Set 100 − 99h = 20 → 99h = 80 → h ≈ 0.808, about an 81% hit rate. Notice how nonlinear it is: going from 81% to 95% hits nearly halves the time again, because every avoided miss is worth ~100 hits.

Go deeper — the complete guide

The card makes the CPU's strategy clear. This chapter sharpens the numbers and the limits, so that when the GPU makes the opposite choice next lesson, you'll feel exactly what it's trading away.

1. The memory hierarchy, with numbers

Approximate figures for a modern desktop CPU (they vary by chip, but the ratios are the point):

LevelTypical latencyTypical sizeIdea
Registersimmediatea few KB totalthe only place math happens
L1 cache~1 ns (~4 cycles)~32–64 KB per corehottest data, split for code/data
L2 cache~4 ns (~12 cycles)~256 KB–2 MB per coreoverflow from L1
L3 cache~15–40 ns~8–64 MB sharedshared across cores
Main memory (DRAM)~80–120 ns~8–128 GBthe slow, big backstop
SSD storage~50,000–100,000 ns~TBspersistent; another world away

The jaw-dropping row is the last: an SSD is roughly a thousand times slower than main memory, which is itself ~100× slower than a cache hit. The processor lives at the top of a cliff of speed, and every level down is a plunge. This is why "just read it from disk each time" is never a plan, and why a GPU carries its own dedicated high-speed memory (Lesson 0.3).

2. Locality, and the cache line

When you read one byte, the cache fetches an aligned 64-byte line containing it. This is a bet on spatial locality, and it has a sharp consequence: reading an array in order gets ~63 free neighbors per miss, while reading it in a scattered order can miss on nearly every access. The classic demonstration is looping over a 2D array in row-major order versus column-major order — same data, same total reads, but the row-major version can be several times faster purely because it walks memory the way the cache lines are laid out. Every serious performance story eventually comes back to "am I moving through memory the way the hardware wants?"

3. Speculation: fast, but not free, and not without risk

Branch prediction is one form of speculation — doing work before you're sure you need it. CPUs speculate aggressively because on average it wins big. But it has two costs worth knowing. First, a misprediction wastes the speculative work and refills the pipeline (tens of cycles). Second — a modern twist — speculation can be a security issue: the Spectre and Meltdown class of vulnerabilities (2018) exploited traces that speculative execution left in the cache. You don't need the details now; the takeaway is that the CPU's cleverness is deep enough to have surprising side effects, and that "guess and maybe undo" is a fundamentally different philosophy from the GPU's "bring so much work that guessing is unnecessary."

4. The ceiling on instruction-level parallelism

Out-of-order execution overlaps independent instructions from one stream. But how many independent instructions are there to find? In typical code, not that many — real programs are full of dependencies (this result feeds that one). Decades of research show that squeezing more parallelism from a single stream yields diminishing returns while costing rapidly more transistors and power. That wall is central: once you can't make one stream go much faster, and you can't raise the clock (the power wall from 0.1), the only road left is more streams — more cores, more threads. The CPU took a few steps down that road; the GPU built a superhighway on it.

5. Why the CPU can't just "add thousands of cores"

If more cores is the answer, why doesn't a CPU simply ship 5,000 of its cores? Because each CPU core is enormous — all that cache and control logic — and power-hungry. Thousands of them wouldn't fit on a chip or within any sane power and heat budget. To put thousands of cores on one chip, you must make each core small and simple: strip out the big private caches, the fancy branch predictor, the out-of-order machinery. But a stripped-down core stalls constantly on memory and mispredicts branches — unless you change the entire strategy so that stalling doesn't matter. That change of strategy is the GPU, and it's the subject of the next lesson.

Gotchas

"More cores always means faster." Only if your task splits into independent pieces. A single-threaded, dependency-heavy task runs on one core no matter how many the chip has; this is Amdahl's law, which we'll make precise in 0.4.
Ignoring the cache line. Touching one byte pulls in 64. Data structures that scatter related fields across memory waste most of every line; packing hot fields together (or choosing arrays-of-structs vs structs-of-arrays wisely) is a real speedup, on CPU and GPU alike.
Assuming caches make memory "fast." They make predictable reuse fast. Stream through data larger than the cache exactly once — as many scientific and AI kernels do — and the cache barely helps; you're back to raw memory bandwidth, and bandwidth (not latency) becomes the limit. That regime is exactly where GPUs shine.
Benchmarking with tiny data. A loop over 1,000 elements fits entirely in L1 and looks lightning-fast; the same code over 100 million elements tells a completely different, memory-bound story. Always test at realistic sizes.

Scenario — the loop that got 10× faster without changing the math

An engineer profiles an image filter that crawls. The inner loop walks the image column by column — for x: for y: process(pixel[y][x]) — because that felt natural. But the image is stored row by row in memory, so each step jumps a whole row's width ahead, landing on a fresh cache line almost every time: near-100% miss rate. She swaps the loop order to for y: for x so it marches along memory the way it's laid out. Now each 64-byte line serves ~16 consecutive pixels before the next miss. The arithmetic is byte-for-byte identical; only the access order changed — and the filter runs roughly 10× faster. She didn't optimize the computation at all; she stopped fighting the cache. This is the CPU's entire personality in one story: it will reward you enormously for feeding it data in a predictable, local order, and punish you for scattering it. Hold onto that instinct — on the GPU, the very same instinct (with the very same payoff) is called coalescing, and it is one of the most valuable things this course will teach you.

Practice

1. In one sentence, why does a CPU devote most of its area to caches and control rather than arithmetic?
Because its goal is low latency for one mostly-serial stream, and the biggest threat to that is waiting on memory and stalling on branches — so most of its silicon is spent preventing those waits (caches, predictors, out-of-order scheduling), leaving arithmetic a small slice.
2. A task is 1 million independent square-roots. Argue briefly whether a CPU's fancy features (branch prediction, out-of-order, big caches) help much here.
They help very little. There are essentially no branches to predict (it's a straight-line computation), little reuse for caches to exploit (each value is read once), and the parallelism is across the million tasks, not within one stream — which out-of-order execution can't reach. This is a throughput problem wearing a latency machine's clothes: the ideal hardware is many simple cores, i.e. a GPU.
3. Estimate: streaming once through a 4 GB array that does not fit in cache, at ~20 GB/s effective memory bandwidth, takes about how long — and does adding L3 cache change it much?
4 GB ÷ 20 GB/s = ~0.2 s, set entirely by bandwidth since each byte is read once and the array dwarfs the cache. Adding or enlarging L3 barely helps — there's no reuse for it to capture. This "streaming, bandwidth-bound, cache doesn't help" regime is extremely common in AI and scientific computing, and it's precisely where the GPU's huge memory bandwidth (Lesson 0.3 and Module 4) pays off.
4. Why are unpredictable, data-dependent branches especially bad — and why should you remember this before we reach the GPU?
Unpredictable branches defeat the branch predictor, causing frequent pipeline flushes (tens of wasted cycles each). On a CPU that's a moderate tax. On a GPU, as you'll see in 0.3, threads run in lockstep groups, and a data-dependent branch can force the group to execute both sides — a much steeper penalty called divergence. Learning to avoid branchy inner loops now pays off doubly later.
5. Reflection: state the CPU's core bet in one sentence, and predict the GPU's opposite bet.
The CPU bets that you have a few urgent, unpredictable tasks, so it spends its silicon making a small number of streams as fast as possible (caches, prediction, out-of-order) to minimize latency. The GPU will bet the opposite: that you have an ocean of identical independent tasks, so it will spend its silicon on a huge number of simple arithmetic units and hide memory waits by always having other work ready — maximizing throughput even if any single task is slow.
