What a computer actually does — instructions, clocks & the fetch–execute loop

A GPU is a special kind of computer, so before we can see what makes it special, we need a clear picture of what any computer does. It all comes from one humble idea: a processor reads a list of absurdly simple instructions and carries them out, one after another, billions of times a second. Get this picture right and every later idea — cores, threads, memory bandwidth, the whole reason GPUs exist — has somewhere to attach.

Concept

A program is a list of absurdly simple steps

It's tempting to imagine a computer "understands" your spreadsheet or your game. It doesn't. Underneath, a processor only knows a small menu of tiny operations: copy this number from memory into me, add these two numbers, compare them, if the result is zero, jump to a different instruction, write this number back to memory. That's roughly the whole vocabulary. A real program is millions of these tiny steps in a row.

The magic isn't cleverness per step — each step is something a schoolchild could do. The magic is speed and quantity: a modern core does billions of these steps every second without ever getting bored or making a mistake. "Adding two lists of a million numbers" isn't one operation to a computer; it's a million rounds of load, load, add, store.

This is the single most useful mental shift for this whole course: stop thinking "the computer does my task" and start thinking "the computer does billions of trivial steps, and my task is a way of arranging them." A GPU is just a machine that does a staggering number of trivial steps at the same time.

The fetch–execute loop — the heartbeat of every processor

How does the processor know which tiny step to do next? It keeps a bookmark called the program counter (PC) — the memory address of the next instruction. Then it repeats one loop forever:

The fetch–execute cycle. The program counter is the bookmark; every loop, structure like "if" and "for" is just an instruction that changes it.

Fetch the instruction the PC points at, figure out what it means, do it, save the result, move the PC to the next instruction, and go again. Branches (if) and loops (for) are nothing mystical — they are just instructions that write a new address into the PC, so the next fetch comes from somewhere else.

The clock — what "3 GHz" actually measures

A processor has a metronome called the clock. Every tick, the machine advances a little. "3 GHz" means three billion ticks per second — so one tick lasts about one-third of a nanosecond (a nanosecond is a billionth of a second). For intuition: in the time light takes to cross a room (~3 ns for a meter), a 3 GHz core has already ticked about ten times. These machines are fast beyond ordinary intuition.

A tempting mistake is "more gigahertz = faster computer." It isn't that simple, and the reasons why are the entire story of this course. Two of them right now: not every instruction finishes in one tick (a memory read can cost hundreds of ticks), and a chip can do more than one thing per tick if it has more hardware. Hold that thought — it's the door the GPU walks through.

Memory: a giant wall of numbered boxes

The instructions and the data both live in memory (RAM): think of it as one enormous row of boxes, each holding one byte, each with a number — its address. The processor is a separate chip from the memory. To add two numbers, the core must first haul them across the gap from memory into itself, and later push the result back.

The von Neumann gap. Arithmetic is almost free; moving data across the bus is the slow, expensive part — roughly a hundred times slower than the add that consumes it.

Here is the punchline that the rest of the course keeps returning to: the arithmetic is cheap; moving the data is expensive. Adding two numbers takes well under a nanosecond, but reaching all the way out to main memory for a number can cost on the order of a hundred nanoseconds. A processor that had to wait for every memory access would spend nearly all its time idle. Every fast computer — CPU or GPU — is, at heart, an elaborate scheme to avoid waiting on memory.

Why this matters for GPUs

A GPU runs the same fetch–execute loop. Nothing about it is magic. The difference is a design choice we'll unpack over the next five lessons: instead of one very clever core that tries hard not to wait, a GPU packs in thousands of simpler cores and keeps them busy by always having other work ready whenever one is waiting on memory. Same heartbeat, multiplied by thousands, and organized entirely around feeding them data. To understand that choice, we first have to meet its opposite — the CPU — which is the next lesson.

Worked example

Task: A single 3 GHz core adds two lists of one billion numbers, element by element. Roughly how long does it take if we pretend each add is one clock tick — and then, why is that estimate wildly optimistic?

1 — the naive compute estimate: one billion adds ÷ three billion ticks per second = 0.33 seconds. That is the best case, counting only the arithmetic.

2 — the hidden cost: each add first needs two numbers read from memory and one result written back — three memory trips per add. If a memory trip can stall the core for ~100 ns and nothing hides that wait, a billion elements could stall for many seconds, not a third of one. The adder was never the bottleneck; the bus was.

3 — the two ways out: (a) keep data close so you rarely pay the full memory cost — this is what caches do, and it's the CPU's whole personality (Lesson 0.2). (b) When one core stalls on memory, have thousands of other threads ready to run so the hardware is never idle — this is the GPU's whole personality (Lesson 0.3).

Decision made: "just buy a higher-GHz CPU" barely helps here, because the core is mostly waiting, not computing. The real levers are keeping data close and doing many things at once — which is exactly why the industry turned to parallel hardware like GPUs.

Key points

  • A processor knows only a tiny menu of trivial operations (load, add, compare, jump, store). A program is millions of these in a row; the power is speed and quantity, not cleverness per step.
  • Every core repeats the fetch–execute loop: fetch the instruction the program counter points to, decode, execute, write back, advance the PC, repeat. if and for are just instructions that change the PC.
  • The clock sets the pace: 3 GHz ≈ 3 billion ticks/second ≈ one tick every ⅓ nanosecond. But "more GHz" is not the same as "faster" — that's the rest of the course.
  • Memory is a huge array of numbered bytes on a separate chip. The processor must haul data across a bus to work on it.
  • The defining imbalance: arithmetic is nearly free (<1 ns); a trip to main memory is ~100× slower. Fast computers are elaborate schemes to avoid waiting on memory.
  • A GPU is the same loop times thousands, designed so that while some cores wait on memory, others keep working — turning the memory-wait problem into an opportunity.

Quiz

1. What does the program counter (PC) hold?
The PC is the processor's bookmark — the address of the next instruction. Loops and branches work by writing a new address into it, which is why "jump" is all you need to build if and for.
2. On a modern machine, roughly how do the costs of "add two numbers already in the core" and "fetch a number from main memory" compare?
Arithmetic is well under a nanosecond; a main-memory fetch is on the order of ~100 ns. This imbalance — cheap math, expensive data movement — is the reason both caches (CPU) and massive multithreading (GPU) exist.

Exercises

Exercise 1 — In one sentence each, describe what "fetch," "decode," "execute," and "write back" do, and say which one a for-loop secretly changes.

Fetch: read the instruction stored at the address in the program counter. Decode: work out what that instruction means and which data it needs. Execute: perform the operation (e.g. add). Write back: store the result into a register or memory. A for-loop changes the program counter: at the bottom of each pass it jumps the PC back to the top of the loop body, so fetch pulls the same instructions again.

Exercise 2 — A 2 GHz core executes one instruction per tick with no memory stalls. How many instructions does it run in one millisecond? Why is the real number usually lower?

2 GHz = 2 × 10⁹ ticks/second, so in 1 ms (10⁻³ s) it manages 2 × 10⁹ × 10⁻³ = 2 million instructions. The real number is usually lower because instructions don't all finish in one tick — memory accesses in particular can stall the core for tens or hundreds of ticks while it waits for data to arrive across the bus.

Exercise 3 — Explain, using only ideas from this lesson, why "just double the clock speed" is a weak way to make the array-adding example faster.

In that example the core spends most of its time waiting for numbers to arrive from memory, not doing arithmetic. Doubling the clock makes the arithmetic (already the cheap part) twice as fast, but it does little for the waiting, which is set by memory latency, not by the core's clock. You'd pay for a faster metronome and still stand around idle. The effective fixes are keeping data close (caches) or overlapping many memory waits at once (parallel threads) — the CPU and GPU strategies we meet next.

Go deeper — the complete guide

The card above makes you functional. This chapter makes the picture precise: what an instruction really is, how the loop pipelines, why the clock is only part of speed, and how the memory wall bends the entire history of computing hardware toward parallel machines like the GPU.

1. What an instruction really is

The menu of operations a particular processor understands is its instruction set architecture (ISA) — x86-64 on most laptops and desktops, ARM on phones and Apple Silicon, and a GPU has its own internal ISA underneath CUDA. An instruction is just a number: a pattern of bits the decode stage reads as "which operation" plus "which registers/addresses." A tiny, illustrative sequence to add two numbers from memory and store the result:

LOAD  r1, [0x1000]     ; copy the number at address 0x1000 into register r1
LOAD  r2, [0x1004]     ; copy the number at address 0x1004 into register r2
ADD   r3, r1, r2       ; r3 = r1 + r2   (this is the cheap part)
STORE [0x1008], r3     ; write r3 back out to address 0x1008

Registers (r1, r2, r3 above) are a handful of tiny storage slots inside the core — the only place arithmetic can actually happen. They are astonishingly fast and astonishingly few (on the order of dozens). Almost everything a processor does is a dance of pulling data from slow memory into fast registers, computing, and pushing results back out. Keep that dance in mind — in Module 5 you'll discover a GPU thread has its own private registers, and running out of them is a real performance limit.

2. The loop, pipelined

Doing fetch → decode → execute → write-back strictly one-at-a-time would waste hardware: while the execute unit works, the fetch unit sits idle. Real cores pipeline — like an assembly line, they fetch instruction 4 while decoding instruction 3, executing instruction 2, and writing back instruction 1. Done well, a pipelined core finishes roughly one instruction per tick even though each instruction takes several ticks end-to-end.

Pipelining has a villain: branches. When the core reaches an if, it doesn't yet know which way execution goes, so it doesn't know which instruction to fetch next. Guess wrong and the half-built assembly line must be flushed and refilled — wasted work. CPUs spend enormous effort predicting branches (Lesson 0.2); GPUs, tellingly, handle branches very differently, and that difference is central to how they think (Lesson 0.3).

3. Why the clock is only part of the story

Performance is often summarized as: time = instructions × cycles-per-instruction ÷ clock rate. Three levers, not one:

LeverWhat it meansWho pushes it
Fewer instructionsa smarter algorithm or compiler doing the same work in fewer stepsyou, and the compiler
Lower cycles-per-instructionthe core doing more per tick: pipelining, running several instructions at once, hiding memory stallsthe hardware architects
Higher clock ratemore ticks per secondphysics, and it has largely stalled

That last row is one of the most important facts in modern computing. For decades, clocks climbed every year and software got faster for free. Around the mid-2000s that stopped: pushing clocks higher made chips too hot to cool. This is the power wall, and it forced the entire industry to a new plan — instead of one core running ever faster, put many cores on one chip and run them in parallel. GPUs are the most extreme expression of that plan.

The free lunch ended around 2005. Before it, you waited a year and your program ran faster on next year's chip. After it, going faster means going parallel — which is a skill, not a purchase. This course teaches that skill. The GPU is where it pays off most.

4. The memory wall — the theme beneath everything

Processor speed and memory speed did not improve at the same rate. Cores got dramatically faster; main memory got faster far more slowly. The gap between them — measured in how many instructions a core could have run in the time it waits for one memory access — grew for decades. This is the memory wall, and it is the reason so much of this course is about data movement rather than arithmetic.

Two responses run through everything you'll learn:

  • Caches — small, fast memories that sit between the core and main memory, holding recently- and soon-to-be-used data close by. When the data you need is already in cache, you skip the long trip. This is the CPU's primary weapon (Lesson 0.2, and Module 4).
  • Latency hiding — if you have thousands of independent tasks, then whenever one is stalled waiting on memory, the hardware simply runs another. The wait still happens, but it's hidden behind useful work. This is the GPU's primary weapon (Lesson 0.3), and it's why a GPU wants far more threads than it has cores.

You will eventually quantify all of this with a single, beautiful diagram called the roofline (Lesson 4.7 and the Labs). For now, just carry the instinct: the score is usually decided by how you move data, not by how you do arithmetic.

5. Sequential by default — the road that leads to the GPU

A single core, left alone, does exactly one thing at a time: one stream of instructions, in order. There are only three ways to make it get more done:

(1) Raise the clock — blocked by the power wall. (2) Do more per tick on one instruction stream — pipelining and running several instructions at once; this is "instruction-level parallelism," and there's a ceiling to how much independent work a single stream contains. (3) Run many streams at once — many cores, many threads; this is the open-ended road, and it's the one the whole industry took. A CPU took a few steps down it (a handful of powerful cores). A GPU sprinted (thousands of small ones). Everything from Lesson 0.2 onward is about how these two very different machines make that choice — and how you, the programmer, feed them.

Gotchas

GHz across different chips means little. A 3 GHz chip of one design can badly outperform a 4 GHz chip of another, because they differ in work-per-tick and in how well they hide memory stalls. Never compare processors by clock alone — especially never a CPU against a GPU that way.
"Memory" is not "storage." Memory (RAM) is the fast, temporary numbered-boxes the processor works from; it is wiped when power is lost. Storage (SSD/disk) is slower, larger, and permanent. In this course "memory" always means RAM and the GPU's own on-board memory unless we say otherwise.
The core is often idle, not busy. Beginners picture the processor pinned at 100% doing math. In memory-heavy work it spends most cycles stalled, waiting for data. Optimizing the math it does while waiting is polishing a part that was never the bottleneck.
Instructions and data share memory. Both your program's steps and its numbers live in the same addressed memory. This is the von Neumann design; it's why a program is "just data" that the PC walks through.

Scenario — the mystery of the idle supercomputer

A research team ports a physics simulation to a shiny new machine with cores twice as fast as their old one, and expects it to run twice as quickly. It runs barely faster at all. Baffled, they profile it — and find the cores sitting idle more than 70% of the time, stalled waiting for data to arrive from memory. The simulation touches a huge grid of numbers once each, so caches barely help, and there's only one stream of work, so nothing fills the waiting. The faster clock made the 30%-that-was-computing quicker and did nothing for the 70%-that-was-waiting. The real fix wasn't a faster core; it was restructuring the problem into thousands of independent pieces so the hardware always had something to do while any one piece waited — in other words, making it look like the kind of work a GPU devours. This lesson's humble ideas — the loop, the clock, the bus, the wait — are exactly the ideas that explain the disappointment and point to the cure. The rest of the course turns that cure into a craft.

Practice

1. Write the four-instruction sequence (in the style shown) to compute c = a + a where a lives at address 0x2000 and c should go to 0x2008.
LOAD  r1, [0x2000]    ; r1 = a
ADD   r2, r1, r1      ; r2 = a + a   (no second LOAD needed — reuse r1)
STORE [0x2008], r2    ; c = r2

Note you only load a once and reuse it from the fast register — a tiny example of the constant theme "touch slow memory as little as possible."

2. A program is 6 billion instructions. On a core that averages one instruction per tick at 3 GHz, what's the ideal run time? Name one realistic reason it will be slower.

6 × 10⁹ ÷ 3 × 10⁹ = 2 seconds ideal. Realistically slower because many instructions stall on memory (cache misses), branches occasionally mispredict and flush the pipeline, and not every instruction truly retires in one tick — so the average cycles-per-instruction is above 1.

3. Explain the power wall in two sentences, and what the industry did in response.

Pushing clock speeds ever higher made chips consume and dissipate too much power to cool, so around the mid-2000s clock rates largely stopped climbing. Rather than one ever-faster core, chipmakers put many cores on a chip and pursued parallelism — with GPUs, containing thousands of small cores, as the most extreme version of that strategy.

4. Why does a GPU want more threads than it has cores? (Answer with the memory wall.)

Because threads frequently stall waiting on memory. If a GPU had exactly one thread per core, a stalled thread would leave its core idle. By over-subscribing — many more threads ready than cores — whenever one thread waits on memory, the core instantly switches to another that's ready, so the memory latency is hidden behind other work and the hardware stays busy. Latency hiding is the GPU's core trick, and it only works with an abundance of independent threads.

5. Reflection: in your own words, why is "the arithmetic is cheap, moving the data is expensive" the most important sentence in this lesson?

Because it re-aims your attention. Almost every performance decision in the course — caches, coalescing, tiling, occupancy, the roofline — is about reducing or hiding the cost of moving data, not about doing the math faster. Once you believe that arithmetic is nearly free and data movement is the price, the design of both CPUs and GPUs (and the reason GPUs win at the right problems) stops being a list of facts and becomes one coherent idea.
