The GPU — built for throughput

The CPU spends its silicon making a few streams fast and never waiting. The GPU makes the opposite bet: fill the chip with thousands of simple cores, accept that any one of them is slow and stalls constantly, and win by keeping so much work in flight that the whole machine is never idle. It turns the memory-wait problem — the CPU's enemy — into its superpower.

Concept

A different goal: throughput, not latency

Throughput is total work finished per second, regardless of how long any single piece takes. A GPU doesn't care that one thread is slow; it cares that millions of threads per second complete. Picture a bank: a CPU is one lightning-fast teller who serves each customer in seconds; a GPU is a hall of a thousand ordinary tellers. Each individual customer may wait longer, but the hall processes vastly more customers per hour. For "add a billion numbers" or "shade eight million pixels," you don't want one genius — you want the hall.

One line to carry through the whole course: the CPU minimizes latency (time per task); the GPU maximizes throughput (tasks per second). Nearly every concrete difference between the two machines is a consequence of this single divergence in goals.

Spend the transistors on arithmetic

A CPU core is mostly cache and control logic with a small arithmetic slice (0.2). The GPU inverts that budget. It strips each core down — tiny caches, no fancy branch predictor, no heavy out-of-order machinery — so each core is small, then packs thousands of them onto one chip. Most of the silicon becomes the thing a CPU spends sparingly: raw arithmetic units.

Proportions are illustrative. The point is real: the CPU spends area on not waiting (cache + control) for a few fast cores; the GPU spends area on doing math across thousands of simple cores.

SIMT — one instruction, many threads

Thousands of independent control units would be wasteful, so the GPU shares. Its threads run in fixed-size groups — NVIDIA calls a group of 32 threads a warp (AMD historically used 64, a wavefront) — and all threads in a group execute the same instruction at the same time, each on its own data. This is SIMT: Single Instruction, Multiple Threads. One instruction is fetched and decoded once, then 32 arithmetic units apply it to 32 different numbers. It's an assembly line where one foreman calls the step and thirty-two hands do it in unison — enormously efficient when every hand really is doing the same step.

Latency hiding — the master trick

Here is the beautiful part. Each GPU core, being simple, has no big cache to avoid memory stalls, so its threads stall constantly. On a CPU that would be a disaster. The GPU's answer: keep far more threads ready than it has cores, and whenever one warp stalls waiting on memory, instantly switch to another warp that's ready to compute. The memory wait still happens — but it's hidden behind other warps' useful work, so the arithmetic units never sit idle.

Four warps, staggered. Each spends most of its life stalled on memory (dashed), yet at every instant some warp is computing — so the cores stay saturated. The GPU doesn't beat memory latency; it hides it behind an abundance of work.

This is why a GPU wants more threads than it has cores — often tens of thousands in flight. Over-subscription isn't wasteful here; it's the fuel that hides latency. A GPU with too few threads is like our teller-hall with only ten customers: most windows idle, throughput wasted. You'll meet this idea again, quantified, as occupancy in Module 5.

The bargain you must uphold

The GPU's speed is conditional. It hands you astonishing throughput if you bring it the right kind of work: thousands of independent tasks (to fill the cores and hide latency), doing the same operation (so SIMT groups stay in step), touching memory in regular, neighborly patterns (so the few caches and wide memory bus are used well). Bring it serial, branchy, or scattered work and it crawls — a thousand tellers are useless for a task that must be done by one person in strict order. Half of this course is learning to reshape problems into the form the GPU devours. The next lesson, 0.4, makes the trade-off between the two machines precise so you always know which tool a problem wants.

Worked example

Task: Compare a CPU and a GPU on one million independent square-roots, using representative numbers. Suppose the CPU finishes one sqrt in ~5 ns and has 8 cores; the GPU takes ~20 ns for any single sqrt (it's a simpler, slower core!) but can keep ~20,000 threads in flight. Which finishes the million first, and what does that reveal?

1 — CPU throughput: 8 cores × (1 sqrt / 5 ns) = 1.6 sqrt/ns. One million ÷ 1.6 per ns = 625,000 ns ≈ 0.63 ms.

2 — GPU throughput: with 20,000 sqrts in flight and each taking ~20 ns, the machine retires roughly 20,000 / 20 ns = 1,000 sqrt/ns. One million ÷ 1,000 per ns = 1,000 ns ≈ 0.001 ms.

3 — the twist: the GPU is 4× slower on any single square-root (20 ns vs 5 ns), yet finishes the whole batch roughly 600× faster. Worse latency, far better throughput. That inversion is the entire point of a GPU.

Decision made: for one urgent sqrt, use the CPU — it answers in 5 ns while the GPU is still launching. For a million, use the GPU — its ocean of slow cores crushes the batch. Choosing the right machine is choosing latency vs throughput for your workload, which is exactly what 0.4 is about. (These figures are illustrative; you'll measure real ones in the Labs.)

Key points

  • The GPU optimizes throughput — total tasks per second — not the latency of any single task. It's a hall of a thousand ordinary tellers, not one genius.
  • It spends most of its silicon on arithmetic units across thousands of simple cores, having stripped out the CPU's big caches and control logic.
  • SIMT: threads run in fixed groups (a warp = 32 on NVIDIA; a wavefront = 64 historically on AMD) that all execute the same instruction in lockstep, one decode driving many arithmetic units.
  • Latency hiding: with far more threads than cores, whenever a warp stalls on memory the hardware runs another ready warp, so the cores stay busy. The GPU hides memory latency rather than avoiding it.
  • Therefore a GPU wants to be over-subscribed with tens of thousands of threads — that abundance is the fuel that hides latency (later: occupancy).
  • The speed is conditional: it needs many independent tasks, doing the same operation, over regular memory patterns. Serial, branchy, or scattered work wastes it.

Quiz

1. A single GPU core is generally slower than a single CPU core. How does a GPU still win overall on the right problems?
A GPU trades single-thread speed for massive parallelism. Thousands of simple cores plus latency hiding (switch to another warp when one stalls) give enormous throughput even though each core is slower and each task has higher latency than on a CPU.
2. What is a "warp" (NVIDIA terminology)?
A warp is 32 threads driven by one instruction stream in lockstep (SIMT). One fetch/decode feeds 32 arithmetic units. (AMD's equivalent, the wavefront, was historically 64 threads.) This sharing is how the GPU affords so many cores.

Exercises

Exercise 1 — In one sentence each, explain SIMT and latency hiding, and say why they depend on each other.

SIMT: threads run in fixed groups that all execute the same instruction at once, each on its own data, so one control unit can drive many arithmetic units. Latency hiding: keep many more warps ready than there are cores, and switch to a ready warp whenever the current one stalls on memory, so the cores never idle. They depend on each other because SIMT makes cores cheap enough to have thousands (creating the need for lots of parallel work), and latency hiding is what keeps that army of cheap, cache-poor cores busy despite their constant stalls.

Exercise 2 — Using the worked example's style, suppose the GPU can keep only 200 sqrts in flight (too few threads). Recompute its throughput and time for one million, and name the concept.

Throughput ≈ 200 / 20 ns = 10 sqrt/ns. Time = 1,000,000 / 10 = 100,000 ns ≈ 0.1 ms — now only ~6× faster than the CPU instead of ~600×, because with too few threads the cores spend most of their time stalled with nothing to switch to. The concept is occupancy: too few threads in flight means latency isn't hidden and throughput collapses. Feeding the GPU enough parallel work is a first-order performance concern (Module 5).

Exercise 3 — Why is a task like "walk a linked list, following each pointer to the next node" a terrible fit for a GPU?

It's inherently serial and scattered: you can't visit node k+1 until you've read node k (a dependency chain, so no parallelism to spread across cores), and each node may live anywhere in memory (irregular, non-neighborly access that the GPU's wide, pattern-loving memory system can't use well). It violates all three parts of the bargain — independence, sameness, regular access — so the thousand tellers stand idle behind one. Pointer-chasing is a classic "give it to the CPU" workload.

Go deeper — the complete guide

The card gives you the GPU's philosophy. This chapter names the machinery you'll spend Modules 4 and 5 mastering, so the words are already familiar when we make them precise.

1. SIMT, precisely — and the shared program counter

Within a warp, the 32 threads share one instruction stream: the hardware fetches an instruction once and applies it across all 32 lanes. Conceptually the warp has a single program counter. This is why SIMT is so efficient — the expensive fetch/decode/schedule work is amortized across 32 arithmetic operations instead of paid per operation. It is also the seed of the GPU's biggest gotcha, next.

2. Warp divergence — the cost of an if

What happens when threads in one warp disagree at a branch — say half satisfy if (x > 0) and half don't? Since the warp shares one instruction stream, it cannot run two different instructions at once. Instead it executes the if-side with the qualifying threads active and the rest masked off (idle), then executes the else-side with the roles reversed. Both sides run; some lanes are wasted on each. This is warp divergence, and a heavily branchy inner loop can halve or worse your effective throughput. The CPU's branch predictor made ifs nearly free; the GPU makes divergent ifs expensive. Writing branch-light, uniform inner loops is a core GPU skill (Module 5).

3. Coalescing — why 32 neighbors should read 32 neighbors

When a warp's 32 threads each read from memory, the hardware is happiest if those 32 addresses are contiguous — thread 0 reads element 0, thread 1 element 1, and so on. Then the whole warp's reads combine (coalesce) into a few wide memory transactions instead of 32 scattered ones. Scatter the accesses and you can waste most of the bandwidth you paid for. This is the direct GPU descendant of the CPU's cache-line and spatial-locality story from 0.2 — same lesson, higher stakes, and the subject of Lesson 5.7 and the Coalescing lab.

4. Occupancy — enough warps to hide the wait

Latency hiding only works if there are enough ready warps to switch to. The ratio of active warps to the maximum the hardware could hold is called occupancy. Too low, and stalls show through as idle cores (as in Exercise 2). But higher isn't automatically better — warps compete for limited on-chip resources (registers and a small fast scratchpad called shared memory), so pushing occupancy up can starve each thread. Finding the sweet spot is a real tuning task, and there's an interactive Occupancy lab for exactly this (Lab 5.6).

5. The GPU's memory: built for bandwidth

A machine with thousands of hungry cores needs to be fed. So a GPU pairs its cores with its own dedicated memory engineered for enormous bandwidth — total bytes per second, not low latency. Where a CPU's main memory delivers on the order of tens of gigabytes per second, a high-end GPU's memory can deliver on the order of terabytes per second — roughly an order of magnitude more, sometimes more. The trade is deliberate: GPU memory often has higher latency per access than CPU memory, but the GPU doesn't mind (it hides latency), and it desperately needs the bandwidth (to feed the sea of cores). Bandwidth, not clock speed, is usually the number that decides GPU performance — which is why the roofline model (Lesson 4.7 and its lab) is built around it.

6. Where the GPU loses

It's as important to know when not to reach for a GPU:

WorkloadWhy the GPU struggles
Small problemsNot enough parallel work to fill thousands of cores; launch overhead dominates. A CPU answers before the GPU has warmed up.
Strictly serial tasksA dependency chain (each step needs the last) can't be spread across cores at all — one slow GPU core does it worse than one fast CPU core.
Heavy, unpredictable branchingWarp divergence forces both paths; SIMT efficiency collapses.
Scattered, pointer-chasing memoryNo coalescing, no regular pattern; the wide memory system is wasted.

The professional skill isn't "always use the GPU" — it's recognizing which parts of a program are throughput-shaped (hand them to the GPU) and which are latency-shaped or serial (keep them on the CPU). Real systems use both, together, which is precisely the partnership Lesson 0.4 examines.

Gotchas

Thinking a GPU is "just a faster CPU." It's slower per thread and per task. It only wins through massive parallelism. Hand it a serial job and it loses to a laptop.
Forgetting the bargain. The GPU's throughput assumes many independent, uniform, regularly-accessed tasks. Miss any of the three — independence, sameness, regular access — and performance falls off a cliff (divergence, poor coalescing, or idle cores).
Under-feeding it. A GPU with only a few hundred threads active behaves like a stalled, mostly-idle chip. It needs tens of thousands in flight to hide latency; "not enough parallelism" is one of the most common reasons GPU code disappoints.
Branch-heavy inner loops. On a CPU, a well-predicted branch is nearly free. Inside a warp, a data-dependent branch can force every lane through both sides. Move branches out of hot loops, or make them uniform across the warp.

Scenario — the pixel shader and the price of one if

A graphics engineer writes a shader that runs once per pixel across an 8-megapixel frame — a textbook throughput problem, and the GPU eats it happily at first. Then a feature lands: if a pixel is in shadow, run an expensive extra lighting calculation; otherwise skip it. Reasonable on a CPU. But pixels in shadow and pixels in light are interleaved across the screen, so within almost every 32-thread warp some pixels take the expensive path and some don't. SIMT forces the whole warp through the expensive branch anyway, masking the lanes that didn't need it — so nearly every warp pays the full cost as if all its pixels were shadowed. Frame time spikes. The fix is pure GPU thinking: reorganize so that threads in a warp tend to agree (group shadowed work together), or replace the branch with a cheaper branch-free formula. Same code, same math, but arranged to respect how the machine actually executes. This is the flip side of 0.2's cache story — on both machines, victory comes from arranging the work to fit the hardware, not from doing less math.

Practice

1. State the CPU's bet and the GPU's bet, each in one sentence.
The CPU bets you have a few urgent, unpredictable tasks, so it spends silicon on caches and control to make a small number of streams fast (minimizing latency). The GPU bets you have an ocean of identical independent tasks, so it spends silicon on thousands of simple arithmetic cores and hides memory stalls with an abundance of threads (maximizing throughput).
2. A job has 50 independent tasks. Is a GPU with 10,000-core capacity likely to shine? Why or why not?
No. Fifty tasks can't fill thousands of cores or provide enough warps to hide memory latency, and the fixed cost of launching work on the GPU may exceed the whole job. This is an "under-fed GPU": you need work in the thousands-to-millions range for the throughput machine to pay off. Fifty tasks belong on the CPU.
3. Explain, using SIMT, why "avoid divergent branches in the inner loop" is GPU gospel.
Because a warp shares one instruction stream, threads that disagree at a branch can't run different instructions simultaneously; the hardware serializes the paths, running each with some lanes masked off and idle. A divergent branch in a hot inner loop therefore wastes a large fraction of the warp's arithmetic units on every iteration. Keeping inner-loop branches uniform (all lanes agree) or branch-free preserves full SIMT efficiency.
4. Why does a GPU carry its own high-bandwidth memory instead of just using the CPU's RAM?
Thousands of cores consume data at a staggering rate, so the GPU needs memory bandwidth far beyond what CPU RAM (and the connection to it) can supply — often on the order of terabytes per second versus tens of gigabytes. It accepts higher per-access latency in exchange for that bandwidth, because it hides latency with parallel warps but cannot manufacture bandwidth it doesn't have. Feeding the cores is the whole design problem, and dedicated high-bandwidth memory is the answer. (The cost of copying data between CPU and GPU memory is a major theme of 0.4 and Module 4.)
5. Reflection: in your own words, how does the GPU turn the memory wall — the CPU's great enemy — into an advantage?
The memory wall means every core spends much of its time waiting for data. The CPU fights this by trying not to wait (caches, prediction), which costs so much silicon that it can only afford a few cores. The GPU instead embraces the waiting: it fills the chip with cheap cores that stall freely, then keeps so many independent warps in flight that whenever one waits, another runs. The very stalls that idle a CPU become the gaps a GPU fills with other work — so the wall that limits one machine becomes the mechanism the other exploits to stay fully busy.
