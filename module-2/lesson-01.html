Your First Program — values, variables & types

Today you stop reading code and start writing it. You already own the math (Module 1); Python is just the fastest way to make a machine do that math. By the end of this lesson your first program will be a genuinely professional artifact: a GPU kernel-time estimator.

Set up in 60 seconds: open colab.research.google.com → New notebook. Type code in a cell, press Shift+Enter to run it. That's the whole loop for this module. (Local option and details: Lab setup.)

Concept

What a program actually is

A program is a text file of instructions executed top to bottom. Python is an interpreter: a running translator that reads your line, does it, and moves on. C (Module 3) is compiled: the whole text is translated to machine code first, then run. The trade is flexibility now versus speed later — and it's why Python is where everyone starts and why GPUs will eventually demand C from you.

print("hello, GPU world")      # run it. You are now a programmer.
print(2**37)                    # 137438953472 — M1 L3's matmul FLOP count, computed by machine

Everything after # is a comment — notes for humans, invisible to Python.

Variables: it's an action, not an equation

M1 L2 warned you: = means "gets," not "equals." Now it's real. A variable in Python is a name tag pointed at an object — and this picture, more than any other, is what makes Python behave the way it does:

flops = 2 * 4096**3         # tag 'flops' → the int 137438953472
flops = flops / 50e12       # re-point: now → the float 0.00274877...
gpu_name = "H100"           # tags can point at any type; names are case-sensitive
GPU_NAME = "different tag"  # this is a DIFFERENT variable

Name rules: letters, digits, underscores; can't start with a digit; snake_case by convention. Give things honest names — bytes_per_element, not b — your future debugging self is the customer.

Strings and f-strings: making output speak

gpu = "H100"
tflops = 989
print(f"{gpu}: {tflops} TFLOP/s fp16")          # f-string: expressions inside {}
print(f"time = {1.37e11 / 5e13 * 1000:.2f} ms")  # :.2f → 2 decimal places → "2.75 ms"
print(f"{16_777_216:,}")                          # underscores in literals, commas out: 16,777,216

The :.2f, :,, :e format codes are how professionals stop printing 0.0027487790694101243 at people. You'll use f-strings in every program you ever write from here.

Converting between types (and when Python refuses)

int("512")       # 512      — parse a string into a number
float("3.5")     # 3.5
str(2.75)        # "2.75"
int(2.99)        # 2        — TRUNCATES toward zero (M1 L2!), not rounds
round(2.99)      # 3        — rounding is a different, explicit operation
"batch=" + 32    # TypeError! Python never guesses; write "batch=" + str(32)
That TypeError is Python being your ally: it refuses to guess whether "2" + 2 means 4 or "22". Languages that guess (JavaScript) produce famous bugs. Read error messages as design feedback, not punishment — Lesson 2.6 makes you fluent in them.

Worked example

Task: Your first real program — the back-of-envelope kernel estimator from M1 L3, as executable code. Given a matrix size and a GPU's specs, print whether a matmul is compute- or memory-bound and its time floor.

# kernel_estimate.py — my first program that would be useful at work
n              = 4096          # square matrix size
peak_flops     = 50e12         # 50 TFLOP/s fp32
bandwidth      = 1.0e12        # 1 TB/s

work_flops   = 2 * n**3                     # M1 L6: matmul costs 2·n³
bytes_moved  = 3 * n**2 * 4                 # 3 matrices, fp32 = 4 bytes (M1 L8)
t_compute_ms = work_flops  / peak_flops * 1000
t_memory_ms  = bytes_moved / bandwidth  * 1000
intensity    = work_flops / bytes_moved     # FLOPs per byte (M1 L3 §4)

print(f"work: {work_flops:.3e} FLOPs, data: {bytes_moved/1e6:.0f} MB")
print(f"compute floor: {t_compute_ms:.2f} ms   memory floor: {t_memory_ms:.2f} ms")
print(f"arithmetic intensity: {intensity:.0f} FLOP/byte")
print(f"bound by: {'COMPUTE' if t_compute_ms > t_memory_ms else 'MEMORY'}")

Output:

work: 1.374e+11 FLOPs, data: 201 MB
compute floor: 2.75 ms   memory floor: 0.20 ms
arithmetic intensity: 683 FLOP/byte
bound by: COMPUTE

Decisions made: names that read as physics (t_compute_ms carries its unit — a professional habit that has prevented actual spacecraft crashes); formatted output a human can scan; and the one-line conditional expression (A if cond else B) as a preview of Lesson 2.2. Change n to 512 and run again — watch it flip to MEMORY-bound. You now own an interactive version of M1 L3's roofline reasoning.

Key points

  • A program runs top to bottom; Python interprets it line by line — immediate, flexible, and ~100 ns per step slower than compiled code (a cost Lesson 2.5 will dodge).
  • = points a name tag at an object; it never copies. x = x + 1 re-points the tag at a new object.
  • Python int is M1 L1's unlimited integer (no overflow); Python float IS M1 L8's fp64 — all its rules apply, starting with "no ==".
  • / always yields float; // floor-divides (negatives floor DOWN, unlike C); % is the remainder; ** is power.
  • f-strings f"{x:.2f}" are the standard way to produce readable output; unformatted float spew is amateur signature.
  • Python never coerces types across +: "a" + 1 is a TypeError — convert explicitly and be glad it asked.

Quiz

1. After x = 7; y = x; x = x + 1, what are x and y — and why?
y = x pointed y's tag at the SAME int 7 object x pointed at. x = x + 1 then re-pointed x at a new object (8); y's tag never moved. Names point at objects; they do not point at other names. (This exact picture becomes critical when the object is a mutable list — 2.4.)
2. What does print(int("7") + int(2.9) + 7 // 2) output?
int("7")=7; int(2.9)=2 — int() truncates toward zero, it does NOT round; 7//2=3 — floor division stays int. Sum: 12. The int()-truncates fact is a recurring interview micro-trap and a real bug source in index math.

Exercises

Exercise 1 — Write a VRAM budget calculator: given params = 7e9 and bytes_per_param = 2 (bf16 — M1 L8), print the weight memory in GiB (not GB — M1 L1!), and the tokens/second ceiling at 3 TB/s if each generated token reads every weight once (M1 L3, Ex.1). Format to 2 decimals.
params          = 7e9
bytes_per_param = 2          # bf16
bandwidth       = 3e12       # 3 TB/s

weight_bytes = params * bytes_per_param
weight_gib   = weight_bytes / 2**30          # GiB uses 2^30 (M1 L1), not 1e9
tok_per_s    = bandwidth / weight_bytes      # one full weight-read per token

print(f"weights: {weight_gib:.2f} GiB")      # 13.04 GiB
print(f"ceiling: {tok_per_s:.2f} tokens/s")  # 214.29 tokens/s

Note the two deliberate choices: 2**30 for GiB (binary units for memory) and names carrying units. If you printed 14.00 "GB," you'd be off by 7.4% versus the GiB the driver reports — M1 L1's marketing-vs-memory gap, now in your own code.

Exercise 2 — Predict, run, explain: print(0.1 + 0.2 == 0.3), print(0.1 + 0.2), print(f"{0.1 + 0.2:.20f}"), and print(10**16 + 1.0 == 10**16). Tie each output to its M1 L8 mechanism.
False                       # 0.1, 0.2, 0.3 are all rounded binary fractions (M1 L8 §"0.1")
0.30000000000000004         # the sum lands one ulp off the rounded 0.3
0.30000000000000004441      # :.20f exposes the stored value's full lie
True                        # 10**16 > 2**53: float64's integer-exact range ends at 2^53
                            # ≈ 9.007e15, so adding 1.0 is ABSORBED (M1 L8 absorption)

The last line is the fp64 version of M1's "+1 at 2²⁴ does nothing in fp32." Python's int would handle 10**16 + 1 exactly — but writing 1.0 made it a float computation. One character, different number system. This is why scientific code audits every literal.

Go deeper — the complete guide

The interpreter's actual pipeline, the object model that explains every "weird" Python behavior in advance, numbers in full (including the decimal escape hatch), string internals, and the input/validation pattern you'll use forever.

1. What really happens when you press Run

Python doesn't interpret your raw text character by character. It compiles your file to bytecode (simple stack-machine instructions) once, then a loop executes those instructions. You can watch:

import dis
dis.dis("flops / 50e12")     # LOAD_NAME flops → LOAD_CONST 5e13 → BINARY_OP / → ...

Each bytecode step costs tens of nanoseconds of bookkeeping (type checks, reference counting, dispatch). That's the "~100 ns per step" from the diagram — irrelevant for 100 operations, fatal for 100 million (Lesson 2.5's whole plot). CPython 3.13/3.14 have been shaving this overhead (adaptive specialization, an experimental JIT), but the order of magnitude stands: per-element Python is slow; Python orchestrating compiled bulk operations is world-class — which is precisely the division of labor in every GPU stack: Python drives, compiled kernels do the work.

2. The object model: three facts that predict everything

(1) Everything is an object — the int 5, the string "H100", functions themselves. Every object has an identity (id(x) — think address, M1 L1), a type, and a value. (2) Names are tags, stored in namespaces (dictionaries, as it happens — 2.4). (3) Objects are either mutable or immutable:

Immutable (value can never change)Mutable (can change in place)
int, float, bool, str, tuplelist, dict, set, NumPy arrays
"changing" one = making a new objectchanging one is visible through EVERY tag on it

All of Module 2's famous traps — aliased lists (2.4), the shared default argument (2.4), views mutating arrays (2.5) — are this table plus the tag picture. You now hold the skeleton key three lessons early. Two curiosities to file: CPython pre-creates small ints (−5..256), so id(7) is shared — harmless, but it's why is sometimes "works" for small numbers and then betrays you at 257. Rule: == compares values; is asks "same object?" — use is only for None.

3. Numbers, completely

0b10101101     # 173 — binary literals (M1 L1 notation, built into the language)
0xAD           # 173 — hex literals
1_000_000      # underscores group digits
5e13           # float scientific notation
7 // 2, -7 // 2    # 3, -4   — floor division FLOORS (C truncates: -3. M1 L2's table)
-7 % 2             # 1       — remainder follows the divisor's sign in Python
divmod(11551, 3)   # (3850, 1) — quotient and remainder in one call (M1 L2 decode!)
abs(-5), round(2.675, 2)   # 5, 2.67 — wait, not 2.68? See below.

round(2.675, 2) == 2.67 because 2.675 isn't representable and stores as 2.67499999… (M1 L8). Also, round uses banker's rounding (ties to even: round(0.5) == 0, round(1.5) == 2) — IEEE-754's tie rule, which you met in M1 L8 §1. When decimal exactness is a requirement (money!), Python ships an escape hatch:

from decimal import Decimal
Decimal("0.1") + Decimal("0.2") == Decimal("0.3")   # True — base-10 arithmetic, slower

Rule of the house: floats for measurements and math, ints for counts and indices, Decimal for money, never floats for money.

4. Strings, enough to be dangerous

s = "NVIDIA H100 SXM"
len(s)          # 15
s[0], s[-1]     # 'N', 'M'    — 0-based, negatives from the end (2.4 formalizes)
s[7:11]         # 'H100'      — half-open slice, M1 L2 intervals again
s.upper(), s.split(" "), s.strip(), s.replace("H100", "B200")
"—".join(["a", "b", "c"])     # 'a—b—c'
f"{3.14159:8.2f}|{42:>6}|{'x':<4}|"   # '    3.14|    42|x   |' — width/align codes

Strings are immutable: s[0] = "n" is a TypeError; every "modification" builds a new string. Consequence worth knowing now: building a big string with += in a loop re-copies everything each time (a Gauss-sum O(n²) of copying — M1 L2 §4); collect pieces in a list and "".join(pieces) at the end. And an f-string debugging gem: f"{x=}" prints x=2.75 — name and value together.

5. Input, validation, and your first defensive pattern

raw = input("matrix size n: ")     # ALWAYS returns a str — "4096", not 4096
n = int(raw)                        # crashes on "40k" — ValueError

Real programs validate at the boundary — convert and check immediately, so garbage can't travel deeper (the same at-ingestion discipline M1 L8 preached for NaNs):

raw = input("matrix size n: ").strip()
if not raw.isdigit():
    print(f"'{raw}' is not a positive integer"); raise SystemExit(1)
n = int(raw)
if not (1 <= n <= 65536):
    print(f"n={n} outside sane range [1, 65536]"); raise SystemExit(1)

(Full error machinery arrives in 2.6; the shape of the pattern — convert, check, fail loudly, fail early — is the takeaway today.)

6. Gotchas

= vs ==. Assignment vs comparison. Python at least refuses if x = 5: with a SyntaxError (C silently accepts the bug — Module 3 will re-warn you).
int() truncates. int(2.99) == 2, int(-2.99) == -2 (toward zero!). For real rounding use round(); for floors of negatives use math.floor — three different operations, choose consciously (M1 L2's negative-division table).
Case sensitivity + lookalikes. Total, total, and totaI (capital i) are three names. NameError on a name you "just defined" is a typo in one of its spellings 95% of the time.
Float display ≠ float value. print(x) shows the shortest string that round-trips; the stored bits may differ (M1 L8). Debug numerics with f"{x:.17g}" or x.hex(), never by eyeballing two prints.
Integer bling in float clothing. 10**16 + 1.0 absorbs (fp64, 2⁵³ limit); 10**16 + 1 is exact (Python int). One misplaced .0 switches number systems. Audit literals in index/size arithmetic.
Shadowing builtins. type = "fp16" or sum = 0 silently kills those functions for the rest of the file (they're just names in the builtins namespace — §2). If sum(xs) ever says "int is not callable," you did this.

Practice

1. Predict without running: 9 / 3, 2**10 == 1024, type(2**10 / 1), -9 // 4, -9 % 4.
3.0 (/ always floats — even exact divisions), True, <class 'float'>, -3 (floors down), 3 (sign of divisor). The last two are Python's floor convention — C would give -2 and -1 (M1 L2).
2. Write one f-string that prints eps=1.19e-07 ulp@1024=1.22e-04 from eps = 2**-23 and ulp = 2**(10-23) (M1 L8 numbers).
print(f"eps={eps:.2e} ulp@1024={ulp:.2e}"). The :.2e code is scientific notation with 2 decimals — the professional format for tiny/huge magnitudes (M1 L3's notation, automated).
3. a = "3"; b = 4. Give all four distinct results you can produce with one conversion each: string concat, int add, float add, repetition — and the one that errors.
a + str(b) → "34"; int(a) + b → 7; float(a) + b → 7.0; a * b → "3333" (string repetition — no conversion needed!); a + b → TypeError. The str*int repetition surprises everyone once; it's why "type errors caught loudly" beats guessing.
4. Why does 0.1 + 0.7 == 0.8 print False but 0.25 + 0.5 == 0.75 print True? State the M1 L8 rule.
0.25, 0.5, 0.75 are p/2ᵏ — exact in binary; the arithmetic is exact, equality holds. 0.1 and 0.7 have factor 5 in the denominator → rounded storage → sum lands an ulp off 0.8's rounding. Representability rule: denominator a pure power of two ⇔ exact.
5. A colleague writes seconds = ms * 1000. The variable names say the bug. Rewrite correctly both directions and state the naming rule that would have caught it in review.
seconds = ms / 1000; ms = seconds * 1000. Rule: units live in names (t_ms, bytes_per_row), so every line can be dimension-checked by reading. The Mars Climate Orbiter was lost to exactly this class of bug — units are not pedantry.
6. Compute in your head using M1 skills, then verify in Python: (2**20 * 3) // 2**10 and 0xFF & 0x0F and 1 << 20.
3·2²⁰/2¹⁰ = 3·2¹⁰ = 3072. 0xFF & 0x0F keeps the low nibble → 0x0F = 15. 1<<20 = 2²⁰ = 1 048 576 (a MiB of bytes). Python's bitwise operators are C's (M1 L1 §5), unlimited-width — and yes, they'll matter again in CUDA.
7. Design: sketch (names + formulas only, no new syntax needed) a "GPU shopping calculator" script: inputs are price, TFLOP/s, and GB/s for two GPUs plus one workload's FLOPs and bytes; it prints which GPU is cheaper per job. Which M1 lessons is it built from?
For each GPU: t = max(flops/peak_flops, bytes/bandwidth) (the two floors — the max is the binding one; M1 L3 roofline), cost_per_job = price_per_hour * t / 3600; print both, compare. Extensions: arithmetic-intensity print to show WHY (M1 L3), GiB-vs-GB honesty for memory fit (M1 L1), and fp16 vs fp32 byte counts (M1 L8).
