Files, Modules & Environments — from scripts to software

"Readily deployable" starts here. Data must survive the process ending (files), code must be reusable across projects (modules), and your setup must be reproducible on machines you've never touched (environments). This is the lesson that turns a folder of experiments into a repo a stranger can run.

Concept

Files are bytes; everything else is interpretation

with open("results.txt", "w", encoding="utf-8") as f:   # 'with' GUARANTEES close,
    f.write(f"median_ms={med:.3f}\n")                    # even if an exception flies (2.6)

with open("results.txt", encoding="utf-8") as f:
    for line in f:                                       # files iterate by line
        key, val = line.strip().split("=")

raw = open("photo.png", "rb").read()                     # 'rb': BYTES, no decoding
raw[:4]            # b'\x89PNG' — the magic number, hex literacy paying rent (M1 L1)

Two rules with no exceptions: always with (the context manager closes on every exit path — the finally from 2.6, packaged), and always name the encoding for text (utf-8); the platform default differs across OSes, which is a classic works-here-breaks-there. Text mode decodes bytes→str; "rb"/"wb" gives raw bytes — images, arrays, anything non-text.

Structured files: CSV and JSON in ten lines

import json, csv
from pathlib import Path

runs = [{"name": "naive", "ms": 300.0}, {"name": "tiled", "ms": 12.5}]     # 2.4's shape
Path("runs.json").write_text(json.dumps(runs, indent=2), encoding="utf-8")
back = json.loads(Path("runs.json").read_text(encoding="utf-8"))
assert back == runs                                       # round-trip: dicts/lists survive

with open("runs.csv", "w", newline="", encoding="utf-8") as f:
    w = csv.DictWriter(f, fieldnames=["name", "ms"]); w.writeheader(); w.writerows(runs)

JSON maps exactly onto 2.4's dicts/lists/strings/numbers — the universal config-and-results format (with one M1 L8 footnote: it round-trips fp64 exactly in modern Python, but writing floats for humans usually means choosing a precision — decide, don't default). CSV is the spreadsheet handshake; note newline="" (a Windows quirk the csv docs mandate). Big arrays don't belong in either: np.save("x.npy", x) / np.load stores dtype+shape+bytes losslessly and 10× smaller than text — the right container for 2.8's images and every tensor after.

Paths: pathlib, not string surgery

from pathlib import Path
DATA = Path(__file__).parent / "data"          # anchored to THIS FILE, not the cwd
DATA.mkdir(exist_ok=True)
for p in sorted(DATA.glob("*.npy")):            # iterate matching files, sorted = deterministic
    print(p.name, p.stat().st_size)

The / operator joins paths portably (Windows vs Unix separators — never hand-concatenate with + "/"). The __file__-anchored pattern kills the #1 script bug: "works when run from the repo root, dies from anywhere else" — relative paths silently depend on the current working directory; anchored paths don't.

Modules: import runs your file (once)

# gpu_math.py is 2.3's toolbox. Any file beside it can now:
import gpu_math                        # runs gpu_math.py top-to-bottom ONCE, caches it
gpu_math.ceil_div(10, 4)
from gpu_math import ceil_div, clamp   # pull names into this namespace
from bench import stats as bench_stats # rename on import — collision control

Importing executes the module's top level (defs run, creating the functions; loose code runs too — which is why 2.3 quarantined the self-checks behind if __name__ == "__main__": — that variable is "__main__" only in the file you launched, and the module's own name when imported). Subsequent imports hit the sys.modules cache: module-level state initializes once per process. A folder of modules becomes a package when you organize it as toolbox/gpu_math.py etc. and import toolbox.gpu_math — same machinery, one more level.

Environments: the deployability ritual

python -m venv .venv                    # create (once per project)
source .venv/bin/activate               # Linux/macOS/WSL   (Windows: .venv\Scripts\activate)
pip install numpy==2.5.0 pytest         # installs INTO the venv only
pip freeze > requirements.txt           # pin the exact world
# — teammate / future-you / CI: —
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt         # identical environment, minutes, any machine

This six-line ritual is what "readily deployable" means at Python scale — and it's a rehearsal: the CUDA stack multiplies the version matrix (driver × toolkit × framework — Lab setup's warnings), and containers (Track A10/B7) are this same idea with the OS included. Colab note: it's one shared env — !pip install applies per-session; pin versions in the first cell of any notebook you care about.

Worked example

Task: Assemble everything Module 2 has built into a deployable repo — the structure you'll clone-and-extend for every project through Module 5 and beyond.

gpu-toolbox/
├── README.md               # what, why, how to run — three honest paragraphs
├── requirements.txt        # numpy==2.5.0, pytest==8.*  (pinned)
├── .gitignore              # .venv/, __pycache__/, *.npy results
├── toolbox/
│   ├── __init__.py         # marks the package; can re-export: from .gpu_math import ceil_div
│   ├── gpu_math.py         # 2.3: ceil_div, clamp, lerp, is_pow2
│   ├── vec.py              # 2.6: normalize (with its contract)
│   └── bench.py            # 2.3/2.4: time_call, bench, stats, report
├── tests/
│   ├── test_gpu_math.py    # 2.6's suites, verbatim
│   ├── test_vec.py
│   └── test_bench.py
└── scripts/
    └── run_bench.py        # the only file with print()s and __main__
# scripts/run_bench.py — the EDGE (2.3: effects live here, logic lives in toolbox/)
import argparse, json
from pathlib import Path
from toolbox.bench import bench, stats

p = argparse.ArgumentParser(description="benchmark a toolbox function")
p.add_argument("--n", type=int, default=1_000_000)
p.add_argument("--repeats", type=int, default=20)
p.add_argument("--out", type=Path, default=Path("results/run.json"))
args = p.parse_args()

times = bench(some_workload, args.n, repeats=args.repeats)
med, iqr, outliers = stats(times)
args.out.parent.mkdir(exist_ok=True)
args.out.write_text(json.dumps({"n": args.n, "median_ms": med*1000,
                                "iqr_ms": iqr*1000, "outliers": outliers,
                                "repeats": args.repeats}, indent=2))
print(f"median {med*1000:.2f} ms → {args.out}")

The acceptance test — run the stranger's sequence in a fresh terminal: clone, venv, pip install -r requirements.txt, pytest -q (all green), python scripts/run_bench.py --n 500000 (JSON appears). If any step needs a verbal footnote from you, the repo isn't done. Decisions made: logic/tests/scripts separated (purity architecture from 2.3, now as directories); results are JSON with the parameters embedded (a result that doesn't record its inputs is a rumor — M1 L7); argparse over input() because flags are scriptable and self-documenting (--help is free). This structure is 90% of what "engineering hygiene" means in interviews.

Key points

  • Files are bytes: text needs an explicit encoding (utf-8, always stated), binary needs "rb"/"wb"; with open(...) guarantees the close on every exit path.
  • JSON ↔ dicts/lists for configs and results; CSV for spreadsheet handshakes; np.save/.npy for arrays — text formats are for humans, not tensors.
  • pathlib with Path(__file__).parent anchoring kills cwd-dependent breakage; / joins portably.
  • import executes the module once and caches it; if __name__ == "__main__": separates "run as program" from "used as library."
  • Never name files after modules you import (numpy.py, random.py) — your folder wins the search and the error messages are surreal.
  • venv + pinned requirements.txt is the reproducibility ritual: same inputs, same environment, same results — on any machine, including future-you's.

Quiz

1. You create test.py to try things, later random.py for dice utilities. Suddenly import numpy fails deep inside with AttributeError: module 'random' has no attribute 'gauss'. What happened?
Import search checks the script's directory before the standard library — your random.py wins, and every consumer of random (NumPy included) gets your dice file. Diagnose with print(random.__file__); fix by renaming (and deleting the stale random.pyc/__pycache__). The error appearing INSIDE numpy is the cruel part: the traceback points at innocent code. Never name files after anything importable — test.py included (pytest tries to collect it).
2. A script works launched as python scripts/run.py from the repo root but crashes with FileNotFoundError from anywhere else. The code says open("data/config.json"). Diagnosis and durable fix?
"data/config.json" means "data under wherever the USER happens to be standing" — launch-location roulette. __file__ anchoring makes the path a property of the code's location, invariant to cwd. (For installed packages the modern tool is importlib.resources, same principle.) This single fix ends a whole genus of "works for me" tickets.

Exercises

Exercise 1 — Results with provenance: extend run_bench.py to embed reproducibility metadata in its JSON — timestamp, python version, numpy version, the random seed, and the exact command line. Write the reader too: a script that loads any results file and prints a one-line summary. (M1 L7's "log the seed," industrialized.)
import sys, json, time, platform
import numpy as np

record = {
    "median_ms": med * 1000, "iqr_ms": iqr * 1000, "outliers": outliers,
    "params": {"n": args.n, "repeats": args.repeats, "seed": args.seed},
    "provenance": {
        "timestamp": time.strftime("%Y-%m-%dT%H:%M:%S"),
        "python": platform.python_version(),          # e.g. "3.13.5"
        "numpy": np.__version__,                      # e.g. "2.5.0"
        "argv": sys.argv,                             # the exact invocation
    },
}
args.out.write_text(json.dumps(record, indent=2), encoding="utf-8")

# reader.py
from pathlib import Path
import json, sys
for p in sorted(Path(sys.argv[1]).glob("*.json")):
    r = json.loads(p.read_text(encoding="utf-8"))
    print(f"{p.name}: {r['median_ms']:.2f} ms  (n={r['params']['n']}, "
          f"numpy {r['provenance']['numpy']})")

Why this matters beyond tidiness: two months from now a result will look wrong, and the question will be "what EXACTLY produced this number?" Provenance-in-the-artifact answers it without archaeology. GPU benchmark reports add driver/toolkit/GPU fields to this same dict in 5.10 — the pattern is set here.

Exercise 2 — Binary vs text, measured: save the same 1M-float32 array as (a) .npy, (b) JSON (list), (c) CSV. Compare file sizes and load times, verify lossless round-trips where they exist, and explain the one that ISN'T lossless by default.
import numpy as np, json, time
from pathlib import Path
x = np.random.default_rng(0).random(1_000_000).astype(np.float32)

np.save("x.npy", x)                                          # (a) 4,000,128 bytes ≈ 3.8 MiB
Path("x.json").write_text(json.dumps(x.tolist()))            # (b) ~19 MB of decimal text
np.savetxt("x.csv", x)                                       # (c) ~25 MB, one number per line

assert np.array_equal(np.load("x.npy"), x)                   # (a) EXACT: dtype+shape+bytes
back_j = np.array(json.loads(Path("x.json").read_text()), dtype=np.float32)
assert np.array_equal(back_j, x)                             # (b) exact — but only because
                                                             # tolist() promoted to fp64 text
back_c = np.loadtxt("x.csv", dtype=np.float32)               # (c) savetxt default %.18e is
assert np.array_equal(back_c, x)                             # lossless here too — BUT trim
                                                             # the format (%.6f) and bits die silently

Sizes: ~4 MB vs ~19 MB vs ~25 MB; load times follow (binary ~10-50×). The precision story (M1 L8): binary stores THE bits; text stores a decimal RENDERING — exact only if you print enough digits (fp32 needs 9 significant; fp64 needs 17). Any human "tidying" of the format string (%.6f for readability) silently truncates ulps, and downstream equality tests start failing mysteriously. Moral: arrays travel as .npy/.npz (or parquet/safetensors later); text is for eyeballs.

Go deeper — the complete guide

Context managers as a concept, import mechanics you can debug with, package layout conventions, config-file patterns, environment troubleshooting, and the .gitignore of numerical repos.

1. with, generalized: acquisition has a shape

with open(p) as f, open(q, "w", encoding="utf-8") as g:   # multiple resources, one line
    g.write(transform(f.read()))
# temporary directory that cleans itself:
import tempfile
with tempfile.TemporaryDirectory() as tmp:
    work(Path(tmp))
# timing block (write your own context manager in one line):
from contextlib import contextmanager
@contextmanager
def timer(label):
    t0 = time.perf_counter()
    yield
    print(f"{label}: {(time.perf_counter()-t0)*1000:.1f} ms")
with timer("matmul"): C = A @ B

The pattern — acquire, use, release no matter what — is everywhere resources are: files, locks, temp dirs, database connections, and (Module 5) GPU memory and CUDA streams (torch.cuda.stream(...) is a context manager for exactly these reasons). Learn the shape once here; recognize it forever.

2. Import mechanics for debugging

import numpy, sys
numpy.__file__                    # WHERE it loaded from — the shadowing detector
sys.path                          # the search list, in order
sys.modules["numpy"]              # the cache; a second import is a dict lookup
import importlib; importlib.reload(mymod)    # dev-loop tool (state may straddle! restart > reload)

Three facts that resolve 95% of import mysteries: (1) module.__file__ never lies about shadowing (quiz 1's one-line diagnosis); (2) the cache means module top-level runs ONCE — mutate a module-level list from two importers and they share it (2.4's aliasing at architecture scale — also the legitimate trick behind 2.4's kernel REGISTRY); (3) circular imports (a imports b imports a) crash with partially-initialized modules — the fix is structural (move shared things to a third module), not syntactic. And __pycache__/: compiled bytecode cache (deep-dive 2.1 §1's compilation, persisted) — ignorable, deletable, gitignored.

3. Package layout: the two conventions that matter

toolbox/__init__.py               # empty is fine; or curate the public API:
from .gpu_math import ceil_div, clamp        # users: from toolbox import ceil_div
from .vec import normalize
__all__ = ["ceil_div", "clamp", "normalize"]

Relative imports (from .gpu_math import ...) bind the package internally; the curated __init__ gives users a stable front door while you refactor rooms behind it. When a project graduates to pip-installability, a small pyproject.toml makes pip install -e . work (editable install — imports resolve to your working copy; the standard dev setup so tests/ can import toolbox from anywhere without path hacks). That's deliberately all the packaging you need until you ship a library.

4. Configs: from constants to files

# evolution of configuration, choose the simplest that suffices:
BLOCK = 256                                   # 1. module constant (2.3) — fine for course code
p.add_argument("--block", type=int, default=256)   # 2. CLI flag — per-run variation
cfg = json.loads(Path("config.json").read_text())  # 3. config file — many related knobs
BLOCK = int(os.environ.get("BLOCK", "256"))        # 4. env var — deployment-time override (Track A10)

Rules that survive contact with teams: configs are DATA (JSON/TOML), never executable Python (importing a config runs it — a security and sanity hazard); validate at load (2.6's boundary: unknown keys are errors, not typos-in-waiting — the match-statement dtype table from 2.2 §6 is the same ethic); and echo the effective config into your results file (Exercise 1's provenance). The precedence stack — defaults < file < env < CLI — is how every serious tool (pytest included) resolves its settings; build it once in 2.8's project.

5. Environment troubleshooting: the four-question protocol

QuestionCommandClassic finding
WHICH python is running?import sys; sys.executablesystem python, not the venv (forgot to activate; IDE picked wrong interpreter)
WHERE did this module load from?mod.__file__shadowing; or an old global install winning over the venv
WHAT versions are here?pip list / np.__version__requirements drift; the "works on my machine" delta
WHO owns this pip?pip --version (shows its python)pip installed into a different interpreter than the one running

Ninety percent of "Python is broken" is a mismatch among these four answers. The same protocol, with nvcc --version / nvidia-smi / torch.version.cuda added, debugs the CUDA stack in Module 5 — quadruply worth internalizing now.

6. Gotchas

Encoding roulette. open(p) without encoding uses a platform default (Windows ≠ Linux); mojibake or UnicodeDecodeError appears only on the OTHER machine — always encoding="utf-8", both directions.
Work at import time. A module that loads a 2 GB file at top level taxes every importer (and pytest collection!). Top level: defs and constants; work: inside functions or under __main__ (2.3's gotcha, now with architectural teeth).
Shadowing stdlib/site-packages. numpy.py, random.py, test.py, email.py — and their lingering __pycache__ even after rename. Quiz 1's protocol: __file__, then rename, then delete the cache.
cwd-relative paths. FileNotFoundError that depends on where you stood when launching (quiz 2). Anchor to __file__; accept user paths as CLI args (Path type in argparse).
pip without a venv. Installs mutate the shared system state — project B breaks project A retroactively (the diagram's fight). If pip install ever suggests --user or sudo, stop: you're not in a venv.
Pinning nothing (or everything, forever). No requirements.txt → the future breaks you silently. Pinned but never refreshed → security/bug fixes never arrive. Ritual: pin exact for apps, refresh deliberately (a monthly "bump + run tests" chore — tests from 2.6 make it safe).

Scenario — "works on my machine," dissected in four acts

Your study partner shares their Module-2 project zip an hour before your group's show-and-tell; on your laptop it detonates in four distinct ways — a perfect specimen collection. Act 1: ModuleNotFoundError: numpy — no requirements.txt; they installed globally months ago and forgot NumPy was a dependency at all. venv + pip freeze on their side, install -r on yours: two minutes. Act 2: FileNotFoundError: data/samples.csv — cwd-relative paths; you launched from ~/Downloads. The __file__ anchor fix, plus moving the data path to a --data flag (configs are per-machine facts, not code). Act 3: a UnicodeDecodeError in the results reader — their Windows wrote the log in cp1252, your Linux read it as utf-8; encoding="utf-8" added at BOTH ends, and the corrupted legacy file regenerated. Act 4, the connoisseur's bug: everything imports, but plots are garbage — their folder contains statistics.py (their own stats helpers), shadowing the stdlib module that one of their dependencies imports internally; statistics.__file__ convicts it in one line (quiz 1's move). Forty minutes, four fixes, and the repo now passes the stranger test — because you ARE the stranger. The meta-lesson your group writes down: every one of these four failures was invisible on the author's machine by construction; only structure (pins, anchors, encodings, naming) defends against a class of bug you cannot see yourself.

Practice

1. Predict each: (a) open("x.npy").read() on a NumPy file; (b) json.dumps({"a": np.float32(2.5)}); (c) Path("a") / "b" / ".." / "c"; (d) importing a module whose top level prints "hello", twice.
(a) UnicodeDecodeError (or mojibake) — binary file opened in text mode; needs "rb". (b) TypeError: not JSON serializable — NumPy scalars aren't Python floats; convert with float() or .item() (a real daily annoyance in results-writing). (c) Path("a/b/../c") — pathlib does NOT simplify ".." until .resolve(). (d) "hello" prints ONCE — the second import is a sys.modules cache hit (§2). Each is a five-minute mystery you've now pre-solved.
2. Write save_run(results: dict, dir: Path) that writes JSON to a timestamped filename (run_20260703_141530.json), creating the directory if needed, refusing (loudly) to overwrite, and returning the path. Name the 2.6 contract you're honoring with the refusal.
def save_run(results, dir): dir.mkdir(parents=True, exist_ok=True); p = dir / time.strftime("run_%Y%m%d_%H%M%S.json"); then if p.exists(): raise FileExistsError(p) (two runs in the same second — rare, real, and data-destroying; add a counter suffix if you'd rather resolve than refuse — but DECIDE) then p.write_text(json.dumps(results, indent=2), encoding="utf-8"); return p. The contract: chosen failure modes — silent overwrite is the file-world's loosen-until-green. Timestamped, append-only results directories are how experiment tracking works before you adopt a tool for it.
3. Your tests pass with pytest from the repo root but "ModuleNotFoundError: toolbox" from inside tests/. Explain via the import-search diagram, and give the two clean fixes (one command-line habit, one repo-level).
From the root, "" (the cwd) is effectively on the path and toolbox/ is visible; from tests/, the search starts THERE — no toolbox in sight. Fixes: (1) habit — always run pytest from the root (where pytest.ini/pyproject.toml lives; pytest's rootdir detection rewards this); (2) structural — make the package pip-installable and pip install -e . into the venv, so toolbox resolves from site-packages regardless of cwd (§3). The second is why "editable installs" exist; path-hacking sys.path.append in test files is the fix that isn't.
4. Design the .gitignore for gpu-toolbox and justify each line class. What must NEVER be committed, and which "results" exception might a course repo legitimately make?
.venv/ (rebuildable from requirements — commit the recipe, not the cake), __pycache__/, *.pyc (machine-generated bytecode), results/, *.npy, *.png outputs (large, regenerable, bloat every clone forever — git history is append-only), .pytest_cache/, .ipynb_checkpoints/, secrets/creds if any ever exist (NEVER committed — history remembers even after deletion). Legitimate exception: small golden fixtures for tests (the 4×4 pooling reference from 2.5 P7) — tiny, load-bearing, versioned ON PURPOSE in tests/fixtures/. The principle: commit sources and contracts, ignore derivatives and environments.
5. A teammate "fixes" a flaky loader by wrapping it in try/except and returning [] on any exception (2.6's laundering, file edition). Their defense: "missing files shouldn't crash the pipeline." Write the version that honors both truths, with FileNotFoundError policy, decode-error policy, and logging.
def load_runs(p: Path) -> list: — if not p.exists(): log.warning("no results at %s — first run?", p); return [] (missing = a legitimate, NAMED state, handled narrowly); then try: return json.loads(p.read_text(encoding="utf-8")) except (json.JSONDecodeError, UnicodeDecodeError): log.exception("corrupt results file %s — refusing to guess", p); raise — corruption is NOT emptiness; silently returning [] would quietly discard real data and let a broken writer keep breaking. Policy per failure mode, narrow catches, evidence preserved: 2.6's constitution applied to I/O. The one-line summary for reviews: "absence is a state; corruption is an error."
6. Environments forensics: pip says "Requirement already satisfied: numpy" but import numpy fails. Using §5's four questions, list the two most likely worlds and the one-liner that distinguishes them.
World A: pip belongs to a DIFFERENT interpreter than the one running your script (system pip vs venv python, or python3 vs an IDE's bundled one) — distinguish: pip --version vs python -c "import sys; print(sys.executable)"; if the pythons differ, case closed (fix: always python -m pip install ... — pip bound to THAT python by construction). World B: shadowing — a numpy.py/__pycache__ in the folder intercepts (fails with AttributeError more often than ImportError; python -c "import numpy; print(numpy.__file__)" convicts). The habit that prevents World A forever: python -m pip, never bare pip.
7. Design: the data layout for 2.8's image project — inputs (a few PNGs), golden outputs (expected results for tests), generated results, and configs. Specify directories, formats, what's committed, path-anchoring, and the config precedence — citing the sections that decide each.
project/ ├ images/ (committed: 2-3 small PNGs — sources) ├ tests/fixtures/ (committed: tiny golden .npy outputs + the 4×4 hand-computed pooling case — P4's exception, §"binary vs text" says .npy for exactness) ├ results/ (gitignored — derivatives, P4) ├ config.json (committed defaults: blur radius, output dir) └ toolbox/ + scripts/pipeline.py as in the worked example. Paths: images and fixtures anchored via Path(__file__) (§ pathlib); results dir from config, overridable by --out (CLI beats file beats defaults — §4's precedence). Formats: intermediate arrays .npy (lossless, M1 L8-safe for golden comparisons); final visual outputs .png for humans. Provenance JSON per run (Ex.1) — parameters + versions embedded.
