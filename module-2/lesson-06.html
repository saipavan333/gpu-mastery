Errors, Debugging & Testing — engineering trust

Code that runs is a rumor; code that's tested is a claim. This lesson makes you fluent in Python's error machinery, systematic (not superstitious) at debugging, and armed with pytest — including the float-tolerance discipline that separates numerical engineers from numerical gamblers.

Concept

Tracebacks: read the autopsy bottom-up

A traceback is the call stack (2.3) at the moment of death, oldest frame first. Professional reading order: ① bottom line — exception type + message; ② the deepest frame in your code — the prime suspect; ③ the chain above — how execution got there. The error type narrows the search instantly:

ExceptionAlmost always means
NameError / AttributeErrortypo, or the object isn't what you think (None from 2.4's .sort()!)
TypeErrorwrong kind of thing: called an int, added str+int, passed f() not f (2.3)
ValueErrorright type, bad value: int("40k"), shape mismatch in your own checks
IndexError / KeyErrorbounds/membership: the fencepost (2.2) or the missing key (2.4)
ZeroDivisionErroran empty input or degenerate case reached arithmetic (M1 L5's normalize(0))

Raising and handling: exceptions are control flow for failure

def load_config(path):
    try:
        text = open(path, encoding="utf-8").read()
    except FileNotFoundError:
        raise ValueError(f"config missing: {path!r} — copy config.example first") from None
    ...

# the caller decides what failure MEANS; the callee just refuses garbage loudly:
if b <= 0:
    raise ValueError(f"block size must be positive, got {b}")     # 2.3's boundary rule

Rules that keep this clean: catch the narrowest type you can handle (never bare except:); catch only where you can do something about it (top of the script, retry loops, resource cleanup) — everywhere else, let it climb; raise ... from None/from e controls the "during handling of..." chain; and finally (or better, with — 2.7) guarantees cleanup. Exceptions beat error-code returns because they cannot be silently ignored — the failure travels until someone deals with it.

Debugging: the scientific method, not the shotgun

1. REPRODUCE   — smallest input that fails, deterministically (seed it! M1 L7)
2. HYPOTHESIZE — one specific claim: "rows is empty by line 40"
3. INSTRUMENT  — print(f"{len(rows)=}"), or breakpoint()
4. TEST        — run; hypothesis dies or survives
5. FIX + LOCK  — repair, then add the test that would have caught it
breakpoint()          # drop into pdb right here
# (pdb) p len(rows)   → inspect     n → next line     s → step into
# (pdb) c             → continue    q → quit          up/down → walk frames

Print debugging is legitimate (every professional does it) — targeted prints with f"{name=}", removed after. The shotgun version (random prints, random edits, "maybe this fixes it") is how afternoons die. Step 5 is the professional tell: every bug becomes a test, so the bug can never return unannounced.

Assertions: executable assumptions

def zscore(X):
    assert X.ndim == 2, f"expected (samples, features), got shape {X.shape}"
    mu = X.mean(axis=0, keepdims=True)
    sd = X.std(axis=0, keepdims=True)
    assert not np.isnan(sd).any(), "NaN in std — upstream data corrupt?"
    return (X - mu) / sd

assert cond, msg crashes early and honestly where the assumption broke — converting 2.5's silent shape accidents into loud, located failures. Contract: asserts guard internal invariants ("this cannot happen if my logic is right"); raise ValueError guards user-facing inputs ("callers might legitimately get this wrong"). Never put side effects in asserts — python -O deletes them.

pytest: tests as tiny facts

# test_gpu_math.py — pytest auto-discovers test_*.py files and test_* functions
from gpu_math import ceil_div, clamp, is_pow2
import pytest

def test_ceil_div_ragged():   assert ceil_div(10, 4) == 3
def test_ceil_div_exact():    assert ceil_div(8, 4) == 2       # the edge M1 L2 warned about
def test_ceil_div_rejects():
    with pytest.raises(ValueError):
        ceil_div(10, 0)                                         # failures are part of the contract

@pytest.mark.parametrize("n,expect", [(1, True), (1024, True), (1000, False), (0, False)])
def test_is_pow2(n, expect):  assert is_pow2(n) is expect

Run pytest -q in the folder; it finds everything. parametrize turns a table of cases into separate tests (edges get names, not comments). In Colab: %%writefile test_x.py then !pytest -q.

Testing floats: tolerances are engineering, not settings

assert fast_result == oracle_result                    # WRONG for floats, forever (M1 L8)
assert np.allclose(fast, oracle, rtol=1e-5, atol=1e-8) # right shape; budget the numbers
assert result == pytest.approx(2.75, rel=1e-6)         # scalar version

Budget, then set (M1 L8 §6): estimate error ≈ ops-on-critical-path × ulp × magnitude, add ~10× headroom. An fp32 dot over 4096 terms with pairwise summation: ~log₂(4096)·ε ≈ 12·1.2e-7 ≈ 1.4e-6 relative → rtol=1e-5 is principled. Copy-pasting fp64 defaults into an fp16 test (ε≈1e-3!) manufactures flakes; loosening until green manufactures lies.

Worked example

Task: Tests-first development of normalize(v) (M1 L5's operation): write the contract as tests, watch them fail, implement, watch them pass.

# test_vec.py — written BEFORE vec.py
import numpy as np, pytest
from vec import normalize

def test_length_one():
    v = np.array([3.0, 4.0], dtype=np.float32)
    u = normalize(v)
    assert np.isclose(np.linalg.norm(u), 1.0, rtol=1e-6)        # the defining property

def test_direction_preserved():
    v = np.array([3.0, 4.0], dtype=np.float32)
    assert np.allclose(normalize(v), [0.6, 0.8], rtol=1e-6)     # M1 L5's exact numbers

def test_input_untouched():                                      # 2.5 Practice 5's scar
    v = np.array([3.0, 4.0], dtype=np.float32); before = v.copy()
    normalize(v)
    assert np.array_equal(v, before)

def test_zero_vector_refused():                                  # M1 L5's NaN factory
    with pytest.raises(ValueError, match="zero"):
        normalize(np.zeros(3, dtype=np.float32))

def test_dtype_preserved():
    u = normalize(np.array([1.0, 0.0], dtype=np.float32))
    assert u.dtype == np.float32                                 # no fp64 creep (2.5 gotcha)
# vec.py — now write the code the tests demand
import numpy as np

def normalize(v):
    """Unit vector in v's direction. Raises ValueError on the zero vector."""
    n = np.linalg.norm(v.astype(np.float32))
    if n == 0.0:                       # == against literal 0 is legitimate here:
        raise ValueError("cannot normalize the zero vector")     # exact underflow-or-zero check
    return (v / n).astype(v.dtype)

What the order bought: the tests are the contract — length 1, direction kept, input untouched, zero refused, dtype stable — and each encodes a scar this course already showed you (aliasing 2.5, NaN M1 L5/L8, fp64 creep 2.5). Run pytest -q: 5 passed. Now every future "optimization" of normalize — NumPy tricks, a C version in M3, a CUDA kernel in M5 — inherits this exact suite as its acceptance gate. Decision made: tests-first isn't ceremony; it forced the zero-vector decision (raise, not NaN) and the mutation policy (pure) before code existed to be defended.

Key points

  • Read tracebacks bottom-up: type + message, then your deepest frame; the exception type alone narrows the bug class (traceback = 2.3's stack, printed).
  • Catch narrow, catch late, raise loudly at boundaries with messages that name the bad value; bare except: converts bugs into mysteries.
  • Debug scientifically: reproduce (seeded, minimal) → hypothesize → instrument (f"{x=}", breakpoint()) → test → fix AND add the regression test.
  • assert = internal invariant (deletable by -O, side-effect-free); raise ValueError = input validation; the two are different contracts.
  • pytest: test_*.py + plain asserts + parametrize for edge tables + pytest.raises for contracted failures — expected failures are part of the API.
  • Float tests use allclose/approx with BUDGETED tolerances (ops × ulp × 10 headroom, per dtype); loosen-until-green is fraud with extra steps.

Quiz

1. A 40-line script wraps everything in try: main() except Exception: print("error, retrying") and loops. Production reports it "hangs at 100% CPU, no logs." What happened?
Catch-all + retry is the classic bug laundering machine: deterministic bugs retry identically forever, and the evidence (traceback) is discarded each time. Fixes: catch only the retryable types (network timeouts), log the FULL traceback (logging.exception), cap retries with backoff, and let everything else crash loudly. "Catch late, catch narrow" is this quiz in four words.
2. Your fp32 kernel test assert np.allclose(fast, oracle, rtol=1e-7) passes on 100-element inputs but fails on 1M-element inputs. The most likely verdict?
rtol=1e-7 is BELOW fp32's single-op ε (1.19e-7) — no two differently-ordered million-term fp32 reductions can meet it (M1 L8: non-associativity, error ~ log n · ε at best). The fix is a computed budget (e.g., rtol=1e-5 for pairwise sums), documented in the test. A scale-dependent bug IS possible — which is why you budget first, then investigate residuals above budget. The test was wrong before the kernel was.

Exercises

Exercise 1 — Write the test file for 2.3/2.4's stats(times) (median, iqr, outliers): normal case, even-length median, the all-equal edge (iqr 0, outliers 0), the single-element edge, input-untouched, and the empty-list contract (you decide: raise or return None — defend the choice in a comment).
# test_stats.py
import pytest
from bench import stats

def test_normal_case():
    m, i, o = stats([2.1, 2.0, 9.7, 2.2, 2.05])
    assert m == 2.1 and o == 1

def test_even_length_median():
    m, _, _ = stats([1.0, 2.0, 3.0, 4.0])
    assert m == pytest.approx(2.5)          # the n%2==0 branch — 2.4's off-by-one habitat

def test_all_equal():
    assert stats([5.0]*8) == (5.0, 0.0, 0)  # degenerate spread must not divide-by-zero anywhere

def test_single_element():
    assert stats([3.0]) == (3.0, 0.0, 0)    # n=1: quartile indices all collapse to 0

def test_input_untouched():
    xs = [3.0, 1.0, 2.0]; stats(xs)
    assert xs == [3.0, 1.0, 2.0]            # sorted() not .sort() — the purity test

def test_empty_refused():
    # DECISION: empty timing lists are a caller bug, not a value — raise, loudly.
    # (Returning None would let a broken benchmark print "None ms" into a report.)
    with pytest.raises(ValueError):
        stats([])

Note what the suite is: every 2.2–2.5 scar (edges n=0/1/2, purity, degenerate spread) written down as executable memory. If stats currently crashes on [] with an IndexError instead of your chosen ValueError — congratulations, the test found its first bug: add the guard.

Exercise 2 — Debug from evidence alone: a teammate's report says "the benchmark harness crashes randomly." The traceback bottom reads IndexError: list index out of range at med = ts[len(ts)//2] in bench(), and above it, their timing loop contains if t < 0.001: continue. Reconstruct the bug mechanism, explain "randomly," and give the two-layer fix.

Mechanism: the continue skips appending timings under 1 ms ("filtering noise") — on a fast machine or a tiny input, EVERY run is under 1 ms, ts ends empty, and ts[0//2] → IndexError. "Randomly" = machine/load-dependent, the classic environment-sensitive crash (it never fails on the author's slow laptop — 2.7's "works on my machine," previewed).

Two-layer fix: (1) the policy bug: don't silently discard data — measurements below a threshold are a FINDING (timer resolution! use more repetitions per timing, or perf_counter_ns), never a deletion (M1 L7's ethics); (2) the robustness bug: bench() must assert its own invariant — assert ts, "no timings collected — check filters/repeats" — so the failure names itself at the source instead of crashing two lines later in index arithmetic. Then, per the method: add test_bench_fast_function() that benches lambda: None and asserts a sane result — the regression test that makes this bug unrepeatable.

Go deeper — the complete guide

The exception hierarchy and custom exceptions, fixtures and test structure, property-based thinking, logging vs print, and the numerical-testing playbook this course uses from here to the CUDA capstone.

1. The hierarchy, and making your own

BaseException
 ├── KeyboardInterrupt / SystemExit        # NOT children of Exception — on purpose
 └── Exception
      ├── ArithmeticError → ZeroDivisionError, OverflowError, FloatingPointError
      ├── LookupError     → IndexError, KeyError
      ├── ValueError, TypeError, RuntimeError, OSError → FileNotFoundError ...
class ShapeError(ValueError):
    """Array shape violates a documented contract."""

except Exception spares Ctrl-C and sys.exit() — that's why it, not bare except:, is the widest net you may ever cast (and only at top level, with logging). Custom exceptions are cheap documentation: except ShapeError reads as policy. Catching by parent works (except LookupError takes both Index and Key) — occasionally exactly right, usually too wide.

2. Fixtures: shared setup without shared state

import pytest, numpy as np

@pytest.fixture
def rng():                       return np.random.default_rng(42)          # seeded! (M1 L7)
@pytest.fixture
def random_matrices(rng):        return rng.random((64, 32), np.float32), rng.random((32, 16), np.float32)

def test_matmul_matches_oracle(random_matrices):
    A, B = random_matrices
    assert np.allclose(A @ B, matmul_lists(A.tolist(), B.tolist()), rtol=1e-5)

Each test receives a fresh fixture — no test can dirty another's data (the shared-state disease of 2.3's scenario, solved structurally). Fixtures compose (random_matrices uses rng). The seeded-rng fixture is THE pattern for numerical suites: random enough to explore, deterministic enough to reproduce a failure by rerunning.

3. Property-based thinking (test laws, not examples)

def test_normalize_idempotent(rng):
    v = rng.normal(size=8).astype(np.float32)
    u = normalize(v)
    assert np.allclose(normalize(u), u, rtol=1e-5)        # normalizing twice = once

def test_matmul_associative_within_budget(rng):
    A, B, C = (rng.random((16, 16), np.float32) for _ in range(3))
    assert np.allclose((A @ B) @ C, A @ (B @ C), rtol=1e-4)   # exact in ℝ, budgeted in fp32 (M1 L8!)

def test_ceil_div_covers():
    for n in range(1, 300):
        for b in (1, 2, 3, 7, 32):
            g = ceil_div(n, b)
            assert g*b >= n and (g-1)*b < n                # the DEFINING property, exhaustively

Example tests pin known answers; property tests pin laws — idempotence, inverses (linearize↔divmod, M1 L2), algebraic identities with float budgets, covering properties. They catch bug classes you didn't foresee, which examples never do. (The hypothesis library automates input generation when you're ready; the mindset matters more than the tool.) Note the middle test doubling as an M1 L8 demonstration: associativity holds only within tolerance — your test suite now encodes floating-point theory.

4. logging: print that scales

import logging
log = logging.getLogger("bench")
logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(name)s: %(message)s")
log.info("median %.3f ms over %d runs", med*1000, len(ts))
log.warning("outlier: %.1f ms (3× median)", t*1000)
try: ...
except OSError:
    log.exception("device query failed")      # logs the FULL traceback, then you decide

Print is for interactive debugging (delete after); logging is for programs that run unattended: levels you can filter (DEBUG→CRITICAL), timestamps for correlating with GPU monitor logs (Track A10), destinations beyond stdout, and — the killer — log.exception preserving evidence inside handlers (quiz 1's fix). Habit: any script that will ever run in a loop or on a schedule gets logging on day one.

6. Gotchas

Bare except: / silent pass. Catches Ctrl-C, typos, everything; the bug survives, the evidence dies. Narrowest type, and if you truly must swallow, log it first.
Catching where you can't act. A library function that try/excepts its own ValueError into a printed apology denies callers the ability to handle failure. Raise there; catch at the edge that owns the decision.
Tests sharing mutable state. Module-level DATA = [] mutated across tests → order-dependent passes (and pytest may reorder!). Fixtures give fresh objects; test independence is non-negotiable.
assert with side effects / for validation. assert cleanup() vanishes under -O, and user-input checks don't belong in asserts at all (they're deletable). Effects on their own line; ValueError for inputs.
pytest.raises around too much. Wrap ONE line. Wrapping ten lets an earlier unrelated TypeError satisfy the expectation and hide the real regression; add match="..." to pin the message.
Loosen-until-green. rtol crept from 1e-6 to 1e-2 across five commits and the suite now certifies garbage. Tolerances change only with a budget recomputation in the diff — treat the number as load-bearing engineering, because it is.

Scenario — the test that failed every fiftieth Tuesday

Your study group's shared repo has one "flaky" test — test_softmax_matches_reference fails roughly 1 in 50 CI runs, and the group's fix so far has been "rerun it," which is how flakes train humans to ignore alarms. You take it apart with this lesson. Reproduce: the failing seed is in the CI log because the fixture prints it (bless layer 3) — default_rng(seed) reruns the failure on demand; it's real, not cosmic rays. Hypothesize: the assert is allclose(fast, ref, rtol=1e-6) on fp32 over 8192-term rows — quiz 2's smell. Budget: pairwise fp32, log₂(8192)=13 halvings → ~13·ε ≈ 1.5e-6 typical, but the reference is a sequential Python sum with O(n·ε) worst case… the budget says the TEST is wrong: two correct implementations can legally disagree past 1e-6. But before loosening, you check the residuals (playbook discipline): failures cluster on rows containing values near 88 — and there it is, a second, REAL bug: the reference softmax lacks the max-subtraction (M1 L3's log-sum-exp), so e⁸⁸ pushes fp32 to the edge and its rounding explodes. Two fixes ship: the reference gets the stable formula (with its own new regression test), and the tolerance becomes rtol=1e-5 with the budget arithmetic in a comment. The test hasn't flaked in months, and the group learned the meta-lesson: a flaky numerical test is either a wrong tolerance or a real bug wearing a tolerance costume — and the budget is how you tell which. That diagnosis skill, interviewers pay for.

Practice

1. Name the exception and the likely 2.x-lesson cause: (a) 'NoneType' object is not subscriptable right after a sort; (b) unhashable type: 'list' at a dict insert; (c) The truth value of an array with more than one element is ambiguous; (d) UnboundLocalError on a variable that's "clearly global."
(a) TypeError — xs = xs.sort() assigned None (2.4 gotcha). (b) TypeError — a list used as a dict key; make it a tuple (2.4 §2). (c) ValueError — if arr > 5: on an array; use .any()/.all() (2.5 gotcha). (d) the assignment-anywhere-makes-it-local rule (2.3): an x = ... later in the function shadows the global for the whole body. Recognizing exceptions on sight = half of all debugging time refunded.
2. Convert this shotgun session into the 5-step method: "my z-scores are all NaN → added prints everywhere → deleted the std line → rewrote with a loop → now it's slow AND NaN." The data is a CSV with one constant column.
Reproduce: 3-row fixture with a constant column → NaN appears deterministically. Hypothesize: std of a constant column is 0 → division 0/0 → NaN (M1 L8: 0/0). Instrument: print(f"{sd.min()=}") → 0.0 confirmed. Test: drop the column → NaNs gone. Fix + lock: decide policy (raise on zero-variance features, or add eps with a warning — a real modeling decision, made explicitly), implement, and add test_constant_column_policy(). Five moves, no rewrites, and the slow loop never happens. The NaN itself was M1 L8 knowledge; the PROCESS was this lesson.
3. Write the pytest for the "must fail" contracts of 2.5's pooling thumbnailer (Practice 7): wrong ndim, wrong dtype policy (you chose: accept uint8 only? or any?), and zero-size input. Use raises with match=.
with pytest.raises(ValueError, match="ndim"): pool(np.zeros((4,6))) — a (H,W) gray image violates the documented (H,W,3) contract (or you widen the contract — but then TEST the widened one). with pytest.raises(TypeError, match="uint8"): pool(np.zeros((4,6,3), np.float32)) if you contracted uint8-only. with pytest.raises(ValueError, match="empty"): pool(np.zeros((0,6,3), np.uint8)). The deeper point: writing these forces the contract DECISIONS (accept-and-convert vs reject) that the happy-path never asks — same as normalize's zero-vector. Failures are API.
4. Your fp16 test budget: elementwise y = a*x + b (one multiply, one add per element, no accumulation). Compute a principled rtol and atol, and justify each from M1 L8 numbers.
Per element: 2 rounded ops → error ≲ 2·ε_fp16 = 2·9.77e-4 ≈ 2e-3 relative; ×10 headroom → rtol=2e-2… too loose? No: headroom ×5 is defensible for 2 ops → rtol=1e-2; document the choice. atol: for outputs near 0 (a*x ≈ −b, catastrophic cancellation possible — M1 L8 §2), relative error explodes; set atol ≈ ε_fp16 × typical |a*x| scale (e.g., 1e-3 for unit-scale data), stated in the test. The exercise's real deliverable is the COMMENT: `# budget: 2 ops × ε₁₆(9.8e-4) × 5 headroom` — auditable numbers, not vibes.
5. logging vs print triage: for each, which and why — (a) inspecting a suspicious stride while debugging in Colab; (b) the nightly ETL job's per-stage row counts; (c) a caught-and-handled retryable timeout; (d) the seed of every benchmark run.
(a) print (interactive, ephemeral — delete after). (b) logging.info (unattended, needs timestamps + filtering). (c) log.warning with log.exception on final failure — evidence preserved even when handled (quiz 1's lesson). (d) logging.info at minimum — reproducibility metadata belongs in the permanent record (M1 L7's ritual); many teams put it in the results file itself too. Rule compressed: humans-now → print; machines-later → logging.
6. A property test for M1 L2's pair: linearize(r, c, W) = r*W+c and delinearize(i, W) = divmod(i, W). State the two round-trip laws, the domain constraint that makes them true, and write one as pytest.
Laws: delinearize(linearize(r,c,W), W) == (r,c) for 0 ≤ c < W (the constraint — c ≥ W aliases into the next row, M1 L2 §3's "requires" column!); and linearize(*delinearize(i,W), W) == i for i ≥ 0. @pytest.mark.parametrize("W", [1, 4, 1920]) / def test_roundtrip(W): for r in range(3): for c in range(min(W, 5)): assert divmod(r*W+c, W) == (r, c). Note W=1 in the table — the degenerate width that breaks hand-rolled index math embarrassingly often. Inverse-pair round-trips are the highest-value property tests in all of numerical indexing.
7. Design: the CI quality gate for this course's repo from here on. Specify: what runs on every push (time budget 60 s), what runs nightly, how numerical tolerances are governed, what a "flaky" label triggers, and the one metric you refuse to gate on. Justify from this lesson + M1 L7.
Every push: pytest -q on unit + contract + fixed-fixture suites (fast, deterministic, < 60 s — layers 1, 2, 5, 6); lint + a no-bare-except grep. Nightly: randomized suites with fresh seeds (logged), property tests at larger sizes, and the benchmark harness with medians + spread archived (trend data, M1 L7). Tolerance governance: every allclose carries a budget comment; changing rtol/atol requires the recomputation in the PR description (the anti-loosen-until-green law). Flaky label: quarantine ≠ ignore — auto-open an issue with the failing seed attached; two weeks unfixed → the test's owner presents the budget analysis (scenario's discipline, institutionalized). Refuse to gate on: raw performance numbers per-push — shared CI machines make ms noise (M1 L7's variance), so perf regressions gate NIGHTLY on median deltas > 5 standard errors (M1 L7 Ex.2's arithmetic), never on single runs. This design is small enough for a study group and is, structurally, how serious GPU teams actually run.
