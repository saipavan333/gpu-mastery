nvcc: the 3.1 pipeline, twice

nvcc -arch=sm_75 hello.cu -o hello       # T4. sm_89=L4 · sm_90=H100 · sm_120=RTX 5090
nvcc -arch=native ...                     # "ask the GPU in this machine" (local builds)
# CUDA 13 removed ≤ Volta targets. Wrong/missing arch at runtime:
# "no kernel image is available for execution on the device" — a LINKER-stage-style

hello.cu — annotated

#include <cstdio>
__global__ void hello() {                       // __global__: GPU code, CPU-callable
    printf("block %d thread %d\n", blockIdx.x, threadIdx.x);
}
int main() {
    hello<<<2, 4>>>();                          // launch config: 2 blocks × 4 threads
    cudaDeviceSynchronize();                     // launches are async (5.3) — wait,
    return 0;                                    // or main exits before the GPU prints!
}

Worked example

Task: The full Colab workflow, end to end — the cell pattern you'll use through 5.11.

# cell 1 — write the file (M2 L7's %%writefile, now shipping CUDA)
%%writefile hello.cu
...the program above...

# cell 2 — compile and run, chained (3.1's stale-binary killer)
!nvcc -arch=sm_75 -O2 hello.cu -o hello && ./hello

block 1 thread 0        ← note: block 1 FIRST this run —
block 1 thread 1          4.4's "no block order" contract,
...                       demonstrated on your first program
block 0 thread 3

Three observations that are the whole module in miniature: (1) the output interleaves across runs — blocks are independent and unordered (4.4 §4's contract, visible); (2) within a block, threads 0–3 print in order — a warp's lanes issued together (all 4 live in one warp); (3) delete the synchronize and the program prints nothing — main exited while the kernel sat in the queue (5.3's asynchrony, teaching its first lesson). Decision made: -O2 from the first compile and the && chain — 3.1's habits port verbatim; nvcc passes host flags straight to your g++.

Key points

  • Colab free tier (T4, sm_75) is fully sufficient through this module; the verify ritual (smi / nvcc / compute_cap) runs on every machine, first.
  • nvcc splits .cu into host (your Module-3 toolchain, unchanged) and device (PTX→SASS per -arch) paths, stitched into a fatbinary; PTX enables forward-compat JIT.
  • -arch names: sm_75 T4 · sm_89 L4/Ada · sm_90 H100 · sm_100/103 B200 · sm_120 RTX 5090; CUDA 13 dropped ≤ Volta — "no kernel image" means your arch isn't in the binary.
  • __global__ marks GPU-code-CPU-callable; <<<blocks, threads>>> is the launch config; built-ins blockIdx/threadIdx/blockDim/gridDim are your grid coordinates.
  • Launches are asynchronous: synchronize (or hit an implicit sync) before reading results or exiting — the missing-output bug is everyone's first.
  • Block execution order is unspecified by contract — your first program already proves it; never depend on it.

Quiz

1. Your binary, built with -arch=sm_90 on the cluster, prints "no kernel image is available" on your laptop's RTX 5090 (sm_120). But a colleague's old sm_75 binary RUNS on the 5090. Explain both facts.
SASS is architecture-specific machine code; PTX is the portable IR the driver can JIT for FUTURE architectures (the toolchain diagram's whole point). Default nvcc embeds PTX for the target's virtual arch — but explicit -arch=sm_90 as code=sm_90 only, or stripped PTX, breaks forward compat. Shipping binaries = fatbin with several SASS + top PTX. This exact confusion fills forums; you now debug it from the diagram.
2. hello<<<2, 4>>>() prints 8 lines. What does hello<<<1, 33>>>() do differently under the hood, and what would hello<<<1, 2048>>>() vs hello<<<1, 4096>>>() do?
Warps are ceil(33/32)=2 (M1 L2's division allocating hardware); non-multiples are LEGAL but waste masked lanes. The block cap is 1024 threads (2048 is per-SM RESIDENCY, not per-block — a classic mix-up worth making once here, cheaply); exceeding it → cudaErrorInvalidConfiguration at launch, silent unless you CHECK (5.4's entire pitch). Nothing truncates silently — but nothing reports loudly either, unless you ask.

Exercises

Exercise 1 — Device interrogation: write query.cu using cudaGetDeviceProperties to print name, compute capability, SM count, max threads/block, shared memory/SM, registers/SM, warp size, and memory bus specs. Then compute and print the theoretical numbers YOUR Module-4 model needs: fp32 peak (SMs × 128 × 2 × clock) and the DRAM bandwidth — your machine-model header (4.7 P6), generated by the machine itself.
#include <cstdio>
int main() {
    cudaDeviceProp p;
    cudaGetDeviceProperties(&p, 0);
    printf("%s  sm_%d%d  SMs=%d\n", p.name, p.major, p.minor, p.multiProcessorCount);
    printf("maxThreads/block=%d  warp=%d\n", p.maxThreadsPerBlock, p.warpSize);
    printf("shared/SM=%zu KB  regs/SM=%d\n", p.sharedMemPerMultiprocessor/1024, p.regsPerMultiprocessor);
    double peak = p.multiProcessorCount * 128.0 * 2.0 * (p.clockRate * 1e3) / 1e12;
    double bw   = 2.0 * p.memoryClockRate * 1e3 * (p.memoryBusWidth / 8.0) / 1e9;
    printf("fp32 peak ≈ %.1f TF   BW ≈ %.0f GB/s   ridge ≈ %.0f FLOP/B\n",
           peak, bw, peak*1e3/bw);
    return 0;
}
/* T4 prints ≈ 8.1 TF, 320 GB/s, ridge ≈ 25 — a modest, honest machine whose
   entire 4.7 roofline you now hold. (Clock fields are deprecated-ish on newest
   toolkits — if zero, take clocks from nvidia-smi -q -d CLOCK instead.) */

This output IS your 4.7 P6 machine-model header — paste it atop every benchmark from here on. The 128 cores/SM constant holds for current consumer/datacenter parts you'll meet (T4 is 64/SM — Turing's layout; if the peak looks 2× high on a T4, that's why: check p.major==7 and use 64. Spec archaeology is part of the job, and the struct hands you the evidence).

Exercise 2 — Break it four ways, file the messages (3.1 Ex.1's phrasebook, CUDA edition): (a) compile with -arch=sm_60 on CUDA 13; (b) run an sm_90-only binary on the T4; (c) launch <<<1, 2000>>>; (d) forget cudaDeviceSynchronize entirely. Record WHERE each failure surfaces (compile / launch / runtime / silence) — the stage-diagnosis table you'll debug from all module.

(a) COMPILE: nvcc errors immediately — "unsupported gpu architecture 'compute_60'" (CUDA 13 removed it; the toolchain refuses cleanly — best failure mode of the four). (b) RUNTIME, first API check: "no kernel image is available" (quiz 1's fatbin story — the launch "succeeds" as a no-op unless checked!). (c) LAUNCH: cudaErrorInvalidConfiguration from cudaGetLastError after the launch — but SILENT if you never ask (the kernel simply doesn't run; downstream results are stale memory — 3.2's uninitialized ghosts at GPU scale). (d) SILENCE: program exits 0, prints nothing, "works" in scripts that don't read output — the most dangerous quadrant. The table's moral, worth the whole exercise: CUDA's default failure mode is silence; 5.4 exists to make every one of these loud. Keep the four messages in your notes file next to 3.1's.

NVCCFLAGS = -arch=native -O2 -g -lineinfo    # -lineinfo: source lines in profilers/sanitizer
%.o: %.cu
	$(NVCC) $(NVCCFLAGS) -c $< -o $@
# debug target adds: -G (device debug; SLOW — never benchmark it: 3.8's sanitized-bench gotcha)
# CMake: enable_language(CUDA) + CMAKE_CUDA_ARCHITECTURES=native — 3.6 §5's promise

3. Gotchas

Benchmarking with -G. Device-debug disables optimization: 10–50× slow. -G for cuda-gdb sessions; -lineinfo (cheap) for profiler line mapping; never confuse them.
Guessing the arch. The compute_cap query answers in one line. Wrong guesses "work" via PTX JIT (slow first launch, silent) or fail at runtime — both worse than asking.
Colab session amnesia. Files vanish on disconnect. Notebook cells + Drive/git are the source of truth; binaries are always disposable (3.1's rule anyway).
printf-from-kernel as a habit. Fine for hello; in real kernels it serializes and buffers weirdly. It's a demo tool — 5.4's sanitizer and 5.10's profilers are the instruments.
Exiting before sync. The silent-nothing bug (Ex.2d). Until 5.3's implicit-sync map is second nature, end every experiment with CUDA_CHECK(cudaDeviceSynchronize()).
Toolkit-newer-than-driver. Local installs: nvcc 13.3 with a driver capped at 12.x → runtime failures. The ritual's comparison (toolkit ≤ driver max) catches it before the first mystery.

Practice

1. Decode each -arch flag choice: a student notebook targeting Colab; a shipping binary for customers with unknown 30/40/50-series cards; your own workstation; a cluster of H100s with occasional B200 nodes.
Colab: -arch=sm_75 (T4 floor; runs via JIT if you land an L4). Shipping: -gencode for sm_75,sm_86,sm_89,sm_120 + compute_120 PTX (fatbin breadth + forward JIT — quiz 1's lesson). Workstation: -arch=native (ask the machine). Cluster: -gencode sm_90 + sm_100 + PTX. The pattern: breadth costs binary size and build time; PTX is the safety net; native is for machines you're sitting at.
2. hello<<<2, 4>>> prints block 1 before block 0 in about half your runs. A teammate adds code that "fixes" the order by having block 1 spin-wait on a flag block 0 sets. Predict the behavior across GPU sizes and condemn it with the right 4.4 clause.
On a big GPU both blocks are resident → it "works". On any GPU that schedules block 1 first AND has one SM-worth of space... block 1 spins forever waiting for block 0, which may never be scheduled while block 1 occupies the SM: DEADLOCK (intermittent, size-dependent — the worst kind). The clause: blocks are independent by CONTRACT, schedulable in any order, any subset concurrently (4.4 §4); inter-block coordination mid-kernel is forbidden (grid sync = separate kernel launches or cooperative groups with strict occupancy guarantees). First-week CUDA students write this bug; you've now condemned it before writing it.
3. Your first launch takes 210 ms; the second takes 0.4 ms. List the three cold-start contributors and the M1 L7 ritual line that handles them all.
(1) CUDA context creation on first API call (~100+ ms — driver init, per process); (2) PTX JIT if your arch wasn't in the fatbin (quiz 1 — and it caches afterward); (3) allocator/first-touch effects. The ritual line: WARMUP RUNS, DISCARDED (M1 L7, unchanged since Module 1) — every benchmark harness this module builds starts with it, and now you know precisely what the warmup is absorbing.
4. Translate the M2 L2 Python launch simulator to real CUDA syntax from memory (N=10, B=4, guard included) — then state which single line the simulator COULDN'T teach and this lesson's hardware did.
saxpy<<<(10+3)/4, 4>>>(d_x, d_y, a, 10); with if (i < n) inside — identical arithmetic, three years of curriculum converging on one line. The unteachable line: cudaDeviceSynchronize() — Python's simulator was synchronous by nature; asynchrony (and its silent-exit failure) only exists on real hardware. That's why Ex.2d's quadrant needed a GPU to be felt.
5. A Makefile builds .cu files with -O2 but no -arch. It works on the dev box, and CI (different GPU) shows every kernel 6× slower on FIRST test run, normal after. Diagnose the mechanism and give the two-character-ish class of fix.
No -arch → nvcc's default target + embedded PTX; CI's newer GPU finds no matching SASS → JIT-compiles PTX on first use (the 6× first-run: JIT time amortizing — quiz 1's machinery measured in CI minutes). Fix class: SET THE ARCH — -arch=native per machine, or the CI matrix's explicit list. Bonus habit: JIT results cache in ~/.nv/ComputeCache — CI containers without persistent cache re-JIT forever, a real pipeline-cost bug you can now name in review.
6. Design your module-5 workspace: the repo layout (which 3.6/2.7 pieces port unchanged), the two Makefile targets that differ from CPU-land, the notebook↔repo sync policy for Colab work, and the one new provenance field every benchmark JSON gains (2.7 Ex.1's dict grows).
Layout unchanged: types.h, timer, tests/, scripts/, Makefile (3.6), provenance JSONs (2.7). New targets: sanitize: compute-sanitizer wrapper (replaces asan target — same role, 5.4) and profile: nsys/ncu invocations (5.10) — both on NON-debug builds. Colab policy: repo is truth (git clone in cell 1), notebooks are terminals — cells never hold code that isn't committed (the workshop scenario's discipline). New provenance fields: gpu name + compute_cap + driver + toolkit versions (the verify ritual, serialized) — because "same code, different numbers" across T4/L4 sessions is EXPECTED and must be attributable (M1 L7's environment honesty, GPU row).
7. Write the five-line "first day on any GPU machine" runbook you'd give a new teammate — commands only, each annotated with the failure it preempts. (This is the lesson as a checklist; it should fit on an index card.)
nvidia-smi — is there a GPU, driver alive, anyone else using it? (preempts: debugging code on a busy/absent device). nvcc --version + compare to smi's max — toolkit≤driver? (preempts: version-mismatch mysteries). nvidia-smi --query-gpu=name,compute_cap --format=csv — the -arch answer (preempts: JIT surprises, no-kernel-image). nvcc -arch=<that> hello.cu -o h && ./h — end-to-end smoke test in 30 s (preempts: discovering a broken toolchain inside a real debugging session). ./query (Ex.1's binary) — machine model header into today's notes (preempts: benchmarking against the wrong roofline). Five commands, five classes of wasted afternoon — the card earns its lamination.
