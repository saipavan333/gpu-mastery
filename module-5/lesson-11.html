Capstone — The Matmul Ladder: everything you know, one repo, defensible

No new concepts today. The capstone is a PROJECT: climb matmul from 2 GFLOP/s to ~40% of your GPU's peak, one audited rung at a time, and package it so a stranger — or an interviewer — can verify every claim. This repo is the deliverable of the entire core curriculum. Build it like it's going on your résumé, because it is.

The spec

DELIVERABLE  a public git repo: sgemm ladder, C = αAB + βC, fp32, row-major
RUNGS        v0 CPU oracle → v1 naive → v2 coalesced → v3 tiled →
             v4 register-tiled → v5 vectorized/tuned → cuBLAS reference
EVERY RUNG   fixture-green (budgeted vs double oracle) · sanitizer-clean ·
             GpuTimer median (5.9) · roofline placement (4.7) · occupancy
             audit (5.6) · ncu table row (5.10) · one-paragraph writeup:
             lever pulled, predicted delta, measured delta, gap named
DEFENSE      README table + the Q&A bank (below) answered in your own words
RULE OF THE GAME  predictions BEFORE measurements, in writing, every rung
             (M1 L7's ritual — the repo's git history should prove it)

TOLERANCE POLICY (write it in the README, cite M1 L8):
  oracle computes in double; kernels in fp32 with FMA. |gpu−oracle| ≤
  rtol·|oracle| with rtol = K·2⁻²³-ish scaled ≈ 1e-4 at K=2048 (each output
  is a K-term sum: error budget GROWS with K — a rtol that ignores K will
  false-alarm on big matrices and rubber-stamp small ones).
THE BITWISE SURPRISE you must be able to explain (defense bank #2):
  v1 through v5 are typically bitwise IDENTICAL to each other — every rung
  accumulates each output's K products in the same k-order with the same
  FMA contraction; tiling reorders LOADS, not ADDS (Module 3's loop-reorder
  lesson, GPU edition). None match the CPU (FMA vs separate mul+add — M1 L8).
  What WOULD break rung-vs-rung bitwise: split-K, atomics (5.8), reordered
  accumulator unrolls. Your fixtures should ASSERT rung-agreement bitwise
  AND oracle-agreement budgeted — two different claims, two different tests.

PHASE 1  v1, v2 (5.2 + 5.7): the one-line index swap IS rung v2 — commit them

PHASE 2  v3 (5.5): TILE=16 skeleton + BOTH barriers; racecheck before timing

PHASE 3  v4 (5.6): 4×4 micro-tiles. Each thread: 16 accumulators + 4+4 shared

         (expect ~90–128 regs), the min() table, the occupancy verdict
         (~50%, registers binding), and the sentence explaining why that's
         FINE (5.6's worked example — you are re-deriving it on your card).
PHASE 4  v5 (5.7): float4 loads for A/B staging (alignment: N%4, else pitch
         or scalar tail); optional double-buffer (5.5 P4) — price its shared
         bill against YOUR occupancy table first, predict, then measure.
PHASE 5  the 5.10 loop on every rung: ncu table (SOL/sectors/occ/stalls) —
         the metrics should MIGRATE exactly as 5.10's worked example showed:
         sectors clean up at v2, SOL-mem falls from 96% toward 60s at v3–v4,
         stall-barrier rises then falls across v3→v4 (5.10 P4's rotation).
         Any metric that DOESN'T match the story: that's your gap to name
         (4.7's law — this is where real learning happens; write it down).

Key points

  • The capstone's thesis: 1500× of matmul is index arithmetic + memory placement + resource budgets — the three literacies of Modules 4–5 — with zero exotic hardware features.
  • Trust stack before speed: plumbing suite, double-precision oracle with K-scaled tolerance, sanitizers, THEN benchmarks — a fast kernel on an unverified stack is a liability with good numbers.
  • Rungs v1–v5 are bitwise identical to each other (same k-order, same FMA) but never to the CPU — assert rung-agreement bitwise and oracle-agreement budgeted, as two separate tests.
  • Every rung ships with prediction-before-measurement, the lever's lesson citation, and the ncu row that confirms the mechanism — the gap between predicted and measured is the rung's real lesson.
  • cuBLAS at ~54% of brochure peak IS the practical ceiling for fp32 CUDA-core sgemm; knowing why (issue-slot sharing, 4.7's derates) and when not to compete (production uses the library) is part of the deliverable.
  • The repo is the credential: commit history proving the ritual, CI proving the habits, README proving you can communicate a performance claim a stranger can verify.

Defense quiz — the two you WILL be asked

1. Interviewer: "Your v5 hits 3.2 TF; cuBLAS hits 4.4 on the same card. Why would anyone ever run your kernel — and when would hand-rolling actually be the right call in production?"
The answer interviewers want has three moves: concede the library's dominance on its home turf (maturity signal), name the exact niches where custom wins WITH mechanisms (fusion = traffic, not FLOPs — the course's deepest refrain), and show the ladder's real purpose (auditable understanding, not competition). Options 3/4 signal a junior who'll burn quarters rediscovering this. "I know when not to compete" is a hire signal at every ML-systems shop.
2. Interviewer: "You claim v3 tiling made matmul 6× faster but the results are bitwise identical to v1. A colleague insists tiling reorders the summation, so identical bits prove your test is broken. Adjudicate."
This is the single most discriminating numerics question in GPU interviews because BOTH naive intuitions are wrong: "tiling must change bits" (no — trace the accumulator's order) and "floats can't be compared bitwise" (no — determinism is about ORDER, and when order is fixed, bits are law: M1 L8). Being able to name the three real bit-breakers, unprompted, is the difference between having read about floating point and having instrumented it. Option 4 flunks 3.6: different PTX, verifiably.

The build — acceptance criteria per phase

Phases 0–2 (day one): trust stack, v1→v3. ACCEPT when: plumbing suite green including the staged direction-typo tripwire (5.3 P7); oracle vs hand-computed 3×3 case exact; v1/v2/v3 fixture-green on all five N-shapes; racecheck clean on v3 WITH the quiz-1-of-5.5 missing-barrier bug staged once as an expected-failure; the v1→v2 commit is ONE line; ladder table rows filled with medians + predictions that were committed BEFORE the measurements.

Guidance, not hand-holding: budget half the day for Phase 0 — it feels slow and is the fastest route (5.3's scenario arithmetic: friend B's week). The N=16 case should be verifiable by hand/NumPy (M2's fixture doctrine: one case you can check with your eyes). The 4095 case will fail on your first v3 — the ragged-edge gotcha (5.5) — that failure is scheduled learning, not a setback: fix loads with zero-fill, stores with guards, barriers unconditional (5.6 P5). Non-square 512×1024×256 catches every M/N/K mix-up your square tests hide (swapped-dims bugs are matmul's most-shipped class — M2 L6's boundary doctrine applied to SHAPE space).

Phases 3–6 (days two–three): v4, v5, profiles, package. ACCEPT when: v4's occupancy audit is written BEFORE its first timing (ptxas number, min() table, "registers binding at ~50%, and here's why that's correct for this kernel" — 5.6's worked example re-derived on your card); v5's float4 path handles N%4 (scalar tail or pitch — and the README says which and why, 5.7 P2); the ncu table shows the metric MIGRATION story across rungs with any surprises named; README passes the stranger test: someone with a GPU and your repo reproduces every number within noise, offline, from the committed scripts alone.

The one place almost everyone stumbles: v4's indexing (each thread's 4×4 patch = four shared rows × four shared cols; off-by-ones multiply). Do it on paper first — draw one thread's patch inside one block's 64×64 tile (the m5l11-regtile diagram is your template; M1 L2's index arithmetic is the whole difficulty). When v4 lands 3–4× over v3, run the 5.10 loop and watch stall-barrier FALL (16 FMAs amortize each sync — 5.10 P4's prediction, confirmed by your own counters: that moment is the course clicking shut). If v5's double-buffer variant does NOT help on your card, that's a valid, documentable result — the occupancy bill exceeded the barrier savings (5.5 P4's warning); a measured "no" with a named mechanism is worth more in the README than a copied "yes".

Beyond the ladder — the honest horizon

1. What the next 1.4× costs (so you can cite it, not chase it)

cp.async / TMA        loads bypass registers into shared, hardware-pipelined —
                      double-buffering without the register bill (Ampere+/Hopper+)
swizzled shared       XOR-permuted layouts: conflict-free AND padding-free
                      (5.5 Ex.2's [33] trick, graduated to bit tricks — M1 L3)
warp-tile scheduling  instruction-level choreography of FMA/load ratios
split-K + 5.8         for skinny-K shapes: parallelize the SUM itself —
                      and now determinism costs something (defense #2's list)
Tensor Cores          fp16/bf16/TF32 MMA: 4–8× beyond ALL of this — Track A's
                      opening act, with M1 L8's budget story rewritten
each is a rung on the same ladder you just climbed: a reuse/latency lever,
an occupancy bill, a fixture question. The FRAME transfers; only the
instruction names change. That is the course's promise, kept.

2. Gotchas (capstone-specific, all bloodied by predecessors)

cuBLAS is column-major. The classic first-benchmark disaster: comparing your row-major C against cublasSgemm's column-major output "proves" your kernel wrong (or worse, you benchmark the TRANSPOSED shape). The identity C_row = (Bᵀ Aᵀ)_col lets you call cuBLAS on swapped operands — and your fixtures adjudicate (M2 L5's layout literacy, cashing its final check).
Benchmarking the wrong regime. N=256 measures launch overhead and tails (5.2's floor), not your tiles. The ladder's claims live at N labeled ≥ 1024; say so in the README (5.9 P6's regime labels).
Timing the allocation. cudaMalloc inside the timed region (5.3's hot-loop gotcha) — GpuTimer brackets the LAUNCH; buffers come from the harness, warm.
Flag asymmetry. Comparing your -O2 -use_fast_math kernel against an -O0 oracle, or vs cuBLAS with different fmad settings — flag parity is part of the experiment's control (M1 L7 + 3.6's -O0 fiction).
fp16 accumulation temptation. When Track A halves your dtypes, accumulate in fp32 regardless — K-term sums in fp16 lose bits M1 L8 can quantify (the tolerance policy's K-scaling, with a vengeance). Pre-registering this now saves a week later.
The eternally-almost-done repo. v5 tuning is a fractal; the package is the deliverable. Ship at 40%±, write "next steps" honestly, and stop — 4.7's stopping rule applies to projects too.

Defense bank — answer all seven in writing, in your own words

1. Walk the ladder: for each rung, the lever, the lesson, the multiplier — 90 seconds, no notes.
Your table, spoken. The grading bar: every multiplier gets a MECHANISM (not "tiling helped" but "traffic ÷16 → AI ×16 → new roofline bound, and I landed at 68% of it"). Rehearse until the 4.7-roofline thread is the spine of the story — bounds predicted, measured, gaps named. Interviewers escalate until you run out of mechanism; the ladder means you don't.
2. Why are your rungs bitwise identical to each other but not to the CPU — and name the three changes that would break rung-agreement.
Quiz 2's answer, in your words, with the Module 3 CPU precedent cited (ikj vs naive) and the breaker list (split-K, atomics, interleaved accumulators). Bonus depth: why FMA specifically splits GPU from CPU (single rounding vs two — M1 L8), and why -fmad=false would cost both speed AND the agreement you'd be trying to create.
3. Your tolerance is rtol ≈ 1e-4 at K=2048. Defend the K-scaling against "just use 1e-6 everywhere" — and what happens to the policy at K=32768? At fp16 inputs?
Each output is a K-term dot product: worst-case relative error grows ~linearly in K for sequential accumulation (M1 L8's absorption arithmetic) — 1e-6 at K=2048 false-alarms on legitimate fp32 results; 1e-4 at K=64 rubber-stamps real bugs. K=32768: rtol scales up ~16× (or you switch the ORACLE claim: pairwise/compensated summation tightens the bound — 5.8 P7's tree argument). fp16 inputs with fp32 accumulate: input quantization (2⁻¹⁰) dominates the budget, not the summation — the policy's TERMS change, which is why it's a written policy, not a magic number (M2 L6's constitution, final clause).
4. N=4095: everything that breaks, everything you did about it, and the measured cost of raggedness on your card.
Breaks: edge tiles read OOB (zero-fill loads — 5.5's gotcha), edge stores trespass (guards), float4 alignment dies mid-row (scalar tail path or pitch — 5.7 P2), and the LAST row/col of blocks diverges (5.6: tail warps only — measure it: typically <2% at N=4095 because 63/64 blocks are full). The senior detail: you MEASURED the ragged tax instead of fearing it — divergence economics (5.6) said it'd be negligible at this shape, and your table proves it. Fear of edge cases priced by arithmetic: that's the course's whole personality.
5. Change ONE assumption: B arrives transposed (both row-major, C = A·Bᵀ). What breaks in each rung, which rung's fix is a data-layout decision (5.7 P4's logic), and when do you pre-transpose vs fuse?
Now A-rows · B-ROWS: v2's B access flips from coalesced to strided (the crime returns, other operand); v3+ absorb it in the TILE LOAD (stage Bᵀ's rows into shared, transpose during the load like 5.7's worked example — the way-station template's whole point: the kernel body never knows). Pre-transpose (a separate 5.7 kernel, ~2 copy costs) pays when B is REUSED across many matmuls (amortized — 4.6's residency ledger); fuse the transpose into the tile load when B is used once (zero extra HBM round trips). The economics, not the code, is the answer — every layout question in this course reduced to trips×tolls (4.6), and this one's no different.
6. Scale it: N=65536 (16 GB per matrix — doesn't fit). Design the out-of-core sgemm with 5.9's machinery: blocking scheme, stream pipeline, pinned pool sizing, the max-lane arithmetic on YOUR PCIe numbers, and the single design choice that dominates whether this is compute-bound or bus-bound.
Block into panel products: C-tiles of (say) 8192² accumulate A-panels × B-panels; each panel-product is compute-heavy (2·8192²·8192 FLOP over 3·8192²·4 B moved → AI = 2·8192³/(3·8192²·4) ≈ 1365 FLOP/B — deeply compute-bound PER TILE if panels are big enough). The dominating choice: PANEL SIZE — big panels amortize the bridge (4.6's ledger: FLOPs grow as size³, traffic as size²: the course's oldest scaling law, from 4.7); small panels drown in PCIe (max-lane = copy). Pipeline: DEPTH-3 ring (5.9 P4's Little's law) of pinned panel slots, H2D of next panels overlapping current tile's compute, C-tiles resident until complete (write once). With T4-Colab's 11 GB/s: shipping a panel-product's two 268 MB panels costs ~49 ms vs 2·8192³ ≈ 1.1 TFLOP ≈ 550 ms of compute at 2 TF — compute-bound by ~11×, and with a DEPTH-3 ring the bus vanishes behind the math entirely. This design IS how real out-of-core and multi-GPU GEMMs work; you derived it from four lesson citations.
7. The stranger test, inverted: list the five ways a README performance claim can be unreproducible even with honest authors, and the specific line in YOUR repo that closes each.
(1) Unlabeled regime (N, dtype, warm/cold) → the table's header row + bench script flags (5.9 P6). (2) Clock/thermal variance → GpuTimer median-of-K + "T4, default clocks, medians of 21" note (M1 L7). (3) Different toolchain → nvcc version + flags committed in Makefile, ptxas log in CI artifacts (5.6's weather gotcha). (4) Fixture-free speed ("fast but is it right?") → CI badge + tolerance policy paragraph (trust stack). (5) Hardware lottery → MACHINE.md with the 5.1 generator output + measured ceilings, so a reader on an A100 knows to re-derive bounds, not expect your numbers (4.7: bounds travel, numbers don't). Closing line for the README and the interview both: "every number in this table is a claim; every claim has a committed script; every script has a fixture. Run it." That sentence is the course, compressed.
