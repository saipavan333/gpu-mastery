Your First Real Kernel — threads, blocks & the formula

saxpy on a million floats, for real. The kernel body you wrote in 3.4, the launch arithmetic from M1 L2, the guard from M2 L2, the hardware from 4.4 — today they compile together. One new skill: thinking "my index" instead of "the loop."

Concept

The inversion: from loop to identity

/* CPU (3.4):                        GPU (today):                              */
for (i = 0; i < n; i++)              __global__ void saxpy(int n, float a,
    y[i] = a*x[i] + y[i];                const float *x, float *y) {
                                         int i = blockIdx.x*blockDim.x + threadIdx.x;
                                         if (i < n) y[i] = a*x[i] + y[i];
                                     }

The loop didn't vanish — it became the grid. Each thread computes its identity from coordinates and does exactly one element's work. Everything you know about the body still applies (const contract 3.3, fp32 literals 3.2, the FMA within M1 L8); the new mental muscle is the identity line — and you've owned its algebra since M1 L2.

Launch geometry: ceil-divide, then guard

int block = 256;                              // multiple of 32, always (4.4 gotcha)
int grid  = (n + block - 1) / block;          // the eternal formula
saxpy<<<grid, block>>>(n, 2.0f, d_x, d_y);   // note: DEVICE pointers (5.3)

2D grids: images get coordinates

dim3 block(16, 16);                                    // 256 threads, 2D-shaped
dim3 grid((W + 15)/16, (H + 15)/16);                   // two ceil-divisions
grayscale<<<grid, block>>>(d_in, d_out, W, H);
// inside: x = blockIdx.x*16 + threadIdx.x;  y = ...y...;  if (x<W && y<H) ...
// threadIdx.x MUST drive the row/column-contiguous index — 4.5's coalescing law.

Grid-stride loops: one launch shape for any n

__global__ void saxpy_gs(int n, float a, const float *x, float *y) {
    for (int i = blockIdx.x*blockDim.x + threadIdx.x;
         i < n;
         i += gridDim.x * blockDim.x)          // stride = the whole grid's width
        y[i] = a*x[i] + y[i];
}
// launch with a FIXED grid (e.g. SMs × blocks-per-SM); each thread handles
// elements i, i+stride, ... — M1 L2 §5's pattern, and NVIDIA's own recommended
// default: decouples launch shape from n, keeps full waves (4.4 §5), amortizes
// per-thread setup. The plain form first (clarity); this form for libraries.

Worked example

Task: saxpy end-to-end with the 4.4 P7 launch ritual — predict, run, compare. (Memory plumbing is next lesson; today's harness uses cudaMallocManaged to defer it honestly.)

// saxpy.cu — first real kernel, ritual included
#include <cstdio>
__global__ void saxpy(int n, float a, const float *x, float *y) {
    int i = blockIdx.x*blockDim.x + threadIdx.x;
    if (i < n) y[i] = a*x[i] + y[i];
}
int main() {
    int n = 1<<20;                             // 1M floats
    float *x, *y;
    cudaMallocManaged(&x, n*sizeof *x);        // 5.3 explains; today it just works
    cudaMallocManaged(&y, n*sizeof *y);
    for (int i = 0; i < n; i++) { x[i] = 1.0f; y[i] = 2.0f; }
    int block = 256, grid = (n + block - 1)/block;   // 4096 blocks
    saxpy<<<grid, block>>>(n, 2.0f, x, y);
    cudaDeviceSynchronize();
    float maxerr = 0;                          // VERIFY before admiring (M2 L6)
    for (int i = 0; i < n; i++) maxerr = fmaxf(maxerr, fabsf(y[i] - 4.0f));
    printf("max error: %f\n", maxerr);         // 0.000000
    cudaFree(x); cudaFree(y);
    return 0;
}

The ritual, filled in (4.4 P7): block 256 ✓ multiple of 32; occupancy — saxpy needs ~16 regs: threads-bound, 100% available ✓; waves = 4096/(8×40 SMs on T4) ≈ 12.8 — deep queue ✓; divergence — only the guard's final warp ✓; coalescing — i maps thread→consecutive floats: 4 sectors/warp ✓; prediction — AI = 0.167 → memory-roof: 12 MB ÷ 320 GB/s ≈ 37 µs on the T4. Measured (5.9's events, once you have them): ~40–45 µs. Within 20% — the 4.4 P7 certificate: your model of the machine is calibrated on day one. Decision made: we verified all 1M outputs before caring about speed (exact 4.0f — integer-valued fp32 arithmetic is exact, M1 L8), and printed the error, not "OK": evidence over vibes, as always.

Key points

  • Kernel = loop body + identity: i = blockIdx.x·blockDim.x + threadIdx.x, guarded by i < n — the M1 L2 formula employed at last.
  • Launch geometry is ceil-division; blocks are multiples of 32; the ragged tail is the guard's job (and the only divergence a map kernel should have).
  • 2D grids use dim3 for both slots with per-axis guards — and threadIdx.x must index the memory-contiguous direction (coalescing law).
  • Grid-stride loops decouple launch shape from n — the library-grade default once the plain form is second nature.
  • Scalars pass by value into kernels (copied to the device at launch); arrays pass as device pointers — the 3.3/5.3 contract.
  • Run the 4.4 P7 ritual before every first launch: a prediction within 20% certifies your model; a miss localizes your misunderstanding — both are wins.

Quiz

1. A teammate writes int i = threadIdx.x + blockIdx.x; (plus instead of times-plus). For <<<4, 256>>>, describe exactly what the kernel computes and what the output looks like.
i ranges only 0..(255+3): four overlapping windows. The races on shared elements are UB-ish (last-writer wins per element, fine for idempotent saxpy... but wrong coverage regardless); the tail is untouched memory (3.2's ghosts). Defense: the fixture test on RAGGED sizes (3.9's discipline) catches coverage bugs instantly — the head-looks-right trap is exactly why tests check the TAIL. This typo ships weekly somewhere; your test suite is why not from you.
2. For a 1920×1080 image with block(16,16), compute the grid, the total threads, the wasted threads, and identify which threads waste — then say why block(32,8) might beat block(16,16) for a row-major image op even at identical occupancy.
One dimension divides, the other doesn't — per-axis ceil + per-axis guards (M1 L2 twice over). The block(32,8) insight: warp shape follows threadIdx.x-major order, so a 32-wide block makes each warp exactly one contiguous 128-B row run (4.5's perfect sector story) — shape the BLOCK so warps align with memory, not just the occupancy math. Rounding down (option 3) silently crops 8 pixel rows: M2 L8's edge-policy sin, GPU edition.

Exercises

Exercise 1 — Port pixelforge's grayscale (M2 L8) as your first 2D kernel: uint8 RGB in, uint8 gray out, luma weights, the dtype dance ON DEVICE (widen to float, round, narrow). Verify against a CPU reference on a ragged 1023×517 synthetic image with EXACT equality — and justify why exact (not allclose) is correct here.
__global__ void grayscale(const unsigned char *rgb, unsigned char *gray, int W, int H) {
    int x = blockIdx.x*blockDim.x + threadIdx.x;
    int y = blockIdx.y*blockDim.y + threadIdx.y;
    if (x < W && y < H) {
        int i = (y*W + x) * 3;                              // M1 L2's channel-last decode
        float g = 0.299f*rgb[i] + 0.587f*rgb[i+1] + 0.114f*rgb[i+2];
        gray[y*W + x] = (unsigned char)fminf(g + 0.5f, 255.0f);   // round + clamp
    }
}

Exact equality is right because both sides run the SAME fp32 expression per pixel (three FMAs, one order — no reductions, no reordering: M1 L8's legitimate-== case, kernel edition), provided the CPU reference also computes in fp32 (float g, f-suffixed constants — 3.2's promotion audit; an fp64 CPU reference WILL differ by a ulp on ~1/10⁶ pixels and teach you the lesson the noisy way). Ragged 1023×517 exercises both guards. The kernel's memory story is imperfect (3-byte RGB strides — 4.5 Ex.1e's AoS tax) — noted, measured in 5.7, accepted today: correctness first, always first.

Exercise 2 — The coverage test-kit: write check_coverage.cu — a kernel that does out[i] = i (identity stamp), plus host verification that every slot got its stamp exactly once. Run it against (a) the correct index formula, (b) quiz 1's plus-typo, (c) a grid one block SHORT. This 30-line kit is your indexing oracle for every kernel this module.
__global__ void stamp(int n, int *out) {
    int i = blockIdx.x*blockDim.x + threadIdx.x;
    if (i < n) out[i] = i;
}
/* host: fill out[] with -1 · launch · sync · then:
   errors = Σ (out[i] != i)  — report FIRST bad index and its value.        */
(a) 0 errors.
(b) plus-typo: out[0..258] stamped (values collide but equal i by luck? NO —
    block1 thread0 writes out[1]=1 ✓ same value! IDENTITY hides races!) —
    first failure appears at i=259: out[259]=-1. Lesson within the lesson:
    the stamp must be i so coverage shows, but collisions on CORRECT values
    are invisible — add an atomicAdd(&hits[i],1) variant when you suspect
    double-writes (5.8 teaches the tool). The kit evolves with you.
(c) short grid: clean -1 band at the tail: [n-block, n) unstamped — instantly
    visible, instantly diagnostic (ceil-division regression = the M1 L2 bug).

The kit's deeper point: indexing bugs have SIGNATURES (head-ok/tail-dead = coverage; scattered wrong = formula; bands = stride confusion), and a purpose-built oracle reads them at a glance — M2 L6's fixture philosophy, specialized for the one bug class that dominates week-one CUDA. It rides shotgun through 5.11.

Go deeper — the details that finish the picture

1. What <<<>>> actually passes (and how scalars travel)

Launch parameters (grid, block, shared-bytes, stream — you've now seen slots 1, 2; 5.5 uses 3; 5.9 uses 4) go to the driver; kernel arguments are copied by value into constant space the device reads — which is why scalars (n, a) just work, pointers must be DEVICE pointers (5.3's whole subject), and passing a big struct by value is legal but copies it per-launch (pass a device pointer instead — the 3.6 by-value/by-pointer judgment, relocated). And dim3 is just a struct{x,y,z} with 1-defaults: <<<256, 64>>> is shorthand for dim3(256,1,1), dim3(64,1,1).

2. Index dialects you'll read in the wild

int i = blockIdx.x*blockDim.x + threadIdx.x;          // canonical (this course)
int i = threadIdx.x + blockDim.x*blockIdx.x;          // same thing, reordered
auto g = cg::this_grid(); i = g.thread_rank();        // cooperative-groups dialect
int tid = threadIdx.x, lane = tid % 32, warp = tid/32; // intra-block roles (5.8's cast)
// 2D-flattened: i = (blockIdx.y*gridDim.x + blockIdx.x)*blockDim.x + threadIdx.x
//   — when a 1D problem exceeds gridDim.x limits (2³¹-1 blocks... rarely) or for
//   grid-layout control. All are M1 L2 linearizations; read for the STRIDE story.

3. Gotchas

The plus-typo family. +, swapped Idx/Dim, y-for-x: all compile, all produce head-plausible output. The coverage kit (Ex.2) is the 30-second immunization — run it on every new index formula.
int overflow in the identity. blockIdx.x·blockDim.x in int wraps past 2³¹ elements — M1 L1's 3-billion bug, kernel edition. size_t/long long for big-n kernels (the M3 types.h idx_t discipline ports).
Guard omitted "because n divides evenly today." Tomorrow's n doesn't; the write lands in the next allocation (5.4's sanitizer names it). The guard is unconditional house style.
blockDim confused with gridDim. The stride in grid-stride loops is gridDim.x·blockDim.x (total threads); using blockDim alone makes each block redo the same elements — races that idempotent test kernels hide (Ex.2b's lesson).
dim3 y/z silently 1. Launching block(1024) then indexing threadIdx.y expecting spread: everything lands on y=0. Print the config in debug builds; asserts on blockDim inside kernels are legal and cheap.
Copy-pasting the 2D template with x/y swapped. Compiles, correct output, 8–30× slow (every warp column-walks — 4.5). The 5.7 sector drill on every index expression, even "obviously correct" ones.

Practice

1. Compute launch configs (grid, total threads, idle): n=1e6 @ block 256; n=1e6 @ block 1024; 4096×4096 image @ (32,8); n=33 @ block 256.
3907 blocks / 1,000,192 threads / 192 idle (M2 L3's launch_shape, forever); 977 / 1,000,448 / 448; grid(128, 512) = 65,536 blocks, 16.78M threads, 0 idle (both divide); 1 block / 256 threads / 223 idle — tiny-n kernels waste by design, and that's fine: correctness of the general formula beats special-casing (the launch cost dwarfs 223 lanes anyway — 4.6 tolls).
2. Write the identity line for: (a) processing every OTHER element (even i only); (b) each thread handling a contiguous CHUNK of 4; (c) 3D volume (D,H,W) with dim3 blocks. State each one's warp-level memory pattern verdict (4.5 drill).
(a) i = 2*(blockIdx.x*blockDim.x + threadIdx.x) — stride-2 warps: 8 sectors, 50% (better: process pairs per thread, or compact the data). (b) base = 4*(bid*bdim + tid); for k in 0..3: y[base+k]... — each thread walks 4 consecutive: warp spans 128 floats = 512B = 16 sectors for 512B: 100% BUT four separate transactions; the float4 form (5.7) does it in one. (c) x/y/z each = blockIdx.*blockDim + threadIdx; linear = (z*H + y)*W + x (M1 L2's 3D) — coalescing rides on x = threadIdx.x, as always. Three formulas, three verdicts, one drill.
3. Predict before running: saxpy correct at n=256 with grid=1, block=256 and NO guard. Your teammate ships it. List the three inputs that break it and the failure each produces.
n=255 (n < launched): thread 255 writes y[255] — past the array: OOB (sanitizer catches; production corrupts — 3.4's law). n=257: element 256 never computed — stale output (the silent quadrant). n=10⁹ with the same one-block launch: 255 elements done, the rest untouched AND nobody noticed because the head looked right (quiz 1's trap at scale). The guard + ceil-division handle all three; "it worked for my n" is 3.2's UB-luck epistemology wearing launch-config clothes.
4. The grid-stride version processes n=1M with grid=80, block=256 (20,480 threads). How many elements per thread? Why might this BEAT the 3907-block plain launch on a 40-SM GPU, and which two 4.x concepts price the answer?
⌈10⁶/20480⌉ ≈ 49 elements per thread (a for-loop per thread — amortizing the identity computation and setup across 49 items). Potential win: (1) wave arithmetic (4.4 §5) — 80 blocks = exactly 2 blocks/SM × 40 SMs: one clean resident set, zero tail waves, vs 3907 blocks' scheduling churn; (2) instruction economy (4.4 §1) — one guard evaluation per 49 elements instead of per element. Usually a few percent on saxpy (memory-bound anyway — 4.7 caps everything), more on setup-heavy kernels. Measure per 3.9's rules; the POINT is you can now argue both sides with named laws.
5. A kernel needs each thread's WARP id and LANE id for 5.8's shuffles. Write the two lines, then explain why lane = threadIdx.x & 31 works and when tid % 32 ≠ lane semantics could bite (hint: 2D blocks).
int lane = threadIdx.x & 31; int warp = threadIdx.x >> 5; — M1 L1's power-of-two mask/shift, live in a kernel. The bite: in 2D blocks, warps are formed from the LINEARIZED thread id (tid = threadIdx.y*blockDim.x + threadIdx.x) — threadIdx.x alone misidentifies lanes when blockDim.x isn't a multiple of 32 (a (16,16) block's warps SPAN two y-rows!). Correct general form: linearize first, then mask. This subtlety decides whether 5.5's (16,16) tiles have clean warp geometry — file it now, cash it there.
6. Port M2 L2's Monte-Carlo π as a kernel skeleton (no RNG yet — Track B4 brings curand; use x[i], y[i] arrays of pre-generated uniforms): each thread tests one dart, writes hit[i] = 0/1. What's deliberately UNFINISHED about this design, and which lesson completes it?
i = bid*bdim+tid; if (i<n) hit[i] = (x[i]*x[i] + y[i]*y[i] <= 1.0f); — branchless by construction (M1 L4's squared-distance + 4.1 Ex.2's comparison-as-data: no divergence). Unfinished: a MILLION hit flags need summing — writing them out and summing on CPU ships 4 MB across the bridge to compute one number (4.6's audit fails it). The completion is the on-device reduction — 5.8's tree + shuffles — turning output from n bytes to 8. Recognizing "this kernel's real output is a reduction" at design time is the instinct; the machinery is two lessons away.
