Streams, Events & Async — three engines, and the timeline you now command

Your GPU has been idling through this whole module: while a kernel computed, the copy engines sat parked; while data crossed the bridge, the SMs did nothing. 4.1's pipeline lesson said overlap is how hardware earns its keep — today you get the steering wheel: streams to order work, events to time and chain it, pinned memory to unlock the DMA engines.

Concept

Streams: ordered lanes, independent lanes

cudaStream_t s1, s2;
cudaStreamCreate(&s1); cudaStreamCreate(&s2);
cudaMemcpyAsync(d_a, h_a, bytes, cudaMemcpyHostToDevice, s1);   // lane s1
kernel<<<grid, block, 0, s1>>>(d_a);                            // 4th launch param!
cudaMemcpyAsync(d_b, h_b, bytes, cudaMemcpyHostToDevice, s2);   // lane s2 —
                                                                 // FREE to overlap s1's kernel
// THE two rules (5.3's quiz 1, now the full law):
//   WITHIN a stream: strict FIFO order — dependency by sequence
//   ACROSS streams:  NO ordering at all — unless you build it (events, below)
// The hardware executing your lanes: 1+ compute engine, and (most cards)
// TWO copy engines — one per direction. Three-way overlap is a HARDWARE
// fact; streams are how your code stops wasting it.

Pinned memory: the price of admission

float *h = (float*)malloc(bytes);          // pageable: OS may move/swap it (3.5)
cudaMemcpyAsync(d, h, bytes, H2D, s1);     // COMPILES, RUNS… and may be
                                            // SILENTLY SYNCHRONOUS: DMA can't
                                            // target movable pages, driver staffs
                                            // a staging copy — overlap gone,
                                            // no warning, no error. THE trap.
cudaMallocHost(&h, bytes);                  // pinned: page-locked (5.3 §1) —
                                            // DMA-able, truly async, 2× raw
                                            // speed (5.3 Ex.2's table, explained
                                            // at last: the staging hop was the tax)
// Pinning is a system-wide resource (locked RAM starves the OS — 4.6's
// gotcha): pin transfer BUFFERS (the 5.3 P6 pool), not your whole dataset.

Events: timestamps and cross-lane dependencies

// USE 1 — the correct GPU stopwatch (every "measure" since 5.5, formalized):
cudaEvent_t t0, t1;  cudaEventCreate(&t0);  cudaEventCreate(&t1);
cudaEventRecord(t0, s);      // a marker dropped INTO stream s's order
kernel<<<g, b, 0, s>>>(...);
cudaEventRecord(t1, s);
cudaEventSynchronize(t1);    // CPU waits for the marker to be reached
cudaEventElapsedTime(&ms, t0, t1);   // GPU-clock ms between markers —
                                      // immune to 5.3's CPU-runs-ahead trap
// USE 2 — ordering ACROSS lanes without stalling the CPU:
cudaEventRecord(uploaded, copyStream);
cudaStreamWaitEvent(computeStream, uploaded);   // computeStream pauses at this
kernel<<<g, b, 0, computeStream>>>(...);        // point until 'uploaded' fires —
                                                 // a DAG edge between lanes,
                                                 // executed entirely on-device

The pipeline: 5.3's pool + streams + a ring

const int DEPTH = 3;                        // 5.3 P6's sizing, employed
for (int c = 0; c < nChunks; ++c) {
    int lane = c % DEPTH;                   // ring of DEPTH stream+buffer pairs
    cudaStreamSynchronize(s[lane]);         // recycle: lane's PREVIOUS chunk done?
    fill(h_pin[lane], c);                   // CPU stages chunk c (pinned slot)
    cudaMemcpyAsync(d_in[lane],  h_pin[lane], CB, H2D, s[lane]);
    process<<<g, b, 0, s[lane]>>>(d_in[lane], d_out[lane]);
    cudaMemcpyAsync(h_out[lane], d_out[lane], CB, D2H, s[lane]);
}   // steady state: lane k uploading, lane k-1 computing, lane k-2 downloading
for (int l = 0; l < DEPTH; ++l) cudaStreamSynchronize(s[l]);   // drain

Worked example

Task: Pipeline a 256 MB elementwise workload (T4 Colab, PCIe gen3 ≈ 11 GB/s pinned each way — 5.3 Ex.2's YOUR-numbers). Predict the ceiling BEFORE coding — 4.1's pipeline law does all the work.

serial:   H2D 23 ms + kernel 3 ms + D2H 23 ms          = 49 ms
pipeline law (4.1): steady-state total ≈ MAX lane, not SUM:
  one copy engine:  H2D and D2H share → copy lane 46 ms → total ≈ 46 + fill ≈ 47
                    (barely better! shared engine = shared queue)
  two copy engines: lanes 23 / 3 / 23 → total ≈ 23 + fill ≈ 25 ms  → 1.96×
measured (4 chunks, DEPTH 3, T4 = 2 copy engines): 26.1 ms  ✓ model holds
  speedup ceiling = 49/23 = 2.1× — and NOTHING in this lesson can beat it:
  the pipe is copy-bound; the only real fixes live OUTSIDE streams:
  send less (dtype, compression — M1 L8), keep data resident (4.6's ledger),
  or stop crossing per-batch (the architecture question, always asked first)

What to internalize: the prediction took four lines of arithmetic and named the ceiling, the engine count dependency, and the futility boundary — before any code. Overlap is NOT free speed; it's recovering idle engines, capped hard at max-lane. When someone says "we'll hide the transfer with streams", your first question is now automatic: what's the max lane, and is the thing you're hiding actually smaller than it? (A 23 ms copy cannot hide behind a 3 ms kernel; the kernel hides behind the COPY.)

Key points

  • Within a stream: FIFO; across streams: no order unless you build it — dependency is something you DECLARE (sequence or events), never something the driver infers from pointers (5.3 quiz 1's law, completed).
  • cudaMemcpyAsync with pageable memory silently degrades toward synchronous — the pipeline "works" and overlaps nothing; pinned buffers (pooled, 5.3 P6) are the admission ticket.
  • Events are stream-order markers: the only honest GPU stopwatch (ElapsedTime), and the cross-stream dependency edge (StreamWaitEvent) that builds DAGs without CPU stalls.
  • Pipeline total ≈ max lane + fill (4.1's law): compute the lanes FIRST — copy-bound pipes need traffic fixes (M1 L8 dtypes, 4.6 residency), not more streams.
  • The legacy default stream synchronizes with everything — one stream-less launch or plain cudaMemcpy in a hot loop is a full-pipeline barrier wearing camouflage (gotcha 1).
  • Syncs are architecture, not statements: every cudaDeviceSynchronize/plain-memcpy in steady-state code is a pipeline bubble — audit them like you audit mallocs in loops (3.5).

Quiz

1. Your pipeline shows ZERO overlap in the profiler: chunks run perfectly serially despite 3 streams and correct Async calls everywhere. The buffers came from a teammate's "fast allocator" that wraps malloc with alignment. Diagnose, and name the 30-second experiment that convicts it without reading any allocator code.
Silent degradation is what makes this THE classic streams bug: every call succeeds, cudaSuccess everywhere, timeline flat (contrast option 4: MISSING dependencies cause wrong ANSWERS or races, not serialization). The one-buffer A/B swap is the controlled experiment habit (M1 L7) — five minutes, no code archaeology. T4 has 2 copy engines; option 3 is checkable in one line: deviceProp.asyncEngineCount (5.1's generator already printed it).
2. To time a kernel in stream s2, an engineer records start/stop events on the DEFAULT stream around the launch, gets 0.003 ms for a kernel that nsys shows takes 4.1 ms, and concludes "events are unreliable on this driver." What actually got measured, and what are the two correct placements?
Same instrument, wrong probe point — the oscilloscope was on the wrong wire. Event semantics are strictly "a marker in ONE stream's FIFO"; cross-stream timing without a declared join measures scheduler coincidence. The habit that prevents it: before reading any timing, say aloud WHICH lane's order both markers live in (the 5.3 async model, now your reflex). "Instrument unreliable" conclusions get expensive (M1 L7's scenario); "probe misplaced" is almost always the truth.

Go deeper — the async fine print that pages people

1. The default stream's two personalities

LEGACY default (the default!): stream 0 synchronizes with ALL other streams —
  one bare kernel<<<g,b>>>() or plain cudaMemcpy in your loop = full barrier
  (Ex.1's saboteur b). Third-party code that launches stream-less does this TO you.
per-thread default (nvcc --default-stream per-thread): stream 0 becomes an
  ordinary lane — old code stops poisoning pipelines, but code that RELIED on
  the implicit barrier now races (both directions of surprise are real!).
Course rule: in pipeline code, EVERY launch and copy names its stream
explicitly — then neither personality can ambush you. (Libraries: pass the
stream in; every serious API — cuBLAS, cuDNN, NCCL — accepts one.)

2. Callbacks, graphs, and what comes after (honest previews)

cudaLaunchHostFunc(s, fn, arg)   // run CPU code when lane s reaches this point
                                  // (logging, notifying a request thread) — the
                                  // fn runs on a DRIVER thread: no CUDA calls
                                  // inside, keep it tiny (µs), or you've built
                                  // a stealth pipeline stall
CUDA Graphs: record a whole chunk-DAG once, replay with ONE launch — amortizes
  5.2's per-launch µs when steady-state work is thousands of tiny nodes
  (Track A's inference-serving bread and butter; know the name today)
cudaMallocAsync(ptr, bytes, s)   // 5.3 §1's pool allocator, stream-ordered:
  alloc/free become lane events — no device-wide sync per allocation. The
  modern default for anything allocating in steady state.

3. Gotchas

One plain call in a hot loop. cudaMemcpy (no Async), cudaFree, cudaDeviceSynchronize, or a legacy-default launch — each is a full pipeline barrier (5.3's implicit-sync roster, now read as a THREAT list). Steady-state code uses only Async + events; syncs live at drain points, by design review.
Reusing a pinned slot before its lane drained. The ring's StreamSynchronize(lane) is load-bearing: skip it and the CPU overwrites h_pin[lane] mid-DMA — corrupted uploads, intermittent (5.3's async model biting the HOST side). DEPTH buffers, DEPTH fences, no exceptions.
Timing with events but forgetting they're async too. ElapsedTime before EventSynchronize(t1) = cudaErrorNotReady (polite) — or reading a STALE previous value if you recycled events without care (impolite). The GpuTimer wrapper exists so this class of bug has one home (5.3's up/down philosophy).
Overlap theater. Chunking a workload whose kernel is 100× smaller than its copies (the worked example's 3 ms vs 46 ms) buys ~6% and complexity forever. Run the max-lane arithmetic FIRST; sometimes the honest answer is "don't pipeline — fix the traffic" (4.6) or "don't cross at all" (residency).
Pinning the world. cudaMallocHost on multi-GB datasets locks RAM the OS needed — host-wide slowdowns, OOM-killer visits (4.6's warning, now with a mechanism). Pin the POOL (MBs), stream the dataset through it.
Depth superstition. DEPTH=8 when 3 suffices costs pinned memory and debuggability for zero throughput (the max lane didn't change!). Little's law sizes it: depth ≈ ceil(total latency / max-lane time) + 1 — usually 2–4. More is not safer; it's just more.

Scenario — the one-line log that doubled p99

An inference service hums at p50 = 8 ms, p99 = 14 ms: a clean DEPTH-3 pipeline (upload batch, run model, download logits). A well-meaning PR adds latency logging to the hot path: cudaDeviceSynchronize(); log(now() - t_start); — "just one sync so the timestamp is accurate." Code review approves it in thirty seconds; it's one line. A week later, p99 has doubled to 29 ms and p50 crept to 11: the sync drains ALL lanes every request (a device-wide barrier — 5.3's roster), so the pipeline never reaches steady state; every request pays fill cost anew, and the tail — where requests queue behind drained pipes — pays worst (4.6's toll arithmetic on latency percentiles). The diagnosis took one nsys capture: beautiful overlap for 200 ms, then a picket fence of barriers marching through the timeline (Ex.1's saboteur b, in production). The fix is this lesson's toolbox: cudaLaunchHostFunc on the REQUEST's stream captures the completion timestamp lane-locally (§2 — the callback runs when THAT lane finishes, no global drain), or cheaper still, an event per request and ElapsedTime read by the metrics thread later. The engineering moral outlives CUDA: in pipelined systems, synchronization is an architectural decision that must survive design review — it cannot enter through a logging PR. The team's new lint rule, copied verbatim into this course's ship checklist (5.11): every cudaDeviceSynchronize outside a drain point carries a comment justifying its existence, signed by a reviewer who saw the timeline.

Practice

1. Classify each as pipeline-safe or barrier (steady-state hot loop): (a) cudaMemcpyAsync pinned, named stream; (b) kernel<<<g,b>>>() bare; (c) cudaEventRecord + later ElapsedTime on drained events; (d) cudaFree of a scratch buffer; (e) cudaMallocAsync in the request's stream; (f) cudaLaunchHostFunc doing a 30 ms database write.
(a) Safe — the designed path. (b) BARRIER: bare = legacy default stream = syncs all lanes (§1; the stealthiest one because it looks identical to every launch you wrote before this lesson). (c) Safe if events already drained (read at metrics time, scenario's fix); NotReady-polling otherwise — design for reading late. (d) BARRIER: cudaFree device-syncs (5.3's roster) — scratch buffers in hot loops use the pool/MallocAsync. (e) Safe — stream-ordered by design (§2), this is exactly its use case. (f) Safe from the GPU's view but a 30 ms squat on the driver's callback thread — OTHER lanes' callbacks queue behind it (§2's "keep it tiny"): enqueue the work to your own thread pool, return in µs. Score: (b) and (d) are the two that ship to production weekly.
2. Your pipeline's lanes: H2D 6 ms, kernel 14 ms, D2H 6 ms per chunk, 10 chunks, 2 copy engines. Compute: serial total, pipelined total (law + fill), speedup, and the ceiling if you then float4+fuse the kernel down to 7 ms. At what kernel time does further kernel optimization become pointless for THROUGHPUT — and what changes about that answer if the metric is per-request LATENCY?
Serial: 10×26 = 260 ms. Pipelined: max lane = kernel 14 → 10×14 + fill (6+6... first chunk's copies ≈ 12) ≈ 152 ms → 1.7×. Kernel→7 ms: max lane becomes... H2D 6 vs kernel 7 vs D2H 6 → still kernel: 10×7+12 ≈ 82 ms. Pointless below 6 ms: the copy lanes take over as max (further kernel gains vanish into engine idle time — the roofline logic of 4.7 applied to PIPELINES: optimize the binding lane only). Latency flips it: per-request time = SUM of that request's stages (6+7+6 = 19 ms) regardless of overlap — kernel work below 6 ms still shortens each request's journey even though throughput froze. Throughput obeys max-lane; latency obeys sum-of-stages; systems serve one master per SLA, and confusing them is how the scenario's PR got approved.
3. Draw (in text) the event DAG for: upload weights ONCE, then per request r: upload input (stream Ur) → compute (stream C, shared, in arrival order) → download (stream Dr) — with the constraint that C must never start request r before its upload completes, and downloads must not block C. Name each edge's mechanism.
Init: W-upload in stream S_w; event E_w recorded; C does StreamWaitEvent(E_w) once (weights fence — all requests inherit it by FIFO within C). Per request: Ur: MemcpyAsync(input_r) → record E_up[r]. C: StreamWaitEvent(C, E_up[r]) → kernel_r → record E_done[r]. Dr: StreamWaitEvent(Dr, E_done[r]) → MemcpyAsync(logits_r) → (optional) HostFunc for the response callback. Edges: within-stream FIFO (C's request order — a free serializer, chosen deliberately for the shared model), cross-stream WaitEvent ×3 (upload→compute, compute→download, weights→everything). Downloads never touch C (they wait on E_done in THEIR lane), so a slow PCIe day delays responses, not compute. This diagram — five streams, four event types — is a real inference server's data path; you just designed it with two primitives.
4. Little's-law the ring depth: chunk = 32 MB, H2D 11 GB/s, kernel processes at 40 GB/s effective, D2H 11 GB/s, two copy engines. Compute each stage time, the max lane, end-to-end latency per chunk, and the minimum DEPTH that keeps the max-lane engine never-idle. Why does DEPTH beyond that number buy nothing?
Stages: H2D 32/11 ≈ 2.9 ms, kernel 32/40 = 0.8 ms, D2H ≈ 2.9 ms; max lane = 2.9 (copy-bound). Per-chunk latency = 2.9+0.8+2.9 = 6.6 ms. Depth ≥ latency/max-lane = 6.6/2.9 = 2.3 → DEPTH 3 (the ring must hold every chunk "in flight" across all stages so the H2D engine always has a next chunk whose buffer is free). Beyond 3: the H2D engine is already never-idle — extra lanes just park chunks in queues (throughput = max-lane engine's rate, saturated; 4.6's Little's law: more inventory past the bottleneck's need = warehouse, not speed). Same arithmetic sized the pinned pool in 5.3 P6 — one law, third appearance, and now you've derived the "+1" too (integer ceiling).
5. Ex.1(a) showed pageable async silently serializing. Write the four-line runtime GUARD that makes this bug impossible to ship: how do you detect at startup that a buffer intended for the pipeline isn't pinned, and what should the failure mode be (crash / warn / fallback)? Cite the course principle that decides.
cudaPointerAttributes attr; cudaPointerGetAttributes(&attr, h_buf); → attr.type == cudaMemoryTypeHost means REGISTERED/pinned; unregistered malloc memory returns type unregistered (on modern CUDA, the call succeeds with type = cudaMemoryTypeUnregistered). Guard: at pool construction, assert every slot reports pinned — CRASH, loudly, at startup. Not warn (nobody reads warnings — the bug's whole danger is silence), not fallback (a silent 2× regression is exactly what we're preventing; graceful degradation of PERFORMANCE contracts is how quiz 1 happens). Principle: fail at the boundary, at startup, at full volume — 3.3's contract-assert philosophy applied to a performance contract. Performance properties that matter get ASSERTED like correctness properties; that one sentence is a senior review comment you'll type fifty times.
6. A teammate benchmarks kernels by launching each 1000× back-to-back in one stream and dividing total event time by 1000. For which kernel class does this OVERSTATE steady-state cost, for which does it UNDERSTATE production latency, and what harness change reports both honestly? (Hints: 5.2's floor; caches between iterations; the scenario's percentiles.)
Overstates per-kernel cost for tiny kernels ONLY IF gaps counted... actually back-to-back FIFO launches amortize launch overhead → UNDERSTATES production cost for small kernels that in real life launch sparsely (each real launch pays the 5.2 µs-floor alone, plus cold caches: iteration 999 enjoys L2 warmth iteration 1 never had — M1 L7's warmup now a distortion instead of a ritual!). It understates LATENCY generally: production requests arrive into pipelines with queues and fills (percentile behavior — scenario), not into a hot loop. Honest harness: report BOTH the amortized number (median of K, warm — "kernel cost when streaming") AND the cold-ish single-shot number (fresh stream, L2 flushed via a scrubbing kernel or cudaCtxResetPersistingL2Cache — "kernel cost as a lone request"), labeled as such. GpuTimer (Ex.2) grows a mode flag; 5.11's ladder table reports the warm number and SAYS so. Benchmarks don't lie; unlabeled regimes do (M1 L7's oldest lesson, final form).
7. Interview closer: "Your training job's GPU utilization is 55%. Walk me through finding and fixing it with streams." Deliver the decision path: the instrument, the three timeline shapes you might see, each shape's fix, and the one shape where streams are the WRONG answer.
Instrument: nsys timeline first (WHERE, not why — 5.10's division of labor). Shape 1 — gaps between kernels, copies filling them serially: classic unpipelined loader → DEPTH-3 ring + pinned pool (this lesson's core), expect utilization → max-lane bound. Shape 2 — overlap present but picket-fenced by barriers: hunt the plain-call/legacy-default offenders (Ex.1b, scenario) — a grep and a lint rule, not a rewrite. Shape 3 — kernels dense but each SM-starved (many tiny launches, 5.2's floor): streams DON'T help serial dependencies — fuse kernels or CUDA Graphs (§2); this is the wrong-answer shape, and naming it unprompted is the senior signal. Then the closing move: "if the timeline shows copies are the max lane even fully overlapped, streams have done all they can — the fix moves up a level: smaller dtypes (M1 L8), data residency (4.6), or accepting the input pipeline as the product's real bottleneck (prefetch from disk, which is ANOTHER pipeline one level up — same law, 4.1's, all the way down)."
