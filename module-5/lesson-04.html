Error Handling & compute-sanitizer — alarms for a machine that fails later

3.8 armed your CPU code with gdb, ASan, UBSan. The GPU needs its own alarm panel, because 5.3's asynchrony adds a twist C never had: the crash happens lines after the crime. Today you learn where errors actually surface, which ones kill the context, and the sanitizer that names the guilty thread.

Concept

Two channels, two moments

cudaError_t err = cudaMalloc(&d_x, bytes);   // channel 1: return value, NOW
saxpy<<<grid, block>>>(n, a, d_x, d_y);      // returns void. No error channel!
err = cudaGetLastError();        // channel 1b: LAUNCH errors (bad config) — now
err = cudaDeviceSynchronize();   // channel 2: EXECUTION errors (OOB, assert) — later
// The kernel ran between those two lines. An illegal access inside it is
// invisible until a sync-ish call — 5.3's queue diagram, now with sirens.

Why the split: a launch can fail immediately (block too big for the SM — 4.4's limits; grid dim 0; too much shared memory), and cudaGetLastError catches those before the kernel even runs. But an out-of-bounds read at thread 31,999 doesn't exist until the kernel EXECUTES, which (5.3) is after the CPU has moved on. So execution errors ride back on the next synchronizing call — which might be a cudaMemcpy twenty lines and three launches away. The error report names the WRONG line unless you force locality.

Sticky vs non-sticky: which errors kill the patient

cudaMalloc(&d_x, (size_t)1 << 60);   // cudaErrorMemoryAllocation — NON-sticky:
                                      // this call failed; the context is fine; free
                                      // something and retry (3.5's malloc-can-fail).
// vs
kernel<<<g,b>>>(...)  → thread derefs a host pointer (5.3's world-crossing)
                      → cudaErrorIllegalAddress — STICKY: the context is
                        CORRUPTED. cudaMemcpy? Same error. cudaMalloc? Same
                        error. cudaFree? Same. The only cure is process restart.

This is 3.2's undefined-behavior contract, enforced harder: on the CPU, UB might limp along corrupted; on the GPU, memory violations poison the entire CUDA context — every subsequent API call returns the original error, forever. The diagnostic signature is unmistakable once you know it: "suddenly EVERYTHING fails with the same error" means scroll UP — the first failure is the real one, everything after is echo. (This is also why 5.3's harness syncs before teardown: surface the sticky error where it happened, not in some destructor.)

The discipline: CHECK everything, bracket launches

#define CUDA_CHECK(call) do {                                          \
    cudaError_t err_ = (call);                                         \
    if (err_ != cudaSuccess) {                                         \
        fprintf(stderr, "CUDA error %s at %s:%d — %s\n",               \
                cudaGetErrorName(err_), __FILE__, __LINE__,            \
                cudaGetErrorString(err_));                             \
        exit(1);                                                       \
    }                                                                  \
} while (0)                    // 3.6's macro hygiene: do/while, no stray ;

// the launch bracket — this pair goes after EVERY kernel launch:
saxpy<<<grid, block>>>(n, a, d_x, d_y);
CUDA_CHECK(cudaGetLastError());          // launch-config errors, immediately
#ifdef DEBUG
CUDA_CHECK(cudaDeviceSynchronize());     // execution errors, LOCALIZED — debug only
#endif                                    // (release: syncing every launch kills 5.9's overlap)

One subtlety worth knowing before an interview asks: cudaGetLastError returns AND CLEARS the error state; cudaPeekAtLastError reads without clearing. The bracket uses Get so a handled non-sticky error doesn't haunt the next check. And the #ifdef DEBUG line is a real engineering tradeoff, not laziness — the sync that localizes errors also serializes the pipeline (5.3's async is a feature you're turning off to debug). CUDA_LAUNCH_BLOCKING=1 in the environment does the same globally without recompiling — Colab's quickest "where did it actually crash" switch.

compute-sanitizer: 3.8's alarm panel, GPU edition

compute-sanitizer --tool memcheck  ./app   # OOB + misaligned access + leaks
                                           #   = ASan's GPU twin (3.8)
compute-sanitizer --tool initcheck ./app   # reads of uninitialized device memory
                                           #   = 3.2's ghosts, caught in the act
compute-sanitizer --tool racecheck ./app   # shared-memory data races (5.5's beat)
compute-sanitizer --tool synccheck ./app   # invalid __syncthreads usage (5.6's beat)

# compile with -lineinfo and reports name FILE:LINE, the exact thread,
# the exact address, and which array it belongs to:
#   Invalid __global__ read of size 4 bytes
#   at saxpy(int, float, const float*, float*)+0x90  saxpy.cu:12
#   by thread (64,0,0) in block (1953,0,0)
#   Address 0x7f... is out of bounds, 4 bytes after alloc of size 4000000

Read that report like the machine log it is: thread (64,0,0) in block (1953,0,0) with blockDim 512 → global index i = 1953·512 + 64 = 1,000,000 — the 5.2 identity, inverted from the report. Cross-check with the other clue: "4 bytes after alloc of size 4,000,000" on a float array = element 1,000,000 of a 1,000,000-element array. Both clues name the same culprit: the first thread past n — the guard is missing or wrong. The sanitizer doesn't just say "bug" — it names the thread, the thread names the element, and the element names the fix. That's 3.8's "alarms turn symptoms into addresses" promise, kept on 100,000 threads at once.

Worked example

Task: A staged crime, solved four ways — saxpy with the guard deleted, hunted up the localization ladder. This is the debug drill you'll run for real within the week.

__global__ void saxpy_bad(int n, float a, const float *x, float *y) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    y[i] = a * x[i] + y[i];                      // guard deleted. n=1,000,000,
}                                                 // grid rounds up to 1,000,448 threads
                                                  // → 448 threads trespass (5.2's math)

RUNG 0 — no checks: prints "PASSED" some runs, garbage others, crashes rarely.
         (The trespass lands in the SAME allocation's slack or a neighbor —
          3.4's overflow physics: damage depends on the neighborhood.)
RUNG 1 — CUDA_CHECK on the next memcpy: "illegal address at memcpy line 47".
         True error, WRONG address — line 47 is innocent (async, 5.3).
RUNG 2 — CUDA_LAUNCH_BLOCKING=1: error now reported at the launch line. Kernel
         identified. But WHICH thread, WHICH access? Still guessing.
RUNG 3 — compute-sanitizer memcheck (-lineinfo build): saxpy.cu:3, thread/block
         named, "4 bytes after alloc of 4,000,000" → element 1,000,000 →
         tail thread → THE GUARD. Fix is one line, found in one run.

The lesson inside the lesson: each rung costs more runtime and buys more precision — checks are free-ish (always on), LAUNCH_BLOCKING is a debug session, sanitizer runs ~10–50× slow (3.8's ASan tax, same shape). The professional habit is entering at the RIGHT rung: "everything fails with one error" → sticky, scroll up (no tools needed); "wrong line blamed" → rung 2; "which of 100k threads" → rung 3. Diagnosis before instrumentation — M1 L7's measure-then-conclude, wearing a tool belt.

Key points

  • Every CUDA API call returns cudaError_t; kernel launches return nothing — bracket them with cudaGetLastError (config, now) + sync (execution, later, debug builds).
  • Execution errors surface at the NEXT synchronizing call — the reported line is often innocent. CUDA_LAUNCH_BLOCKING=1 or debug-syncs restore locality.
  • Sticky errors (illegal address, asserts) corrupt the context: every later call echoes the same error; only a process restart recovers. First failure = real failure.
  • cudaGetLastError clears the error; cudaPeekAtLastError doesn't — the bracket uses Get so handled errors don't haunt the next check.
  • compute-sanitizer memcheck/initcheck/racecheck/synccheck = ASan-family for GPU; with -lineinfo it names file:line, thread, block, and the offending address's owner.
  • The sanitizer report + the 5.2 index identity = the failing INPUT: thread coordinates invert to the element, the element names the bug. Reports are machine logs, not vibes.

Quiz

1. Mid-service, every CUDA call in your inference server starts returning cudaErrorIllegalAddress — including plain cudaMalloc calls that "can't" be wrong. The on-call engineer proposes adding retry loops around the mallocs. Verdict and correct playbook?
The "everything fails identically" signature IS the diagnosis (sticky diagram). GetLastError clears the RECORD, not the corruption — the context stays dead (a classic interview trap). Real inference servers (Triton et al.) implement exactly this watchdog-restart pattern because one bad request's OOB must not brick the server for the next thousand requests — 5.3's scenario logic at service scale.
2. Your debug build (sync after every launch) shows the error at kernel K3's launch line. Your release build blames a cudaMemcpy 200 lines later. A teammate concludes "the release compiler miscompiles K3". Better hypothesis, and the 30-second test that settles it?
The reported line is where the error was NOTICED, not where it happened (channel-2 diagram). Moving error lines between build modes is the asynchrony signature, not a compiler one. LAUNCH_BLOCKING changes surfacing without changing compilation — a controlled experiment isolating one variable (M1 L7's method, debugging edition). Miscompilation exists but is the LAST hypothesis, after your own async model — 3.2's humility rule.

# Makefile targets — note -lineinfo in BOTH (it's free at runtime; -G is not):

Go deeper — the rest of the alarm panel

1. The error taxonomy you'll actually meet

cudaErrorMemoryAllocation      non-sticky   OOM: free/retry/shrink batch (3.5's law)
cudaErrorInvalidValue          non-sticky   bad arg (n=0 memcpy is FINE; null dst isn't)
cudaErrorInvalidConfiguration  non-sticky   block too big / too much smem (4.4 limits)
cudaErrorIllegalAddress        STICKY       OOB / world-crossing deref — restart
cudaErrorAssert                STICKY       device-side assert(x) fired — restart
cudaErrorLaunchTimeout         STICKY       display-GPU watchdog killed a long kernel
                                            (Colab/headless: no watchdog; laptops: yes)
cudaErrorMisalignedAddress     STICKY       float4 loads off 16-B alignment (5.7's beat)

2. printf and assert inside kernels

__global__ void k(...) {
    if (blockIdx.x == 0 && threadIdx.x == 0)   // gate it! 100k threads × printf
        printf("n=%d x[0]=%f\n", n, x[0]);      // = 100k lines of soup
    assert(i < n);                               // fires → cudaErrorAssert (sticky)
}
// printf writes to a device-side ring buffer (default 1 MB), flushed at sync
// points — no sync, no output (5.3's asynchrony biting printf-debugging!).
// Ungated printf from many threads: interleaved, truncated-at-1MB soup.
// Rule: printf for exploring ONE thread's view; sanitizer for finding WHICH
// thread; assert for contracts (3.3) you want enforced on-device in debug.

3. cuda-gdb, in one honest paragraph

It exists, it's gdb (3.8's muscle memory transfers: break/run/print/backtrace), compiled with -G, plus GPU verbs: cuda thread (31,0,0) switches focus to a thread, info cuda kernels lists what's resident. Honesty: on 100,000 threads, single-stepping is a microscope when you usually need the sanitizer's smoke detector — pros reach for cuda-gdb AFTER memcheck names the thread, to watch that one thread's variables evolve. It also can't attach usefully inside Colab notebooks (no TTY); it shines on local boxes. Know it exists, know the -G flag, don't feel guilty for using it monthly, not daily.

4. Gotchas

Checking the launch but not syncing — then blaming the next call. The bracket's two lines catch DIFFERENT errors (config vs execution). Teams that only check getLastError ship quiz 2's confusion into production logs.
cudaGetLastError as a cleaner for sticky errors. It clears the flag, not the corruption (quiz 1's trap). The context is still dead; you've just deleted the evidence.
Benchmarking -G builds. -G disables device optimization — numbers are fiction (3.6's -O0 lesson, GPU edition). -lineinfo is the always-on flag; -G is the debug-session flag.
Sanitizer clean ≠ correct. memcheck proves no ILLEGAL access — quiz-5.3's aliasing bug (wrong-but-legal reads) sails through. Sanitizers catch crimes, fixtures catch lies (M2 L6's layers: both, always).
printf-debugging without a sync. Kernel crashed before the flush point → your printf "never ran" (it ran; the buffer died with the context). Sync early when printf-hunting, or the absence of output misleads.
The laptop watchdog. A 10-second kernel on a DISPLAY GPU gets killed (LaunchTimeout, sticky) — students conclude "my kernel has a bug" when the bug is running on the GPU that draws the desktop. Colab/cluster GPUs have no watchdog. Know which machine you're on (5.1's machine model, line 1).

Scenario — the 40-minute production fire, replayed with this lesson

An ML platform team's overnight batch job dies at 3 a.m.: logs show illegal address at allreduce_kernel — so the on-call pages the distributed-training owner, who spends 40 minutes proving allreduce innocent. The real bug: a data-loader kernel two stages EARLIER read past a ragged batch's end (an OOB born from an unpadded final batch — 5.2's tail, in disguise); its sticky error surfaced at the next sync, which happened to live inside allreduce. The fix took five minutes once someone ran the failing shard under compute-sanitizer. Post-mortem actions — the ones this lesson already gave you: (1) launch brackets everywhere, so surfacing distance shrinks from "two stages" to "one launch"; (2) a CI job running the sanitizer on every kernel's fixture suite weekly (crimes caught before 3 a.m.); (3) the runbook's first line for illegal-address pages: "the blamed kernel is the witness, not the suspect — find the first error, or sanitize the repro." Cost of the pattern-knowledge you now have: one lesson. Cost of learning it at 3 a.m.: 40 minutes, one wrong page, and a very tired allreduce owner.

Practice

1. Classify: (a) cudaMemcpy with byte count 0, (b) launch with grid=(0,1,1), (c) kernel derefs nullptr, (d) cudaMalloc returns OOM, (e) device assert fires. Sticky or not, which channel reports it, and the one-line response to each.
(a) Success — zero-byte copies are legal no-ops (5.3 P7's n=0 contract). (b) cudaErrorInvalidConfiguration, channel 1b (getLastError), non-sticky: fix the grid math (5.2's ceiling formula outputs ≥1 for n≥1 — grid 0 means n was 0 or the formula is wrong upstream). (c) IllegalAddress, channel 2 (next sync), STICKY: restart + sanitizer on the repro. (d) Non-sticky, channel 1 return value: shrink the ask or free (3.5). (e) cudaErrorAssert, channel 2, STICKY: the contract told you exactly what failed — read the assert's message, fix the caller (3.3's contract philosophy: the assert did its job).
2. Why does the launch bracket use cudaGetLastError (clearing) rather than cudaPeekAtLastError — and construct the specific two-error scenario where using Peek in the bracket causes a FALSE positive on an innocent kernel.
Scenario: kernel A's launch fails (InvalidConfiguration, non-sticky, recorded). Your code handles it (shrinks the block, relaunches fine). Later, innocent kernel B's bracket calls Peek — which reads the STILL-UNCLEARED record from A's original failure and convicts B. Get clears on read: each bracket consumes its own kernel's verdict, leaving a clean slate. The general principle is 3.5's ownership, applied to error state: whoever CHECKS the error OWNS clearing it — dangling error records mislead exactly like dangling pointers. (Peek's legitimate niche: checking without consuming when a later handler also needs to see it — rare, deliberate.)
3. A kernel produces correct results every run, but compute-sanitizer initcheck flags "read of uninitialized global memory" in it. Teammate: "false positive, results are right — ship it." Give the 3.2-grounded rebuttal and the two most likely innocent-LOOKING causes worth finding.
Rebuttal: "correct today" + uninitialized read = 3.2's UB contract — the read returns SOMETHING (currently harmless: maybe multiplied by zero, maybe overwritten later), but its value depends on allocator history (5.3 P3's session-dependent ghosts); a driver update, allocation-order change, or bigger batch reshuffles the heap and the answer changes silently. Likely causes: (1) padded/rounded-up allocation where the kernel reads the full padded width but only the valid region is initialized (M2 L5's shapes vs storage); (2) a first-iteration read of an accumulator buffer initialized only from iteration 2 onward (works because ×0 or overwritten — until someone changes the loop). Both are one-line cudaMemset fixes. "Sanitizer findings are load-bearing even when outputs pass" — that's the fixture+alarm two-layer doctrine (M2 L6) in one sentence.
4. Your service must survive a bad request that triggers an illegal access, with <2 s recovery budget. Sticky errors kill the process. Design the architecture in four lines (hint: 3.5's process isolation + this lesson's stickiness).
(1) CUDA work lives in a WORKER process (or pool), not the serving process — stickiness dies at the process boundary (the OS reclaims everything: 3.5 §1's "process exit is the ultimate free"). (2) Serving process watchdogs workers: sticky error → SIGKILL + respawn (~1 s including context re-init; keep a warm spare to hit the budget). (3) The poisoned REQUEST is quarantined + logged for offline sanitizer replay (the scenario's runbook). (4) Health check = a tiny known-answer kernel (round-trip fixture!) after respawn. This is genuinely how production inference servers handle it — your 3.5/5.3/5.4 vocabulary just designed one.
5. Rank these four builds for (i) daily development, (ii) benchmark runs, (iii) sanitizer runs, (iv) cuda-gdb sessions — and name the single flag that belongs in ALL four: -O2; -O2 -lineinfo; -G -lineinfo; -O0.
(i) -O2 -lineinfo + DEBUG sync-brackets: real codegen, named lines, localized errors. (ii) -O2 -lineinfo, syncs OFF: measure what ships (-lineinfo costs nothing at runtime — it's metadata). (iii) -O2 -lineinfo under compute-sanitizer: sanitize OPTIMIZED code (bugs can vanish at -G like 3.6's -O0 heisenbugs; catch what production runs). (iv) -G -lineinfo: only here does -G belong — real device debugging needs unoptimized, symbol-rich code. The universal flag: -lineinfo (sanitizer lines, profiler lines in 5.10, zero runtime cost). Plain -O2 and -O0 appear nowhere: one is blind, the other is fiction.
6. compute-sanitizer memcheck reports "Invalid __global__ write of size 4, address is 16 bytes BEFORE alloc of size 4000000". Before opening the code: what bug class writes BEFORE an array, which two arithmetic bugs from this module produce it, and what does "size 4" narrow down?
Negative indexing (writes AFTER = tail/guard bugs; writes BEFORE = the index went below the base). Producers: (1) signed underflow/reversed arithmetic in the index — e.g., i - offset where offset > i (halo/stencil patterns, 5.5's territory: element i-1 at i=0 → address −4... but −16 means i−4, a radius-4 stencil's left edge with no clamp); (2) a 5.2-style identity typo like blockIdx−1 sneaking into the formula. "Size 4" = a 4-byte element (float/int — consistent with the float array). "16 bytes before" ÷ 4 = index −4 EXACTLY: the report literally hands you the offending offset. Address arithmetic on sanitizer output is a skill (M1 L2 + 3.4's pointer math) — the fix (clamp or skip the halo edge, 5.5) is usually visible before the editor opens.
7. Write the module's debugging decision tree as an 8-line runbook: symptom → first move, covering: everything-fails-identically; wrong-line blamed; works-debug-fails-release; garbage-but-no-error; sanitizer-clean-but-wrong; hangs-forever; correct-but-slow; works-Colab-fails-laptop. Each line cites its lesson.
(1) Everything fails identically → sticky: scroll to FIRST error, restart, sanitize the repro (5.4). (2) Wrong line blamed → LAUNCH_BLOCKING=1 or debug syncs: surfacing ≠ scene (5.4 quiz 2). (3) Debug-passes/release-fails → usually surfacing distance or a race debug-timing hides; LAUNCH_BLOCKING on release first (5.4), racecheck second (5.5). (4) Garbage, no error → wrong-but-legal: fixtures + the plumbing suite localize the layer (5.3 P7, M2 L6). (5) Sanitizer-clean-but-wrong → logic bug: shrink n until traceable, print ONE thread's view (5.4 §printf), diff against the CPU oracle (M2 L6's reference-implementation layer). (6) Hangs → watchdogless infinite loop or a __syncthreads divergence deadlock (5.6): synccheck + inspect loop bounds. (7) Correct-but-slow → not a bug: profiler first, guesses never (5.10, M1 L7). (8) Colab-yes/laptop-no → machine model diff: arch flags (5.1), watchdog (5.4 gotcha), or memory size — diff the two machine-model files (5.1's generator earning rent). The tree's meta-rule: every branch starts by NAMING the symptom class, and each class has a cheapest-first move — diagnosis is a search problem, and you now hold the heuristic (3.8's closing promise, delivered).
