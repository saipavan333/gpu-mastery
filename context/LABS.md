# Labs (read for: interactive labs, calculators, visualizers, WebGPU pages)

All labs are root-level standalone pages (`lab-*.html`), listed and cross-linked
from `labs.html`, which groups them into four sections:

- **Reason with it (calculators)** — `lab-roofline.html`, `lab-occupancy.html`,
  `lab-coalescing.html`, `lab-floatbits.html`. Pure JS + canvas 2D, no GPU. Pattern:
  a `.tool` card with `.row` controls (sliders/chips/inputs), a `<canvas>` drawn
  with a hand-rolled 2D context routine (see `render()` in `lab-roofline.html` for
  the reference implementation: log-scale axis mapping, chip presets, a live
  `.verdict` panel), then an `<h2>How to read it</h2>` explanation tying back to a
  specific lesson number.
- **Run it (real GPU kernels)** — `track-d/lab-webgpu.html` (reduction),
  `lab-matmul.html` (naive vs. tiled matmul). WebGPU, with graceful degradation:
  feature-detect `'gpu' in navigator` → `requestAdapter()` → `requestDevice()`,
  disable the run button and show the WGSL anyway if any step fails. Always
  verify GPU results against a CPU oracle with an error budget (never bitwise —
  see the "fixture doctrine" language in both labs) — for anything too large to
  fully replay on the CPU in a tab (matmul at N≥1024), spot-check a handful of
  random output elements instead of the full result.
- **Go deeper on your track (track visualizers)** — `lab-montecarlo.html` (Track
  B, dart-throwing π estimator + log-log error-vs-N plot), `lab-pbr.html` (Track
  C, per-pixel Cook-Torrance BRDF on a canvas-shaded sphere). Pure JS/canvas, no
  GPU. These exist to make one track's central idea interactive even though the
  track has no other lab yet — natural next candidates: an ML/Track A visualizer
  (mixed-precision or attention), an HPC MPI communication-pattern visualizer.
- **Remember it (study tools)** — see `STUDY-TOOLS.md`, not this file.

## Conventions every lab follows
- Nav + `.lesson-top` badge row (`<span class="badge">Interactive Lab</span>` +
  a topic badge) + a "← all labs" link back to `labs.html`.
- `gm-seo:start/end` meta block (canonical/OG/Twitter) — regenerated by
  `tools/build-seo.js`, don't hand-edit.
- An `<h2>How to read it</h2>` (or similarly named) section is mandatory: explain
  what the control does, what the visualization means, and tie it to a specific
  lesson/track. A lab without this section fails the course's own teaching
  standard, not just a style nit.
- `assets/app.js` at the end, same as every page (motion, search, the assistant,
  etc. all still apply to lab pages — they're not a separate system).
- **Verify before shipping the math**, not just the syntax: `node --check` only
  catches parse errors, not wrong formulas or runtime scope bugs (a block-scoped
  variable referenced outside its loop is syntactically valid and will throw only
  when actually executed). For canvas-only labs, write a small Node harness with a
  no-op DOM/canvas shim (a `Proxy` that no-ops any method call works well) and
  actually CALL the render/state-machine functions across the real slider range
  before considering the lab done — this caught two real bugs (an epsilon dimming
  the PBR highlight at low roughness, and a `ReferenceError` from a scope leak)
  that pure syntax-checking missed. For anything with a closed-form or physical
  law (convergence rate, energy conservation, algorithm equivalence), verify the
  actual math/statistics in Node first — see `TRACKS-PROGRESS.md`'s "Motion fix +
  context split + three new labs" entry for the specific checks run on each of
  the three most recent labs.
